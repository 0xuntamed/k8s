Sixty lessons taught you to build a cluster and put workloads on it — by typing kubectl apply. That is fine for learning and fatal for a team: nobody knows what is running, nobody can reproduce it, and everyone has production credentials. CI/CD is the discipline that turns "a commit" into "a running, verified version" with no human in the loop except for decisions. This page builds the vocabulary the rest of the track uses, and shows why the container image you learned to build on Day 2 is the centre of everything.

Where the course left you

Picture the workflow you have been using: edit a Dockerfile, docker build, docker push, edit a Deployment, kubectl apply, kubectl rollout status. Every step works. Now imagine six engineers doing it, forty times a day, across three clusters.

Manual deploys

  • Which commit is running in prod? Whatever was on someone's laptop when they ran build.
  • Were the tests run? Depends on the person.
  • Who changed the replica count last Tuesday? kubectl leaves no history.
  • Everyone who can deploy holds a kubeconfig with write access to prod (Day 32).
  • Rollback = remember what the previous tag was.

A pipeline

  • Every deployed image is tagged with the commit it was built from.
  • Tests run on every commit, the same way, on a clean machine.
  • Every change to what runs is a commit with an author, a diff and a review.
  • Humans hold no cluster credentials; the pipeline (or a controller in the cluster) does.
  • Rollback = deploy the previous commit.

CI, CD and the other CD

Continuous Integration
Every push to a shared branch is automatically built and tested. The point is integration: small changes merged often, so conflicts and breakages surface in minutes, not at "release time". Output: a verified artifact (for us, an image) — or a red X.
Continuous Delivery
Every verified artifact is deployable at the press of a button: the deployment itself is automated and rehearsed, but a human decides when (an approval, a merged promotion PR).
Continuous Deployment
Same, without the button: what passes goes to production automatically. Requires excellent tests, good probes (Day 23), progressive rollouts and fast rollback — because the pipeline is the release manager.

CI answers "is this commit good?". CD answers "how does a good commit reach an environment?". Everything in this track is one of those two questions. GitHub Actions and Jenkins are mainly CI tools that can do CD by pushing; Argo CD is a CD tool that does nothing else.

Anatomy of a pipeline

Regardless of vendor, a pipeline is: a trigger (a push, a pull request, a schedule, a manual click) starts a run; the run executes stages (lint → test → build → scan → push → deploy) on a runner (a machine or container the CI system controls); stages pass artifacts forward (a compiled binary, a test report, an image tag); each stage's exit code decides whether the next one runs.

Strip away the YAML and a CI stage is a shell script run by a child process on a Linux machine. The runner forks a shell (bash -e — exit on the first failing command), the script runs, and the runner reads the exit status. 0 = green, anything else = red. Environment variables carry inputs ($GITHUB_SHA, $BUILD_NUMBER); files in the workspace carry outputs. When a pipeline "mysteriously" fails, it is almost always one of: a non-zero exit from a command you did not think could fail, a missing env var, or a file not where the next step expected it. The tools from L10 (set -euo pipefail, $?, tee, xargs) are CI tools.

$ cd /workspace && git clone --depth 1 https://github.com/acme/api . && git checkout $GITHUB_SHA
$ export CI=true GITHUB_SHA=9f2e1c3 IMAGE=ghcr.io/acme/api
$ bash -e ./step.sh                 # your "run:" block, written to a temp file
$ echo $?                           # 0 → next stage; non-zero → run fails, notifications go out

The artifact is the image

In a Kubernetes world the thing CI produces is a container image, and the thing CD changes is one field: spec.template.spec.containers[].image. Everything hinges on how that image is named.

Digest
sha256:aa11… — the content hash of the manifest. Immutable by construction; two images with the same digest are byte-identical (Day 5: the manifest lists the layers, the layers are content-addressed too — L4).
Immutable tag
A tag you never move: the commit SHA (api:9f2e1c3), a build number, a semver you never republish. Your pipeline should only create these.
Mutable tag
latest, main, stable — a pointer that gets re-pointed. Convenient for humans, useless for a controller that decides whether anything changed by comparing text.

Two facts from the course explain every "I pushed a new image and nothing happened" ticket. (1) A Deployment starts a rollout only when its Pod template changes; if the template still says api:latest, nothing changed as far as the Deployment is concerned. (2) The kubelet's imagePullPolicy defaults to IfNotPresent for any tag except :latest, so even a restarted Pod may run the cached old image on one node and the new one on another. Immutable tags fix both: the text changes, the rollout happens, every node pulls exactly that image.

$ TAG=$(git rev-parse --short HEAD)                              # 9f2e1c3 — the commit is the version
$ docker build -t ghcr.io/acme/api:$TAG . && docker push ghcr.io/acme/api:$TAG
$ docker buildx imagetools inspect ghcr.io/acme/api:$TAG | grep Digest   # sha256:aa11… — pin this if you want to be paranoid
$ kubectl set image deploy/api api=ghcr.io/acme/api:$TAG           # template changed → new ReplicaSet → rolling update (Day 10)
$ kubectl rollout status deploy/api --timeout=120s                 # exit 1 on failure → the pipeline goes red

Environments and promotion

You do not build a separate image for staging and production. You build one image and run it with different configuration: replica counts, resource limits, hostnames, feature flags, database URLs. The image moves — is promoted — through environments; the config stays put in each.

build once → api:9f2e1c3→dev (auto)→staging (auto + smoke tests)→prod (approval)

"Same image, different config" is exactly what Kustomize overlays and Helm values files are for, and why config lives in ConfigMaps and Secrets instead of being baked into the image. A promotion is literally "change the image tag in overlays/prod" — one line, one commit, one review. That commit is what CD reacts to.

config-repo/ ├── base/ # Deployment, Service, Ingress — no environment specifics │ ├── deployment.yaml │ ├── service.yaml │ └── kustomization.yaml └── overlays/ ├── dev/kustomization.yaml # images: [{name: ghcr.io/acme/api, newTag: 9f2e1c3}] replicas: 1 ├── staging/kustomization.yaml # newTag: 9f2e1c3 replicas: 2 └── prod/kustomization.yaml # newTag: 4b7d0e9 replicas: 6 (not promoted yet)

Push or pull?

Once CI has a verified image, something has to change the cluster. There are only two shapes:

Push (CI deploys)

The pipeline holds cluster credentials and runs kubectl apply / helm upgrade at the end. Simple, immediate, and what most teams start with. Costs: every CI system becomes a cluster admin; nothing notices if someone changes the cluster by hand afterwards; N clusters means N sets of credentials in CI.

Covered in C3 (GitHub Actions) and C5 (Jenkins).

Pull (GitOps)

CI only writes the new tag into a git repo. A controller inside the cluster watches that repo and applies whatever it says — continuously, reverting drift. CI has no cluster access; the cluster has read-only git access. Costs: one more component to run, and a mental shift: "deploy" means "merge".

Covered in C6 onwards (Argo CD).

Pull-based CD is the reconcile loop from Day 7 with one substitution: the desired state lives in git instead of in etcd. You already know how this controller behaves — it is the same loop as a ReplicaSet, just with a different source of truth.

Hands-on lab (20 min) — a pipeline by hand, so you know what the tools automate

You need a KIND cluster and Docker. We use ttl.sh, an anonymous registry where images expire (the tag is the TTL) — no login needed.

$ mkdir ci-lab && cd ci-lab && git init -q
$ cat > app.sh <<'EOF'
#!/bin/sh
echo "version: $(cat /VERSION)"; exec python3 -m http.server 8080
EOF
$ cat > Dockerfile <<'EOF'
FROM python:3.12-alpine
ARG VERSION=dev
RUN echo "$VERSION" > /VERSION
COPY app.sh /app.sh
CMD ["sh", "/app.sh"]
EOF
$ cat > test.sh <<'EOF'
#!/bin/sh
set -eu
grep -q 'http.server' app.sh          # a "test": fails with exit 1 if the line is missing
echo "tests passed"
EOF
$ git add -A && git commit -qm "initial" 
$ REPO=ttl.sh/$(uuidgen | tr A-Z a-z)          # your private throwaway repo name
$ cat > ci.sh <<EOF
#!/bin/bash
set -euo pipefail                               # any failing command fails the pipeline
TAG=\$(git rev-parse --short HEAD)               # stage 0: the version IS the commit
echo "== test";  sh test.sh                      # stage 1: exit code decides
echo "== build"; docker build --build-arg VERSION=\$TAG -t $REPO:\$TAG .    # stage 2: immutable tag
echo "== push";  docker push $REPO:\$TAG          # stage 3: artifact leaves the runner
echo "== deploy"; kubectl set image deploy/lab lab=$REPO:\$TAG   # stage 4: only the template changes
kubectl rollout status deploy/lab --timeout=90s  # stage 5: red if the rollout does not finish
EOF
$ kubectl create deploy lab --image=$REPO:bootstrap --port=8080 2>/dev/null || true    # first ever "release" will fail to pull; that's fine
$ bash ci.sh                                    # run the pipeline
$ kubectl get deploy lab -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
$ kubectl logs deploy/lab | head -1             # version: <commit>

Now break it and watch the pipeline protect the cluster:

$ sed -i 's/http.server/http.serve/' app.sh && git commit -qam "typo"
$ bash ci.sh; echo "exit=$?"                    # "== test" then exit=1: build, push, deploy never ran
$ git revert --no-edit HEAD && bash ci.sh       # rollback is a commit; the pipeline redeploys the old code with a NEW immutable tag
$ kubectl rollout history deploy/lab            # every run = one revision (Day 10)

Everything in the next nine pages is this script — with a runner instead of your laptop, a trigger instead of bash ci.sh, secrets instead of your Docker login, and (from C6) a controller doing the last two stages instead of the script.

Your Deployment says image: api:latest. CI pushed a new latest. kubectl get pods shows the same Pods, unchanged. Why, and what are two ways to force the new version?

The Pod template did not change (the string api:latest is identical), so the Deployment controller has nothing to reconcile (Day 10). Quick hacks: kubectl rollout restart deploy/api (adds a restart annotation to the template) with imagePullPolicy: Always so every node re-pulls. The real fix: tag with the commit SHA and change the template.

Your team wants to "deploy to prod from CI in one click". Is that Continuous Delivery or Continuous Deployment? What credential does the CI system need in a push model, and what is the pull-model alternative?

Delivery (a human presses the button). In a push model CI holds a kubeconfig/token with write access to prod — ideally a dedicated ServiceAccount bound to a narrow Role (Day 36, Day 37). In a pull model CI only needs write access to the config repo; Argo CD inside the cluster applies the change.

Key takeaways

  • CI = every commit built and tested the same way on a clean runner; CD = a rehearsed, automated path from a verified artifact to an environment.
  • A pipeline stage is a shell script; its exit code is the verdict. Debug pipelines like you debug shell scripts.
  • The artifact is the image. Tag it immutably (commit SHA); a Deployment only rolls when its template text changes.
  • Build once, promote through environments by changing config (overlays/values), never by rebuilding.
  • Push CD gives CI cluster credentials; pull CD (GitOps) puts a reconciling controller in the cluster and gives CI only git access.
