C2 gave you a workflow that builds and tests. This page finishes the push-style pipeline: build the image properly (BuildKit, layer cache, immutable tags), push it to a registry the cluster can pull from, and deploy it — first with a kubeconfig stored as a secret, then the modern way with OIDC so no long-lived credential exists anywhere. It ends with runners inside the cluster, and with the reasons push-based deploys eventually make teams reach for GitOps.

What you'll learn

Build and push, properly

jobs:
  build:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }     # packages:write → push to ghcr.io/<owner>/…
    outputs: { tag: ${{ steps.meta.outputs.version }}, digest: ${{ steps.push.outputs.digest }} }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-qemu-action@v3                 # only for multi-arch (arm64 on an amd64 runner)
      - uses: docker/setup-buildx-action@v3               # BuildKit builder with cache export support
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,prefix=,format=short          # 9f2e1c3  ← the immutable tag CD will use
            type=ref,event=branch                  # main     ← convenience, mutable
            type=semver,pattern={{version}}        # 1.4.2 on a v1.4.2 tag
      - id: push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: ${{ github.event_name != 'pull_request' }}    # PRs: build only
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          provenance: false
buildx / BuildKit
The modern builder: parallel stages, better caching, cache export/import, multi-platform manifests. docker build already uses BuildKit; setup-buildx-action gives you a builder that can export cache to external stores.
type=gha cache
Layers are stored in GitHub's Actions cache between runs. Second build of an unchanged npm ci layer is a cache hit even though the VM is brand new. mode=max caches intermediate stages of a multi-stage build too.
metadata-action
Computes tags/labels from the event: the short SHA, the branch, semver from a git tag. Put the SHA first — it is what you will write into manifests.
digest output
The content hash of what was pushed. Pin it in manifests (image: ghcr.io/acme/api@sha256:…) for supply-chain strictness; the tag is for humans.

A cache hit is a cache hit on layers — the OverlayFS lowerdirs from L4. BuildKit hashes each instruction plus its inputs (the files a COPY touches, the previous layer); an identical hash means it can reuse the stored tarball instead of running the command. This is why the Dockerfile order from Day 5 matters more in CI than on a laptop: put COPY package*.json + RUN npm ci before COPY . ., and a source-only change never reinstalls dependencies.

Can the cluster pull it?

Images pushed to GHCR under a private repo are private. The kubelet needs credentials: a kubernetes.io/dockerconfigjson Secret referenced by imagePullSecrets (or attached to the ServiceAccount) — exactly Day 45. Use a fine-grained PAT with read:packages, not your account password, and rotate it.

$ kubectl create secret docker-registry ghcr --docker-server=ghcr.io --docker-username=acme-bot --docker-password=$GHCR_READ_TOKEN -n shop
$ kubectl patch sa default -n shop -p '{"imagePullSecrets":[{"name":"ghcr"}]}'     # every Pod in the ns can pull

Deploying from a job — option A: a kubeconfig secret

The simplest push deploy: give the job a kubeconfig and run kubectl. Do it with a purpose-built identity, not a copy of your admin config.

# in the cluster: an identity for CI that can only update Deployments in one namespace
apiVersion: v1
kind: ServiceAccount
metadata: { name: ci-deployer, namespace: shop }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: deployer, namespace: shop }
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "patch", "update"]
- apiGroups: ["apps"]
  resources: ["replicasets"]              # needed by rollout status / undo
  verbs: ["get", "list"]
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: ci-deployer, namespace: shop }
roleRef: { kind: Role, name: deployer, apiGroup: rbac.authorization.k8s.io }
subjects: [{ kind: ServiceAccount, name: ci-deployer, namespace: shop }]
$ TOKEN=$(kubectl -n shop create token ci-deployer --duration=8760h)          # bound token, 1 year (Day 37); rotate it
$ CA=$(kubectl config view --raw --minify -o jsonpath='{.clusters[0].cluster.certificate-authority-data}')
$ SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
$ cat > ci-kubeconfig <<EOF
apiVersion: v1
kind: Config
clusters: [{name: prod, cluster: {server: $SERVER, certificate-authority-data: $CA}}]
users: [{name: ci-deployer, user: {token: $TOKEN}}]
contexts: [{name: prod, context: {cluster: prod, user: ci-deployer, namespace: shop}}]
current-context: prod
EOF
$ kubectl --kubeconfig ci-kubeconfig auth can-i patch deploy -n shop       # yes
$ kubectl --kubeconfig ci-kubeconfig auth can-i delete secret -n shop      # no — good
$ gh secret set KUBECONFIG_PROD --env production < ci-kubeconfig

That kubeconfig is the one from Day 32 minus the client certificate: a cluster (server + CA), a user (a bearer token), a context. The token is a projected ServiceAccount token (Day 37), the API server authenticates it, and the Role from Day 36 limits what it can do. auth can-i is your unit test for CI permissions.

  deploy:
    needs: [build]
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - run: |
          install -m 600 /dev/null "$RUNNER_TEMP/kubeconfig"
          printf '%s' "$KUBECONFIG_B64" | base64 -d > "$RUNNER_TEMP/kubeconfig"
          echo "KUBECONFIG=$RUNNER_TEMP/kubeconfig" >> "$GITHUB_ENV"
        env: { KUBECONFIG_B64: ${{ secrets.KUBECONFIG_PROD }} }
      - run: kubectl set image deploy/api api=ghcr.io/${{ github.repository }}:${{ needs.build.outputs.tag }}
      - run: kubectl rollout status deploy/api --timeout=180s          # exit 1 → job fails
      - if: failure()
        run: kubectl rollout undo deploy/api                            # automatic rollback (Day 10)

Reachability. A GitHub-hosted runner is on the public internet; your API server must be reachable from it (public endpoint + an allowlist of GitHub's IP ranges, or a bastion). If the cluster is private, you need a self-hosted runner inside the network — see actions-runner-controller below.

With Helm or Kustomize instead of set image

$ helm upgrade --install api ./chart -n shop --set image.tag=$TAG --wait --timeout 3m --atomic   # --atomic rolls back on failure
$ cd overlays/prod && kustomize edit set image ghcr.io/acme/api=ghcr.io/acme/api:$TAG && kubectl apply -k . && kubectl rollout status deploy/api

helm --wait --atomic does the rollout-status-and-undo dance for you. Notice that kustomize edit set image modifies a file in git — if you commit it instead of applying it, you have just built the handoff GitOps uses (C6).

Deploying from a job — option B: OIDC, no stored secret

A stored kubeconfig is a long-lived credential sitting in GitHub. With managed clusters (EKS, GKE, AKS) you can avoid it entirely: the job proves who it is with a short-lived token that GitHub signs, and the cloud exchanges that for temporary credentials mapped to a role. Nothing to leak, nothing to rotate.

  deploy:
    runs-on: ubuntu-latest
    permissions: { id-token: write, contents: read }      # lets the job request an OIDC token
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy-shop
          aws-region: eu-west-1
      - run: aws eks update-kubeconfig --name prod --region eu-west-1   # writes a kubeconfig whose user is an exec plugin
      - run: kubectl set image deploy/api api=… && kubectl rollout status deploy/api --timeout=180s
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
      "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:acme/api:environment:production" }
    }
  }]
}
sub claim
Identifies the workflow run: repo:acme/api:ref:refs/heads/main, or repo:acme/api:environment:production when the job uses an environment. The trust policy pins it — a fork or another branch cannot assume the role.
aud claim
Who the token is for (sts.amazonaws.com); prevents replaying a token meant for one cloud at another.
Mapping into Kubernetes
EKS access entries (or the legacy aws-auth ConfigMap) map the IAM role to a Kubernetes group; a RoleBinding gives that group the deployer Role. GKE uses Workload Identity Federation + IAM roles; AKS uses federated credentials on a managed identity + Azure RBAC. Same three hops everywhere: GitHub identity → cloud identity → Kubernetes RBAC.

An OIDC token is a JWT: a signed statement of claims. The cloud verifies the signature with GitHub's published public keys (a JWKS at a well-known URL) — the same "trust the signer's public key" idea as certificates in Day 31. Kubernetes uses the identical mechanism inside the cluster: projected ServiceAccount tokens (Day 37) are OIDC JWTs signed by the API server, and cloud IAM can trust those too (IRSA / Workload Identity) — the reverse direction of this page.

Runners inside the cluster: actions-runner-controller

ARC is a Kubernetes controller (with CRDs — Day 40) that listens to GitHub's job queue and creates one ephemeral runner Pod per job. The Pod registers, runs one job, and is deleted. You get self-hosted runners that scale to zero, sit inside your network (private clusters, internal registries), and are clean every time.

$ helm install arc --namespace arc-systems --create-namespace oci://ghcr.io/actions/actions-runner-controller-charts/gha-runner-scale-set-controller
$ helm install arc-runners --namespace arc-runners --create-namespace \
    --set githubConfigUrl=https://github.com/acme \
    --set githubConfigSecret.github_token=$GH_PAT \
    --set minRunners=0 --set maxRunners=10 \
    oci://ghcr.io/actions/actions-runner-controller-charts/gha-runner-scale-set
$ kubectl -n arc-runners get autoscalingrunnersets,ephemeralrunners      # the CRDs doing the work
jobs:
  build:
    runs-on: arc-runners          # the scale set's name is the label

Building images inside a runner Pod hits the wall from Day 41: docker build needs a Docker daemon, and a daemon needs privileged (it creates namespaces, mounts overlays, writes iptables — L6). ARC's containerMode: dind runs a privileged sidecar for exactly that, which is a big grant. The rootless alternatives — kaniko, BuildKit rootless, buildah — execute the Dockerfile in user space and push layers directly to the registry with no daemon at all. C5 goes through kaniko in detail; the same Pod works as a GitHub runner.

Why push deploys eventually hurt

  • Credentials fan out. Every CI system, every environment, every cluster: a token in a secret store, each one an admin-ish key living outside the cluster. OIDC helps, but only on managed clouds.
  • No reconciliation. The job runs once. If someone kubectl edits the Deployment afterwards, or a node fails and a manual fix is applied, the cluster silently diverges from what CI last pushed. Nothing notices until the next deploy overwrites it (or does not).
  • Git is not the truth. The pipeline computed the manifest and applied it; the resulting state exists only in etcd. To know what is running you ask the cluster, not the repo.
  • Multi-cluster is N pipelines. Or one pipeline with N secrets and N sequential steps.

The pull model fixes all four at once by moving the last step into the cluster: C6.

Hands-on lab (30 min) — deploy to your KIND cluster from a real workflow

Hosted runners cannot reach a cluster on your laptop, so you will run a self-hosted runner locally — which also demystifies what a runner is.

  1. Register a runner: repo → Settings → Actions → Runners → New self-hosted runner. Follow the commands: download, ./config.sh --url … --token … --ephemeral, then ./run.sh in a terminal. Watch it appear as Idle.
  2. Create the CI identity in the cluster: apply the ServiceAccount/Role/RoleBinding above (namespace shop), create deploy/api with any image (kubectl create deploy api --image=nginx:1.26 -n shop), build the kubeconfig with create token, and check it with auth can-i.
  3. Workflow: runs-on: self-hosted; steps: checkout, docker build -t api:${GITHUB_SHA::7} ., kind load docker-image api:${GITHUB_SHA::7} (instead of a registry), then the kubeconfig + set image + rollout status + if: failure() undo steps from this page. Store the kubeconfig as a repo secret with gh secret set.
  4. Push and watch gh run watch and, in another terminal, kubectl get rs -n shop -w — a new ReplicaSet scales up while the old scales down (Day 10).
  5. Break the rollout: change the Dockerfile's CMD to ["false"], push, and watch: CrashLoopBackOff → rollout status times out → job fails → the undo step restores the previous ReplicaSet. Confirm with kubectl rollout history deploy/api -n shop.
  6. Drift: kubectl scale deploy/api --replicas=5 -n shop. Nothing in GitHub notices. Remember this for C6.
Your deploy job fails with error: You must be logged in to the server (Unauthorized). List three things to check, in order.

(1) Is the kubeconfig actually there and selected — did the step that writes it run, is KUBECONFIG set via $GITHUB_ENV? (2) Has the ServiceAccount token expired (create token --duration) or was the SA deleted? Decode the JWT's exp with cut -d. -f2 | base64 -d. (3) With OIDC: does the trust policy's sub condition match this branch/environment, and does the job have id-token: write? A 403 Forbidden instead of 401 means authentication worked and RBAC said no.

Why should the CI Role not include create on Deployments or any verb on Secrets?

Least privilege: CI updates the image of an existing Deployment; it should not be able to create arbitrary workloads (a compromised pipeline could run a crypto-miner) or read Secrets. If a job is compromised via a malicious action, the blast radius is "change the image tag of api in shop" — which is visible and revertible.

Key takeaways

  • Build with buildx, cache layers with type=gha, tag with the short SHA, record the digest; push on merges, not on PRs.
  • A private registry needs imagePullSecrets in the cluster — same as Day 45.
  • Push deploys need an identity: a dedicated ServiceAccount + narrow Role, or OIDC federation into cloud IAM mapped to RBAC. Test with auth can-i.
  • rollout status --timeout turns a bad rollout into a red job; if: failure() + rollout undo (or helm --atomic) auto-reverts.
  • ARC gives ephemeral runner Pods in-cluster; build images there rootlessly (kaniko/BuildKit), not with a privileged daemon.
  • Push deploys do not reconcile and scatter credentials — the problem GitOps exists to solve.
