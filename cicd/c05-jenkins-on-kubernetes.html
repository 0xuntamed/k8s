Static Jenkins agents are VMs you pay for while they idle and clean up by hand. On Kubernetes the controller can instead ask the API server for a Pod per build: it appears when a job is queued, runs the stages, and is deleted. This page shows how the Kubernetes plugin does that — using nothing but the objects from the course — and solves the one problem every cluster-native CI hits: building container images inside a container without a Docker daemon.

What you'll learn

  • Running the controller in-cluster: StatefulSet + PVC, Helm chart, JCasC
  • How the Kubernetes plugin creates agents: ServiceAccount, RBAC, the API calls
  • The agent Pod: the jnlp container, tool containers, the shared workspace volume, container()
  • Pod templates in a Jenkinsfile; requests/limits, node pools, priority
  • Building images without Docker: socket mounting, DinD, Kaniko, BuildKit rootless
  • Failure modes: Pending Pods, agents that never connect, wrong container names

The controller as a Kubernetes workload

The controller is a single stateful process with a directory it must keep — the definition of a StatefulSet with one replica and a PVC for JENKINS_HOME (Day 27). The official Helm chart (Day 43) does exactly that, plus a Service for the UI, a second Service for inbound agents on port 50000, a ServiceAccount with the RBAC the plugin needs, and JCasC configuration in a ConfigMap.

$ helm repo add jenkins https://charts.jenkins.io && helm repo update
$ helm install jenkins jenkins/jenkins -n jenkins --create-namespace -f values.yaml
$ kubectl -n jenkins get sts,pvc,svc,sa,role,rolebinding,cm      # what the chart made
$ kubectl -n jenkins exec sts/jenkins -c jenkins -- cat /run/secrets/additional/chart-admin-password; echo
$ kubectl -n jenkins port-forward svc/jenkins 8080:8080
# values.yaml (excerpt)
controller:
  numExecutors: 0                      # the controller never runs builds
  installPlugins: [kubernetes, workflow-aggregator, git, configuration-as-code, credentials-binding]
  resources: { requests: { cpu: 500m, memory: 1Gi }, limits: { memory: 3Gi } }
  JCasC:
    configScripts:
      welcome: |
        jenkins:
          systemMessage: "Managed by JCasC — do not click-configure"
  ingress:
    enabled: true
    hostName: jenkins.example.com
persistence:
  enabled: true
  size: 20Gi
  storageClass: gp3
agent:
  podName: default
  image: { repository: jenkins/inbound-agent, tag: latest-jdk17 }
  resources: { requests: { cpu: 250m, memory: 256Mi }, limits: { memory: 1Gi } }
  containerCap: 10                     # max concurrent agent Pods
  podRetention: Never

Everything you would click in the UI becomes a value or a JCasC snippet stored in a ConfigMap (Day 28) that the chart mounts and a sidecar reloads. Combined with a pinned plugin list, the controller becomes reproducible: helm upgrade recreates it from values, and only the PVC (build history) is state worth backing up — a volume snapshot of the PV.

How the plugin creates agents

The controller is just another API client. Its Pod runs with a ServiceAccount whose projected token (Day 37) lets it talk to https://kubernetes.default.svc; a Role in the namespace allows exactly what the plugin needs:

rules:
- apiGroups: [""]
  resources: ["pods", "pods/exec", "pods/log"]
  verbs: ["get", "list", "watch", "create", "delete", "patch"]     # create/delete agents; exec = container() steps; log = diagnostics
- apiGroups: [""]
  resources: ["events"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "list", "watch"]                                     # only if you sync Kubernetes Secrets into Jenkins credentials
$ kubectl -n jenkins auth can-i create pods --as=system:serviceaccount:jenkins:jenkins      # yes — required
$ kubectl -n jenkins auth can-i create pods/exec --as=system:serviceaccount:jenkins:jenkins # yes — container() needs it
$ kubectl -n jenkins auth can-i create deployments --as=system:serviceaccount:jenkins:jenkins  # no — good
# what the controller uses (Manage Jenkins → Clouds → kubernetes):
#   Kubernetes URL   https://kubernetes.default.svc           (in-cluster; CA + token from the SA mount)
#   Jenkins URL      http://jenkins.jenkins.svc.cluster.local:8080
#   Jenkins tunnel   jenkins-agent.jenkins.svc.cluster.local:50000   ← agents connect here (Day 12 ClusterIP, Day 48 DNS)

Three course lessons in one screen: the controller authenticates as system:serviceaccount:jenkins:jenkins (Day 37), RBAC decides it may create Pods (Day 36), and the agent finds its way back through a ClusterIP Service resolved by CoreDNS (Day 12, Day 48). If any of those three is broken, agents never come online; auth can-i, kubectl get endpointslices -n jenkins and a nslookup from a debug Pod find which.

Anatomy of an agent Pod

apiVersion: v1
kind: Pod
metadata:
  labels: { jenkins/label: kaniko-agent }
spec:
  serviceAccountName: jenkins-agent     # NOT the controller's SA — least privilege
  restartPolicy: Never
  containers:
  - name: jnlp                          # injected by the plugin if you omit it
    image: jenkins/inbound-agent:latest-jdk17
    env:
    - { name: JENKINS_URL, value: http://jenkins.jenkins.svc:8080 }
    - { name: JENKINS_TUNNEL, value: jenkins-agent.jenkins.svc:50000 }
    - { name: JENKINS_SECRET, value: "…per-agent secret…" }
    - { name: JENKINS_AGENT_NAME, value: kaniko-agent-x7k2p }
    resources: { requests: { cpu: 100m, memory: 256Mi } }
  - name: kaniko
    image: gcr.io/kaniko-project/executor:debug
    command: ["sleep"]
    args: ["infinity"]                  # kept alive; steps are exec'd into it
    resources: { requests: { cpu: 1, memory: 2Gi }, limits: { memory: 4Gi } }
    volumeMounts:
    - { name: regcred, mountPath: /kaniko/.docker }
  volumes:
  - name: workspace-volume              # injected: emptyDir mounted at /home/jenkins/agent in EVERY container
    emptyDir: {}
  - name: regcred
    secret:
      secretName: ghcr
      items: [{ key: .dockerconfigjson, path: config.json }]
  nodeSelector: { workload: ci }
  tolerations: [{ key: ci, operator: Exists, effect: NoSchedule }]
  priorityClassName: ci-low
  • jnlp — the Jenkins agent itself (agent.jar in a small image). It connects out to the tunnel Service with a one-time secret, becomes an online node with one executor, and runs plain sh steps.
  • tool containers — one per toolchain (kaniko, maven, node, kubectl). They idle on sleep infinity; container('kaniko') { sh '…' } runs the step inside them.
  • workspace-volume — an emptyDir (Day 26) mounted into every container at the same path, so a file written by git clone in jnlp is visible to kaniko: the multi-container pattern from Day 21.
  • serviceAccountName — give agents their own SA with no RBAC unless a step needs the API (a deploy step could get a namespaced deployer Role, as in C3).
  • regcred — the dockerconfigjson Secret from Day 45, mounted as a file for kaniko's push instead of used for the kubelet's pull.
  • resources / nodeSelector / tolerations / priority — builds are bursty: put them on a tainted CI node pool (Days 16–17), set requests so they schedule predictably (Day 19), and a low PriorityClass so they are preempted before production is (Day 46).

container('kaniko') is kubectl exec (Day 13): the controller opens a pods/exec stream to the API server, the kubelet asks containerd to spawn a process inside the kaniko container's namespaces (L2), and the durable-task mechanism from C4 runs there. All containers in the Pod share the network namespace (so localhost works between them) and the emptyDir mount; they do not share their root filesystems — each has its own image layers under OverlayFS (L4), which is why a tool installed in one container is absent in another.

Pod templates in a Jenkinsfile

pipeline {
  agent {
    kubernetes {
      defaultContainer 'kaniko'                     // sh steps run here unless wrapped in container()
      yaml '''
        spec:
          containers:
          - name: kaniko
            image: gcr.io/kaniko-project/executor:debug
            command: [sleep]
            args: [infinity]
            volumeMounts: [{ name: regcred, mountPath: /kaniko/.docker }]
          - name: kubectl
            image: bitnami/kubectl:1.31
            command: [sleep]
            args: [infinity]
          volumes:
          - name: regcred
            secret: { secretName: ghcr, items: [{ key: .dockerconfigjson, path: config.json }] }
      '''
    }
  }
  environment { TAG = "${env.GIT_COMMIT.take(7)}"; IMAGE = "ghcr.io/acme/api" }
  stages {
    stage('Build & push') {
      steps {
        sh '''/kaniko/executor --context "$WORKSPACE" --dockerfile Dockerfile \\
              --destination "$IMAGE:$TAG" --cache=true --cache-repo "$IMAGE/cache"'''
      }
    }
    stage('Deploy') {
      steps {
        container('kubectl') {                      // switch container; same workspace, same Pod
          sh 'kubectl -n shop set image deploy/api api=$IMAGE:$TAG && kubectl -n shop rollout status deploy/api --timeout=180s'
        }
      }
    }
  }
}

Scripted form: podTemplate(yaml: '…') { node(POD_LABEL) { container('kaniko') { sh '…' } } }. Templates can also be defined once in the cloud configuration (or JCasC) with a label and inherited: agent { kubernetes { inheritFrom 'kaniko-agent' } }.

Building images without a Docker daemon

Inside a Pod there is no Docker. The kubelet talks to containerd over CRI (Day 25); docker build has no daemon to talk to. Four ways out:

OptionHowPrivilegeVerdict
Mount /var/run/docker.sockhostPath to the node's Docker socketRoot on the node: the socket owner controls every container (L6)Only works on Docker nodes; never on shared clusters
Docker-in-Docker sidecardocker:dind container, privileged: true, DOCKER_HOST=tcp://localhost:2375privileged = all capabilities, no seccomp (Day 41)Works everywhere; blocked by Pod Security restricted; use only on an isolated CI pool
KanikoExecutes the Dockerfile in userspace, snapshots layers, pushes straight to the registryNone beyond a normal containerThe default choice for CI Pods
BuildKit rootless / buildahUser namespaces + fuse-overlayfs; a real builder without rootNeeds --oci-worker-no-process-sandbox or specific seccomp/AppArmor profilesFaster and more featureful than kaniko; a bit more setup

Why does Docker need root but kaniko does not? A daemon builds by creating containers: new namespaces, OverlayFS mounts, veth pairs — all CAP_SYS_ADMIN work (L6). Kaniko never creates a container. It is the container: it unpacks the base image's layers into its own root filesystem, runs each RUN as an ordinary child process, and after each instruction walks the filesystem to compute what changed — that diff, tarred, is the new layer (L4 without the mount). Because it runs unprivileged, a RUN that needs privileges (mounting, iptables, chroot tricks) fails inside kaniko, which is exactly the class of Dockerfile you should not have.

Hands-on lab (35 min) — Jenkins in KIND with Pod agents and a kaniko build

  1. Install with the values above minus the ingress and storageClass lines (KIND has a default StorageClass): helm install jenkins jenkins/jenkins -n jenkins --create-namespace -f values.yaml. Watch kubectl -n jenkins get pods -w until jenkins-0 is 2/2 (the second container is the JCasC reloader).
  2. Prove the RBAC: the three auth can-i commands above. Look at the Role the chart created: kubectl -n jenkins get role jenkins-schedule-agents -o yaml.
  3. Port-forward, log in (password from the exec command above) and open Manage Jenkins → Clouds → kubernetes. Note the URLs — they are Service DNS names from Day 12/48.
  4. Registry secret: kubectl -n jenkins create secret docker-registry ghcr --docker-server=ghcr.io --docker-username=YOU --docker-password=$PAT — or, with no account, skip the secret and push to ttl.sh (anonymous) by changing IMAGE.
  5. Pipeline job with the Jenkinsfile above (drop the Deploy stage for now). Build it. In another terminal: kubectl -n jenkins get pods -w — a Pod named after the template appears, runs, disappears.
  6. While it runs: kubectl -n jenkins describe pod <agent> (two containers, the emptyDir, the env vars) and kubectl -n jenkins logs <agent> -c jnlp (the connection to the tunnel).
  7. Break it three ways and read the symptom each time: (a) set container('kanikoo'); (b) add requests: { cpu: 64 } to kaniko → Pending; (c) apply a default-deny NetworkPolicy in jenkins (Day 47) → jnlp cannot connect. Remove it afterwards.
  8. Add the Deploy stage with a jenkins-agent ServiceAccount bound to the deployer Role from C3 (namespace shop). You now have the full push pipeline running inside the cluster it deploys to.
A pipeline runs docker build in a Pod agent and fails with Cannot connect to the Docker daemon. Someone suggests mounting /var/run/docker.sock. Two reasons that is wrong on a kubeadm/EKS cluster?

The nodes run containerd, not Docker — there is no such socket. And even where there is one, the socket grants root on the node: any build could start a privileged container with the host filesystem mounted. Use kaniko or BuildKit rootless.

The controller can create Pods but every agent Pod sits in Running for 2 minutes and is then deleted; the build never starts. Where do you look?

kubectl logs <agent> -c jnlp: the agent could not reach the controller (wrong Jenkins URL/tunnel, a NetworkPolicy, or the jenkins-agent Service has no endpoints). The plugin deletes agents that fail to connect within the timeout.

Key takeaways

  • Controller = StatefulSet + PVC, installed by Helm, configured by JCasC; executors 0. Agents = Pods created per build by the Kubernetes plugin through the API server with a ServiceAccount and a namespaced Role.
  • An agent Pod is the jnlp container plus tool containers sleeping, sharing an emptyDir workspace; container('x') is an exec into that container.
  • Agents connect out to the jenkins-agent Service on 50000 — Services, DNS, RBAC and NetworkPolicies from the course are the failure points.
  • No Docker daemon in Pods: build with kaniko (unprivileged, pushes layers directly) or BuildKit rootless; DinD needs privileged; the Docker socket is root on the node.
  • Treat builds as workloads: requests, a tainted CI node pool, low priority, podRetention for debugging.
