"Synced" and "Healthy" are two different questions, and most Argo CD confusion comes from mixing them up. Synced means the cluster matches git. Healthy means what is running actually works — which Argo CD decides using the same signals the course taught you: rollout conditions, readiness probes, bound PVCs, load-balancer addresses. This page explains both, then the mechanics of a sync operation — phases, hooks, waves, options — how to stop diffs from lying, and how to go back.

Two statuses

Sync status — "does live match git?"

  • Synced — every rendered object exists and its relevant fields match.
  • OutOfSync — something differs: a new commit (expected), a manual change (drift), or an object is Missing. argocd app diff shows what.
  • Unknown — comparison could not run (repo error, invalid manifests). See status.conditions.

Health status — "is it working?"

  • Healthy — all resources report good.
  • Progressing — something is still converging (a rollout, a pending LB).
  • Degraded — something failed (rollout deadline exceeded, CrashLoopBackOff, Job failed).
  • Suspended — paused on purpose (a suspended CronJob, a paused Rollout).
  • Missing — in git, not in the cluster.
  • The app's health is the worst of its resources.

# argocd-cm: a custom health check for a CRD (Lua)
data:
  resource.customizations.health.cert-manager.io_Certificate: |
    hs = {}
    if obj.status ~= nil and obj.status.conditions ~= nil then
      for _, c in ipairs(obj.status.conditions) do
        if c.type == "Ready" and c.status == "True" then hs.status = "Healthy"; hs.message = "Certificate issued"; return hs end
      end
    end
    hs.status = "Progressing"; hs.message = "Waiting for certificate"
    return hs

Argo CD does not invent health. For a Deployment it reads the same status.conditions that kubectl rollout status reads (Day 10); for Pods it trusts the readiness probes you wrote (Day 23). A Deployment with no readiness probe goes Healthy the instant its containers start — Argo CD will happily report a broken release as Healthy if you gave it nothing to check.

The sync operation

Phases
PreSync → Sync → PostSync, plus SyncFail (runs if any phase fails) and PostDelete. Ordinary manifests belong to Sync; hooks are manifests annotated into the other phases.
Hooks
argocd.argoproj.io/hook: PreSync on a Job (Day 29) or any resource. A phase waits for its hooks to be Healthy (a Job: Succeeded) before continuing; a failed hook fails the operation. hook-delete-policy: BeforeHookCreation (default: delete the old one before creating the new), HookSucceeded, HookFailed. Use generateName so each sync gets a fresh Job.
Waves
argocd.argoproj.io/sync-wave: "2" (default 0, negatives allowed). Within a phase, Argo CD applies wave by wave and waits for each wave to be Healthy before starting the next. Inside a wave, the order is by kind (Namespace, then CRDs, RBAC, ConfigMaps/Secrets… Services… workloads) then name.
Prune
Objects with the app's tracking marker that are absent from the render are deleted — at the end (PruneLast=true) or as part of their wave. Individually protect with argocd.argoproj.io/sync-options: Prune=false (a PVC, a namespace).
Automated sync
Fires when the target revision produces a different render (new commit) and, with selfHeal, when live drifts. It will not retry a revision whose sync already failed — fix forward with a new commit or a manual sync, or set retry. Sync windows can block it by schedule.
apiVersion: batch/v1
kind: Job
metadata:
  generateName: db-migrate-
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migrate
        image: ghcr.io/acme/api:9f2e1c3         # same image as the app; the same tag CI wrote
        command: ["./manage.py", "migrate"]
---
apiVersion: v1
kind: Namespace
metadata: { name: shop, annotations: { argocd.argoproj.io/sync-wave: "-2", argocd.argoproj.io/sync-options: Prune=false } }
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: api, annotations: { argocd.argoproj.io/sync-wave: "1" } }
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: api, annotations: { argocd.argoproj.io/sync-wave: "2" } }     # only after the Deployment is Healthy

A hook Job is a Pod with restartPolicy: Never whose exit code (L1) is the whole verdict: 0 → Succeeded → the sync continues; non-zero → Failed → the sync fails and SyncFail hooks run. backoffLimit: 0 so a failed migration is not retried blindly. Read its logs with argocd app logs api --kind Job or kubectl logs job/… — the failure detail is never in Argo CD's UI, it is in the Pod.

Sync options

OptionEffect
CreateNamespace=trueCreate the destination namespace if missing (not tracked/pruned).
ServerSideApply=trueUse server-side apply: managed-fields ownership, no 262 KB annotation limit on big CRDs, cooperative with other controllers (Day 9).
PruneLast=truePrune after all waves are healthy instead of per wave.
ApplyOutOfSyncOnly=trueApply only the objects that differ — faster for big apps; hooks still run.
Replace=truekubectl replace instead of apply: for immutable-field changes (a Job's template, a Service's clusterIP). Destructive; usually per-resource via annotation.
Validate=falseSkip schema validation (CRDs whose schema the cluster does not know yet).
SkipDryRunOnMissingResource=trueLet a CR sync in the same operation as its CRD.
PrunePropagationPolicy=foregroundDelete dependents first (Day 10 owner references) before the owner disappears.
RespectIgnoreDifferences=trueDo not overwrite ignored fields when syncing (otherwise ignore only affects the diff).

Diffs that lie, and how to fix them

An app that is always OutOfSync with nothing to see is a diff problem. Live objects carry fields the manifest never set: defaults filled by the API server, status, fields other controllers own. Argo CD normalises the common ones; you configure the rest.

spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers: [/spec/replicas]                          # HPA (Day 20) owns replicas
  - group: admissionregistration.k8s.io
    kind: MutatingWebhookConfiguration
    jqPathExpressions: [.webhooks[].clientConfig.caBundle]  # cert-manager injects this
  - group: apps
    kind: Deployment
    managedFieldsManagers: [kube-controller-manager]        # anything that manager wrote (server-side apply metadata)
  syncPolicy:
    syncOptions: [RespectIgnoreDifferences=true]            # and don't clobber them on sync
# argocd-cm: globally, for every app
data:
  resource.customizations.ignoreDifferences.all: |
    managedFieldsManagers: [kube-controller-manager]
  resource.customizations.ignoreDifferences.apps_Deployment: |
    jsonPointers: [/spec/template/metadata/annotations/kubectl.kubernetes.io~1restartedAt]   # kubectl rollout restart

Every entry here is a second controller writing to the same object: the HPA (Day 20), a mutating webhook (Day 38), the Deployment controller itself. Server-side apply's managed fields (Day 9) exist precisely to record who owns which field; managedFieldsManagers lets Argo CD use that record instead of a hand-written pointer list. Turn on ServerSideApply=true and most of these entries become unnecessary.

$ argocd app diff api-prod                          # what OutOfSync means, line by line
$ argocd app get api-prod --refresh                 # re-compare now (normally every 3 min + webhook)
$ argocd app get api-prod --hard-refresh            # also drop the cached render (after editing files the cache key misses)
$ kubectl -n argocd annotate app api-prod argocd.argoproj.io/refresh=hard --overwrite     # the same, declaratively

History and rollback

$ argocd app history api-prod
ID  DATE                           REVISION
41  2025-06-02 10:14:09 +0000 UTC  main (7a1c9e2)
42  2025-06-02 11:02:51 +0000 UTC  main (e4d5c6b)     ← current, Degraded
$ argocd app rollback api-prod 41                   # re-applies the manifests rendered at 7a1c9e2
# ⚠ rollback DISABLES automated sync for the app (otherwise it would immediately sync forward to main again)
$ argocd app set api-prod --sync-policy automated   # re-enable when git is fixed

argocd app rollback

Fast, one command, no git involved. But the cluster now disagrees with git on purpose, auto-sync is off, and the next person to look at the repo sees a version that is not running. Use it as a fire extinguisher — then do the git revert and re-enable auto-sync.

git revert + sync

The GitOps way: the desired state moves back, auto-sync deploys it, history is linear, and reviewers see what happened. Slightly slower (a PR, a webhook). The rollout itself is the same rolling update as Day 10's rollout undo, driven by the manifest.

Hands-on lab (30 min) — hooks, waves, a broken release, a revert

  1. Add a PreSync hook to your C7 app's overlay: the migrate Job above, with command: ["sh", "-c", "echo migrating; sleep 10"]. Commit. Watch the sync in the UI: the Job runs first, the Deployment waits.
  2. Waves: annotate the Deployment with wave 1 and the Service with wave 2; add a readiness probe with initialDelaySeconds: 20. Commit; watch wave 2 wait until the Deployment is Healthy.
  3. Fail the hook: change the command to exit 1. Commit. The sync fails; the Deployment is untouched; argocd app logs --kind Job shows why. Fix and commit — note auto-sync did not retry the failed revision until the new commit.
  4. Break the release: set the image tag to one that does not exist. Sync succeeds (the manifest applied fine); health goes Progressing then Degraded (ImagePullBackOff, Day 22). Read it in argocd app get.
  5. Two rollbacks: first argocd app rollback to the previous ID — observe auto-sync got disabled. Then git revert the bad commit, re-enable auto-sync, and see it converge the GitOps way.
  6. A lying diff: add an HPA to the overlay (Day 20) while keeping replicas: 2 in the Deployment. Watch OutOfSync appear whenever the HPA scales. Add the ignoreDifferences entry and RespectIgnoreDifferences=true; confirm it stays Synced.
An app shows Synced · Degraded. Is the problem in git, in Argo CD, or in the workload? What is the first command?

The workload. Synced means the manifests applied exactly as written; Degraded means the resulting objects are unhealthy. argocd app get to find the Degraded resource, then kubectl describe/logs on it — the manifest that is in git is wrong (bad image, bad config), so the fix is a commit or revert.

You need a ConfigMap change to be picked up by Pods that mount it as env vars. Argo CD syncs the ConfigMap; nothing restarts. Why, and what are two fixes?

Env vars are read at container start (Day 28); updating the ConfigMap does not change the Pod template, so no rollout. Fixes: hash the ConfigMap content into a Pod annotation (Kustomize's configMapGenerator does this by appending a hash suffix to the name, which changes the template), or run a controller like Reloader that restarts on ConfigMap changes.

Key takeaways

  • Sync = git vs live; Health = is it working, computed per kind from the same status fields and probes the course taught. An app can be Synced and Degraded.
  • A sync runs PreSync → Sync → PostSync; hooks are annotated Jobs; waves order resources and wait for health between them; prune removes what left git.
  • Sync options tune apply behaviour — ServerSideApply, CreateNamespace, PruneLast, Replace — globally or per resource via annotation.
  • Perpetual OutOfSync is a second controller owning a field: ignoreDifferences (pointers, jq, managed-field managers) + RespectIgnoreDifferences.
  • app rollback is the fire extinguisher (and disables auto-sync); git revert is the rollback.
  • Stuck syncs are waiting for health; failed syncs are rejected objects or failed hooks — the detail is always in the Kubernetes object, not in Argo CD.
