One Application deploying one overlay is the tutorial. Real platforms have forty services, three environments, a handful of clusters and a stack of infrastructure charts — and nobody wants to hand-write two hundred Application manifests. This page is the scaling toolkit: rendering Helm and Kustomize sources properly, bootstrapping everything from one root app, generating Applications from templates, managing many clusters from one hub, automating image updates, and rolling out progressively with Argo Rollouts.

What you'll learn

  • Source types: directory, Kustomize, Helm (repo, OCI, values), multi-source, plugins — and how Argo CD renders each
  • App of Apps: bootstrapping a cluster from one Application
  • ApplicationSets: list, git, cluster, matrix and pull-request generators
  • Multi-cluster: hub-and-spoke, cluster Secrets and labels, sharding
  • Image updates: CI commits vs Argo CD Image Updater
  • Progressive delivery with Argo Rollouts; notifications; performance settings

Sources: how Argo CD renders

The repo-server turns a source into plain manifests. What it runs depends on what it finds at path — and you can steer it.

Directory
Plain YAML/JSON. directory: { recurse: true, include: "*.yaml", exclude: "test/*" }. Multi-document files are fine.
Kustomize
A kustomization.yaml at the path → kustomize build. Overrides without touching the repo: kustomize: { images: ["ghcr.io/acme/api:9f2e1c3"], namePrefix: canary-, commonLabels: {…}, buildOptions: "--enable-helm" }. This images field is exactly what CI's kustomize edit set image writes into the file — the file is the GitOps way, the field is the escape hatch (Day 42).
Helm
A Chart.yaml at the path, or chart: + a Helm repo URL / OCI registry → helm template. helm: { valueFiles: [values-prod.yaml], values: "replicaCount: 3", valuesObject: {…}, parameters: [{name: image.tag, value: 9f2e1c3}], releaseName: api, skipCrds: false }. Helm hooks are translated into Argo CD hooks (pre-install → PreSync, post-install → PostSync). No Helm release exists in the cluster: Argo CD applies the rendered objects itself, so helm list is empty and rollback is Argo's or git's, not Helm's (Day 43).
Multi-source
sources: (plural): a chart from a public repo plus values from your config repo — the pattern for third-party charts.
Plugins (CMP)
A sidecar on the repo-server that renders anything else (Jsonnet, cdk8s, SOPS-decrypting Helm) via a ConfigManagementPlugin spec.
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: ingress-nginx, namespace: argocd }
spec:
  project: platform
  sources:
  - repoURL: https://kubernetes.github.io/ingress-nginx     # the chart, from a Helm repo (or oci://…)
    chart: ingress-nginx
    targetRevision: 4.11.2
    helm:
      releaseName: ingress-nginx
      valueFiles: [$values/infra/ingress-nginx/values-prod.yaml]   # $values → the ref below
  - repoURL: https://github.com/acme/platform-config          # our values, from git
    targetRevision: main
    ref: values
  destination: { server: https://kubernetes.default.svc, namespace: ingress-nginx }
  syncPolicy: { automated: { prune: true, selfHeal: true }, syncOptions: [CreateNamespace=true, ServerSideApply=true] }

You used helm install on Day 43 and kubectl apply -k on Day 42. Argo CD uses the same two tools — only the template/build half of them — and replaces the apply half with its own controller. Everything you know about values precedence, overlays and patches transfers unchanged; what changes is that helm rollback and release Secrets are gone, because git is the release history now.

App of Apps: bootstrapping

Applications are resources; a directory of Application manifests can itself be the source of an Application. That root app is how a fresh cluster goes from "Argo CD installed" to "everything deployed" with one kubectl apply.

platform-config/argocd/ ├── root.yaml # THE one manifest you apply by hand: an Application whose path is argocd/apps/ ├── projects/ # AppProjects (C7), synced by root too │ └── shop.yaml └── apps/ ├── argocd.yaml # Argo CD manages itself (Helm chart + values in git) wave -3 ├── cert-manager.yaml # wave -2 ├── ingress-nginx.yaml # wave -1 ├── monitoring.yaml # kube-prometheus-stack (Day 56) wave -1 └── shop-apps.yaml # an ApplicationSet for the team's services (below) wave 0
# argocd/root.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: root, namespace: argocd, finalizers: [resources-finalizer.argocd.argoproj.io] }
spec:
  project: default                              # root needs to create AppProjects and Applications in argocd
  source: { repoURL: https://github.com/acme/platform-config, targetRevision: main, path: argocd, directory: { recurse: true } }
  destination: { server: https://kubernetes.default.svc, namespace: argocd }
  syncPolicy: { automated: { prune: true, selfHeal: true } }
$ kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml   # day 0
$ kubectl apply -f argocd/root.yaml                                                                          # day 0, step 2 — that's it
$ argocd app list                    # root, argocd, cert-manager, ingress-nginx, monitoring, shop-* — all created by root

Deleting the root app with its finalizer cascades to every child Application and, through their finalizers, to every workload. Protect it: argocd.argoproj.io/sync-options: Prune=false on child Applications you never want auto-removed, Argo CD RBAC that denies delete on root, and preserveResourcesOnDeletion on ApplicationSets.

ApplicationSets: generating Applications

An ApplicationSet is a template plus generators that produce parameter sets; the controller creates one Application per set and keeps them in step — add a directory or a cluster and an app appears, remove it and the app goes.

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: shop-apps, namespace: argocd }
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
  - matrix:
      generators:
      - git:                                               # one entry per app directory
          repoURL: https://github.com/acme/platform-config
          revision: main
          directories: [{ path: "apps/*" }]
      - clusters:                                          # one entry per registered cluster with this label
          selector: { matchLabels: { env: prod } }
  template:
    metadata:
      name: "{{.path.basename}}-{{.name}}"                 # api-prod-eu, api-prod-us, web-prod-eu…
      labels: { team: shop }
    spec:
      project: shop
      source:
        repoURL: https://github.com/acme/platform-config
        targetRevision: main
        path: "{{.path.path}}/overlays/{{.metadata.labels.env}}"
      destination: { server: "{{.server}}", namespace: "{{.path.basename}}" }
      syncPolicy: { automated: { prune: true, selfHeal: true }, syncOptions: [CreateNamespace=true] }
  syncPolicy:
    preserveResourcesOnDeletion: true                      # removing an app from the set does not delete its workloads
  strategy:
    type: RollingSync                                      # progressive: sync by label group, wait for health
    rollingSync:
      steps:
      - matchExpressions: [{ key: env, operator: In, values: [staging] }]
      - matchExpressions: [{ key: env, operator: In, values: [prod] }]
GeneratorProduces one set per…Typical use
listLiteral element you writeA few environments with explicit values
git (directories / files)Directory matching a glob, or a JSON/YAML config file found in the repo"Every folder under apps/ is an app"; per-app config.json
clustersRegistered cluster (Secret) matching a label selectorDeploy the same thing to every prod cluster
matrix / mergeCartesian product / join of two generatorsapps × clusters; clusters enriched with per-cluster config
pullRequestOpen PR on the app repoPreview environment per PR: namespace pr-123, deleted on merge
scmProviderRepository in a GitHub/GitLab orgEvery repo with a deploy/ directory gets an app
pluginWhatever your HTTP plugin returnsAn inventory system, a CMDB

An ApplicationSet is a controller that creates other custom resources — the same layered-operator pattern as a Deployment creating ReplicaSets creating Pods (Day 40). The generated Applications are owned (ownerReferences) by the set; edit one by hand and the controller puts it back, exactly like editing a ReplicaSet under a Deployment.

Many clusters

Hub and spoke

One Argo CD manages N clusters through stored credentials (argocd cluster add, C7). One UI, one RBAC, cluster generators. Costs: the hub must reach every API server; the hub's cluster Secrets are powerful; the hub is a single point of failure for deploys (not for running workloads).

Per-cluster Argo CD

Each cluster runs its own instance pulling the same repo (often via an ApplicationSet whose cluster generator only matches "in-cluster"). No cross-cluster credentials, no hub reachability, survives hub loss. Costs: N UIs and N upgrades — mitigated by managing all instances from git.

# a cluster Secret (what `argocd cluster add` creates); labels drive the cluster generator
apiVersion: v1
kind: Secret
metadata:
  name: prod-eu
  namespace: argocd
  labels: { argocd.argoproj.io/secret-type: cluster, env: prod, region: eu }
stringData:
  name: prod-eu
  server: https://prod-eu.k8s.acme.internal:6443
  config: |
    { "bearerToken": "…argocd-manager SA token…", "tlsClientConfig": { "insecure": false, "caData": "…" } }

The config field is a kubeconfig in JSON (Day 32). cluster add binds argocd-manager to cluster-admin in the spoke — convenient and too much. For production, create the ServiceAccount yourself with a ClusterRole limited to the kinds your apps deploy (Day 36), and rotate the token (Day 37) — or use the cloud's IAM-based exec auth in config.execProviderConfig.

# sharding: spread apps across controller replicas (each replica owns a subset of clusters)
$ kubectl -n argocd scale sts/argocd-application-controller --replicas=3
$ kubectl -n argocd patch cm argocd-cmd-params-cm -p '{"data":{"controller.sharding.algorithm":"round-robin","controller.status.processors":"50","controller.operation.processors":"25"}}'
# repo-server: more replicas for render throughput; a webhook instead of 3-minute polling
$ kubectl -n argocd scale deploy/argocd-repo-server --replicas=3
$ kubectl -n argocd patch cm argocd-cm -p '{"data":{"timeout.reconciliation":"300s","resource.exclusions":"- apiGroups: [\"metrics.k8s.io\"]\n  kinds: [\"*\"]\n  clusters: [\"*\"]"}}'

Getting new images in: three options

CI commits the tag
The C6 handoff. Explicit, reviewed if you want, works with any renderer. The default answer.
Argo CD Image Updater
A controller that polls the registry for tags matching a policy and writes the change — ideally back to git (write-back-method: git), producing the commit CI would have made. Configure with annotations on the Application: argocd-image-updater.argoproj.io/image-list: api=ghcr.io/acme/api, …/api.update-strategy: semver (or digest, latest, name), …/api.allow-tags: regexp:^v[0-9]+. Good for dev environments that should always run the newest build.
Kustomize/Helm parameter override (argocd write-back)
The updater (or argocd app set --kustomize-image) patches the Application instead of git. Fast, but the repo no longer describes what runs — not GitOps. Avoid outside experiments.

Progressive delivery: Argo Rollouts

A Deployment's rolling update (Day 10) replaces Pods as fast as probes allow; it cannot send 10 % of users to the new version, watch error rates for ten minutes and back out. Argo Rollouts adds a Rollout CRD — a drop-in for Deployment with a strategy of canary or blueGreen steps — plus AnalysisTemplates that query Prometheus (Day 56) and traffic shaping through an Ingress, Gateway API or a mesh (Days 49–52).

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: api }
spec:
  replicas: 10
  selector: { matchLabels: { app: api } }
  template: { … same Pod template as the Deployment … }
  strategy:
    canary:
      canaryService: api-canary            # Rollouts manages selectors on these two Services
      stableService: api
      trafficRouting:
        nginx: { stableIngress: api }      # writes canary-weight annotations on a generated Ingress
      steps:
      - setWeight: 10
      - pause: { duration: 5m }
      - analysis: { templates: [{ templateName: error-rate }] }
      - setWeight: 50
      - pause: {}                          # manual promotion: kubectl argo rollouts promote api
      - setWeight: 100
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: error-rate }
spec:
  metrics:
  - name: 5xx-ratio
    interval: 1m
    count: 5
    failureLimit: 1
    successCondition: result[0] < 0.01
    provider:
      prometheus:
        address: http://prometheus.monitoring:9090
        query: sum(rate(http_requests_total{app="api",canary="true",code=~"5.."}[2m])) / sum(rate(http_requests_total{app="api",canary="true"}[2m]))
$ kubectl create ns argo-rollouts && kubectl apply -n argo-rollouts -f https://github.com/argoproj/argo-rollouts/releases/latest/download/install.yaml
$ kubectl argo rollouts get rollout api -w          # the kubectl plugin: live view of steps, weights, analysis runs
$ kubectl argo rollouts promote api                 # release a manual pause
$ kubectl argo rollouts abort api                   # back to stable; Argo CD shows the Rollout as Degraded until the manifest is fixed

A Rollout is Day 10 with the decisions externalised: it still manages ReplicaSets; the canary and stable Services (Day 12) select Pods by a pod-template hash label; the Ingress controller (Day 49) does the weighted split; Prometheus (Day 56) supplies the verdict. Argo CD knows Rollouts' health natively — Suspended while paused, Degraded when aborted — so the GitOps loop and the delivery loop compose. Flagger does the same job with a Deployment left in place.

data:

# subscribe an Application (or a whole AppProject) with an annotation:
#   notifications.argoproj.io/subscribe.on-health-degraded.slack: shop-alerts

Built-in triggers cover sync succeeded/failed/running, health degraded, and deployment of a new revision; GitHub commit statuses are a service too, closing the loop back to the PR.

Hands-on lab (40 min) — from one app to a generated fleet

  1. Kustomize layout: in your config repo make apps/api/{base,overlays/dev,overlays/prod} and apps/web/… (any two images, e.g. nginx and httpd). Commit.
  2. Environments as a list: KIND has only the in-cluster destination and Argo CD keeps no Secret for it by default, so instead of a clusters generator use list: { elements: [{env: dev}, {env: prod}] } with destination.server: https://kubernetes.default.svc. (On a real fleet you would label cluster Secrets and swap the list for clusters.)
  3. ApplicationSet with a matrix of git directories: apps/* × list: [{env: dev}, {env: prod}], template path {{.path.path}}/overlays/{{.env}}, namespace {{.path.basename}}-{{.env}}. Apply; argocd app list shows four apps. Open the UI.
  4. Grow the fleet: add apps/worker/…, commit — two more apps appear without touching Argo CD. Delete the directory — they disappear; with preserveResourcesOnDeletion the namespaces stay.
  5. Helm multi-source: create the ingress-nginx Application above with your own values.yaml (set controller.service.type: NodePort for KIND). Confirm helm list -A is empty even though the chart is deployed.
  6. App of Apps: move the ApplicationSet and the ingress-nginx Application into argocd/apps/, create root.yaml, delete the objects you applied by hand, apply only root.yaml. Everything comes back. Now delete your KIND cluster, create a new one, install Argo CD, apply root: your platform is rebuilt from git.
  7. Optional — canary: install Argo Rollouts, convert api's Deployment into a Rollout with setWeight: 20 → pause: {} (no traffic routing needed for a pause-only canary), commit a new tag, watch kubectl argo rollouts get rollout api -w, and note Argo CD's health as Suspended until you promote.
Your ApplicationSet uses a clusters generator with matchLabels: {env: prod}. You register a new prod cluster with argocd cluster add and nothing deploys there. Why?

The cluster Secret has no env: prod label — cluster add does not know your labels. Add it (kubectl -n argocd label secret cluster-… env=prod) and the generator produces the new parameter sets on its next reconcile.

An app rendered from a Helm chart is perpetually OutOfSync on a Secret whose value changes every sync. What is happening?

The chart generates a random value (randAlphaNum) when no value is supplied, so every helm template differs. Supply the value (from a sealed/external secret), or ignore the field with ignoreDifferences (C8).

Key takeaways

  • Argo CD renders with kustomize build/helm template and applies the result itself — no Helm releases; values, overlays and multi-source combine third-party charts with your config.
  • App of Apps: one root Application (with waves) bootstraps Argo CD itself, infrastructure and team apps from a directory of Applications.
  • ApplicationSets stamp out Applications from generators (git, clusters, list, matrix, PRs); the set owns them like a Deployment owns ReplicaSets.
  • Multi-cluster is a Secret per cluster (a kubeconfig) with labels; scope the spoke ServiceAccount, shard controllers, prefer webhooks to polling.
  • New images arrive via CI commits (default) or Image Updater writing to git; avoid non-git write-back.
  • Argo Rollouts turns Day 10's rolling update into canary/blue-green steps judged by Prometheus, with traffic split by your Ingress or Gateway; Argo CD understands its health.
