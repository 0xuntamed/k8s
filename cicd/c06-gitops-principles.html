Every controller in this course works the same way: read the desired state, observe the actual state, act on the difference, repeat. GitOps applies that loop to deployment itself. The desired state of a whole environment lives in a git repository; a controller running in the cluster continuously makes the cluster match it. Deploying becomes merging. Rollback becomes revert. Drift becomes a status you can see. This page is the idea; C7 onwards is Argo CD, the implementation.

The four principles

The OpenGitOps definition has four parts. None of them is new to you.

1 · Declarative
The desired state is expressed as data, not as steps: manifests, Kustomize overlays, Helm values. You have written nothing else since Day 9.
2 · Versioned and immutable
That data is stored in a system that keeps history and never rewrites it: git. Every state the cluster was ever in is a commit with an author and a reviewer. Compare: etcd stores only now.
3 · Pulled automatically
Software agents fetch the desired state from the store. Nothing outside the cluster pushes into it; the cluster reaches out. This is the inversion that changes the security model.
4 · Continuously reconciled
The agents keep comparing and correcting, forever — not once per pipeline run. The control loop from Day 7, with a git repo where the Deployment spec used to be.

Kubernetes already is GitOps one level down: you declare a Deployment in etcd, controllers reconcile Pods to it. GitOps adds one more level: you declare the Deployment (and everything else) in git, and a controller reconciles etcd to it. Same loop, one more layer of desired state.

The push pipeline from C3 is not wrong — it is how most teams start, and for a single cluster with OIDC it is fine. It becomes wrong the day someone runs kubectl edit in prod to "fix it quickly" and nothing notices, or the day the third cluster arrives. The pull model is the answer to those two days.

The loop, with git as the truth

Desired state
A commit in the config repo, rendered (Kustomize/Helm) into plain objects. The agent tracks a branch (main) or a tag/commit for stricter environments.
Live state
What the API server returns for those objects: the same three-way comparison kubectl apply does (Day 9), minus fields the agent knows to ignore (status, defaults, fields other controllers own).
Sync
Applying the rendered manifests so live = desired. Manual (a human clicks / runs a command after reviewing the diff) or automated (on every change).
Drift / OutOfSync
Live ≠ desired. Either git moved (a new commit: expected drift, sync forward) or the cluster moved (someone edited an object: unexpected drift). The agent shows the diff either way.
Self-heal
Automated sync also for cluster-side drift: the manual change is reverted. Turn it on when git is truly the only accepted path.
Prune
Delete live objects that were removed from git. Off by default in most tools because it is destructive; on for mature setups so that "delete the file" means delete.
Interval + webhook
The agent polls git every few minutes and also accepts webhooks for immediacy. Reconciliation of live state uses watches, so cluster-side drift is noticed within seconds.

Not every live change is drift. The HPA (Day 20) rewrites spec.replicas; a Deployment's controller stamps annotations; admission webhooks inject sidecars (Day 38). A GitOps agent must be told to ignore those fields or it will fight the other controllers — the same "two controllers owning one field" problem as an HPA plus a hard-coded replicas. C8 covers ignoreDifferences.

Repository design

Application repository

Source code, Dockerfile, tests, the CI workflow/Jenkinsfile. Produces an image. Changes many times a day; owned by the app team; CI runs on every push.

Configuration (deployment) repository

Manifests for one or many apps and environments: Kustomize bases and overlays, Helm values, the GitOps agent's own objects. Produces a cluster state. Changes when a version is promoted or config changes; reviewed by whoever owns the environment; the agent watches it.

Why separate them? CI on the app repo should not trigger a redeploy on a README change; deploying should not require rebuilding; the people allowed to merge to prod config are not the people allowed to merge app code; and one config repo can describe apps from twenty app repos.

platform-config/ # one config repo, one team (or one per team) ├── apps/ │ └── api/ │ ├── base/ # Deployment, Service, Ingress, kustomization.yaml │ └── overlays/ │ ├── dev/kustomization.yaml images: [{name: ghcr.io/acme/api, newTag: 9f2e1c3}] │ ├── staging/kustomization.yaml images: [{name: ghcr.io/acme/api, newTag: 9f2e1c3}] │ └── prod/kustomization.yaml images: [{name: ghcr.io/acme/api, newTag: 4b7d0e9}] ← behind ├── infra/ # cert-manager, ingress controller, monitoring: Helm values per cluster │ ├── cert-manager/values-prod.yaml │ └── ingress-nginx/values-prod.yaml └── argocd/ # the agent's own config: Applications / ApplicationSets (C7, C9) ├── apps.yaml └── projects.yaml

Environments are directories, not branches. A prod branch sounds natural and fails in practice: environment branches diverge, cherry-picks carry unrelated changes, and "merge staging into prod" moves every change at once. With directories, promoting one app is a one-line diff in one file, and a PR shows exactly what changes in that environment. Kustomize overlays (Day 42) and per-environment values files (Day 43) exist for this.

What does not go in git

  • Secrets in plain text. Options: encrypt them in git (Sealed Secrets, SOPS + age/KMS) so the controller in the cluster decrypts; or keep only a reference in git (External Secrets Operator, Vault) and let a controller create the Secret from a vault. Either way the Secret object of Day 28 ends up in the cluster without ever being committed.
  • Generated or owned-elsewhere fields. status, HPA-managed replicas, webhook-injected containers, cloud-assigned load balancer addresses.
  • Images. Only their names and tags. The registry is the artifact store; git holds pointers.

The handoff: how the tag reaches git

The one place CI and CD touch is a commit that changes an image tag in the config repo. Three ways to make it:

# 1. CI commits directly (the common pattern; needs a bot identity with write access to the config repo)
$ git clone https://x-access-token:$CONFIG_REPO_TOKEN@github.com/acme/platform-config && cd platform-config
$ cd apps/api/overlays/dev && kustomize edit set image ghcr.io/acme/api=ghcr.io/acme/api:$TAG   # or: yq -i '.image.tag = strenv(TAG)' values-dev.yaml
$ git -c user.name=ci-bot -c user.email=ci@acme.dev commit -am "api: dev → $TAG" && git push
# on a rejected push (someone else committed first): git pull --rebase && git push   — retry a few times

# 2. CI opens a pull request instead (for environments that need review): gh pr create --title "api: prod → $TAG" --body "$CHANGELOG"

# 3. An image-update controller (Argo CD Image Updater, Flux image automation) watches the registry for new tags matching a pattern
#    and writes the commit itself. No CI involvement; the tag pattern (semver, sha-*) is the policy.

That handoff is shell: git, kustomize/yq, sed, a retry loop, an exit code. The classic bugs are the classic shell bugs from L10 — a yq that rewrote quoting so the diff is noisy, a set -e missing so a failed push is ignored, two pipelines racing on the same branch (fix: pull --rebase + retry, or one queue).

What GitOps does not do

  • Build anything. CI still builds, tests, scans and pushes images (C2–C5).
  • Order arbitrary steps. "Run the DB migration before the new Pods start" needs hooks and waves (C8), not a plain apply.
  • Decide if a release is good. Probes (Day 23) and health checks say whether it is up; canary analysis (C9, Argo Rollouts) says whether it is better.
  • Manage secrets by itself. See above.
  • Remove the need to understand Kubernetes. When an Application is Degraded, the fix is still kubectl describe and everything from Module 12.

Hands-on lab (25 min) — GitOps with a shell loop, before any tool

Build the reconciler yourself, so Argo CD is never magic. Use the Kustomize layout from Day 42 (or app/ from that lab) in a git repo — local is fine.

  1. Config repo: git init config && cd config; put base/ and overlays/dev/ there (a Deployment with 2 replicas and a Service); commit.
  2. The agent — a loop that pulls and applies:
    $ cat > agent.sh <<'EOF'
#!/bin/bash
set -u
cd "$(dirname "$0")"
while true; do
  git pull -q --ff-only 2>/dev/null || true                          # desired state: latest commit
  if ! kubectl diff -k overlays/dev >/dev/null 2>&1; then          # exit 1 = OutOfSync
    echo "$(date +%T) OutOfSync → syncing"; kubectl apply -k overlays/dev
  else
    echo "$(date +%T) Synced"
  fi
  sleep 15
done
EOF
$ bash agent.sh
  3. Cluster-side drift: in another terminal, kubectl scale deploy/web --replicas=5. Within 15 s the agent reports OutOfSync and applies — replicas go back to 2. That is self-heal. Now kubectl delete svc web — recreated. Now edit the Deployment's image by hand — reverted.
  4. Git-side change: edit overlays/dev/kustomization.yaml to set a new newTag, commit. Next tick: OutOfSync → sync → a rolling update (Day 10). Then git revert HEAD — rollback with no kubectl.
  5. What the loop cannot do: delete service.yaml from the base and commit. The Service stays in the cluster — no prune. Add --prune -l app=web to the apply and try again (kubectl apply --prune is the primitive Argo CD builds on).
  6. Write down what is missing before reading C7: health (is the rollout done? are Pods Ready?), a diff you can read, ordering, many apps and clusters, permissions, a UI, an audit of who synced what. Every one of those is an Argo CD feature.
Your team keeps dev, staging and prod as git branches of the config repo. A hotfix to prod's replica count needs to happen now. What goes wrong, and what is the directory-based equivalent?

You commit on prod; later "merge staging → prod" conflicts with it or reverts it, and the reverse merge drags every staging change into prod. With directories, the hotfix is a one-line change to overlays/prod/kustomization.yaml on main, reviewed, and it never collides with what dev/staging are doing.

An HPA scales a Deployment to 6 replicas; the config repo says 3. Your GitOps agent has self-heal on. What happens, and how do you fix it?

The agent sees live ≠ desired and sets replicas back to 3; the HPA raises it; they fight forever. Either remove replicas from the manifest (let the HPA own it) or configure the agent to ignore /spec/replicas for that object.

Key takeaways

  • GitOps = declarative + versioned + pulled + continuously reconciled. It is the Kubernetes control loop with git as the desired state.
  • Pull inverts the trust: the cluster reaches out; CI only writes commits. Drift becomes visible and (optionally) self-corrected.
  • App repos produce images; a config repo produces cluster state; environments are directories with overlays/values; promotion is a one-line PR.
  • The CI → CD handoff is a commit that changes an image tag — by CI, by a PR, or by an image-update controller.
  • GitOps does not build, order steps, judge releases or manage secrets on its own; it needs CI, hooks, probes/analysis and a secrets operator alongside.
