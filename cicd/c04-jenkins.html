Jenkins is the CI server most companies already run: a Java application you host yourself, extended by plugins, that executes pipelines written in a Jenkinsfile. It predates containers, so it thinks in machines — a controller that schedules and agents that do the work — which is exactly why understanding it makes the Kubernetes version (C5) obvious. This page covers the architecture, the declarative pipeline syntax, credentials, triggers, and reuse, with a look at what a sh step really does on the agent.

Architecture: one controller, many agents

Controller
The Jenkins process itself (a Java web app on port 8080): UI, REST API, job definitions, build queue, scheduling, plugin host, credential store. It should not run builds — set its executor count to 0 in production so a malicious build cannot read the controller's disk.
Agent
A machine (VM, container, Pod) running the small agent JAR that executes builds on the controller's behalf. Each agent advertises labels (linux, docker, arm64) and a number of executors — concurrent build slots. A pipeline says agent { label 'docker' } and the controller picks any agent with that label and a free executor.
Workspace
A directory on the agent per job ($WORKSPACE, typically ~/workspace/<job>) where the repo is checked out and the build runs. It persists between builds on static agents (fast incremental builds, but state leaks) — use cleanWs() or ephemeral agents.
JENKINS_HOME
The controller's state directory: config.xml, jobs/<name>/config.xml and builds/N/ (log, results, artifacts), plugins/, secrets/, users/, nodes/. Back this directory up and you have backed up Jenkins.

How agents connect

  • SSH — the controller SSHes to the agent and starts agent.jar. Controller needs network access to agents.
  • Inbound (JNLP) — the agent starts agent.jar -url … -secret … and connects to the controller on TCP 50000 (or over WebSocket on 8080). Works from behind NAT/firewalls; this is what Kubernetes Pod agents use (C5).
  • Cloud plugins — Docker, Kubernetes, EC2: the controller creates agents on demand and discards them.

Job types

  • Freestyle — configured by clicking in the UI. Legacy; avoid.
  • Pipeline — a Jenkinsfile, inline or "from SCM" (the repo). This is the standard.
  • Multibranch Pipeline — scans a repo, creates a job per branch/PR that has a Jenkinsfile, deletes them when branches go. Pair with a webhook.
  • Organization folder — multibranch for every repo in a GitHub org.

On a VM, jenkins is a systemd unit like the kubelet from L7: systemctl status jenkins, journalctl -u jenkins -f, config via systemctl edit jenkins (Environment="JENKINS_HOME=/var/lib/jenkins", JAVA_OPTS=-Xmx2g). Everything it knows is files under JENKINS_HOME; the "database" is XML on disk, which is why backups are tar and why the controller needs a fast disk — every build log write goes there. In Docker, the same directory is a volume at /var/jenkins_home (Day 24).

The declarative Jenkinsfile

pipeline {
  agent none                                        // no global executor; each stage that needs one says so
  options {
    timeout(time: 30, unit: 'MINUTES')
    disableConcurrentBuilds()
    buildDiscarder(logRotator(numToKeepStr: '30'))
    timestamps()
  }
  environment {
    REGISTRY = 'ghcr.io/acme'
    TAG      = "${env.GIT_COMMIT.take(7)}"          // Groovy string interpolation, evaluated on the controller
    GHCR     = credentials('ghcr-bot')              // binds GHCR_USR and GHCR_PSW, masked in logs
  }
  parameters {
    choice(name: 'TARGET', choices: ['dev', 'staging'], description: 'Environment to deploy after build')
    booleanParam(name: 'RUN_E2E', defaultValue: false)
  }
  triggers { cron('H 3 * * 1-5') }                  // nightly on weekdays; webhooks need no trigger block
  stages {
    stage('Test') {
      agent { label 'linux && docker' }             // checkout scm happens automatically on each stage agent
      steps { sh 'make test' }
      post { always { junit 'reports/*.xml' } }
    }
    stage('Checks') {
      parallel {
        stage('Lint')  { agent { label 'linux' } steps { sh 'make lint' } }
        stage('Scan')  { agent { label 'linux' } steps { sh 'trivy fs --exit-code 1 --severity CRITICAL .' } }
      }
    }
    stage('Build & push') {
      agent { label 'linux && docker' }
      when { branch 'main' }                        // skipped on feature branches
      steps {
        sh 'echo "$GHCR_PSW" | docker login ghcr.io -u "$GHCR_USR" --password-stdin'
        sh "docker build -t $REGISTRY/api:$TAG . && docker push $REGISTRY/api:$TAG"
      }
    }
    stage('Approve') {
      when { branch 'main' }                        // no agent here → no executor is held while a human decides
      steps { input message: "Deploy ${TAG} to ${params.TARGET}?", ok: 'Deploy' }
    }
    stage('Deploy') {
      agent { label 'linux' }
      when { branch 'main' }
      steps {
        withCredentials([file(credentialsId: "kubeconfig-${params.TARGET}", variable: 'KUBECONFIG')]) {
          sh "kubectl set image deploy/api api=$REGISTRY/api:$TAG && kubectl rollout status deploy/api --timeout=180s"
        }
      }
    }
  }
  post {
    always  { echo "result: ${currentBuild.currentResult}" }      // no agent here: archive/cleanWs belong in a stage post
    failure { slackSend channel: '#ci', message: "FAILED ${env.JOB_NAME} #${env.BUILD_NUMBER} ${env.BUILD_URL}" }
  }
}
agent
Where it runs. A top-level agent holds one executor for the whole run and gives every stage the same workspace; agent none at the top with per-stage agents lets stages use different machines and lets agent-less stages (an input) hold nothing — at the cost that each stage gets its own workspace (Jenkins re-runs checkout scm; move build outputs with stash/unstash). agent { docker { image 'golang:1.23' } } runs the stage inside a container on the agent (needs Docker there).
stages / steps
Stages are the visual units (the boxes in the UI); steps are the work. sh, bat, checkout scm, junit, archiveArtifacts, stash/unstash (move files between agents), input, timeout, retry, withCredentials, withEnv, script { } (escape hatch to Groovy).
when
Conditional stage: branch, tag, changeRequest() (a PR), environment, expression { }, anyOf/allOf/not. The stage is shown as skipped, not failed.
parallel
Sibling stages run concurrently — on the same agent (sharing the workspace) or on their own via per-stage agents. failFast true aborts siblings on first failure.
input
Pauses for a human. Inside an executor-holding stage it occupies the executor while waiting — with a top-level agent that means the whole run's executor. Use top-level agent none and give the input stage no agent. This is Continuous Delivery's approval gate, Jenkins-style; GitHub Actions does the same with environments.
post
Runs after stages (or after a stage, if nested): always, success, failure, unstable (tests failed but build succeeded), changed, aborted, cleanup. Steps that touch the workspace (archiveArtifacts, cleanWs) belong in a stage's post when the top level has no agent.
Scripted pipeline
The older Groovy form: node('linux') { stage('x') { sh '…' } }. Full Groovy power, no structure, no post/when. Use declarative; drop into script { } when you need a loop.

Mapping to GitHub Actions: Jenkinsfile ≈ workflow file; stage ≈ job or step group; agent/label ≈ runs-on; executor ≈ a runner slot; credentials ≈ secrets; plugins ≈ marketplace actions; shared library ≈ reusable workflow; input ≈ environment approval; stash ≈ artifacts between jobs. One real difference: a Jenkins pipeline is a single Groovy program whose stages can share one workspace, whereas GitHub jobs are always separate machines.

What sh actually does

A sh step is not the controller running a shell. The controller sends the script to the agent; the agent writes it to a temp directory next to the workspace and launches it in a detached way so that it survives a brief agent disconnect; the controller then polls the output file and streams it into the build log.

Under workspace/api@tmp/durable-<id>/ you will find script.sh (your step), jenkins-log.txt (its stdout/stderr), jenkins-result.txt (its exit code, written when it finishes) and pid. The launcher is essentially nohup sh -c 'sh script.sh > jenkins-log.txt 2>&1; echo $? > jenkins-result.txt' & — a background process reparented to init that ignores SIGHUP (L1). That is why a build keeps running when the agent's connection flaps, why aborting a build sends SIGTERM to that process group, and why a step that spawns a daemon and exits still "hangs" the step until the daemon closes the log file descriptor. If a step prints nothing for a long time you will see process apparently never started or heartbeat warnings — the controller is polling those files.

Credentials

Credentials live in the controller's store (global, per folder, or per user), encrypted at rest with a master key in $JENKINS_HOME/secrets/. Pipelines reference them by ID; the values are injected into the step's environment and masked in the log.

// kinds: usernamePassword, string (secret text), file, sshUserPrivateKey, certificate, dockerCert…
withCredentials([
  usernamePassword(credentialsId: 'ghcr-bot', usernameVariable: 'REG_USER', passwordVariable: 'REG_PASS'),
  string(credentialsId: 'slack-token', variable: 'SLACK'),
  file(credentialsId: 'kubeconfig-prod', variable: 'KUBECONFIG')          // written to a temp file, path in $KUBECONFIG, deleted after
]) {
  sh 'echo "$REG_PASS" | docker login ghcr.io -u "$REG_USER" --password-stdin'   // single quotes: the SHELL expands, Groovy never sees the secret
}

Use single-quoted sh '…$SECRET…' so the shell reads the variable. With double quotes, Groovy interpolates the secret into the command string on the controller before it is sent — it then appears in the build's stored script, in ps output on the agent, and masking may miss it. Same class of bug as ${{ }} injection in C2, opposite direction.

Jenkins credentials are to pipelines what Kubernetes Secrets are to Pods (Day 28): referenced by name, injected as env vars or files, encrypted at rest — and readable by anything that runs in the same context. A pipeline that can run sh can print any credential it is given; restrict who can edit Jenkinsfiles and which folders can see which credentials.

Triggers and multibranch

# GitHub → Jenkins webhook (GitHub plugin): repo settings → Webhooks → payload URL
https://jenkins.example.com/github-webhook/           # content type application/json; events: push, pull request
# Generic: POST https://jenkins.example.com/job/api/build?token=TOKEN    (job "Trigger builds remotely")
# Multibranch: "Scan Multibranch Pipeline Now" indexes branches; the webhook triggers a re-scan + build of the changed branch
# Polling fallback (avoid): triggers { pollSCM('H/5 * * * *') }   — H spreads load across the hour

A multibranch job gives every branch and PR its own build history and exposes env.BRANCH_NAME, env.CHANGE_ID (PR number), env.CHANGE_TARGET — which is what when { branch 'main' } and when { changeRequest() } read.

Shared libraries and plugins

def call(Map cfg) {                          // usable as a step: buildImage(name: 'api')
  def tag = env.GIT_COMMIT.take(7)
  sh "docker build -t ${cfg.registry ?: 'ghcr.io/acme'}/${cfg.name}:${tag} ."
  sh "docker push ${cfg.registry ?: 'ghcr.io/acme'}/${cfg.name}:${tag}"
  return tag
}
@Library('acme-pipeline@v3') _            // configured under Manage Jenkins → System → Global Pipeline Libraries
pipeline {
  agent { label 'docker' }
  stages { stage('Build') { steps { script { env.TAG = buildImage(name: 'api') } } } }
}

Plugins are Jenkins' strength and its operational burden: hundreds of them, each with its own release cadence and security advisories, and upgrades that occasionally break each other. Pin plugin versions (a plugins.txt baked into your own controller image), upgrade on a schedule, and read Manage Jenkins → Security warnings.

Hands-on lab (30 min) — a controller in Docker, a pipeline, and a look under the hood

  1. Run the controller
    $ docker volume create jenkins_home
$ docker run -d --name jenkins -p 8080:8080 -p 50000:50000 -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts-jdk17
$ docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword     # unlock at http://localhost:8080, install suggested plugins
  2. Look at JENKINS_HOME: docker exec jenkins ls /var/jenkins_home — config.xml, plugins/, secrets/, users/. Nothing else is state.
  3. Create a Pipeline job named lab, "Pipeline script from SCM", pointing at your C1 lab repo, and add this Jenkinsfile to the repo:
    pipeline {
  agent any
  stages {
    stage('Test')  { steps { sh 'sh test.sh' } }
    stage('Slow')  { steps { sh 'for i in 1 2 3 4 5 6; do echo tick $i; sleep 5; done' } }
  }
  post { always { echo "result: ${currentBuild.currentResult}" } }
}
  4. Build it and, while the Slow stage runs, inspect the durable task on the (built-in) agent:
    $ docker exec jenkins sh -c 'ls /var/jenkins_home/workspace/lab@tmp/durable-*/ && cat /var/jenkins_home/workspace/lab@tmp/durable-*/jenkins-log.txt'
$ docker exec jenkins ps -ef | grep -v grep | grep script.sh          # the nohup-ed shell
  5. Break the test in the repo, push, build again. Open the console log; note the exit code line and result: FAILURE. Then find the same build on disk: docker exec jenkins cat /var/jenkins_home/jobs/lab/builds/2/log | tail.
  6. Add a credential (Manage Jenkins → Credentials → secret text, id demo) and a stage with withCredentials([string(credentialsId: 'demo', variable: 'S')]) { sh 'echo "len=${#S}"; echo "$S" }' }. Observe that the value is masked as **** in the log — and that the length is not.
  7. Set the built-in node's executors to 0 (Manage Jenkins → Nodes) and build again: it queues forever with "Waiting for next available executor". That is the production posture — builds need agents, which is C5.
A stage does sh "curl -H 'Authorization: Bearer ${TOKEN}' …" with TOKEN from credentials(). Why is this worse than single quotes?

Double quotes make Groovy interpolate on the controller: the secret becomes part of the command text sent to the agent and can show up in the pipeline's stored script and in the agent's process list. With single quotes the shell expands $TOKEN from its environment at run time; only the environment holds it, and masking works reliably.

The build queue shows "Waiting for next available executor on 'docker'" for an hour. Three things to check?

(1) Is any agent online with label docker (Manage Jenkins → Nodes)? (2) Are all its executors busy — perhaps by a pipeline sitting in an input step inside an executor-holding stage? (3) Did the agent disconnect (inbound agents die with their process; check its host with journalctl / kubectl logs)?

Key takeaways

  • Controller schedules and stores; agents execute. Labels route pipelines to agents; executors are the concurrency slots. Keep the controller's executors at 0.
  • JENKINS_HOME is Jenkins: config, jobs, builds, plugins, secrets — all files. Back it up; run the controller as a systemd service or a container with a volume.
  • Declarative Jenkinsfile: agent, environment, options, parameters, triggers, stages (when / parallel / input), post. Escape to script {} only when needed.
  • sh runs a detached script on the agent and polls its log; that mechanism explains most "hung step" behaviour.
  • Credentials by ID, single-quoted sh, masked logs; treat any pipeline with sh as able to read its own credentials.
  • Webhooks + multibranch for triggers, shared libraries for reuse, JCasC + plugins.txt to keep the controller reproducible.
