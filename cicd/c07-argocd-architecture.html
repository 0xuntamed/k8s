Argo CD is the GitOps loop from C6 packaged as a set of Kubernetes controllers, three CRDs and a web UI. Once you see that an Application is a custom resource (Day 39) reconciled by a controller (Day 40) that renders Kustomize or Helm (Days 42–43) and talks to the API server with a ServiceAccount (Day 37), there is nothing left to be mysterious about. This page installs it, tours the components, and goes through every field of the Application spec that matters.

What you'll learn

  • The components: api-server, repo-server, application-controller, redis, dex, applicationset- and notifications-controllers
  • Installing (manifests or Helm), first login, exposing the UI
  • The Application spec: source, destination, project, syncPolicy, and status
  • How Argo CD tracks which live objects belong to an app
  • Repository and cluster credentials as Secrets
  • AppProject boundaries, Argo CD RBAC and SSO

Components

argocd-server
The API (gRPC + REST) and the web UI. Authenticates users (local accounts, SSO via Dex or OIDC), enforces Argo CD's own RBAC, and serves the resource tree, diffs, logs and sync buttons. It is not the reconciler — it reads state the controller has computed (via Redis) and forwards actions.
argocd-repo-server
Clones repositories (cached on disk), checks out the requested revision and renders manifests: kustomize build, helm template, plain YAML directories, Jsonnet, or a config-management plugin sidecar. Output is cached in Redis keyed by revision. Has no cluster access at all.
argocd-application-controller
The reconciler (a StatefulSet, shardable). Watches Application objects; for each one asks the repo-server for manifests, keeps informers on the live objects in the destination cluster, computes sync status (diff) and health status, and performs sync operations (apply, prune, hooks). Writes results into Application.status.
argocd-redis
Cache: rendered manifests, app state, cluster inventory. Losing it costs a re-render, nothing more — all durable state is in the Application CRs and Secrets.
argocd-dex-server
An OIDC identity broker for SSO (GitHub, GitLab, LDAP, SAML…). Optional if you point Argo CD at an OIDC provider directly.
argocd-applicationset-controller
Turns ApplicationSet templates into many Applications (C9).
argocd-notifications-controller
Sends events (sync succeeded, health degraded) to Slack, email, webhooks, GitHub commit statuses.

Map it onto Day 7: argocd-server is the API server of the Argo world, application-controller is its controller-manager, repo-server is a stateless worker, Redis a cache rather than etcd — because the durable state is stored as CRs in the real API server. It is an operator (Day 40) whose "custom resource" is an entire deployed application.

Install and log in

$ kubectl create namespace argocd
$ kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
#   variants: core-install.yaml (no UI/API — CLI in core mode), ha/install.yaml (HA redis, multiple servers)
#   or Helm: helm repo add argo https://argoproj.github.io/argo-helm && helm install argocd argo/argo-cd -n argocd
$ kubectl -n argocd get deploy,sts,svc,cm,secret,crd | grep -E 'argocd|argoproj'
$ kubectl -n argocd rollout status deploy/argocd-server
$ kubectl -n argocd port-forward svc/argocd-server 8080:443 &
$ argocd admin initial-password -n argocd            # or: kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
$ argocd login localhost:8080 --username admin --password '…' --insecure     # self-signed cert on port-forward
$ argocd account update-password && kubectl -n argocd delete secret argocd-initial-admin-secret
$ argocd version; argocd cluster list; argocd app list

Behind an Ingress (Day 49): terminate TLS at the Ingress and run the server in plain HTTP with server.insecure: "true" in the argocd-cmd-params-cm ConfigMap, or pass TLS through so Argo CD's own certificate is used. The CLI speaks gRPC; if your Ingress does not support it, log in with --grpc-web.

The initial password is a random string stored in a Secret — the same "bootstrap credential you rotate immediately" pattern as a kubeadm join token. The self-signed certificate the server presents on port 8080 is generated at first start into the argocd-server-tls Secret; inspect it with the tools from L9 (openssl s_client -connect localhost:8080). And every component is a Deployment whose logs you read with kubectl logs, not journalctl — the Argo processes are containers, not systemd units.

The Application resource

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-prod
  namespace: argocd                  # Applications live in Argo CD's namespace (by default)
  finalizers:
  - resources-finalizer.argocd.argoproj.io   # deleting the Application deletes what it deployed
spec:
  project: shop
  source:
    repoURL: https://github.com/acme/platform-config
    targetRevision: main             # branch, tag, or commit SHA
    path: apps/api/overlays/prod     # a directory: Kustomize here
    # helm: { valueFiles: [values-prod.yaml], parameters: [{name: image.tag, value: 9f2e1c3}] }
    # directory: { recurse: true }   # plain YAML tree
  destination:
    server: https://kubernetes.default.svc   # or name: prod-eu (a registered cluster)
    namespace: shop
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
      allowEmpty: false
    syncOptions:
    - CreateNamespace=true
    - ServerSideApply=true
    retry:
      limit: 3
      backoff: { duration: 10s, factor: 2, maxDuration: 2m }
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers: [/spec/replicas]   # HPA owns this field (Day 20)
  revisionHistoryLimit: 10
  • source — where the desired state comes from: a repo, a revision, a path. What is at the path decides the renderer: a kustomization.yaml → Kustomize; a Chart.yaml → Helm; otherwise plain manifests. Per-tool options live under helm:, kustomize:, directory:. sources: (plural) combines several — a chart from one repo with values from another (C9).
  • targetRevision — main follows the branch; v1.4.0 or a SHA pins. Prod often tracks a tag or a release branch that a promotion PR advances.
  • destination — which cluster (server URL or registered name) and namespace. https://kubernetes.default.svc is the cluster Argo CD runs in.
  • project — the AppProject that fences what this app may do. default allows everything; do not use it in production.
  • syncPolicy.automated — sync on git change without a click. prune: delete objects removed from git. selfHeal: also re-sync on cluster-side drift. Omit the block entirely for manual sync (review the diff, then Sync).
  • syncOptions — behaviour switches (C8): create the namespace, server-side apply, prune last, replace instead of apply, skip validation.
  • ignoreDifferences — fields other controllers own; excluded from the diff so the app is not perpetually OutOfSync.
  • finalizer — with it, kubectl delete application cascades to the deployed objects; without it only the Application object goes and the workload stays (orphaned).
$ kubectl apply -f api-prod.yaml                      # an Application is just a CR — GitOps the Application too (C9: app of apps)
$ argocd app create api-prod --repo https://github.com/acme/platform-config --path apps/api/overlays/prod \
    --dest-server https://kubernetes.default.svc --dest-namespace shop --project shop --sync-policy automated --self-heal --auto-prune
$ argocd app get api-prod                             # sync status, health, each resource with its own status
$ argocd app diff api-prod                            # rendered vs live
$ argocd app sync api-prod [--prune] [--dry-run]      # a manual sync
$ argocd app manifests api-prod                       # what the repo-server rendered
$ kubectl -n argocd get app api-prod -o jsonpath='{.status.sync.status} {.status.health.status}{"\n"}'
$ kubectl -n argocd get app api-prod -o jsonpath='{range .status.conditions[*]}{.type}: {.message}{"\n"}{end}'   # ComparisonError etc.

kubectl explain application.spec --api-version argoproj.io/v1alpha1 works because the CRD carries an OpenAPI schema (Day 39). status is written by the controller and read by you — the same contract as every built-in object (Day 9), so JSONPath queries against Applications are the fastest way to monitor a fleet from a script.

How Argo CD knows what belongs to an app

When it applies a manifest, Argo CD stamps a tracking marker on the object — by default the label app.kubernetes.io/instance: <app name>; optionally the annotation argocd.argoproj.io/tracking-id: <app>:<group>/<kind>:<ns>/<name> (set application.resourceTrackingMethod: annotation in argocd-cm). The controller's informers index live objects by that marker; anything with the app's marker that is not in the rendered manifests is a prune candidate, and anything in the manifests with no live counterpart is Missing.

$ kubectl -n shop get deploy api -o jsonpath='{.metadata.labels.app\.kubernetes\.io/instance}{"\n"}'     # api-prod
$ kubectl -n shop get all -l app.kubernetes.io/instance=api-prod                                       # everything this app owns

If your Helm chart already sets app.kubernetes.io/instance to the release name (most do), two apps deploying the same chart collide. Switch to annotation tracking, or set helm.releaseName to the app name. A resource claimed by two Applications shows a SharedResourceWarning condition.

Credentials: repositories and clusters

Argo CD keeps credentials as Kubernetes Secrets in its namespace with a well-known label — so they, too, can be created declaratively (and sealed/external — C6).

apiVersion: v1
kind: Secret
metadata:
  name: platform-config-repo
  namespace: argocd
  labels: { argocd.argoproj.io/secret-type: repository }      # repo-creds: the same, matching a URL prefix
stringData:
  type: git
  url: https://github.com/acme/platform-config
  username: not-used
  password: ghp_…readonly-token…                                # or sshPrivateKey: | …  with url git@github.com:acme/platform-config.git
$ argocd repo add https://github.com/acme/platform-config --username x --password $TOKEN     # same Secret, made for you
$ argocd repo add git@github.com:acme/platform-config.git --ssh-private-key-path ~/.ssh/argocd   # deploy key, read-only
$ argocd cluster add prod-eu --name prod-eu            # a kubeconfig context → creates SA argocd-manager + ClusterRoleBinding IN THAT CLUSTER,
                                                       # stores its token in a Secret labelled argocd.argoproj.io/secret-type: cluster
$ kubectl -n argocd get secret -l argocd.argoproj.io/secret-type=cluster

argocd cluster add is Day 37 + Day 36 + Day 32 in one command: it creates a ServiceAccount in the target cluster, binds it to cluster-admin (tighten this!), mints a token, and stores server URL + CA + token — the three parts of a kubeconfig — in a Secret. For the in-cluster destination it simply uses its own Pod's ServiceAccount.

Projects, RBAC and SSO

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata: { name: shop, namespace: argocd }
spec:
  description: Shop team workloads
  sourceRepos: ["https://github.com/acme/platform-config", "https://charts.bitnami.com/bitnami"]
  destinations:
  - { server: https://kubernetes.default.svc, namespace: "shop*" }        # shop, shop-canary…
  - { name: prod-eu, namespace: shop }
  clusterResourceWhitelist: []                    # no cluster-scoped objects (no ClusterRoles, no CRDs, no Namespaces…)
  namespaceResourceBlacklist:
  - { group: "", kind: ResourceQuota }
  - { group: "", kind: LimitRange }
  roles:
  - name: developer
    policies: ["p, proj:shop:developer, applications, sync, shop/*, allow"]
    groups: ["acme:shop-devs"]                    # SSO group
  syncWindows:
  - { kind: deny, schedule: "0 22 * * *", duration: 8h, applications: ["*"] }   # no syncs overnight
data:
  policy.default: role:readonly
  policy.csv: |
    p, role:platform, applications, *, */*, allow
    p, role:platform, clusters, *, *, allow
    p, role:platform, repositories, *, *, allow
    g, acme:platform-team, role:platform
  scopes: "[groups, email]"
AppProject
A boundary around a set of Applications: which repos may be sources, which clusters/namespaces may be destinations, which resource kinds may be created. It is enforced at sync time: an app that violates it gets an InvalidSpecError or a sync error naming the rule. This is how one Argo CD serves many teams without one team's manifests landing in another's namespace.
RBAC
Casbin-style policies over Argo CD's own objects (applications, projects, repositories, clusters, accounts) and actions (get, create, sync, delete, override, action/…). Subjects are SSO groups or local accounts. Separate from Kubernetes RBAC — Argo CD applies manifests with its ServiceAccount; Argo RBAC decides which humans may push its buttons.
SSO
Dex connectors (GitHub org/teams, GitLab, SAML, LDAP) or a direct OIDC issuer in argocd-cm. Groups arrive as claims and match the g, lines. Local accounts are for automation (argocd account generate-token) and break-glass.

Two RBAC layers, two questions. Kubernetes RBAC (Day 36): may Argo CD's ServiceAccount create a Deployment in shop? Argo CD RBAC + AppProject: may this user sync this app, and may this app touch that namespace? Namespaces (Day 14) are the unit both layers agree on — one project per team, one or more namespaces per project.

Hands-on lab (30 min) — install, deploy, watch the loop

  1. Install Argo CD in KIND with the manifests above; port-forward; log in with the CLI; change the admin password.
  2. Tour the components: kubectl -n argocd get pods; kubectl -n argocd logs deploy/argocd-repo-server --tail=20; kubectl get crd | grep argoproj; kubectl explain application.spec.syncPolicy --api-version argoproj.io/v1alpha1.
  3. First app from the public example repo:
    $ argocd app create guestbook --repo https://github.com/argoproj/argocd-example-apps.git --path guestbook \
    --dest-server https://kubernetes.default.svc --dest-namespace guestbook --sync-option CreateNamespace=true
$ argocd app get guestbook            # OutOfSync / Missing: nothing applied yet (manual sync policy)
$ argocd app diff guestbook           # the whole manifest, because live is empty
$ argocd app sync guestbook && argocd app get guestbook      # Synced / Progressing → Healthy
  4. See the tracking label: kubectl -n guestbook get all -l app.kubernetes.io/instance=guestbook. Open the UI: the resource tree is exactly that query.
  5. Your own repo: push the C6 lab's config repo to GitHub (public is fine), create an Application for overlays/dev with --sync-policy automated --self-heal --auto-prune, and repeat the C6 drift experiments — scale by hand, delete the Service, commit a new tag, revert. Watch argocd app get -w alongside.
  6. Project fence: create the shop AppProject above (with only your repo and only namespace shop*), move the app into it (argocd app set … --project shop), then edit the Application's destination namespace to kube-system and read the error.
  7. Break the repo credential: point the Application at a private repo without adding credentials. argocd app get shows a ComparisonError; fix with argocd repo add.
The UI shows an app as Unknown sync status with a ComparisonError. Which component failed, and how do you see why?

The repo-server could not render the source (bad credentials, wrong path, invalid kustomization, a Helm values file that does not exist). argocd app get prints the condition message; kubectl -n argocd logs deploy/argocd-repo-server has the underlying git/kustomize/helm error.

You deleted an Application from the UI and its Deployment is still running. Why?

The Application had no resources-finalizer.argocd.argoproj.io finalizer (the UI asks "foreground/background/non-cascading"; non-cascading skips it). Without the finalizer only the Application CR is removed and the deployed objects are orphaned. Re-create the app and delete it with cascade, or clean up with the tracking label.

Key takeaways

  • Argo CD = argocd-server (API/UI/RBAC) + repo-server (render) + application-controller (diff, health, sync) + Redis (cache) + optional Dex, ApplicationSet and notifications controllers — all Deployments/StatefulSets in the argocd namespace.
  • An Application is a CR: source (repo, revision, path) → destination (cluster, namespace), fenced by a project, with a syncPolicy. Its status carries sync and health.
  • Ownership is a tracking label/annotation on every applied object; the resource tree is a label query.
  • Repo and cluster credentials are labelled Secrets; cluster add creates a ServiceAccount in the target cluster.
  • AppProjects fence repos, destinations and kinds; Argo CD RBAC decides what humans may do; Kubernetes RBAC decides what Argo CD's ServiceAccount may do.
