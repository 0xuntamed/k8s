A Kubernetes cluster is a small number of control-plane processes that hold and act on desired state, plus any number of worker nodes that run the actual containers. Every process talks only to the API server, and the API server talks only to etcd. This page names each component, then follows one kubectl apply of a Deployment through all of them — the single most useful sequence to have in your head for the exam and for real troubleshooting.

What you'll learn

  • The control-plane components: kube-apiserver, etcd, kube-scheduler, kube-controller-manager, cloud-controller-manager
  • The node components: kubelet, kube-proxy, container runtime (containerd) and the CNI plugin
  • The hub-and-spoke rule: everything goes through the API server; only the API server touches etcd
  • Step by step: what happens between kubectl apply -f deployment.yaml and a running container
  • How these components are actually installed on a Linux machine (static Pods and systemd)

The map

Control plane

kube-apiserver
The front door and the only component that reads or writes etcd. Every request — from kubectl, from the scheduler, from a kubelet — is a REST call to the API server, where it is authenticated, authorized, run through admission controllers, validated, and persisted. It is stateless and can be scaled horizontally behind a load balancer.
etcd
A distributed, strongly consistent key-value store (Raft consensus). It holds the entire cluster state: every object you have ever created lives here as a key like /registry/deployments/default/web. Lose etcd without a backup and you lose the cluster's memory; the nodes keep running containers, but nothing can be changed. Runs as 1, 3 or 5 members (odd numbers, for quorum).
kube-scheduler
Watches for Pods that have no spec.nodeName, evaluates every node (filtering: enough CPU? tolerates the taints? matches affinity? — then scoring: spread, least-loaded, image locality) and writes its decision back to the API as a Binding. It never talks to nodes.
kube-controller-manager
One binary running dozens of control loops: the Deployment controller, ReplicaSet controller, Node controller (marks nodes NotReady), Job controller, EndpointSlice controller, ServiceAccount controller, garbage collector… Each watches its kind of object and acts through the API.
cloud-controller-manager
The cloud-specific loops split out so Kubernetes core stays vendor-neutral: creating cloud load balancers for type: LoadBalancer Services, attaching disks, labelling nodes with zone/region, deleting Node objects when the VM is gone.

Worker nodes

kubelet
The node agent. It registers the node, watches the API server for Pods assigned to it, and makes them real: pulls images, asks the runtime to create containers, mounts volumes, runs probes, and reports Pod and node status back. It is the only Kubernetes component that is not a Pod — it is a systemd service on the host, because something has to start the Pods.
Container runtime
containerd (or CRI-O). The kubelet talks to it over the Container Runtime Interface (a gRPC socket, /run/containerd/containerd.sock). It pulls images and drives runc, exactly as on Day 1.
kube-proxy
Watches Services and EndpointSlices and programs the node's iptables (or IPVS) rules so that traffic to a Service's virtual IP is DNAT'ed to a healthy Pod. Runs as a DaemonSet. (Some CNIs, e.g. Cilium, replace it with eBPF.)
CNI plugin
Calico, Cilium, Flannel, … Called by the runtime when a Pod is created to give it an IP and wire it into the cluster network. Not part of Kubernetes proper — a cluster without one has nodes stuck in NotReady. Day 25.
Mental model: hub and spoke

No component talks to another component directly — everyone watches and writes the API server. The scheduler does not tell the kubelet "start this"; it writes nodeName on the Pod, and the kubelet notices because it is watching for Pods with its name. This decoupling is why any single component can crash and restart without the others caring, and why the whole thing is extensible: your own controller uses the same watch-and-write pattern (Day 40).

From kubectl apply to a running container

Play this one slowly. It is the sequence behind every exam question of the form "the Pod is Pending / ContainerCreating / not on the node I expected — why?"

  1. kubectl → API server. kubectl reads your kubeconfig, converts the YAML to JSON and sends POST /apis/apps/v1/namespaces/default/deployments over TLS.
  2. Authentication, authorization, admission. The API server checks who you are (client cert / token), whether RBAC allows create deployments in that namespace, then runs admission plugins that may mutate (add defaults) or reject the object. Days 35–38.
  3. Persist to etcd. The validated Deployment is written. The API server responds 201 Created. Nothing is running yet.
  4. Deployment controller (in kube-controller-manager) receives a watch event: new Deployment with no ReplicaSet → it creates a ReplicaSet with the Pod template and replicas: 3.
  5. ReplicaSet controller sees a ReplicaSet with 0/3 Pods → creates three Pod objects. Each has spec.nodeName empty and status Pending.
  6. Scheduler sees unscheduled Pods. For each: filter nodes, score the survivors, pick the winner, write a Binding. The Pod now has nodeName: worker-2. Still Pending.
  7. kubelet on worker-2 sees a Pod bound to it. It calls the CRI: pull image, create the Pod sandbox (the shared network namespace — the CNI plugin assigns the IP here), create and start containers. Status becomes ContainerCreating then Running.
  8. Status flows back. The kubelet PATCHes the Pod status (IP, phase, container states) to the API server → etcd. kubectl get pods reads it from there — kubectl never contacts a node.
  9. kube-proxy (if a Service selects these Pods) sees new EndpointSlices and rewrites iptables on every node so the Service IP now includes the new Pod.
Under the hood · Linux (how the control plane is actually installed)

On a kubeadm cluster the four control-plane components are ordinary containers — but a chicken-and-egg problem exists: who starts the API server before there is an API server? The answer is static Pods: the kubelet watches the directory /etc/kubernetes/manifests/ and runs any Pod YAML it finds there, no API server required. So:

$ systemctl status kubelet                 # the one real service
$ ls /etc/kubernetes/manifests/            # etcd.yaml  kube-apiserver.yaml  kube-controller-manager.yaml  kube-scheduler.yaml
$ crictl ps | grep -E 'apiserver|etcd|scheduler|controller'   # they are just containers
$ sudo ls /var/lib/etcd/member/            # etcd's data on disk
$ ls /etc/kubernetes/pki/                  # the certificates they use to talk to each other

Edit a manifest in that directory and the kubelet restarts that component — this is how you change API-server flags, and it is how Day 57 breaks and fixes control planes. Managed services (EKS, GKE, AKS) hide the control plane entirely; you only ever see worker nodes.

CKA exam tip

Map symptoms to components: Pods stuck Pending with no node → scheduler (or no node fits); Pending with a node but nothing happening → kubelet/runtime on that node; kubectl times out → API server (or kubeconfig/cert); Deployments not creating ReplicaSets → controller-manager; Service traffic not arriving → kube-proxy/CNI; new Pods never get an IP → CNI. kubectl get componentstatuses is deprecated — use kubectl get pods -n kube-system and kubectl get --raw /healthz.

Hands-on lab (10 min)

Needs a cluster — create one on Day 8 and come back, or use a killercoda playground.

$ kubectl get nodes -o wide
$ kubectl get pods -n kube-system -o wide         # find apiserver, etcd, scheduler, controller-manager, kube-proxy, coredns
$ kubectl create deployment web --image=nginx --replicas=2
$ kubectl get deploy,rs,pods -o wide             # Deployment → ReplicaSet → Pods, with nodeName
$ kubectl get events --sort-by=.metadata.creationTimestamp | tail -20   # Scheduled, Pulling, Created, Started
$ kubectl describe pod -l app=web | grep -A12 Events
$ docker exec kind-control-plane ls /etc/kubernetes/manifests   # KIND: static pod manifests inside the node container

Key takeaways

  • Control plane = API server (front door), etcd (memory), scheduler (placement), controller-manager (reconcile loops), cloud-controller-manager (cloud glue).
  • Node = kubelet (runs Pods, reports status), container runtime via CRI, kube-proxy (Service rules), CNI (Pod networking).
  • Hub and spoke: all components watch/write the API server; only the API server touches etcd.
  • apply → authn/authz/admission → etcd → Deployment ctrl → RS ctrl → Pods → scheduler binds → kubelet runs → status returns.
  • Control-plane components are static Pods from /etc/kubernetes/manifests; the kubelet is the one systemd service.
