Role-Based Access Control is four objects and one idea. A Role is a list of permissions (verbs on resources) in a namespace; a ClusterRole is the same list without a namespace. A RoleBinding grants a Role or ClusterRole to subjects in a namespace; a ClusterRoleBinding grants a ClusterRole everywhere. The idea: permissions are purely additive — there is no deny, so the question is always "does any binding give this subject this verb on this resource here?"

What you'll learn

  • Role and ClusterRole rules: apiGroups, resources, verbs, resourceNames, nonResourceURLs
  • RoleBinding and ClusterRoleBinding: subjects (User, Group, ServiceAccount) and roleRef
  • The four combinations and what scope each grants — including the ClusterRole-via-RoleBinding trick
  • Default ClusterRoles (cluster-admin, admin, edit, view) and aggregation
  • Verifying with auth can-i, impersonation, and debugging 403s

Roles: what may be done

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]                 # core group
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "patch"]
- apiGroups: [""]
  resources: ["configmaps"]
  resourceNames: ["app-config"]   # only this one object
  verbs: ["get", "update"]
  • apiGroups — "" for core (pods, services, configmaps, secrets, nodes…); apps, batch, networking.k8s.io… "*" = all.
  • resources — lowercase plural, as in kubectl api-resources. Subresources as pods/log, pods/exec, deployments/scale.
  • verbs — get list watch create update patch delete deletecollection, or "*". Remember: get pods ≠ list pods; edit/apply need patch or update.
  • resourceNames — restrict to named objects. Cannot be used with list/create (the name is not known yet).
  • Each rule is independent; the Role is the union.
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-viewer            # no namespace
rules:
- apiGroups: [""]
  resources: ["nodes", "persistentvolumes", "namespaces"]   # cluster-scoped resources need a ClusterRole
  verbs: ["get", "list", "watch"]
- nonResourceURLs: ["/healthz", "/metrics"]                 # non-resource endpoints, ClusterRole only
  verbs: ["get"]
$ kubectl create role pod-reader --verb=get,list,watch --resource=pods,pods/log -n dev
$ kubectl create clusterrole node-viewer --verb=get,list,watch --resource=nodes,persistentvolumes
$ kubectl create role cm-editor --verb=get,update --resource=configmaps --resource-name=app-config -n dev

Bindings: who may do it

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: jane                          # from the client cert CN / OIDC claim
  apiGroup: rbac.authorization.k8s.io
- kind: Group
  name: developers                    # cert O= / OIDC groups claim / system:* groups
  apiGroup: rbac.authorization.k8s.io
- kind: ServiceAccount
  name: ci-runner
  namespace: build                    # SAs are namespaced; may bind across namespaces
roleRef:                              # exactly one; immutable after creation
  kind: Role                          # or ClusterRole
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
  • subjects — any mix of Users, Groups and ServiceAccounts. Users and Groups are just strings the authenticator produced; Kubernetes has no user objects.
  • roleRef — the Role or ClusterRole being granted. Immutable: to change it, delete and re-create the binding.
  • A RoleBinding grants within its namespace only — even when it references a ClusterRole.
  • A ClusterRoleBinding (no namespace) grants a ClusterRole across every namespace and cluster-scoped resources.
$ kubectl create rolebinding read-pods --role=pod-reader --user=jane --group=developers --serviceaccount=build:ci-runner -n dev
$ kubectl create rolebinding dev-edit --clusterrole=edit --group=developers -n dev        # ClusterRole, namespace-scoped grant
$ kubectl create clusterrolebinding ops-view --clusterrole=view --group=ops                # everywhere

Default ClusterRoles

cluster-admin
* on *, plus all non-resource URLs. Bound to group system:masters by a ClusterRoleBinding — which is why the kubeadm admin cert's O=system:masters (or kubeadm:cluster-admins) is all-powerful. Note that the system:masters group is special-cased in the API server and bypasses RBAC entirely.
admin
Full control within a namespace, including creating Roles and RoleBindings — for namespace owners. Cannot touch quotas or the namespace object itself.
edit
Read/write most namespaced objects (Deployments, Services, ConfigMaps, Secrets, PVCs…) but not RBAC — for developers.
view
Read-only on most namespaced objects, excluding Secrets — for auditors, dashboards.
system:*
Roles for components: system:node, system:kube-scheduler, system:controller:*, system:discovery, system:basic-user (lets every authenticated user run auth can-i on themselves). Bound automatically; do not edit them (the API server reconciles them on start).
$ kubectl get clusterroles | grep -v system:
$ kubectl describe clusterrole edit | head -40
$ kubectl get clusterrolebinding cluster-admin -o yaml       # subject: Group system:masters

Aggregation: admin, edit and view are built by aggregating any ClusterRole labelled e.g. rbac.authorization.k8s.io/aggregate-to-edit: "true". A CRD's operator ships a small ClusterRole with that label and its resources automatically become editable by everyone with edit — no changes to the built-ins.

Verifying and debugging

$ kubectl auth can-i list pods -n dev --as=jane
$ kubectl auth can-i '*' '*' --as=jane                          # is she cluster-admin?
$ kubectl auth can-i --list --as=jane -n dev                    # everything jane can do in dev
$ kubectl get rolebindings,clusterrolebindings -A -o wide | grep -E 'jane|developers'   # where is she bound?
$ kubectl get rolebinding read-pods -n dev -o yaml
$ kubectl --as=jane --as-group=developers get pods -n dev       # impersonate for a real request (needs "impersonate" verb)
# Reading a 403:
# Error from server (Forbidden): pods is forbidden: User "jane" cannot list resource "pods" in API group "" in the namespace "dev"
#   → user jane · verb list · resource pods · group "" · namespace dev: find or create a binding that covers exactly those
Common mistakes
  • Binding a Role from namespace A in a RoleBinding in namespace B — not allowed; the Role must be in the binding's namespace (or use a ClusterRole).
  • Granting get and expecting kubectl get pods to work: that is list.
  • Granting pods and expecting logs/exec to work: those are pods/log and pods/exec (exec needs create).
  • Expecting a Role to grant access to nodes or persistentvolumes: cluster-scoped resources need a ClusterRole + ClusterRoleBinding.
  • Granting edit and being surprised the user can read Secrets: edit includes Secrets; view does not.
  • Privilege escalation: you can only grant permissions you hold yourself (unless you have the escalate/bind verbs).
Under the hood · Linux

RBAC is the cluster-level analogue of Unix permissions with groups: subjects are like users/groups, verbs like rwx, and namespaces like directories — except there is no owner, no deny bit, and evaluation is "union of all matching grants". Just as id shows your uid and groups on Linux, kubectl auth whoami shows the identity RBAC is evaluating. And the reason system:masters is dangerous is the same reason uid 0 is: it is a hard-coded bypass, not a policy you can edit — never issue certificates with that group to humans.

CKA exam tip
  • Imperative forms save minutes: create role/clusterrole --verb --resource, create rolebinding/clusterrolebinding --role|--clusterrole --user|--group|--serviceaccount=ns:name.
  • Always finish with kubectl auth can-i <verb> <resource> --as=<user> -n <ns> — it checks the exact thing the grader checks.
  • For a ServiceAccount subject use --serviceaccount=namespace:name; for can-i use --as=system:serviceaccount:namespace:name.
  • Copy the exact resource/verb words from the 403 message.

Hands-on lab (20 min)

$ kubectl create ns dev
$ kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
$ kubectl create rolebinding jane-pods --role=pod-reader --user=jane -n dev
$ kubectl auth can-i list pods -n dev --as=jane          # yes
$ kubectl auth can-i list pods -n default --as=jane      # no — RoleBinding is namespaced
$ kubectl auth can-i get pods --subresource=log -n dev --as=jane    # no — pods/log not granted
$ kubectl create rolebinding jane-edit --clusterrole=edit --user=jane -n dev
$ kubectl auth can-i delete deployments -n dev --as=jane  # yes, via ClusterRole in a RoleBinding
$ kubectl auth can-i get nodes --as=jane                  # no
$ kubectl create clusterrolebinding jane-nodes --clusterrole=node-viewer --user=jane 2>/dev/null || kubectl create clusterrole node-viewer --verb=get,list --resource=nodes && kubectl create clusterrolebinding jane-nodes --clusterrole=node-viewer --user=jane
$ kubectl auth can-i get nodes --as=jane                  # yes
$ kubectl auth can-i --list --as=jane -n dev | head
$ kubectl delete ns dev; kubectl delete clusterrolebinding jane-nodes; kubectl delete clusterrole node-viewer

Key takeaways

  • Role/ClusterRole = rules (apiGroups + resources + verbs); RoleBinding/ClusterRoleBinding = subjects + one roleRef.
  • RoleBinding → namespace scope, even with a ClusterRole (the reuse pattern). ClusterRoleBinding → everywhere.
  • Additive only; no deny. The 403 message names the exact user/verb/resource/group/namespace to grant.
  • Use the built-ins: cluster-admin (careful), admin, edit, view. system:masters bypasses RBAC — never give it to people.
  • Verify with auth can-i --as; find grants with get rolebindings,clusterrolebindings -A -o wide.
