Everything in a cluster finds everything else by name: api, postgres-0.postgres, kubernetes.default.svc. Those names are answered by CoreDNS, a small DNS server that watches Services and Pods and synthesises records for them. This lesson first covers how DNS works at all (the companion video), then exactly how a Pod's resolver is configured, which records exist, and how to debug the "it can't resolve" class of outage.

What you'll learn

  • DNS from scratch: resolvers, the hierarchy, record types, TTLs
  • CoreDNS: the Deployment, the kube-dns Service, and the Corefile
  • What the kubelet writes into every Pod's /etc/resolv.conf and why ndots:5 matters
  • The record set: Services, headless Services, Pods, SRV, ExternalName
  • dnsPolicy, dnsConfig, and a debugging checklist

Part 1 — How DNS works

Stub resolver
The library code in every program (glibc/musl getaddrinfo) that reads /etc/resolv.conf and sends queries to the configured nameserver. It does not recurse.
Recursive resolver
The server the stub asks (your ISP's, 8.8.8.8, systemd-resolved, CoreDNS). It walks the hierarchy on your behalf and caches answers for their TTL.
Root → TLD → authoritative
Root servers know who serves .com; .com servers know who serves example.com; example.com's authoritative servers hold the actual records.
Record types
A name → IPv4; AAAA → IPv6; CNAME alias → name; SRV service → host+port; PTR IP → name; NS, MX, TXT.
TTL
How long a cached answer is valid. Kubernetes records use a TTL of 30 s by default (CoreDNS ttl).
Search list & ndots
Client-side conveniences: for a name with fewer than ndots dots, the stub tries name.<search1>, name.<search2>… before the bare name. This is the key to Kubernetes short names.
$ dig +short kubernetes.io A                 # just the answer
$ dig kubernetes.io +trace | tail -20        # walk root → TLD → authoritative
$ dig @10.96.0.10 api.shop.svc.cluster.local # ask a specific server (CoreDNS)
$ nslookup api.shop.svc.cluster.local        # simpler, available in busybox

Part 2 — CoreDNS in the cluster

$ kubectl -n kube-system get deploy,svc,cm -l k8s-app=kube-dns
NAME                      READY   UP-TO-DATE   AVAILABLE
deployment.apps/coredns   2/2     2            2
NAME               TYPE        CLUSTER-IP   PORT(S)
service/kube-dns   ClusterIP   10.96.0.10   53/UDP,53/TCP,9153/TCP     # the IP every pod's resolv.conf points at
configmap/coredns
.:53 {
    errors
    health { lameduck 5s }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {   # synthesise records for the cluster domain
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {                        # everything else → the node's upstream resolvers
        max_concurrent 1000
    }
    cache 30                                            # cache upstream answers
    loop
    reload                                              # pick up ConfigMap changes
    loadbalance
}

The kubernetes plugin watches Services and EndpointSlices through the API and answers queries under cluster.local from memory. Anything outside that zone is forwarded to whatever the CoreDNS Pod's own /etc/resolv.conf says — the node's resolvers (since the Pod runs with dnsPolicy: Default). Edit the ConfigMap to add stub zones, rewrite rules or custom hosts; reload applies it within a couple of minutes.

What a Pod sees

$ kubectl run t --rm -it --image=busybox:1.36 -n shop -- cat /etc/resolv.conf
nameserver 10.96.0.10
search shop.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

The kubelet writes this file for every Pod with the default dnsPolicy: ClusterFirst. Three consequences:

  1. api → tried as api.shop.svc.cluster.local first → found. Short names work within the namespace.
  2. api.prod → api.prod.shop.svc.cluster.local (NXDOMAIN) → api.prod.svc.cluster.local → found. Two queries.
  3. www.google.com has 2 dots < ndots 5 → four failed lookups (www.google.com.shop.svc.cluster.local, …svc.cluster.local, …cluster.local, then bare) before the answer. Every external call from every Pod pays this unless the app uses FQDNs with a trailing dot (www.google.com.) or you lower ndots.

  dnsPolicy: ClusterFirst
  dnsConfig:                  # merged into the generated resolv.conf
    options:
    - name: ndots
      value: "2"              # fewer wasted lookups for external names

    nameservers: [10.0.0.53]  # appended (max 3 total)

Debugging checklist

# 1. is CoreDNS up and does the Service have endpoints?
$ kubectl -n kube-system get pods -l k8s-app=kube-dns -o wide
$ kubectl -n kube-system get endpointslices -l kubernetes.io/service-name=kube-dns
# 2. can a pod reach it? (NetworkPolicy blocking port 53 is the #1 cause after "CoreDNS is down")
$ kubectl run t --rm -it --image=busybox:1.36 -- nslookup kubernetes.default 10.96.0.10
# 3. what does the pod's resolv.conf say? (wrong dnsPolicy, hostNetwork)
$ kubectl exec app -- cat /etc/resolv.conf
# 4. does the record exist? (Service in the right namespace? selector matches → endpoints?)
$ kubectl get svc,endpointslices -n shop
# 5. CoreDNS logs — add "log" to the Corefile temporarily to see every query
$ kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50
# 6. upstream: can CoreDNS itself resolve external names? (node resolv.conf, egress firewall)
$ kubectl -n kube-system exec deploy/coredns -- cat /etc/resolv.conf 2>/dev/null || kubectl run t --rm -it --image=busybox:1.36 -- nslookup example.com
# 7. kube-proxy / CNI: DNS traffic to the ClusterIP 10.96.0.10 is Service traffic — if all Services are broken, so is DNS (Day 12, Day 58)
Under the hood · Linux

There is no DNS client in the kernel: resolution happens in the C library of each process, driven by /etc/nsswitch.conf (hosts: files dns — /etc/hosts first, then DNS) and /etc/resolv.conf. The kubelet writes those files into the container's rootfs at start (/etc/hosts gets the Pod's own hostname/IP plus hostAliases). Alpine's musl resolver behaves differently from glibc: it queries all nameservers in parallel and historically ignored some options — one reason "works in the Debian image, not in the Alpine one". ndots is purely a client-side rule; CoreDNS just sees a stream of NXDOMAIN-producing queries. A node-local DNS cache (NodeLocal DNSCache DaemonSet) puts a caching resolver on every node to cut that traffic and avoid conntrack races on UDP 53.

CKA exam tip
  • Know the FQDN pattern cold: svc.ns.svc.cluster.local; for StatefulSets pod.svc.ns.svc.cluster.local. Questions ask you to write these into a ConfigMap or test them with nslookup.
  • "DNS resolution failing in namespace X" → check NetworkPolicies there, then CoreDNS Pods/endpoints, then the Pod's resolv.conf.
  • CoreDNS config lives in the coredns ConfigMap in kube-system; the Service is kube-dns (historical name).
  • busybox:1.36 has nslookup; nicolaka/netshoot has dig, curl, tcpdump and everything else.

Hands-on lab (20 min)

$ kubectl create ns shop && kubectl create deploy api --image=nginx -n shop && kubectl expose deploy api --port=80 -n shop
$ kubectl run t --rm -it --image=busybox:1.36 -n shop -- sh -c 'cat /etc/resolv.conf; nslookup api; nslookup api.shop.svc.cluster.local; nslookup kubernetes.default'
$ kubectl run t --rm -it --image=busybox:1.36 -- nslookup api                 # default ns: fails (NXDOMAIN) — wrong search domain
$ kubectl run t --rm -it --image=busybox:1.36 -- nslookup api.shop           # works
$ kubectl -n kube-system get cm coredns -o yaml | grep -A3 'kubernetes cluster'
# watch queries: enable logging for a minute
$ kubectl -n kube-system get cm coredns -o yaml | sed 's/    errors/    log\n    errors/' | kubectl apply -f -
$ sleep 60; kubectl run t --rm -it --image=busybox:1.36 -- nslookup example.com >/dev/null; kubectl -n kube-system logs -l k8s-app=kube-dns --tail=10   # see the ndots search attempts
$ kubectl -n kube-system get cm coredns -o yaml | sed '/^    log$/d' | kubectl apply -f -
$ kubectl run t --rm -it --image=busybox:1.36 --overrides='{"spec":{"dnsPolicy":"Default"}}' -- sh -c 'cat /etc/resolv.conf; nslookup api.shop || echo "no cluster DNS with dnsPolicy Default"'
$ kubectl delete ns shop

Key takeaways

  • DNS = stub resolver (resolv.conf) → recursive resolver → hierarchy; records are cached for their TTL.
  • CoreDNS (Service kube-dns, 10.96.0.10) synthesises cluster.local records from Services/EndpointSlices and forwards the rest upstream. Config = the coredns ConfigMap.
  • Pods get search ns.svc.cluster.local svc.cluster.local cluster.local + ndots:5: short names work in-namespace; external names cost extra lookups.
  • Records: Service A, headless → Pod IPs, pod.svc.ns.svc.cluster.local for StatefulSets, SRV for named ports, CNAME for ExternalName.
  • Debug: CoreDNS Pods/endpoints → NetworkPolicy on 53 → Pod resolv.conf/dnsPolicy → record exists → CoreDNS logs → upstream.
