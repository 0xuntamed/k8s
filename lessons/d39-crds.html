Every object type you have used — Pod, Deployment, Service — is a resource served by the API server and stored in etcd. A CustomResourceDefinition lets you add a new type with a schema, and from then on the API server stores, validates, versions and serves it exactly like the built-ins: kubectl get, apply, describe, RBAC, watches. On its own a custom resource is just structured data; pair it with a controller (Day 40) and you have taught Kubernetes a new noun and a new verb.

What you'll learn

  • CRD vs CR: the type definition vs the instances
  • Anatomy of a CRD: group, names, scope, versions, OpenAPI schema, subresources, printer columns
  • Validation, defaulting and CEL rules inside the schema
  • Versioning and conversion at a glance
  • What the API server does for you — and what it does not (nothing happens until a controller exists)

Definition vs instance

CRD — the type

A cluster-scoped object of kind CustomResourceDefinition (group apiextensions.k8s.io). Creating it makes the API server start serving a new REST path, e.g. /apis/stable.example.com/v1/namespaces/*/databases. Analogy: a table schema.

CR — the instances

Objects of the new kind, e.g. kind: Database. Stored in etcd under the group, validated against the CRD's schema. Analogy: rows.

A complete CRD

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.stable.example.com      # MUST be .
spec:
  group: stable.example.com
  scope: Namespaced                        # or Cluster
  names:
    plural: databases
    singular: database
    kind: Database
    shortNames: [db]
    categories: [all]                      # include in "kubectl get all"
  versions:
  - name: v1
    served: true
    storage: true                          # exactly one version is the storage version
    schema:
      openAPIV3Schema:
        type: object
        required: [spec]
        properties:
          spec:
            type: object
            required: [engine, storageGB]
            properties:
              engine:
                type: string
                enum: [postgres, mysql]
              version:
                type: string
                default: "16"
              storageGB:
                type: integer
                minimum: 1
                maximum: 1024
              replicas:
                type: integer
                default: 1
            x-kubernetes-validations:
            - rule: "self.replicas <= 5 || self.engine == 'postgres'"
              message: "mysql supports at most 5 replicas"
          status:
            type: object
            properties:
              phase: {type: string}
              endpoint: {type: string}
    subresources:
      status: {}                           # /status endpoint; spec and status updated separately
      scale:
        specReplicasPath: .spec.replicas
        statusReplicasPath: .status.replicas
    additionalPrinterColumns:
    - name: Engine
      type: string
      jsonPath: .spec.engine
    - name: Phase
      type: string
      jsonPath: .status.phase
    - name: Age
      type: date
      jsonPath: .metadata.creationTimestamp
  • metadata.name — plural.group, no exceptions.
  • group — a DNS-style name you own; becomes the API path /apis/stable.example.com. Built-in groups (apps, *.k8s.io) are reserved.
  • scope — Namespaced (like Pods) or Cluster (like Nodes).
  • names — how kubectl and manifests refer to it. kubectl get db, kind: Database.
  • versions[] — each has a schema; served = accepts requests; storage = the format written to etcd (one only).
  • openAPIV3Schema — structural schema: types, required, enum, min/max, patterns, defaults (applied on read and write). Fields not in the schema are pruned unless x-kubernetes-preserve-unknown-fields: true.
  • x-kubernetes-validations — CEL rules with access to self (and oldSelf for updates): cross-field checks the schema cannot express.
  • subresources.status — separates spec (users) from status (controllers) exactly like built-ins; scale makes kubectl scale and HPA work.
  • additionalPrinterColumns — what kubectl get shows.

Using it

$ kubectl apply -f database-crd.yaml
$ kubectl get crd databases.stable.example.com
$ kubectl api-resources | grep database         # databases  db  stable.example.com/v1  true  Database
$ kubectl explain database.spec                  # generated from your schema
$ cat <<EOF | kubectl apply -f -
apiVersion: stable.example.com/v1
kind: Database
metadata:
  name: orders
spec:
  engine: postgres
  storageGB: 50
EOF
$ kubectl get db                                 # NAME  ENGINE  PHASE  AGE  (printer columns; version defaulted to "16")
$ kubectl get database orders -o yaml
$ kubectl apply -f - <<EOF                       # validation in action
apiVersion: stable.example.com/v1
kind: Database
metadata: {name: bad}
spec: {engine: oracle, storageGB: 5000}
EOF
# The Database "bad" is invalid: spec.engine: Unsupported value: "oracle"; spec.storageGB: Invalid value: 5000: must be <= 1024
$ kubectl delete crd databases.stable.example.com   # deletes EVERY Database object too

What you get for free — and what you do not

The API server provides

  • Storage in etcd, optimistic concurrency (resourceVersion), watches
  • Schema validation, defaulting, pruning, CEL rules
  • kubectl get/describe/apply/edit/delete/explain, printer columns, short names
  • RBAC on the new resource (apiGroups: [stable.example.com], resources: [databases])
  • Finalizers, owner references, garbage collection, labels/annotations, admission webhooks
  • Multi-version serving with conversion webhooks

Nothing happens

Creating a Database object creates a record. No Postgres appears. No Pod, no PVC, no Service. The status stays empty forever. Turning intent into reality requires a controller that watches Databases and creates StatefulSets, Secrets and Services in response — which is exactly what an Operator is. Until then a CR is a very well-validated ConfigMap.

Versions and conversion

Add v2 to versions[] with its own schema; keep v1 served for old clients. Only one is the storage version. If the schemas differ in shape, set spec.conversion.strategy: Webhook and run a conversion webhook that translates between versions; the default None strategy only rewrites apiVersion. This is the same mechanism that let Deployment move from extensions/v1beta1 to apps/v1 — built-ins just do it in compiled Go.

CRDs vs aggregated API servers

The other way to add types is an aggregated API server — your own binary registered via APIService, which the main API server proxies to (metrics-server is one). It can do anything (custom storage, custom verbs) but you operate a whole API server. CRDs cover 99% of cases with zero code for the type itself.

CKA exam tip
  • You will be asked to read CRDs more than write them: "list the CRDs of group X", "what are the printer columns / versions", "create an instance of kind Y" — kubectl get crd, kubectl explain <kind>, kubectl api-resources --api-group=….
  • To create a CR you need the group/version (kubectl api-resources APIVERSION column) and the required spec fields (kubectl explain kind.spec).
  • Deleting a CRD cascades to all its objects. Deleting a CR with a finalizer set by a missing controller hangs — clear the finalizer (Day 14).

Hands-on lab (15 min)

# apply the CRD from this page, then:
$ kubectl api-resources --api-group=stable.example.com
$ kubectl explain database.spec.engine
$ kubectl apply -f - <<EOF
apiVersion: stable.example.com/v1
kind: Database
metadata: {name: orders}
spec: {engine: postgres, storageGB: 50}
EOF
$ kubectl get db -o wide; kubectl get db orders -o jsonpath='{.spec.version}{"\n"}'   # default applied
$ kubectl apply -f - <<EOF
apiVersion: stable.example.com/v1
kind: Database
metadata: {name: m}
spec: {engine: mysql, storageGB: 10, replicas: 9}
EOF
# rejected by the CEL rule
$ kubectl scale db orders --replicas=3 && kubectl get db orders -o jsonpath='{.spec.replicas}{"\n"}'   # scale subresource works
$ kubectl patch db orders --subresource=status --type=merge -p '{"status":{"phase":"Ready"}}'; kubectl get db
$ kubectl create role db-viewer --verb=get,list --resource=databases.stable.example.com; kubectl auth can-i list databases --as=x   # RBAC sees the new resource
$ kubectl delete crd databases.stable.example.com; kubectl delete role db-viewer

Key takeaways

  • A CRD adds a new resource type to the API server; CRs are its instances. Name = plural.group.
  • The OpenAPI schema gives validation, defaults and pruning; CEL rules add cross-field checks; subresources give /status and /scale.
  • You get storage, kubectl, RBAC, watches, GC and versioning for free — but no behaviour.
  • Behaviour needs a controller. CRD + controller = Operator (next lesson).
