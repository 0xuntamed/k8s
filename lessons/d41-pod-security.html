A container is a process on a shared kernel, so "container security" is mostly "process security": which user does it run as, which of root's powers does it keep, can it write its own filesystem, can it gain privileges after starting. The Pod securityContext maps directly onto those Linux knobs — UIDs, capabilities, seccomp, AppArmor, no_new_privs — and the Pod Security Standards package them into three profiles a namespace can enforce. This lesson explains the knobs by what they do to the process.

What you'll learn

  • Pod-level vs container-level securityContext, and which fields live where
  • Users and groups: runAsUser, runAsGroup, runAsNonRoot, fsGroup, supplementalGroups
  • Linux capabilities: what root really is, why privileged is "all of them plus more", drop ALL / add one
  • readOnlyRootFilesystem, allowPrivilegeEscalation, seccomp and AppArmor profiles
  • Pod Security Admission: privileged / baseline / restricted, enforce / audit / warn per namespace

Where the fields go

apiVersion: v1
kind: Pod
metadata:
  name: hardened
spec:
  securityContext:                      # POD level: applies to all containers (+ volumes)
    runAsUser: 1000
    runAsGroup: 3000
    runAsNonRoot: true
    fsGroup: 2000                       # volumes are chowned to this GID; files created get it
    supplementalGroups: [4000]
    seccompProfile:
      type: RuntimeDefault
    sysctls:
    - name: net.ipv4.ip_unprivileged_port_start
      value: "80"
  containers:
  - name: app
    image: myapp:2.1
    securityContext:                    # CONTAINER level: overrides the Pod level for this container
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
        add: ["NET_BIND_SERVICE"]
      privileged: false
      runAsUser: 1000                   # may repeat/override pod-level
      appArmorProfile:
        type: RuntimeDefault
    volumeMounts:
    - {name: tmp, mountPath: /tmp}
  volumes:
  - {name: tmp, emptyDir: {}}
FieldLevelEffect on the process
runAsUser / runAsGroupPod, ContainerUID/GID the first process starts as (overrides the image's USER). Numeric only.
runAsNonRoot: truePod, ContainerKubelet refuses to start the container if the effective UID is 0 — or if the image says USER by name and the UID cannot be determined.
fsGroupPodVolumes that support it are recursively chowned to this group at mount time; the process gets it as a supplementary group. This is how a non-root app writes to a PVC.
capabilities.drop/addContainerRemove/add Linux capabilities from the bounding set (below).
privileged: trueContainerAll capabilities, all devices, no seccomp/AppArmor, writable /sys — effectively root on the node. For CNI/CSI/monitoring agents only.
allowPrivilegeEscalation: falseContainerSets no_new_privs: setuid binaries and file capabilities cannot raise privileges. Implied false when privileged is false and CAP_SYS_ADMIN is not added… but set it explicitly.
readOnlyRootFilesystem: trueContainerThe image's filesystem is mounted read-only; writes only to mounted volumes. Blocks an intruder from modifying binaries or dropping tools.
seccompProfilePod, ContainerSyscall filter: RuntimeDefault (containerd's profile, blocks ~40 dangerous syscalls), Localhost (a JSON profile on the node), Unconfined.
appArmorProfilePod, ContainerMAC profile on AppArmor kernels (Ubuntu/Debian): file/network access rules.
procMount, sysctls, windowsOptions, seLinuxOptionsvariousRarer; SELinux on RHEL-family nodes.

Users: root is UID 0, nothing more

Most images run as root because their Dockerfile never said otherwise. Inside a container root is still UID 0 on the host kernel; only namespaces and capabilities limit what it can do. If an attacker escapes the container (a runtime bug, a hostPath mount), being root on the host is game over. So: run as a non-root UID, and make the kubelet enforce it.

$ kubectl exec app -- id                       # uid=1000 gid=3000 groups=2000,4000
$ kubectl exec app -- ps -o user,pid,comm      # every process as 1000
$ kubectl run r --image=nginx --overrides='{"spec":{"securityContext":{"runAsNonRoot":true}}}'
$ kubectl get pod r                            # CreateContainerConfigError: container has runAsNonRoot and image will run as root
# fix: runAsUser: 101 (nginx's uid) + use the unprivileged nginx image (nginxinc/nginx-unprivileged listens on 8080)

Capabilities: root, split into pieces

Since Linux 2.2 "root" is not one bit but ~40 capabilities: CAP_NET_BIND_SERVICE (bind ports < 1024), CAP_CHOWN, CAP_NET_RAW (raw sockets — ping, but also ARP spoofing), CAP_SYS_ADMIN (mount, and a grab-bag so large it is "the new root"), CAP_SYS_PTRACE, CAP_NET_ADMIN (interfaces, routes, iptables)… A container runtime gives a root container a default subset of about 14; privileged gives all of them. The safe pattern is drop ALL, add back the one you need.

$ kubectl exec app -- cat /proc/1/status | grep Cap          # CapEff: 0000000000000400 = only NET_BIND_SERVICE
$ kubectl exec app -- sh -c 'apk add -q libcap 2>/dev/null; capsh --decode=0000000000000400'
$ kubectl exec app -- ping -c1 1.1.1.1                       # fails without NET_RAW (modern ping may use ICMP sockets instead)
Under the hood · Linux

Every field above becomes something in the OCI runtime spec that runc applies before execing your process: process.user.uid/gid/additionalGids (setuid/setgid/setgroups), process.capabilities.{bounding,effective,permitted,inheritable} (capset), process.noNewPrivileges (prctl(PR_SET_NO_NEW_PRIVS)), linux.seccomp (a BPF filter loaded with seccomp(2)), process.apparmorProfile, and root.readonly (a read-only bind remount). See them with crictl inspect <id> | jq .info.runtimeSpec.process on the node. Capabilities are per-thread attributes the kernel checks on privileged syscalls — bind() to port 80 asks for CAP_NET_BIND_SERVICE; without it, even UID 0 gets EACCES. privileged simply sets every capability and skips the seccomp/AppArmor/masked-paths setup, which is why it is equivalent to root on the node.

Pod Security Standards and Admission

Three profiles, defined by the project, enforced by the built-in PodSecurity admission plugin per namespace via labels (PodSecurityPolicy, its predecessor, was removed in 1.25):

privileged

No restrictions. For system namespaces running CNI/CSI/agents.

baseline

Blocks the known privilege escalations: no privileged, no hostNetwork/hostPID/hostIPC, no hostPath, no dangerous capabilities added (SYS_ADMIN, NET_ADMIN…), no unconfined seccomp/AppArmor, restricted sysctls. Most apps pass unchanged.

restricted

Baseline plus: runAsNonRoot: true, allowPrivilegeEscalation: false, capabilities.drop: [ALL] (only NET_BIND_SERVICE may be added), seccompProfile RuntimeDefault or Localhost, volumes limited to the safe types. The hardened Pod above passes.

$ kubectl label ns prod pod-security.kubernetes.io/enforce=restricted \
                        pod-security.kubernetes.io/enforce-version=latest \
                        pod-security.kubernetes.io/warn=restricted \
                        pod-security.kubernetes.io/audit=restricted
$ kubectl run root --image=nginx -n prod
# Error: pods "root" is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile
$ kubectl label ns dev pod-security.kubernetes.io/warn=baseline     # warn only: prints violations, still admits
$ kubectl label --dry-run=server --overwrite ns prod pod-security.kubernetes.io/enforce=restricted   # preview: which existing pods would fail
enforce
Reject violating Pods (Deployments are accepted, but their Pods fail to appear — watch kubectl get events and the ReplicaSet).
warn
Admit, but return a warning to the client.
audit
Admit, but annotate the audit log entry.
Exemptions
Configured cluster-wide in the API server's admission config (usernames, RuntimeClasses, namespaces like kube-system).

For anything finer (e.g. "only images from our registry", "must have resource limits") use a policy engine — Kyverno or Gatekeeper — or a ValidatingAdmissionPolicy (Day 38).

CKA exam tip
  • Typical: "run the Pod as UID 1010 with capabilities SYS_TIME added" → securityContext.runAsUser at Pod level, capabilities.add at container level (there is no Pod-level capabilities field — a classic trap).
  • runAsNonRoot + root image → CreateContainerConfigError. Either set runAsUser to a non-zero UID or pick an unprivileged image.
  • Pods silently not appearing for a Deployment in a namespace with enforce labels → kubectl describe rs shows the PodSecurity rejection.
  • Remember the label key: pod-security.kubernetes.io/enforce.

Hands-on lab (20 min)

$ kubectl run asroot --image=busybox --command -- sleep 3600
$ kubectl exec asroot -- id; kubectl exec asroot -- grep CapEff /proc/1/status          # uid 0, default caps
$ kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata: {name: locked}
spec:
  securityContext: {runAsUser: 1000, runAsGroup: 1000, runAsNonRoot: true, fsGroup: 2000, seccompProfile: {type: RuntimeDefault}}
  containers:
  - name: c
    image: busybox
    command: [sleep, "3600"]
    securityContext: {allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, capabilities: {drop: [ALL]}}
    volumeMounts: [{name: data, mountPath: /data}]
  volumes: [{name: data, emptyDir: {}}]
EOF
$ kubectl exec locked -- id                          # uid=1000 gid=1000 groups=2000
$ kubectl exec locked -- grep CapEff /proc/1/status  # 0000000000000000
$ kubectl exec locked -- touch /etc/x                # Read-only file system
$ kubectl exec locked -- touch /data/x && kubectl exec locked -- ls -l /data   # group 2000 via fsGroup
$ kubectl create ns strict && kubectl label ns strict pod-security.kubernetes.io/enforce=restricted pod-security.kubernetes.io/warn=restricted
$ kubectl run x --image=busybox -n strict --command -- sleep 1      # forbidden, with the list of violations
$ kubectl get pod locked -o yaml | grep -v 'status:' | sed 's/name: locked/name: locked2\n  namespace: strict/' | kubectl apply -f -   # passes restricted
$ kubectl delete pod asroot locked $now; kubectl delete ns strict

Key takeaways

  • securityContext = Linux process attributes: UID/GID, capabilities, no_new_privs, read-only rootfs, seccomp, AppArmor. Pod level for user/group/fsGroup/seccomp; container level for capabilities/privileged/readOnlyRootFilesystem/allowPrivilegeEscalation.
  • Root in a container is UID 0 on the node's kernel. Run non-root, enforce it with runAsNonRoot, use fsGroup for volume writes.
  • Capabilities split root's power; drop ALL and add back only what is needed. privileged = everything = root on the node.
  • Pod Security Admission enforces privileged/baseline/restricted per namespace via labels; use warn/audit before enforce.
