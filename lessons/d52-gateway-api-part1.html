Ingress has two structural problems: everything beyond host/path routing lives in controller-specific annotations, and one object mixes the infrastructure operator's concerns (which load balancer, which ports, which certs) with the developer's (which path goes where). The Gateway API — GA since 2023, in the CKA curriculum since 2025 — splits those into three resources with clear owners, and specifies matching, header manipulation, traffic splitting and more in the API itself. This lesson is the model; Day 53 runs it with NGINX Gateway Fabric.

What you'll learn

  • Why Ingress reached its limits
  • The role-oriented model: GatewayClass (provider), Gateway (infra), HTTPRoute (app)
  • Listeners, hostnames, parentRefs, matches, filters, backendRefs
  • Cross-namespace attachment and ReferenceGrant
  • The other route kinds (GRPCRoute, TCPRoute, TLSRoute, UDPRoute) and the implementation landscape

What Ingress cannot express

  • Header- or method-based routing, traffic splitting by weight (canary), request/response header modification, redirects and rewrites — all only via annotations that differ per controller.
  • Non-HTTP: TCP/UDP/TLS passthrough have no Ingress representation.
  • Roles: the same object holds the cert reference and LB config (platform team) and the routes (app team). RBAC cannot separate them.
  • Cross-namespace: an Ingress can only point at Services in its own namespace.

Three resources, three owners

GatewayClass (cluster-scoped)
Names an implementation, like IngressClass: controllerName: gateway.nginx.org/nginx-gateway-controller. Installed by whoever installs the controller. Owner: infrastructure provider.
Gateway (namespaced)
An actual entry point: "a load balancer of class X with these listeners (port, protocol, hostname, TLS cert), accepting routes from these namespaces". Creating one makes the implementation provision the data plane (an LB, or proxy Pods). Owner: cluster/platform operator.
HTTPRoute (namespaced)
Routing rules that attach to a Gateway (parentRefs) for some hostnames: matches on path/header/method/query → filters → backend Services with weights. Owner: application developer, in their own namespace.

GatewayClass

apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: nginx
spec:
  controllerName: gateway.nginx.org/nginx-gateway-controller

Gateway

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: main
  namespace: infra
spec:
  gatewayClassName: nginx
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces:
        from: All              # Same (default) · All · Selector
  - name: https
    protocol: HTTPS
    port: 443
    hostname: "*.example.com"
    tls:
      mode: Terminate          # or Passthrough (TLSRoute)
      certificateRefs:
      - name: wildcard-tls     # kubernetes.io/tls Secret in infra
    allowedRoutes:
      namespaces:
        from: Selector
        selector:
          matchLabels: {gateway-access: "true"}
  # addresses: [{type: IPAddress, value: 203.0.113.7}]   # request a specific IP if supported
  • listeners[] — one per port/protocol/hostname combination. Each has a name that routes can target with sectionName.
  • tls — certs belong to the Gateway (platform), not the route (app). Terminate decrypts; Passthrough forwards raw TLS to backends by SNI.
  • allowedRoutes — which namespaces may attach routes. This is the multi-tenancy control Ingress lacks.
  • status.addresses — filled in by the implementation with the LB IP/hostname; status.listeners[].attachedRoutes counts routes.

HTTPRoute

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
  namespace: shop
spec:
  parentRefs:
  - name: main
    namespace: infra
    sectionName: https        # attach to one listener (optional)
  hostnames: [shop.example.com]
  rules:
  - matches:
    - path: {type: PathPrefix, value: /api}
      headers:
      - name: X-Version
        value: v2
    filters:
    - type: RequestHeaderModifier
      requestHeaderModifier:
        add: [{name: X-Gateway, value: main}]
    backendRefs:
    - name: api-v2
      port: 8080
  - matches:
    - path: {type: PathPrefix, value: /api}
    backendRefs:
    - name: api
      port: 8080
      weight: 90
    - name: api-canary
      port: 8080
      weight: 10
  - matches:
    - path: {type: PathPrefix, value: /old}
    filters:
    - type: RequestRedirect
      requestRedirect: {path: {type: ReplacePrefixMatch, replacePrefixMatch: /new}, statusCode: 301}
  - matches:
    - path: {type: PathPrefix, value: /}
    backendRefs:
    - name: web
      port: 80
  • parentRefs — the Gateway(s) to attach to, possibly in another namespace. Attachment succeeds only if the Gateway allows this namespace; check status.parents[].conditions (Accepted, ResolvedRefs).
  • hostnames — must intersect the listener's hostname; the route only applies to these.
  • matches[] — path (Exact, PathPrefix, RegularExpression), headers, query params, method. Multiple matches in one rule are OR; conditions within a match are AND. Precedence is specified: longest path, then most headers/query, then… — no controller-specific surprises.
  • filters[] — RequestHeaderModifier, ResponseHeaderModifier, RequestRedirect, URLRewrite, RequestMirror, ExtensionRef (implementation CRDs).
  • backendRefs[] — Services with optional weight for traffic splitting. Cross-namespace refs require a ReferenceGrant in the target namespace.

Cross-namespace and ReferenceGrant

A route in shop may attach to a Gateway in infra if the Gateway's allowedRoutes permits it — the target decides. For a route to send traffic to a Service in another namespace, that namespace must publish a ReferenceGrant saying "HTTPRoutes from namespace X may reference my Services". Same for a Gateway referencing a TLS Secret in another namespace. Nothing can reach into a namespace without that namespace's consent.

apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-shop-routes
  namespace: backend            # the namespace being referenced
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    namespace: shop
  to:
  - group: ""
    kind: Service

Other route kinds and the landscape

KindForStatus
HTTPRouteHTTP/HTTPS (terminated)GA
GRPCRoutegRPC by service/methodGA
TLSRouteTLS passthrough by SNIExperimental channel
TCPRoute / UDPRouteL4 forwardingExperimental channel

Implementations: NGINX Gateway Fabric, Envoy Gateway, Istio, Cilium, Traefik, Kong, Contour, and every major cloud (AWS LB Controller, GKE Gateway, AKS AGC). The Gateway API CRDs are installed separately from the implementation (standard vs experimental channel), then the implementation registers its GatewayClass. Ingress is not deprecated, but new features land only in Gateway API; the ingress2gateway tool converts existing Ingresses.

Mental model

Ingress: "here is a routing table and, in annotations, whatever else this controller understands". Gateway API: "the platform owns the door (Gateway: address, ports, certs, who may use it); each team owns its routes through that door; the spec, not the vendor, defines what a route can do." Same data plane underneath — a proxy watching objects and reprogramming itself.

CKA exam tip
  • Expect to create an HTTPRoute for an existing Gateway: parentRefs (name + namespace), hostnames, rules[].matches[].path, backendRefs (name + port). Copy the skeleton from the docs.
  • Route not working → kubectl describe httproute: Accepted=False (namespace not allowed / no such listener / hostname mismatch) or ResolvedRefs=False (Service missing / cross-namespace without ReferenceGrant).
  • kubectl get gateway -o wide shows ADDRESS and PROGRAMMED; kubectl get gatewayclass shows ACCEPTED.

Key takeaways

  • Gateway API = GatewayClass (which implementation) + Gateway (listeners, certs, address — platform-owned) + routes (matches, filters, weighted backends — app-owned).
  • Routes attach via parentRefs; the Gateway controls which namespaces may attach; ReferenceGrant controls cross-namespace backends and Secrets.
  • Matching precedence, header manipulation, redirects, rewrites, splitting and mirroring are in the spec — portable across implementations.
  • HTTPRoute and GRPCRoute are GA; L4 routes are experimental. Ingress remains, but Gateway API is where features go.
