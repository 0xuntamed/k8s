Persistent storage in Kubernetes separates three concerns that used to be one: what storage exists (a PersistentVolume, cluster-scoped, created by an admin or a provisioner), what an application needs (a PersistentVolumeClaim, namespaced, written by the developer), and how to create more on demand (a StorageClass). The Pod only ever references the claim. This decoupling is what lets the same manifest run on EBS, Ceph or a local disk.

What you'll learn

  • PV: capacity, access modes, reclaim policy, volume mode, node affinity
  • PVC: how a claim finds and binds a volume, and why binding is one-to-one
  • StorageClass and dynamic provisioning; volumeBindingMode: WaitForFirstConsumer; expansion
  • hostPath and local volumes — and why hostPath is for single-node testing only
  • PV/PVC phases and the troubleshooting path for Pending claims and FailedMount Pods

The three objects

PersistentVolume (cluster-scoped)

apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-01
spec:
  capacity:
    storage: 20Gi
  accessModes:
  - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs
  volumeMode: Filesystem
  mountOptions: [hard, nfsvers=4.1]
  nfs:
    server: 10.0.0.50
    path: /exports/data
  • capacity.storage — size. A claim binds to a PV with at least this much.
  • accessModes — what the backend supports: ReadWriteOnce (RWO, one node), ReadOnlyMany (ROX), ReadWriteMany (RWX, many nodes — NFS, CephFS, EFS), ReadWriteOncePod (RWOP, one Pod). Block devices like EBS are RWO only.
  • persistentVolumeReclaimPolicy — what happens when the claim is deleted: Retain (keep data, PV becomes Released and must be cleaned by hand), Delete (provisioner deletes the backend disk — default for dynamic PVs). Recycle is deprecated.
  • storageClassName — a label that claims must match. Empty string = only claims that ask for no class.
  • volumeMode — Filesystem (mounted) or Block (raw device at volumeDevices).
  • The last block is the source: nfs, csi, hostPath, local, iscsi, fc…

PersistentVolumeClaim (namespaced)

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
  namespace: shop
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: fast-ssd
  volumeMode: Filesystem
  # selector:              # optional, static PVs only
  #   matchLabels: {tier: gold}
  • A claim is a request: size, modes, class. The control plane finds a PV that satisfies it (or creates one).
  • Binding rules: PV capacity ≥ request; PV modes ⊇ requested modes; same storageClassName; selector matches PV labels; not already bound. Among candidates, the smallest sufficient PV wins.
  • Binding is exclusive and one-to-one: a 100 Gi PV bound to a 10 Gi claim gives that claim all 100 Gi and nobody else anything.
  • Omit storageClassName and the cluster's default StorageClass is used (if one is annotated as default). Set it to "" to force a static PV with no class.
# the Pod references only the claim
spec:
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data
  containers:
  - name: db
    image: postgres:16
    volumeMounts:
    - name: data
      mountPath: /var/lib/postgresql/data

StorageClass and dynamic provisioning

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com             # which CSI driver creates volumes
parameters:                              # driver-specific
  type: gp3
  iops: "6000"
  encrypted: "true"
reclaimPolicy: Delete                    # applied to PVs it creates
volumeBindingMode: WaitForFirstConsumer  # or Immediate
allowVolumeExpansion: true

With a StorageClass present, a PVC that names it (or the default) triggers the provisioner to create a backend volume and a matching PV, then bind. Nobody pre-creates PVs. This is how every cloud cluster works; static PVs are for NFS servers, pre-existing disks and bare metal.

volumeBindingMode: Immediate
Provision and bind as soon as the PVC exists. Problem on multi-zone clouds: the disk may be created in zone A while the Pod is later scheduled to zone B and cannot attach.
volumeBindingMode: WaitForFirstConsumer
Leave the PVC Pending until a Pod using it is scheduled; then provision in that Pod's zone. The PVC shows WaitForFirstConsumer in its events — this is not an error. Recommended for block storage.
allowVolumeExpansion
Edit the PVC's requests.storage upward and the CSI driver grows the disk and (for most filesystems) the filesystem online. Shrinking is never supported.
Default class
At most one should carry the annotation; kubectl get sc marks it (default). kubectl patch sc X -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'.

hostPath and local

hostPath

volumes:
- name: data
  hostPath:
    path: /data/db
    type: DirectoryOrCreate   # Directory · File · Socket · ""

Mounts a directory of whichever node the Pod lands on. Reschedule the Pod and the data is "gone" (it is still on the old node). No capacity, no scheduling awareness, and root on the node is one hostPath: / away. Use for: node agents (log collectors, CNI), single-node dev (KIND, minikube), the course demos. Never for production data.

local

kind: PersistentVolume
spec:
  capacity: {storage: 500Gi}
  accessModes: [ReadWriteOnce]
  storageClassName: local-nvme
  local:
    path: /mnt/nvme0
  nodeAffinity:              # REQUIRED
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values: [worker-3]

A PV backed by a node disk, with mandatory nodeAffinity so the scheduler puts any Pod using the claim on that node. Proper capacity, proper binding, used with a WaitForFirstConsumer class. The right way to use fast local disks for databases that replicate themselves (Cassandra, Kafka).

Phases and troubleshooting

ObjectPhaseMeaning
PVAvailableFree, not yet bound.
PVBoundBound to a claim (shown in CLAIM column).
PVReleasedClaim deleted, policy Retain: data still there, but not reusable until you remove spec.claimRef (or delete and re-create the PV).
PVFailedAutomatic reclamation failed.
PVCPendingNo matching PV and no provisioner did anything — or WaitForFirstConsumer with no Pod yet.
PVCBoundReady to use.
$ kubectl get pv,pvc -A
$ kubectl describe pvc data          # Events: "no persistent volumes available for this claim and no storage class is set" / "waiting for first consumer" / provisioner errors
$ kubectl get sc                     # is there a default? does the class name match?
$ kubectl describe pod db | grep -A5 Events   # FailedMount / FailedAttachVolume / "volume node affinity conflict"
$ kubectl get volumeattachments      # CSI attach state
$ kubectl patch pv pv-01 -p '{"spec":{"claimRef": null}}'   # make a Released PV Available again (data intact)
Two objects, two lifetimes

Deleting a Pod never deletes its PVC. Deleting a PVC that a Pod still uses is blocked by a finalizer (kubernetes.io/pvc-protection) until the Pod is gone — the PVC shows Terminating meanwhile. Deleting a PVC with a Delete-policy PV deletes the backend disk: there is no undo. For anything you care about, use Retain and snapshots.

Under the hood · Linux

For a block-backed PV on a node: the CSI node plugin's NodeStageVolume finds the attached device (/dev/nvme1n1), formats it if blank (mkfs.ext4/xfs), and mounts it once at a global staging path /var/lib/kubelet/plugins/kubernetes.io/csi/<driver>/<hash>/globalmount. NodePublishVolume then bind-mounts that into /var/lib/kubelet/pods/<uid>/volumes/kubernetes.io~csi/<pv>/mount, and the runtime bind-mounts that into the container. Three nested mounts, all visible in findmnt on the node. For NFS the "stage" is a network mount; for hostPath there is no stage at all — just one bind mount of the node path. RWO is enforced by the attach step (the cloud refuses to attach one disk to two VMs), not by the kernel.

CKA exam tip
  • Static flow to memorise: create PV (with hostPath in the exam), create PVC with matching size/mode/class, reference persistentVolumeClaim.claimName in the Pod. Verify get pv,pvc shows Bound.
  • PVC Pending: compare storageClassName (a PV with no class only binds a PVC with storageClassName: "" or unset and no default class), access modes, and size.
  • Reuse a Released PV: clear spec.claimRef.
  • Expanding: edit the PVC, not the PV; the class must allow expansion.

Hands-on lab (20 min)

# static: hostPath PV + PVC (KIND)
$ cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: PersistentVolume
metadata: {name: pv-manual}
spec:
  capacity: {storage: 1Gi}
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath: {path: /tmp/pv-manual, type: DirectoryOrCreate}
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: claim-manual}
spec:
  accessModes: [ReadWriteOnce]
  resources: {requests: {storage: 500Mi}}
  storageClassName: manual
EOF
$ kubectl get pv,pvc                              # both Bound; PV capacity 1Gi even though 500Mi was asked
$ kubectl run w --image=busybox --command -- sh -c 'echo hi > /data/f; sleep 3600' $do | sed '/spec:/a\  volumes: [{name: d, persistentVolumeClaim: {claimName: claim-manual}}]' | sed '/image: busybox/a\    volumeMounts: [{name: d, mountPath: /data}]' | kubectl apply -f -
$ kubectl exec w -- cat /data/f
$ kubectl delete pod w $now; kubectl delete pvc claim-manual; kubectl get pv     # Released
$ kubectl patch pv pv-manual -p '{"spec":{"claimRef":null}}'; kubectl get pv       # Available again
# dynamic: KIND's default class
$ kubectl get sc
$ kubectl apply -f - <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: dyn}
spec: {accessModes: [ReadWriteOnce], resources: {requests: {storage: 1Gi}}}
EOF
$ kubectl get pvc dyn; kubectl describe pvc dyn | tail -3     # Pending: WaitForFirstConsumer
$ kubectl run w2 --image=busybox --command -- sleep 3600 $do | sed '/spec:/a\  volumes: [{name: d, persistentVolumeClaim: {claimName: dyn}}]' | sed '/image: busybox/a\    volumeMounts: [{name: d, mountPath: /data}]' | kubectl apply -f -
$ kubectl get pv,pvc                                            # a PV appeared and bound once the Pod was scheduled
$ kubectl delete pod w2 $now; kubectl delete pvc dyn; kubectl get pv   # Delete policy: PV gone
$ kubectl delete pv pv-manual

Key takeaways

  • PV = supply (cluster-scoped), PVC = demand (namespaced), Pod references the PVC. Binding is exclusive, one-to-one, by size/modes/class.
  • Access modes describe the backend; RWO block disks vs RWX file systems. Reclaim policy decides what happens to data after the claim is gone.
  • StorageClass + provisioner = dynamic provisioning; use WaitForFirstConsumer on multi-zone clusters; expansion is one-way.
  • hostPath is node-local and unsafe for real data; local PVs with nodeAffinity are the proper node-disk option.
  • Released PVs need claimRef cleared; PVCs in use are protected from deletion.
