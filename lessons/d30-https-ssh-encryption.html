Every component in a Kubernetes cluster authenticates every other with TLS certificates, and every kubectl call is an HTTPS request. If you have only ever treated HTTPS as "the padlock", the next four lessons will feel like magic. So we start from nothing: what encryption is, why there are two kinds, what a hash is for, and how SSH and HTTPS combine them. No Kubernetes on this page at all — just the primitives.

What you'll learn

  • Symmetric encryption: one shared key, fast, but how do you share the key?
  • Asymmetric encryption: a key pair, and the two things you can do with it (encrypt to someone, sign as someone)
  • Hashing and digital signatures — integrity and authenticity
  • How SSH uses key pairs both to identify the server and to log you in
  • How HTTPS uses asymmetric crypto to agree on a symmetric key, and why it still needs certificates

The problem

Two parties want to exchange data over a network that anyone can listen on (and tamper with). They need three guarantees: confidentiality (nobody else can read it), integrity (nobody changed it in transit), and authenticity (I am really talking to who I think I am). Encryption gives the first, hashing the second, and signatures with a trust anchor the third.

Symmetric encryption

One secret key encrypts and decrypts. AES-256 is the standard: extremely fast (hardware-accelerated in every CPU), used for all bulk data. The flaw is not the algorithm — it is distribution: both sides must have the same key, and you cannot send it over the network you are trying to protect.

$ openssl rand -hex 32 > key.txt                                        # a 256-bit key
$ openssl enc -aes-256-cbc -pbkdf2 -in secret.txt -out secret.enc -pass file:key.txt
$ openssl enc -d -aes-256-cbc -pbkdf2 -in secret.enc -pass file:key.txt   # same key decrypts

Asymmetric encryption

A key pair: a private key you never share and a public key you give to everyone. They are mathematically linked (RSA, or elliptic curves like ECDSA/Ed25519) so that:

Encrypt with public → decrypt with private

Anyone can seal a message that only the key owner can open. Solves key distribution: send me your public key, I encrypt a fresh symmetric key with it, only you can read it.

Sign with private → verify with public

Only the key owner can produce a signature that the public key verifies. Proves who produced a message and that it was not altered. This is how certificates and SSH logins work.

Asymmetric operations are thousands of times slower than AES, so they are used only for small things: exchanging a symmetric key and signing hashes.

$ openssl genrsa -out me.key 2048                     # private key (keep secret, chmod 600)
$ openssl rsa -in me.key -pubout -out me.pub          # derive the public key
$ openssl pkeyutl -encrypt -pubin -inkey me.pub -in msg.txt -out msg.enc   # anyone can do this
$ openssl pkeyutl -decrypt -inkey me.key -in msg.enc  # only the private key can

Hashing and signatures

A hash (SHA-256) turns any input into a fixed 32-byte fingerprint: deterministic, one-way, and any change to the input changes the whole output. It is integrity, not secrecy — anyone can compute it. A digital signature is a hash encrypted with a private key: the verifier recomputes the hash of what they received, decrypts the signature with the signer's public key, and compares. Match → the exact bytes came from the private key's owner.

$ sha256sum kubectl                                                   # compare with the published checksum
$ openssl dgst -sha256 -sign me.key -out msg.sig msg.txt              # sign
$ openssl dgst -sha256 -verify me.pub -signature msg.sig msg.txt      # Verified OK

How SSH works

  1. Key exchange. Client and server run Diffie-Hellman: each contributes a public value, both derive the same secret without ever sending it. That secret becomes the symmetric session key (AES/ChaCha20) for everything that follows.
  2. Server authentication. The server signs the exchange with its host key. Your client checks the host's public key against ~/.ssh/known_hosts. First connection: "The authenticity of host … can't be established" — you are being asked to establish trust manually. A changed key later means either a reinstalled server or a man-in-the-middle.
  3. Client authentication. With password auth, you send the password inside the encrypted channel. With key auth (ssh-keygen → ~/.ssh/id_ed25519 + .pub), the server has your public key in ~/.ssh/authorized_keys; it sends a random challenge, your client signs it with your private key, the server verifies with the public key. Your private key never leaves your machine.

Both directions use the same primitive — sign a challenge with a private key, verify with a known public key — which is mutual authentication. The difference from TLS is how trust in the public key is established: SSH uses lists you maintain by hand; TLS uses certificates signed by an authority.

How HTTPS works

  1. Client hello. Browser says: I speak TLS 1.3, here are my cipher suites, and here is my Diffie-Hellman public value.
  2. Server hello + certificate. Server picks a suite, sends its DH value (both sides now derive the session key), and sends its certificate: its public key plus its identity (CN=api.example.com) signed by a Certificate Authority.
  3. Certificate verification. The browser checks the CA's signature using the CA public key it already trusts (shipped with the OS/browser), checks the name matches the URL, checks expiry and revocation.
  4. Server proves possession. The server signs the handshake transcript with the private key matching the certificate. Without the private key, a stolen certificate is useless.
  5. Encrypted application data. Everything after this is AES with the session key. One round-trip in TLS 1.3.
Mental model

Asymmetric crypto answers "who am I talking to?" (signatures, certificates) and "how do we agree on a secret?" (key exchange). Symmetric crypto then does the actual work fast. A certificate is just a public key with a name on it and a CA's signature vouching for the pairing. Everything on Day 31 onward is variations of this: who signs whose public key, and who trusts which signer.

Under the hood · Linux

Your system's trusted CA public keys live in /etc/ssl/certs/ (Debian/Ubuntu: ca-certificates.crt is the bundle; update-ca-certificates adds your own). curl, kubectl, Go and Python programs all read this bundle unless told otherwise — which is why adding an internal CA to that directory makes a whole machine trust it. openssl s_client -connect host:443 -showcerts shows a live handshake and certificate chain; ssh -v shows the SSH negotiation. The OpenSSL page has the full toolkit you will use on Days 33–34.

Hands-on lab (15 min)

# asymmetric round-trip
$ openssl genrsa -out a.key 2048 && openssl rsa -in a.key -pubout -out a.pub
$ echo "hello" > m.txt && openssl pkeyutl -encrypt -pubin -inkey a.pub -in m.txt -out m.enc
$ openssl pkeyutl -decrypt -inkey a.key -in m.enc
# signature: tamper and watch it fail
$ openssl dgst -sha256 -sign a.key -out m.sig m.txt && openssl dgst -sha256 -verify a.pub -signature m.sig m.txt
$ echo "hellO" > m.txt && openssl dgst -sha256 -verify a.pub -signature m.sig m.txt     # Verification Failure
# a real TLS handshake
$ openssl s_client -connect kubernetes.io:443 -servername kubernetes.io < /dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
# ssh key auth, if you have a server: ssh-keygen -t ed25519; ssh-copy-id user@host; ssh -v user@host 2>&1 | grep -E 'Offering|Authenticated'

Key takeaways

  • Symmetric (AES): one shared key, fast, key-distribution problem. Asymmetric (RSA/EC): public/private pair, slow, solves distribution and enables signatures.
  • Encrypt to a public key; sign with a private key; a hash is a fingerprint, a signature is a signed fingerprint.
  • SSH: DH session key + host key in known_hosts + your key pair in authorized_keys — mutual auth with hand-managed trust.
  • HTTPS: DH session key + a certificate (public key + name + CA signature) that the client verifies against a trusted CA.
