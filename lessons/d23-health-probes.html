A process that is running is not necessarily working. It may be deadlocked, still loading a model, or unable to reach its database. Probes let the kubelet ask the application itself, on a schedule, and act on the answer — and there are three of them because there are three different questions: should I restart you? (liveness), should I send you traffic? (readiness), and have you finished starting? (startup). Confusing them causes outages; using them well is what makes rolling updates invisible.

What you'll learn

  • The three probes, what each one's failure triggers, and why they must ask different questions
  • Probe mechanisms: httpGet, tcpSocket, exec, grpc
  • Timing fields: initialDelay, period, timeout, success/failure thresholds
  • The classic mistakes: liveness that checks dependencies, readiness that never passes, missing startup probes on slow apps

Three probes, three questions

ProbeQuestionOn failure (after failureThreshold)Typical check
livenessIs the process irrecoverably broken?Kubelet kills and restarts the container (per restartPolicy)A trivial endpoint proving the event loop responds: /healthz → 200
readinessCan it serve requests right now?Pod marked NotReady → removed from Service endpoints. No restart./ready: warmed up, dependencies reachable, not overloaded, not draining
startupHas it finished starting?Kill and restart. While it runs, liveness and readiness are disabled.Same as liveness, with a generous failureThreshold × period budget
The mistake that causes cascading outages

A liveness probe that checks dependencies ("can I reach the database?") turns a database blip into a fleet-wide restart storm: every replica fails liveness, every replica is killed, the restarts add load, the database recovers slower. Liveness must only test the process itself. Dependency checks belong in readiness, where failure just pauses traffic to that Pod until the dependency returns.

The spec

containers:
- name: api
  image: myapi:2.1
  ports: [{name: http, containerPort: 8080}]
  startupProbe:
    httpGet: {path: /healthz, port: http}
    periodSeconds: 5
    failureThreshold: 60          # up to 5 min to start before the first restart
  livenessProbe:
    httpGet:
      path: /healthz
      port: http
      httpHeaders: [{name: X-Probe, value: liveness}]
    periodSeconds: 10
    timeoutSeconds: 2
    failureThreshold: 3           # 3 × 10 s = 30 s of failures → restart
  readinessProbe:
    httpGet: {path: /ready, port: http}
    periodSeconds: 5
    successThreshold: 1
    failureThreshold: 2           # out of rotation after 10 s of failures
initialDelaySeconds
Wait before the first probe (default 0). Prefer a startup probe over a large initial delay — the delay is fixed, the startup probe adapts.
periodSeconds
How often (default 10).
timeoutSeconds
How long a single probe may take (default 1 — often too short for HTTP under load).
successThreshold
Consecutive successes to be considered healthy after failing (default 1; must be 1 for liveness and startup).
failureThreshold
Consecutive failures before acting (default 3).
terminationGracePeriodSeconds
Can be set per liveness/startup probe to override the Pod's value for probe-triggered kills.

Mechanisms

httpGet

GET to scheme://podIP:port/path. 200–399 = success. Add headers for auth or to tell probes apart in logs. scheme: HTTPS skips cert verification.

tcpSocket

Can the kubelet open a TCP connection to the port? Cheap; proves the listener exists, not that it works. Good for databases and non-HTTP services.

exec

Run a command in the container; exit 0 = success. Flexible but heavy (a process per probe) and needs the binary in the image. cat /tmp/healthy, pg_isready, redis-cli ping.

grpc

Calls the standard gRPC Health service (grpc.health.v1.Health/Check) on the port; service selects a sub-service. Needs the app to implement the health protocol.

livenessProbe:
  exec:
    command: ["redis-cli", "ping"]
readinessProbe:
  tcpSocket: {port: 5432}
livenessProbe:
  grpc: {port: 9090, service: ""}

How probes interact with everything else

  • Services only route to Pods whose Ready condition is true. Readiness is your traffic switch. A Pod with no readiness probe is Ready as soon as its containers start — before the app is listening.
  • Rolling updates wait for new Pods to be Ready before continuing (maxUnavailable logic, Day 10). No readiness probe → the rollout proceeds on "container started", and a broken build replaces the whole fleet before you notice.
  • Termination: during the grace period the Pod is already out of endpoints; a readiness probe that fails during shutdown does not matter, but an app that flips /ready to 503 on SIGTERM helps external load balancers that poll it.
  • Restarts from liveness follow the same back-off as crashes (Day 22). describe pod shows Liveness probe failed: … events with the HTTP status or exec output.
  • Startup resets when the container restarts, so a slow app gets its full budget every time.
$ kubectl describe pod api | grep -E 'Liveness|Readiness|Startup'         # configured probes
$ kubectl get events --field-selector reason=Unhealthy -w                 # live probe failures
$ kubectl get pod api -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'
$ kubectl get endpointslices -l kubernetes.io/service-name=api -o yaml | grep -B2 ready
CKA exam tip
  • Task: "add a liveness probe that runs X every N seconds with initial delay D" — the fields are exactly exec.command, periodSeconds, initialDelaySeconds. Copy the block from kubectl explain pod.spec.containers.livenessProbe.
  • Pod Running 0/1 with Unhealthy readiness events → check the probe's port/path against the container (kubectl exec … -- wget -qO- localhost:8080/ready).
  • Pod restarting with Liveness probe failed → usually a too-short timeoutSeconds or a slow start needing a startup probe.
  • Probes go under containers[], not under spec. For a Deployment: spec.template.spec.containers[].

Hands-on lab (20 min)

$ cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: {name: probed, labels: {app: probed}}
spec:
  containers:
  - name: web
    image: nginx
    ports: [{containerPort: 80}]
    readinessProbe: {httpGet: {path: /ready.html, port: 80}, periodSeconds: 3, failureThreshold: 1}
    livenessProbe:  {httpGet: {path: /, port: 80}, periodSeconds: 5, failureThreshold: 2}
EOF
$ kubectl expose pod probed --port=80
$ kubectl get pod probed -w                  # Running 0/1 — ready.html does not exist
$ kubectl get endpointslices -l kubernetes.io/service-name=probed   # no ready endpoints
$ kubectl exec probed -- sh -c 'echo ok > /usr/share/nginx/html/ready.html'
$ kubectl get pod probed                     # 1/1 within 3 s; endpoint appears
$ kubectl exec probed -- rm /usr/share/nginx/html/ready.html; sleep 4; kubectl get pod probed    # 0/1 again, RESTARTS still 0
$ kubectl exec probed -- rm /usr/share/nginx/html/index.html; sleep 12; kubectl get pod probed   # liveness fails → RESTARTS 1
$ kubectl describe pod probed | grep -E 'Unhealthy|Killing'
$ kubectl delete pod probed $now; kubectl delete svc probed

Key takeaways

  • Liveness → restart; readiness → in/out of endpoints; startup → gates the other two while the app boots.
  • Liveness checks the process only. Dependencies go in readiness. Slow starts get a startup probe, not a big initialDelay.
  • httpGet for web apps, tcpSocket for listeners, exec for everything else, grpc for gRPC.
  • Without a readiness probe, Pods receive traffic before they can serve it and rollouts cannot detect a bad release.
