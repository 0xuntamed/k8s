Helm is the package manager for Kubernetes. A chart is a directory of templated manifests plus a values.yaml of parameters; helm install renders the templates with your values and applies the result as a named, versioned release that can be upgraded and rolled back as a unit. Almost every piece of third-party software you will run — ingress controllers, Prometheus, cert-manager, databases — ships as a chart. This lesson installs charts, reads them, writes a small one, and shows exactly where Helm keeps its state.

What you'll learn

  • Charts, repositories, releases, revisions — the vocabulary

Vocabulary

TermMeaning
ChartA package: Chart.yaml metadata + values.yaml defaults + templates/. Distributed as a .tgz.
RepositoryAn HTTP index of charts (index.yaml + tgz files), or an OCI registry (oci://ghcr.io/org/charts/x). Add with helm repo add.
ValuesThe parameters. Chart defaults ← your values file ← --set flags, later wins.
ReleaseOne installation of a chart in one namespace under a name. Two releases of the same chart are independent.
RevisionEach install/upgrade/rollback increments it; Helm keeps the history so it can roll back.

Installing a chart

$ helm repo add bitnami https://charts.bitnami.com/bitnami
$ helm repo update
$ helm search repo nginx                                   # charts in added repos
$ helm search hub prometheus | head                        # Artifact Hub (public index)
$ helm show values bitnami/nginx | less                    # every parameter and its default — read this first
$ helm show chart bitnami/nginx                            # Chart.yaml: version, appVersion, dependencies

$ helm install web bitnami/nginx --namespace demo --create-namespace \
    --set replicaCount=2 --set service.type=ClusterIP
$ helm install web bitnami/nginx -n demo -f my-values.yaml --version 18.1.0   # pin the CHART version
$ helm install web oci://registry-1.docker.io/bitnamicharts/nginx -n demo    # OCI form

$ helm list -n demo                                        # NAME REVISION STATUS CHART APP VERSION
$ helm status web -n demo                                  # NOTES.txt output: how to reach the app
$ helm get values web -n demo                              # what you overrode (--all for effective values)
$ helm get manifest web -n demo                            # the rendered YAML that was applied
replicaCount: 3
image:
  tag: 1.27.0
service:
  type: NodePort
  nodePorts:
    http: "30080"
resources:
  requests: {cpu: 100m, memory: 128Mi}
  limits: {cpu: 500m, memory: 256Mi}

In a GitOps setup Argo CD runs only the template half of Helm (helm template) and applies the result itself — there are no release Secrets and helm rollback is replaced by git revert (C9). In a push pipeline, helm upgrade --install --atomic from a job is the deploy step (C3).

Upgrade, rollback, history

$ helm upgrade web bitnami/nginx -n demo -f my-values.yaml --set replicaCount=5      # revision 2
$ helm upgrade --install web bitnami/nginx -n demo -f my-values.yaml                 # idempotent: install if missing (CI's favourite)
$ helm history web -n demo
REVISION  UPDATED   STATUS      CHART         APP VERSION  DESCRIPTION
1         …         superseded  nginx-18.1.0  1.27.0       Install complete
2         …         deployed    nginx-18.1.0  1.27.0       Upgrade complete
$ helm rollback web 1 -n demo                                                        # revision 3 = contents of 1
$ helm upgrade web … --atomic --timeout 5m     # roll back automatically if the upgrade fails / pods never become ready
$ helm uninstall web -n demo                   # deletes everything the release created (keep history with --keep-history)
Where the state lives

Helm 3 has no server component. Each revision is stored as a Secret in the release's namespace, type helm.sh/release.v1, named sh.helm.release.v1.web.v2, containing the gzipped, base64 chart + values + rendered manifest. helm rollback just re-applies an older Secret's manifest. That is why kubectl get secrets -n demo shows them, why RBAC on Secrets is enough to use Helm, and why deleting those Secrets makes Helm forget a release (the objects stay). Helm applies manifests with a three-way merge like kubectl apply, tracking ownership with the labels app.kubernetes.io/managed-by: Helm and annotations meta.helm.sh/release-name/-namespace.

Inside a chart

$ helm create mychart                     # scaffold
$ tree mychart

├── values.yaml           # defaults; the chart's public API
├── charts/               # dependency charts (helm dependency update)
├── templates/
│   ├── _helpers.tpl      # named template snippets (labels, names)
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── serviceaccount.yaml
│   ├── hpa.yaml
│   ├── NOTES.txt         # printed after install
│   └── tests/test-connection.yaml
└── .helmignore

name: mychart
description: A web service
type: application
version: 0.3.1            # chart version — bump on any chart change (SemVer)
appVersion: "2.4.0"       # version of the software inside
dependencies:
- name: redis
  version: "20.x.x"
  repository: https://charts.bitnami.com/bitnami
  condition: redis.enabled
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "mychart.fullname" . }}          # release-name-chart-name, from _helpers.tpl
  labels:
    {{- include "mychart.labels" . | nindent 4 }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
  selector:
    matchLabels:
      {{- include "mychart.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}   # config change → rollout
      labels:
        {{- include "mychart.selectorLabels" . | nindent 8 }}
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
        ports:
        - containerPort: {{ .Values.service.port }}
        {{- with .Values.resources }}
        resources:
          {{- toYaml . | nindent 10 }}
        {{- end }}
        env:
        {{- range $k, $v := .Values.env }}
        - name: {{ $k }}
          value: {{ $v | quote }}
        {{- end }}

Render before you apply

$ helm lint mychart                                          # structural checks
$ helm template web mychart -f my-values.yaml                # render locally, no cluster needed
$ helm template web mychart --show-only templates/deployment.yaml
$ helm install web mychart --dry-run --debug                 # render + server-side validation, print everything
$ helm install web mychart -n demo --wait --timeout 3m       # block until pods are Ready
$ helm package mychart && helm push mychart-0.3.1.tgz oci://ghcr.io/acme/charts
$ helm test web -n demo                                      # run templates/tests/

Hooks and CRDs

  • Hooks (helm.sh/hook: pre-install, post-upgrade, pre-delete… annotations on a Job/Pod) run at lifecycle points — database migrations before an upgrade, cleanup before delete. They are not part of the release's normal manifest and need helm.sh/hook-delete-policy to be cleaned up.
  • CRDs in a chart's crds/ directory are installed on first install and never upgraded or deleted by Helm (too dangerous). Operators' charts document how to update CRDs by hand.
Helm vs Kustomize, settled

Use Helm to consume software written by others (it is how they ship it, with parameters and upgrade paths) and to distribute your own when others will install it with different settings. Use Kustomize (Day 42) for your own services across your own environments, where you want plain YAML in git and no templating logic. Combining them — helm template … | kubectl kustomize, or Kustomize's helmCharts — is normal.

CKA exam tip
  • Expect: helm repo add/update, helm install with --set or -f, helm upgrade to a new --version, helm rollback, helm list -A, helm uninstall. Practise each once.
  • "Find which chart version deploys app version X": helm search repo chart --versions | grep X.
  • Always -n: releases are per namespace; helm list without -A shows only the current namespace.
  • helm show values beats guessing key names; the docs site is allowed too.

Hands-on lab (20 min)

$ curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
$ helm repo add bitnami https://charts.bitnami.com/bitnami && helm repo update
$ helm show values bitnami/nginx | grep -E '^replicaCount|^  type:'
$ helm install web bitnami/nginx -n demo --create-namespace --set replicaCount=2 --set service.type=ClusterIP
$ helm list -n demo; kubectl get all -n demo
$ kubectl get secret -n demo -l owner=helm                  # sh.helm.release.v1.web.v1
$ helm upgrade web bitnami/nginx -n demo --set replicaCount=3 --set service.type=ClusterIP
$ helm history web -n demo; kubectl get deploy -n demo      # 3 replicas, revision 2
$ helm rollback web 1 -n demo && kubectl get deploy -n demo # back to 2, revision 3
$ helm get manifest web -n demo | grep -c '^kind:'
# your own chart
$ helm create hello && helm template hello ./hello --set replicaCount=2 | grep -A2 'replicas'
$ helm install hello ./hello -n demo --set image.tag=1.27 && helm list -n demo
$ helm uninstall web hello -n demo; kubectl delete ns demo

Key takeaways

  • Chart = templates + values; release = a named install; revisions enable rollback. State is Secrets in the namespace; no server.
  • Workflow: repo add/update → show values → install -f values → upgrade / rollback / uninstall; upgrade --install for CI.
  • Templates are Go templates over .Values, .Release, .Chart; helm template and --dry-run show the YAML first.
  • Hooks run Jobs at lifecycle points; CRDs in crds/ are install-only.
  • Helm for consuming/distributing packaged software; Kustomize for your own environments.
