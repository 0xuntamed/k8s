A kubeadm cluster carries about twenty certificates and three CAs, and every one of them exists for a specific conversation: kubectl → API server, API server → etcd, API server → kubelet, kubelet → API server, scheduler → API server. Once you can say who is the client, who is the server, and which CA do they share for each arrow, /etc/kubernetes/pki stops being a pile of files and becomes a map — and expired-certificate outages become ten-minute fixes.

What you'll learn

  • The three CAs: cluster CA, etcd CA, front-proxy CA — and why there are three
  • Every file in /etc/kubernetes/pki and which component uses it as server or client
  • The kubelet's certificates and the kubeconfigs of the control-plane components
  • ServiceAccount signing keys (sa.key/sa.pub) — the one pair that is not X.509
  • Reading and verifying any of them with openssl and kubeadm certs

Every flag above is one row of the table: a serving pair, a client pair, or a CA to verify the other side. The kubeconfigs admin.conf, super-admin.conf, scheduler.conf, controller-manager.conf and kubelet.conf in /etc/kubernetes/ embed the cluster CA plus each component's client cert and key (kubelet.conf points at the rotating file in /var/lib/kubelet/pki).

Kubelet certificates and rotation

The kubelet is special: it bootstraps. On kubeadm join it uses a short-lived bootstrap token to submit a CSR for its client certificate (CN=system:node:<name>, O=system:nodes), which the controller-manager's CSR approver signs automatically. The result is /var/lib/kubelet/pki/kubelet-client-current.pem, valid one year, and with rotateCertificates: true the kubelet renews it itself before expiry. Its serving cert (kubelet.crt) is self-signed by default; enabling serverTLSBootstrap: true makes it request a CA-signed one (needed if you want the API server to verify kubelets, e.g. for metrics-server without --kubelet-insecure-tls).

sa.key / sa.pub: the odd pair out

These are not certificates. sa.key is a plain RSA private key the API server (actually the token controller in kube-controller-manager, plus the API server for TokenRequest) uses to sign ServiceAccount JWTs; sa.pub verifies them. Lose sa.key and every SA token in the cluster becomes invalid at once. Day 37.

$ sudo openssl verify -CAfile /etc/kubernetes/pki/ca.crt /etc/kubernetes/pki/apiserver.crt
$ sudo openssl verify -CAfile /etc/kubernetes/pki/etcd/ca.crt /etc/kubernetes/pki/apiserver-etcd-client.crt

Leaf certificates are issued for 1 year; CAs for 10 years. kubeadm upgrade renews all leaves automatically, so clusters upgraded at least yearly never expire — clusters left alone do, exactly one year after install, all at once. Renewal is on Day 34.

Under the hood · Linux

The control-plane static Pods get these files via hostPath mounts of /etc/kubernetes/pki (read-only) — look at the volumes in kube-apiserver.yaml. Permissions matter: *.key files are 0600 root, certificates 0644. The etcd Pod runs as root and reads pki/etcd; to use etcdctl yourself you pass the same three files: ETCDCTL_API=3 etcdctl --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/healthcheck-client.crt --key=/etc/kubernetes/pki/etcd/healthcheck-client.key endpoint health — which is precisely the "client presents / server presents / both verify against" triple from the table, and the command you will need for etcd backups.

CKA exam tip
  • "Which certificate does the API server use to talk to etcd?" → apiserver-etcd-client.crt. "…to kubelets?" → apiserver-kubelet-client.crt. "What are the SANs of the API server cert?" → openssl x509 -ext subjectAltName.
  • etcdctl needs --cacert --cert --key from pki/etcd/ — memorise the paths; the backup/restore task depends on them.
  • Control plane down + kubelet logs full of "x509: certificate has expired" → kubeadm certs renew all, restart the static Pods, copy the new admin.conf.

Key takeaways

  • Three CAs: cluster (ca.crt), etcd (etcd/ca.crt), front-proxy. Each conversation has a client cert, a server cert and a shared CA.
  • API server: serves with apiserver.crt; is a client with apiserver-kubelet-client, apiserver-etcd-client, front-proxy-client.
  • Kubelets bootstrap their own client certs (CN=system:node:<name>) and rotate them; serving certs are self-signed unless configured.
  • sa.key/sa.pub sign and verify ServiceAccount tokens — not X.509.
  • Leaves last 1 year, CAs 10; kubeadm certs check-expiration is the first command when a cluster "just stopped working".
