A taint is a property of a node that says "do not put Pods here unless they explicitly accept this". A toleration is a property of a Pod that says "I accept that taint". The direction matters: taints repel; tolerations permit. They never attract. That one sentence resolves most of the confusion between taints and the affinity rules of the next lesson.

What you'll learn

  • Taint syntax: key=value:effect and the three effects — NoSchedule, PreferNoSchedule, NoExecute
  • Tolerations with Equal and Exists, and tolerationSeconds
  • The built-in taints Kubernetes applies automatically (control plane, node conditions) and the default tolerations every Pod gets
  • Common uses: dedicated nodes, GPU pools, draining, and the control-plane taint

Taints on nodes

$ kubectl taint nodes worker-1 gpu=true:NoSchedule        # add
$ kubectl taint nodes worker-1 gpu=true:NoSchedule-       # remove (trailing minus)
$ kubectl taint nodes worker-1 gpu-                       # remove all taints with key gpu
$ kubectl describe node worker-1 | grep -A3 Taints
$ kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
EffectNew Pods without a matching tolerationPods already running without one
NoScheduleNot scheduled hereKeep running
PreferNoScheduleAvoided if any other node fits; used as a last resortKeep running
NoExecuteNot scheduled hereEvicted (immediately, or after tolerationSeconds)

Tolerations on Pods

apiVersion: v1
kind: Pod
metadata:
  name: trainer
spec:
  tolerations:
  - key: gpu                # match this taint key
    operator: Equal         # value must match too
    value: "true"
    effect: NoSchedule      # and this effect (omit effect = any effect)
  - key: dedicated
    operator: Exists        # any value, just the key must exist
  - key: node.kubernetes.io/unreachable
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 60   # stay 60 s after the taint appears, then be evicted
  containers:
  - name: trainer
    image: nvidia/cuda
  • A toleration matches a taint when key and effect match and either operator: Exists or Equal with the same value.
  • Empty key with Exists tolerates everything (that is what DaemonSets for monitoring agents use).
  • Tolerating a taint does not force the Pod onto the node — it merely allows it. Other nodes without the taint remain candidates. To also attract, combine with node affinity (Day 18).

Taints Kubernetes adds by itself

node-role.kubernetes.io/control-plane:NoSchedule
kubeadm taints control-plane nodes so ordinary workloads stay off them. Single-node clusters remove it: kubectl taint nodes --all node-role.kubernetes.io/control-plane-. (KIND removes it for you; on the exam it is usually present.)
node.kubernetes.io/not-ready · unreachable
NoExecute taints applied by the node controller when a node's condition changes. This is the mechanism that moves Pods off a dead node.
node.kubernetes.io/memory-pressure · disk-pressure · pid-pressure
NoSchedule, applied by the kubelet when the node is under pressure. New Pods avoid the node; existing ones may be evicted by the kubelet's own eviction logic.
node.kubernetes.io/unschedulable
What kubectl cordon actually sets (spec.unschedulable: true plus this taint).
node.cloudprovider.kubernetes.io/uninitialized
Present until the cloud-controller-manager has initialised the node.
The 300-second default

Every Pod gets two tolerations injected by the DefaultTolerationSeconds admission plugin: not-ready and unreachable, both NoExecute with tolerationSeconds: 300. That is why Pods on a node that goes dark stay "Running" for five minutes before they are evicted and rescheduled. Lower it per Pod if you need faster failover; raise it for workloads that should ride out short network blips.

Typical uses

Dedicated node pool

kubectl taint nodes -l pool=batch dedicated=batch:NoSchedule. Only Pods tolerating dedicated=batch land there. Add node affinity so they land only there.

Special hardware

GPU nodes are tainted nvidia.com/gpu:NoSchedule by the device plugin's installer so cheap web Pods never occupy expensive machines.

Maintenance

kubectl drain = cordon (NoSchedule) + evict everything. Day 55.

Testing NoExecute

Taint a node NoExecute and watch its Pods disappear and reappear elsewhere — a safe way to practise what a node failure looks like.

CKA exam tip
  • Pod Pending, describe says 0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) had untolerated taint {gpu: true} → add a toleration or remove the taint, whichever the task implies.
  • Taint syntax is unforgiving: key=value:Effect, effect capitalised exactly. Removal needs the trailing -.
  • The imperative kubectl run has no toleration flag — generate YAML and add the block under spec.

Hands-on lab (15 min)

$ kubectl taint nodes cka-worker gpu=true:NoSchedule
$ kubectl create deploy web --image=nginx --replicas=4 && kubectl get pods -o wide   # all on worker2 (control-plane may be tainted too)
$ kubectl run t --image=nginx $do | sed '/spec:/a\  tolerations:\n  - key: gpu\n    operator: Equal\n    value: "true"\n    effect: NoSchedule' | kubectl apply -f -
$ kubectl get pod t -o wide                                                        # may land on either node
$ kubectl taint nodes cka-worker gpu=true:NoSchedule- && kubectl taint nodes cka-worker gpu=true:NoExecute
$ kubectl get pods -o wide -w                                                      # untolerating pods on cka-worker are evicted
$ kubectl taint nodes cka-worker gpu-
$ kubectl get pod t -o yaml | grep -B2 -A3 tolerationSeconds                       # the injected 300s defaults

Key takeaways

  • Taints (on nodes) repel; tolerations (on Pods) permit. Neither attracts.
  • NoSchedule blocks new Pods; PreferNoSchedule discourages; NoExecute also evicts running ones (after tolerationSeconds).
  • Kubernetes taints nodes itself for control-plane role, readiness/unreachability and resource pressure; every Pod tolerates not-ready/unreachable for 300 s.
  • For dedicated nodes, pair a taint (keep others out) with node affinity (keep yours in).
