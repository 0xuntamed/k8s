Every Kubernetes object is a JSON document stored in etcd; YAML is just the friendlier way to write it. Learn the handful of YAML rules that matter, the four top-level keys every manifest has, and the three ways to get a manifest into the cluster — because create, replace and apply behave differently in ways that bite later.

What you'll learn

  • YAML in ten minutes: maps, lists, scalars, multi-line strings, and the indentation traps
  • The universal manifest shape: apiVersion, kind, metadata, spec (and the read-only status)
  • kubectl explain and api-resources — never guess a field again
  • Imperative commands vs imperative object config vs declarative apply, and the three-way merge
  • The --dry-run=client -o yaml workflow that the exam is built around

YAML in ten minutes

# a map (key: value)
name: web
replicas: 3            # integer
enabled: true          # boolean
version: "1.21"        # string — quote things that look like numbers!
port: 8080

# nested map: indent with SPACES (2 is the convention), never tabs
metadata:
  name: web
  labels:
    app: web
    tier: frontend
# a list: each item starts with "- "
ports:
- 80
- 443

# a list of maps (the most common shape in Kubernetes)
containers:
- name: nginx
  image: nginx:1.27
- name: sidecar
  image: busybox

# inline forms (same meaning)
args: ["--verbose", "--port=8080"]
labels: {app: web, tier: frontend}
# multi-line strings
script: |            # "|" keeps newlines — for scripts and config files
  #!/bin/sh
  echo hello
  exec nginx
description: >       # ">" folds newlines into spaces — for long prose
  This is one
  long paragraph.
---                  # three dashes separate documents in one file
apiVersion: v1
kind: Service
The traps
  • Tabs are illegal. A tab in indentation gives "found character that cannot start any token". Configure your editor for spaces.
  • Unquoted values get typed. version: 1.10 becomes the float 1.1; enabled: yes may become true; a value like 0755 becomes octal. Quote anything that must stay a string — ports in annotations, versions, tokens.
  • List item indentation is flexible — - name: may sit at the same level as its parent key or two spaces in; both are valid. Just be consistent, and keep the keys inside an item aligned with each other.
  • Keys are case-sensitive. ImagePullPolicy is silently ignored (or rejected with strict validation). It is imagePullPolicy.

The shape of every manifest

apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: default
  labels:
    app: web
  annotations:
    owner: "team-a"
spec:
  containers:
  - name: nginx
    image: nginx:1.27
    ports:
    - containerPort: 80
status:            # you never write this
  phase: Running
  podIP: 10.244.1.7
  • apiVersion — which API group and version the kind belongs to. Core objects (Pod, Service, ConfigMap, Namespace, PV/PVC) are v1; Deployment/ReplicaSet/StatefulSet/DaemonSet are apps/v1; Job/CronJob are batch/v1; Ingress/NetworkPolicy are networking.k8s.io/v1; RBAC is rbac.authorization.k8s.io/v1.
  • kind — the object type. Case matters: Pod, not pod.
  • metadata — identity: name (unique per namespace per kind), namespace, labels (for selection, must be short key=value), annotations (free-form metadata for tools).
  • spec — the desired state; its fields differ per kind. This is what you write and controllers read.
  • status — the observed state written by controllers and kubelets. Present when you get -o yaml, ignored when you apply.

Never guess a field

$ kubectl api-resources                        # every kind, its short name, API group, namespaced?
$ kubectl api-resources --namespaced=false     # cluster-scoped kinds (Node, PV, Namespace, ClusterRole…)
$ kubectl explain pod.spec.containers          # documentation for any path, with types
$ kubectl explain deployment.spec.strategy --recursive   # the whole subtree
$ kubectl explain cronjob.spec.jobTemplate.spec.template.spec.restartPolicy
CKA exam tip

kubectl explain is faster than the docs site and works offline. Memorise the apiVersion of the eight or so kinds above; for anything else, kubectl api-resources | grep -i <name> gives the group in the APIVERSION column.

Three ways to create things

1 · Imperative commands

No file. Tell kubectl what to do right now.

kubectl run web --image=nginx
kubectl create deploy web --image=nginx
kubectl expose deploy web --port=80
kubectl scale deploy web --replicas=3
kubectl set image deploy/web nginx=nginx:1.27
kubectl edit deploy web

Fastest for the exam and for experiments. No record of what you did.

2 · Imperative object config

A file, but you tell kubectl the operation.

kubectl create -f web.yaml    # fails if it exists
kubectl replace -f web.yaml   # fails if it does not; overwrites entirely
kubectl delete -f web.yaml

Predictable, but replace throws away fields other tools added.

3 · Declarative

A file (or directory); kubectl works out the operation.

kubectl apply -f web.yaml
kubectl apply -f ./manifests/
kubectl apply -k ./overlay/    # kustomize
kubectl diff -f web.yaml       # preview

Create if missing, patch if present. The basis of GitOps. Use this for anything you keep.

How apply decides what to change

apply does a three-way merge: it compares (a) the last configuration you applied — stored on the object in the annotation kubectl.kubernetes.io/last-applied-configuration, (b) your new file, and (c) the live object. That is what lets it remove a field you deleted from the file, while leaving alone fields set by other actors (the HPA changing replicas, a defaulter adding imagePullPolicy).

Do not mix them on one object

Objects created with create or run have no last-applied annotation, so the first apply cannot know what you "own" and prints a warning. Objects managed by apply and then edited with kubectl edit or scale will drift back the next time you apply the file — which is correct, and confusing. Pick one style per object; for real systems, pick declarative.

The workflow you will use 100 times

$ export do="--dry-run=client -o yaml"                     # once per session
$ kubectl run web --image=nginx --port=80 $do > pod.yaml   # generate, don't type
$ vim pod.yaml                                             # tweak: add a label, resources, a volume
$ kubectl apply -f pod.yaml
$ kubectl get pod web -o yaml                              # see what the server added (status, defaults)
$ kubectl apply -f pod.yaml --dry-run=server               # validate against the real API, incl. admission

--dry-run=client only renders locally (fast, no cluster needed, no validation of unknown fields). --dry-run=server sends the request and lets the API server validate and run admission, but does not persist. -o yaml prints; -o json, -o wide, -o name, -o jsonpath (Day 59) are the other formats you will use.

Labels, selectors and annotations

Labels are the glue of Kubernetes: Services find Pods by label, ReplicaSets own Pods by label, kubectl get -l filters by label. Annotations are for tools and humans, never for selection.

$ kubectl get pods -l app=web,tier!=cache
$ kubectl get pods -l 'env in (dev,staging)'
$ kubectl label pod web tier=frontend          # add
$ kubectl label pod web tier-                  # remove
$ kubectl annotate pod web note="scaled by hand"
$ kubectl get pods --show-labels
$ kubectl get pods -L app,tier                 # labels as columns

Hands-on lab (10 min)

$ kubectl create deploy web --image=nginx --replicas=2 $do > deploy.yaml
$ kubectl apply -f deploy.yaml
$ kubectl scale deploy web --replicas=4                  # imperative change
$ kubectl get deploy web -o yaml | grep -A1 last-applied   # note: replicas still 2 in the annotation
$ kubectl apply -f deploy.yaml && kubectl get deploy web   # back to 2 — apply enforces the file
$ sed -i 's/replicas: 2/replicas: 3/' deploy.yaml && kubectl diff -f deploy.yaml
$ kubectl explain deploy.spec.template.spec.containers.resources

Key takeaways

  • YAML: spaces not tabs, quote ambiguous scalars, - for list items, | for literal blocks, --- between documents.
  • Every manifest: apiVersion, kind, metadata, spec; status is written by the system.
  • kubectl explain and api-resources replace memorisation.
  • Imperative for speed and experiments; apply (three-way merge) for anything you keep. Don't mix on one object.
  • Generate with --dry-run=client -o yaml, edit, apply, inspect with get -o yaml.
