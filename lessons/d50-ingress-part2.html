On AWS the Ingress controller that matters is the AWS Load Balancer Controller: instead of running a proxy inside the cluster, it turns each Ingress into an Application Load Balancer with listener rules and target groups that point straight at Pod IPs. This lesson deploys two services behind one ALB with path-based routing, and explains the IAM plumbing (IRSA) that lets a Pod create AWS resources. The same manifests work with ingress-nginx on KIND — only the class and annotations change.

What you'll learn

  • How the AWS LB Controller maps Ingress → ALB → listener rules → target groups
  • IRSA: giving the controller's ServiceAccount an IAM role
  • Installing the controller with Helm and the alb IngressClass
  • Path-based routing to two Services with the annotations that matter
  • Verifying in the AWS console and with curl; the equivalent on KIND

Prerequisites: IRSA

The controller calls the AWS API (elasticloadbalancing:*, ec2:Describe*…). It needs credentials, and the right way is IAM Roles for Service Accounts: the cluster's OIDC issuer is registered with IAM, the controller's ServiceAccount is annotated with a role ARN, and AWS STS exchanges the Pod's projected token (Day 37) for temporary AWS credentials. No access keys anywhere.

$ eksctl utils associate-iam-oidc-provider --cluster cka --approve
$ curl -o iam-policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json
$ aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy --policy-document file://iam-policy.json
$ eksctl create iamserviceaccount --cluster cka --namespace kube-system --name aws-load-balancer-controller \
    --attach-policy-arn arn:aws:iam::<acct>:policy/AWSLoadBalancerControllerIAMPolicy --approve
$ kubectl -n kube-system get sa aws-load-balancer-controller -o yaml | grep role-arn     # eks.amazonaws.com/role-arn: …

Install the controller

$ helm repo add eks https://aws.github.io/eks-charts && helm repo update
$ helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system \
    --set clusterName=cka --set serviceAccount.create=false --set serviceAccount.name=aws-load-balancer-controller
$ kubectl -n kube-system rollout status deploy/aws-load-balancer-controller
$ kubectl get ingressclass                      # alb
# subnets must be tagged so the controller can pick them:
#   public:  kubernetes.io/role/elb=1        private: kubernetes.io/role/internal-elb=1

Two services, one ALB

$ kubectl create ns shop
$ kubectl create deploy web --image=nginx -n shop --port=80 && kubectl expose deploy web --port=80 -n shop
$ kubectl create deploy api --image=hashicorp/http-echo -n shop --port=5678 -- -text="hello from api" && kubectl expose deploy api --port=5678 -n shop
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing       # or internal
    alb.ingress.kubernetes.io/target-type: ip               # pods as targets (needs VPC CNI); "instance" = NodePort
    alb.ingress.kubernetes.io/healthcheck-path: /
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}]'
    alb.ingress.kubernetes.io/group.name: shop              # optional: share one ALB across several Ingresses
spec:
  ingressClassName: alb
  rules:
  - http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service: {name: api, port: {number: 5678}}
      - path: /
        pathType: Prefix
        backend:
          service: {name: web, port: {number: 80}}
$ kubectl apply -f ingress.yaml
$ kubectl get ingress -n shop -w                # ADDRESS fills in after ~2 min: k8s-shop-shop-abc123-1234567890.eu-west-1.elb.amazonaws.com
$ ALB=$(kubectl get ingress shop -n shop -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
$ curl -s http://$ALB/api            # hello from api
$ curl -s http://$ALB/ | head -3     # nginx welcome page
$ kubectl get targetgroupbindings -n shop        # one per backend service
$ kubectl -n kube-system logs deploy/aws-load-balancer-controller --tail=20   # "created loadBalancer", "created targetGroup", "registered targets"

In the AWS console: EC2 → Load Balancers shows the ALB; its HTTP:80 listener has rules — priority 1: path-pattern /api* → target group api; priority 2: /* → web; default → 404. Each target group lists Pod IPs with health status. Scale the Deployment and targets appear; delete a Pod and its target drains.

Path ordering

ALB evaluates rules by priority; the controller orders them so that more specific paths come first — but Prefix on the ALB is implemented as /api*, which also matches /apix. If that matters, use Exact or a trailing slash. On ingress-nginx the standard Prefix semantics (path-segment boundary) apply. This kind of controller-specific behaviour is why the Gateway API (Day 52) specifies matching precisely.

The same thing on KIND / ingress-nginx

$ kubectl create ingress shop -n shop --class=nginx --rule="/api*=api:5678" --rule="/*=web:80"
$ curl -s localhost/api; curl -s localhost/ | head -3          # via the Day 8 port mappings

Identical rules; the difference is who proxies (nginx Pods vs an ALB) and which annotations exist. Keep Ingress specs portable by putting only routing in spec and controller specifics in annotations that a Kustomize overlay can swap.

Useful annotations (AWS LB Controller)

AnnotationPurpose
alb.ingress.kubernetes.io/schemeinternet-facing or internal
alb.ingress.kubernetes.io/target-typeip (Pods) or instance (NodePort)

alb.ingress.kubernetes.io/listen-ports'[{"HTTP":80},{"HTTPS":443}]'
alb.ingress.kubernetes.io/certificate-arn, ssl-redirectTLS (Day 51)

alb.ingress.kubernetes.io/subnets, security-groups, load-balancer-attributesOverride auto-discovery; access logs, idle timeout, deletion protection
alb.ingress.kubernetes.io/actions.<name>Redirects, fixed responses, weighted target groups (canary)
CKA exam tip

The exam is cloud-agnostic — you will see ingress-nginx or similar, never an ALB. What transfers: ingressClassName, path rules with pathType, backend Service/port in the same namespace, and reading kubectl describe ingress to confirm backends resolve to endpoints. If ADDRESS stays empty, the controller is not processing the object (wrong class or controller down).

Hands-on lab (30 min, EKS) — or 10 min on KIND

# EKS
$ eksctl create cluster --name cka --region eu-west-1 --nodes 2 --node-type t3.medium   # ~15 min
# … IRSA + helm install from above …
$ kubectl apply -f ingress.yaml && kubectl get ingress -n shop -w
$ ALB=$(kubectl get ingress shop -n shop -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'); curl -s http://$ALB/api
$ kubectl scale deploy api -n shop --replicas=3; aws elbv2 describe-target-health --target-group-arn $(aws elbv2 describe-target-groups --query 'TargetGroups[?contains(TargetGroupName,`api`)].TargetGroupArn' --output text)
$ kubectl delete ingress shop -n shop            # the ALB is deleted too (watch the controller log)
$ eksctl delete cluster --name cka               # do not forget — ALBs and nodes cost money
# KIND: see "The same thing on KIND" above

Key takeaways

  • AWS LB Controller turns an Ingress into an ALB with listener rules and target groups of Pod IPs; nothing proxies inside the cluster.
  • It needs an IAM role via IRSA (OIDC + annotated ServiceAccount) and tagged subnets.
  • Path-based routing: rules in spec, AWS specifics in alb.ingress.kubernetes.io/* annotations; group.name shares one ALB.
  • Same Ingress spec works on ingress-nginx with a different class — keep specs portable.
