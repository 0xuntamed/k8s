GitOps and Argo CD

You have used kubectl apply and Helm from a terminal. In production nobody should: the source of truth for what runs in the cluster should be a git repository, and something should continuously make the cluster match it. That is GitOps, and Argo CD is the standard implementation — and it is, once again, a controller with a CRD (Day 40).

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/acme/platform
    targetRevision: main
    path: apps/shop/overlays/prod        # Kustomize overlay (Day 42) — or a Helm chart with values
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true                        # delete objects removed from git
      selfHeal: true                     # revert manual kubectl changes
    syncOptions: [CreateNamespace=true]
$ kubectl create ns argocd && kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
$ kubectl -n argocd port-forward svc/argocd-server 8080:443     # UI; password: kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
$ argocd app create shop --repo … --path … --dest-namespace shop --dest-server https://kubernetes.default.svc --sync-policy automated
$ argocd app get shop; argocd app diff shop; argocd app sync shop; argocd app history shop; argocd app rollback shop 3
  • Reconcile loop: every 3 minutes (and on webhook) Argo renders the source (plain YAML, Kustomize, Helm, Jsonnet), compares with the live objects (a three-way diff like kubectl apply, Day 9), and reports Synced/OutOfSync and Healthy/Degraded per resource. With automated it applies; with selfHeal it undoes drift.
  • Rollback = point at an older git commit. Audit log = git log. Access control = who can merge.
  • Multi-cluster: one Argo CD manages many clusters via kubeconfigs stored as Secrets; ApplicationSet generates Applications from templates (one per cluster, per directory, per PR).
  • Alternatives: Flux (same idea, more Kubernetes-native CRDs, no UI by default).

GitHub Actions (C2–C3) and Jenkins, standalone and on Kubernetes with Pod agents and kaniko (C4–C5), each get their own pages in the track — and C10 wires CI, the registry, git and Argo CD into one pull-request-to-production pipeline.

CI: Jenkins (and everything like it)

Argo CD deploys what is in git; something has to put it there. A CI pipeline builds the image from source (Days 2–5), tests it, pushes it to a registry with an immutable tag, and then commits the new tag into the manifests repository — which Argo CD notices. Jenkins is the veteran (a controller + agents running pipeline stages, often as Kubernetes Pods via the Kubernetes plugin); GitHub Actions, GitLab CI, Tekton and Argo Workflows do the same job.

pipeline {
  agent { kubernetes { yaml '''
    spec:
      containers:
      - name: kaniko
        image: gcr.io/kaniko-project/executor:debug
        command: [sleep]; args: [infinity]
        volumeMounts: [{name: regcred, mountPath: /kaniko/.docker}]
      volumes: [{name: regcred, secret: {secretName: regcred, items: [{key: .dockerconfigjson, path: config.json}]}}]
  ''' } }
  environment { TAG = "${env.GIT_COMMIT.take(7)}" }
  stages {
    stage('Test')  { steps { sh 'make test' } }
    stage('Build') { steps { container('kaniko') { sh "/kaniko/executor --context . --destination ghcr.io/acme/api:${TAG}" } } }   // build without a Docker daemon
    stage('Promote') { steps { sh """
      git clone https://github.com/acme/platform && cd platform
      cd apps/api/overlays/prod && kustomize edit set image ghcr.io/acme/api=ghcr.io/acme/api:${TAG}
      git commit -am "api ${TAG}" && git push
    """ } }
  }
}

Notice how much of the course this touches: a Pod template for the agent (Day 21), an imagePullSecrets-style Secret (Day 45), building images without root (kaniko, because privileged is off — Day 41), a Kustomize overlay (Day 42), and git as the handoff to the deploy controller. CI builds and proposes; CD (Argo) applies and reconciles. Keeping them separate is the whole GitOps idea.

Two weeks to the exam

Week 1 — rebuild the muscle

  • Days 54–58 on real VMs: init, join, break, fix, upgrade, etcd backup/restore. Twice.
  • Re-do every lab from Modules 3, 4, 6, 8 and 11 with only the docs site open.
  • Time yourself: a Deployment + Service + Ingress + NetworkPolicy in under 8 minutes.

Week 2 — simulate

  • killer.sh (two sessions come with the exam). Score, review every mistake, redo.
  • Killercoda CKA scenarios for troubleshooting reps.
  • Last two days: light review of the cheatsheet, aliases, vim settings. Sleep.
Day-of checklist
  • First 60 seconds: alias k=kubectl, export do="--dry-run=client -o yaml", export now="--force --grace-period=0", ~/.vimrc with set ts=2 sw=2 et.
  • Every question: kubectl config use-context … as given, read the namespace, note the exact names.
  • Flag and skip anything over ~8 minutes; come back. Partial credit exists; unfinished questions at the end score zero.
  • Verify each answer with a get/describe/auth can-i/curl before moving on.
  • Node tasks: ssh node, sudo -i, do the work, exit back — commands run on the wrong host are the classic silent failure.

Security specialist (requires CKA): cluster hardening, image scanning (Trivy), runtime security (Falco), audit logs, network policy depth, secrets management, supply chain. Modules 8 and 11 are the base.

The ecosystem

Service mesh (Istio/Linkerd/Cilium mesh), Crossplane (cloud resources as CRDs), KEDA, Karpenter, Backstage, cluster API. Each one is a controller with CRDs — you know how to read them now.

Key takeaways

  • GitOps: git is the desired state, a controller (Argo CD / Flux) reconciles the cluster to it, rollback is a revert.
  • CI (Jenkins or any) builds and pushes images and updates manifests; CD applies them. Keep the roles separate.
  • Both bonus courses are applications of what you already know: controllers, CRDs, Kustomize/Helm, Pods, Secrets.
  • Practise troubleshooting on real nodes and take the simulators before the exam; set aliases first, verify every answer.
