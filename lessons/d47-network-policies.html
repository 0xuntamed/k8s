By default every Pod can talk to every other Pod in the cluster, across namespaces, on every port. A NetworkPolicy is a firewall rule attached to a set of Pods: once any policy selects a Pod, that Pod only accepts (or sends) the traffic some policy explicitly allows. The rules are enforced by the CNI plugin, not by Kubernetes itself — and that one fact explains the most common surprise: policies that do nothing because the CNI ignores them.

What you'll learn

  • The model: allow-all until selected, then default-deny plus allow rules; policies are additive
  • podSelector, policyTypes, ingress/egress with podSelector, namespaceSelector, ipBlock, ports
  • The AND/OR semantics of from/to lists that trip everyone
  • Standard patterns: default deny, allow DNS, allow from ingress controller, tier-to-tier
  • Testing policies and knowing whether your CNI enforces them

The model

  • A Pod is unrestricted until at least one NetworkPolicy in its namespace selects it (via spec.podSelector) for a given direction.
  • Once selected for ingress, only connections matching some policy's ingress rule are accepted. Same for egress. The directions are independent.
  • Policies are additive: the allowed set is the union of all matching policies' rules. There is no deny rule and no ordering.
  • Policies are namespaced and can only select Pods in their own namespace — but their rules can refer to peers in other namespaces.
  • Established connections are stateful: allowing ingress to port 80 also allows the replies out, without an egress rule.

The spec

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-policy
  namespace: shop
spec:
  podSelector:                  # WHICH pods this policy applies to
    matchLabels: {app: api}
  policyTypes: [Ingress, Egress] # which directions this policy restricts
  ingress:
  - from:                       # a list of PEERS (OR-ed)
    - podSelector:              # same namespace, label app=web
        matchLabels: {app: web}
    - namespaceSelector:        # any pod in namespaces labelled team=ops
        matchLabels: {team: ops}
    - namespaceSelector:        # AND within one item: pods labelled app=monitor
        matchLabels: {name: monitoring}
      podSelector:              #   IN namespaces labelled name=monitoring
        matchLabels: {app: prometheus}
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector:
        matchLabels: {app: db}
    ports:
    - port: 5432
  - to:                         # DNS: without this, name resolution breaks
    - namespaceSelector: {}     # any namespace
      podSelector:
        matchLabels: {k8s-app: kube-dns}
    ports:
    - {protocol: UDP, port: 53}
    - {protocol: TCP, port: 53}
  - to:
    - ipBlock:
        cidr: 10.0.0.0/8
        except: [10.0.5.0/24]
  • podSelector — {} selects every Pod in the namespace. Required (may be empty).
  • policyTypes — if omitted, Ingress is implied, plus Egress only if an egress section exists. Set it explicitly.
  • ingress[].from / egress[].to — each list item is a peer. Items are OR-ed. Inside one item, namespaceSelector + podSelector are AND-ed ("pods matching X in namespaces matching Y"). Note the YAML: a - before podSelector starts a new item (OR); no dash means same item (AND).
  • ports — apply to that rule; omitted = all ports. endPort for ranges. Named ports allowed.
  • ipBlock — CIDR for traffic outside the cluster (or node IPs). Pod IPs are unreliable here because of NAT; use selectors for Pods.
  • An empty rule (ingress: [{}]) allows everything in that direction; an empty list (ingress: []) or a missing key with the type set allows nothing.

Patterns you will actually write

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny, namespace: shop}
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-dns, namespace: shop}
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector:
        matchLabels: {kubernetes.io/metadata.name: kube-system}
      podSelector:
        matchLabels: {k8s-app: kube-dns}
    ports: [{protocol: UDP, port: 53}, {protocol: TCP, port: 53}]
spec:
  podSelector: {matchLabels: {app: web}}
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels: {kubernetes.io/metadata.name: ingress-nginx}
    ports: [{port: 8080}]
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: {}     # any pod in THIS namespace

The label kubernetes.io/metadata.name=<ns> is set automatically on every namespace, so you can select a namespace by name without adding your own labels.

Under the hood · Linux

A NetworkPolicy becomes packet-filter rules on every node hosting a selected Pod. Calico (iptables mode) programs chains named cali-pi-…/cali-po-… per policy, attached to the Pod's veth via the cali-fw-/cali-tw- chains, using ipsets that Calico keeps updated with the IPs of Pods matching each selector — so a new Pod matching app=web is allowed within milliseconds without touching the rules. Cilium does the same with eBPF programs attached to the veth, matching on identities (numeric labels-sets carried in packets) instead of IPs. Either way, the policy is enforced at the Pod's network interface on the node — which is why it applies to traffic that never leaves the node, and why iptables -L / cilium policy get on the node is the ground truth when debugging.

Testing

$ kubectl get netpol -n shop; kubectl describe netpol api-policy -n shop        # human-readable rule summary
$ kubectl run t --rm -it --image=nicolaka/netshoot -n shop -- sh                # then: curl -m2 api:8080 / nc -zv db 5432 / nslookup api
$ kubectl run t --rm -it --image=busybox:1.36 -n other --labels=app=web -- wget -qO- --timeout=2 http://api.shop:8080
# a policy "not working": is the CNI enforcing? does podSelector match? (kubectl get pods --show-labels) — dash vs no-dash in from:?
# with Calico: kubectl logs -n calico-system -l k8s-app=calico-node | grep -i denied   (if flow logging is enabled)
# with Cilium: hubble observe --verdict DROPPED
CKA exam tip
  • Exam clusters use a policy-capable CNI. The classic task: "allow only Pods with label X in namespace Y to reach the db Pods on port 5432". Write podSelector for db, policyTypes: [Ingress], one from item with namespaceSelector + podSelector in the same item (no dash between them), and ports.
  • Always set policyTypes explicitly. If omitted it defaults to [Ingress] (plus Egress only when an egress section exists) — so a policy with only egress rules and no policyTypes also default-denies ingress to the selected Pods, which is rarely what you meant.
  • Default-deny questions: podSelector: {} + policyTypes, nothing else. Then remember DNS.
  • Copy the YAML skeleton from the docs "Network Policies" page — the from/to indentation is the whole difficulty.

Hands-on lab (25 min) — needs a policy-capable CNI

$ kubectl create ns shop && kubectl label ns shop tier=app
$ kubectl create deploy web --image=nginx -n shop && kubectl expose deploy web --port=80 -n shop
$ kubectl create deploy api --image=nginx -n shop && kubectl expose deploy api --port=80 -n shop
$ kubectl run t --rm -it --image=busybox:1.36 -n shop -- wget -qO- --timeout=2 http://api | head -1     # works: allow-all
$ kubectl apply -n shop -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny}
spec: {podSelector: {}, policyTypes: [Ingress, Egress]}
EOF
$ kubectl run t --rm -it --image=busybox:1.36 -n shop -- wget -qO- --timeout=2 http://api      # times out (and DNS fails too)
$ kubectl apply -n shop -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-dns}
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to: [{namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}, podSelector: {matchLabels: {k8s-app: kube-dns}}}]
    ports: [{protocol: UDP, port: 53}, {protocol: TCP, port: 53}]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: web-to-api}
spec:
  podSelector: {matchLabels: {app: api}}
  policyTypes: [Ingress]
  ingress:
  - from: [{podSelector: {matchLabels: {app: web}}}]
    ports: [{port: 80}]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: web-egress}
spec:
  podSelector: {matchLabels: {app: web}}
  policyTypes: [Egress]
  egress:
  - to: [{podSelector: {matchLabels: {app: api}}}]
    ports: [{port: 80}]
EOF
$ kubectl exec -n shop deploy/web -- curl -s -m2 http://api | head -1        # works: web → api allowed both ways
$ kubectl run t --rm -it --image=busybox:1.36 -n shop -- wget -qO- --timeout=2 http://api   # still blocked: t is not app=web
$ kubectl run t --rm -it --image=busybox:1.36 -n shop --labels=app=web -- wget -qO- --timeout=2 http://api | head -1   # works
$ kubectl delete ns shop

Key takeaways

  • No policy = allow all. Any policy selecting a Pod = default deny for that direction + the union of allow rules.
  • from/to items are OR; namespaceSelector + podSelector in one item are AND. Watch the dash.
  • Start with default-deny, then allow DNS, then allow tier-to-tier and from the ingress controller.
  • Enforcement is the CNI's job (Calico, Cilium yes; Flannel, old kindnet no). Test with a throwaway Pod.
