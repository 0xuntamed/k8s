Day 30 left one hole: when a server sends its public key, how do you know it is really the server's and not an attacker's? The answer is a certificate — a public key bundled with a name and signed by a Certificate Authority you already trust. This lesson builds that idea up from a man-in-the-middle attack, through CA hierarchies and the TLS 1.3 handshake, to the three kinds of CA you will meet: public, private, and self-signed. Kubernetes runs its own private CA; by the end of this page you will know exactly why.

What you'll learn

  • The man-in-the-middle problem that raw public keys cannot solve
  • What is inside an X.509 certificate and what a CA signature proves
  • Root → intermediate → leaf chains, trust stores, and expiry
  • The TLS 1.3 handshake step by step
  • Public CAs vs private CAs vs self-signed certificates — and which Kubernetes uses

The attack certificates prevent

You connect to bank.com. Something on the path (a rogue Wi-Fi router, a compromised ISP) intercepts, sends you its own public key, and forwards your traffic to the real bank with its own connection. Your encryption works perfectly — with the attacker. Raw public keys carry no proof of whose they are. You need a third party both sides trust to vouch: "this public key belongs to bank.com".

What a certificate is

$ openssl x509 -in server.crt -noout -text
Certificate:
    Data:
        Version: 3
        Serial Number: 4c:1f:…
        Signature Algorithm: sha256WithRSAEncryption
        Issuer: CN=kubernetes                      ← who signed it (the CA)
        Validity
            Not Before: Jan  1 00:00:00 2025 GMT
            Not After : Jan  1 00:00:00 2026 GMT   ← expiry — the #1 cause of outages
        Subject: CN=kube-apiserver                 ← who it identifies
        Subject Public Key Info:                   ← the public key
            Public Key Algorithm: rsaEncryption
        X509v3 extensions:
            X509v3 Subject Alternative Name:       ← every name/IP it is valid for
                DNS:kubernetes, DNS:kubernetes.default.svc, DNS:kubernetes.default.svc.cluster.local, IP Address:10.96.0.1, IP Address:192.168.1.10
            X509v3 Extended Key Usage: TLS Web Server Authentication
    Signature Value: 3a:9b:…                       ← CA's signature over everything above

A certificate is the public key, the subject (CN and SANs — clients match the hostname against SANs, not CN), a validity window, usage flags (server auth, client auth), and the issuer's signature over all of it. Anyone can read it; nobody can alter it without breaking the signature; and only the matching private key can prove ownership during a handshake.

Certificate Authorities and chains

Root CA
A key pair whose certificate is self-signed. Trust in it is not derived — it is installed: in browsers, operating systems, and in every Kubernetes component's config. Public roots keep the private key offline in hardware modules and use it only to sign intermediates.
Intermediate CA
Signed by the root; does the day-to-day signing. If compromised, only it is revoked, not the root. Servers send their leaf and the intermediates so clients can build the chain up to a root they hold.
Leaf (end-entity)
The server's or client's certificate. Cannot sign other certificates (CA:FALSE).
Trust store
The set of root certificates a client accepts: /etc/ssl/certs, the browser's list, or a single ca.crt passed to a program. Verification = "can I build a valid signature chain from this leaf to something in my store, with every link unexpired and name-matching?"
$ openssl verify -CAfile ca.crt server.crt                 # server.crt: OK
$ openssl verify -CAfile ca.crt -untrusted intermediate.crt server.crt
$ openssl s_client -connect example.com:443 -showcerts < /dev/null 2>/dev/null | grep -E 's:|i:'   # the chain as sent

The TLS 1.3 handshake

TLS 1.3 (2018) removed everything weak and folded key exchange into the first flight: one round trip and the connection is encrypted. The server proves two things — that its certificate chains to a CA you trust (identity), and that it holds the matching private key (possession, via the CertificateVerify signature). Older TLS 1.2 needed two round trips and could negotiate RSA key exchange without forward secrecy; 1.3 always uses ephemeral Diffie-Hellman, so a stolen private key cannot decrypt past traffic.

Mutual authentication (preview)

In the handshake above only the server presented a certificate; the client is anonymous (or identifies later with a password/cookie). TLS also allows the server to send a CertificateRequest, after which the client presents its own certificate and signs the transcript with its private key. Both sides are then cryptographically identified — mTLS. This is how every Kubernetes component talks to the API server, and it is Day 32.

Three kinds of CA

Public CA

Let's Encrypt, DigiCert, GlobalSign. Their roots are pre-installed everywhere, so any browser trusts what they sign. They only sign certificates for public DNS names you can prove you control (ACME challenges). Used for: anything on the internet — your Ingress on Day 51.

Private (internal) CA

Your own root key, trusted only by systems you configure. You can sign any name — kube-apiserver, 10.96.0.1, etcd-peer — for free, instantly, with any validity. Used for: everything inside a Kubernetes cluster. kubeadm creates one at /etc/kubernetes/pki/ca.crt.

Self-signed certificate

A leaf that signs itself; issuer = subject. Nobody trusts it unless they pin that exact certificate. Fine for a quick lab, a problem in production because every client needs the specific cert, not a CA. A root CA is technically self-signed too — the difference is that it is meant to be a trust anchor and signs other things.

Mental model

"Trust" in TLS is a configuration decision, not a property of math. Math only proves "this signature was made by the key that matches this public key". Deciding which public keys may vouch for names is what a trust store is — and inside a cluster, that store is one file, ca.crt, handed to every component. Day 33 shows exactly which components hold which CA.

Under the hood · Linux

Build a private CA in four commands and you will never be confused by /etc/kubernetes/pki again:

$ openssl genrsa -out ca.key 4096
$ openssl req -x509 -new -key ca.key -days 3650 -subj "/CN=my-root-ca" -out ca.crt       # self-signed root
$ openssl genrsa -out server.key 2048
$ openssl req -new -key server.key -subj "/CN=api.internal" -addext "subjectAltName=DNS:api.internal,IP:10.0.0.5" -out server.csr
$ openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 365 -copy_extensions copy -out server.crt
$ openssl verify -CAfile ca.crt server.crt      # OK — and any client given ca.crt will trust server.crt

kubeadm does exactly this (in Go) for the cluster CA, the etcd CA and the front-proxy CA. The OpenSSL page covers inspecting, verifying and debugging.

CKA exam tip
  • Know how to read a cert: openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -text | grep -A2 -E 'Subject:|Not After|Alternative'. Questions about "which names is the API server cert valid for" and "when does it expire" are common.
  • "Certificate signed by unknown authority" in kubectl = the client's CA (in kubeconfig) does not match what signed the server cert. "x509: certificate has expired" = renew (Day 34).

Hands-on lab (15 min)

# build a CA and a server cert with the commands above, then:
$ openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName
$ openssl verify server.crt                     # fails: no trust store contains my-root-ca
$ openssl verify -CAfile ca.crt server.crt      # OK
# run a TLS server and connect with/without the CA
$ openssl s_server -accept 8443 -cert server.crt -key server.key -www &
$ curl -s https://localhost:8443 | head -2      # SSL certificate problem: unable to get local issuer certificate
$ curl -s --cacert ca.crt --resolve api.internal:8443:127.0.0.1 https://api.internal:8443 | head -2   # works: CA trusted, SAN matches
$ kill %1
# a real cluster's cert
$ docker exec cka-control-plane openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -subject -issuer -ext subjectAltName -dates

Key takeaways

  • A certificate binds a public key to a name (CN/SANs) with a validity window, signed by a CA. Clients verify the chain against a trust store and the name against the SANs.
  • Root (installed, offline) → intermediate (signs daily) → leaf (server/client). Trust is configured, not computed.
  • TLS 1.3: one round trip; ephemeral DH for the session key; server proves identity (chain) and possession (signature).
  • Public CAs for internet names; a private CA for everything inside a cluster (kubeadm's ca.crt); self-signed only for labs.
