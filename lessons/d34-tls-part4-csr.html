A new engineer, Jane, needs access to the cluster. Kubernetes has no user database, so "creating a user" means: Jane generates a key pair, sends a Certificate Signing Request containing her public key and desired name, the cluster CA signs it, and the resulting certificate goes into her kubeconfig. Kubernetes has a first-class API object for the middle step so you never have to hand the CA private key to anyone. This is also the lesson on renewing the cluster's own certificates before they expire.

What you'll learn

  • What a CSR contains and why it is safe to send
  • The CertificateSigningRequest API: signers, usages, approval, retrieval
  • Building a working kubeconfig for the new user and binding RBAC
  • Manual signing with the CA key (the openssl equivalent)
  • Renewing and rotating cluster certificates with kubeadm certs

Step 1 — Jane generates a key and a CSR

$ openssl genrsa -out jane.key 2048
$ openssl req -new -key jane.key -subj "/CN=jane/O=developers/O=payments" -out jane.csr
$ openssl req -in jane.csr -noout -subject     # subject=CN = jane, O = developers, O = payments

The CSR holds Jane's public key, the requested Subject (CN → username, each O → a group), and a signature made with her private key proving she holds it. The private key never leaves her machine; the CSR can be emailed in the clear. Whoever signs it decides whether to honour the requested subject — approval is where the security lives.

Step 2 — Submit a CertificateSigningRequest object

$ cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: jane
spec:
  request: $(base64 -w0 jane.csr)               # the PEM CSR, base64-encoded
  signerName: kubernetes.io/kube-apiserver-client   # "sign with the cluster CA, for client auth"
  expirationSeconds: 7776000                    # 90 days (optional; default 1 year, signer may cap)
  usages:
  - client auth
EOF
$ kubectl get csr
NAME   AGE   SIGNERNAME                            REQUESTOR          REQUESTEDDURATION   CONDITION
jane   5s    kubernetes.io/kube-apiserver-client   kubernetes-admin   90d                 Pending
signerName
Which built-in signer handles it. kubernetes.io/kube-apiserver-client — client certs for users (needs manual approval). kubernetes.io/kube-apiserver-client-kubelet — kubelet client certs (auto-approved for bootstrap tokens and node identities). kubernetes.io/kubelet-serving — kubelet serving certs. kubernetes.io/legacy-unknown — no signer; for external CAs.
usages
Must include client auth for a client cert (server auth for serving). The signer rejects mismatches.
request
Base64 of the PEM. base64 -w0 (GNU) or base64 | tr -d '\n' — newlines break it.

Step 3 — An admin approves; the CA signs

$ kubectl describe csr jane            # review Subject: CN=jane O=developers O=payments — is that what she should get?
$ kubectl certificate approve jane     # or: kubectl certificate deny jane
$ kubectl get csr jane                 # CONDITION: Approved,Issued

Approval is an RBAC-protected action (certificatesigningrequests/approval, held by cluster-admin). Once approved, the csrsigning controller in kube-controller-manager — which holds ca.key via --cluster-signing-cert-file/--cluster-signing-key-file — signs the certificate and writes it into status.certificate. Nobody had to touch the CA key by hand.

Step 4 — Retrieve the certificate and build the kubeconfig

$ kubectl get csr jane -o jsonpath='{.status.certificate}' | base64 -d > jane.crt
$ openssl x509 -in jane.crt -noout -subject -issuer -dates      # issuer=CN=kubernetes; 90 days

# give Jane a kubeconfig (do this on her machine with her key, or hand her the file securely)
$ kubectl config set-cluster prod --server=https://10.0.0.10:6443 --certificate-authority=ca.crt --embed-certs=true --kubeconfig=jane.kubeconfig
$ kubectl config set-credentials jane --client-certificate=jane.crt --client-key=jane.key --embed-certs=true --kubeconfig=jane.kubeconfig
$ kubectl config set-context jane@prod --cluster=prod --user=jane --namespace=payments --kubeconfig=jane.kubeconfig
$ kubectl config use-context jane@prod --kubeconfig=jane.kubeconfig
$ kubectl --kubeconfig=jane.kubeconfig auth whoami          # jane [developers payments system:authenticated]
$ kubectl --kubeconfig=jane.kubeconfig get pods              # Forbidden — authenticated but not authorized

Step 5 — Authorize

A valid certificate only gets Jane through authentication. Every request is still 403 Forbidden until RBAC grants something to user jane or group developers:

$ kubectl create rolebinding dev-edit --clusterrole=edit --group=developers -n payments
$ kubectl --kubeconfig=jane.kubeconfig get pods              # works, in payments only

Groups in the certificate are the scalable way to do this — bind roles to developers once; every cert with O=developers inherits them. Day 36 is all about that.

The manual alternative: sign with openssl

If you hold ca.key (you are on the control-plane node), you can skip the API:

$ sudo openssl x509 -req -in jane.csr -CA /etc/kubernetes/pki/ca.crt -CAkey /etc/kubernetes/pki/ca.key -CAcreateserial -days 90 -out jane.crt
$ openssl verify -CAfile /etc/kubernetes/pki/ca.crt jane.crt    # OK — identical result

Same certificate, same trust. The CSR API exists so that approval can be delegated, audited (kubectl get csr is a log of every issued identity) and automated (kubelets, cert-manager) without copying the CA key around.

Renewing the cluster's own certificates

$ sudo kubeadm certs check-expiration                   # anything under a few weeks? renew
$ sudo kubeadm certs renew all                           # rewrites every leaf under /etc/kubernetes/pki and the *.conf kubeconfigs
$ sudo kubeadm certs renew apiserver                     # or one at a time
# the static pods must be restarted to load the new files:
$ sudo mv /etc/kubernetes/manifests/*.yaml /tmp/ && sleep 20 && sudo mv /tmp/*.yaml /etc/kubernetes/manifests/
# (or just restart the kubelet: systemctl restart kubelet — it re-reads the manifests)
$ sudo cp /etc/kubernetes/admin.conf ~/.kube/config     # admin.conf was renewed too
$ kubectl get nodes
  • kubeadm upgrade (Day 55) renews all certs implicitly, so a cluster upgraded yearly never expires.
  • Kubelet client certs rotate themselves (rotateCertificates: true); the API server auto-approves those CSRs.
  • The CAs (10 years) are not renewed by renew all; rotating a CA is a documented multi-step procedure — plan it before year 9.
  • Expired cert symptoms: every kubectl call fails with x509: certificate has expired or is not yet valid; kubelets go NotReady; the API server may refuse to start. Fix from the node with the commands above; if kubectl is dead, kubeadm certs renew still works because it only needs files.
Under the hood · Linux

Inspect a CSR before approving: kubectl get csr jane -o jsonpath='{.spec.request}' | base64 -d | openssl req -noout -text shows the subject, public key and any requested extensions. The signer ignores requested SANs and key usages beyond what the signerName allows — you cannot smuggle CA:TRUE or a server-auth cert through the client signer. Certificates have no revocation in Kubernetes: to "remove" Jane you remove her RBAC bindings (instant) and let the cert expire — which is why short expirationSeconds matter for humans and why OIDC (Day 37) is preferred for user identity at scale.

CKA exam tip
  • Full flow to memorise: openssl genrsa → openssl req -new -subj "/CN=name" → CSR object with signerName: kubernetes.io/kube-apiserver-client, usages: [client auth], request: $(base64 -w0) → kubectl certificate approve → get csr -o jsonpath='{.status.certificate}' | base64 -d → set-credentials → RBAC.
  • Forgetting -w0 (or leaving newlines in the base64) is the #1 reason the CSR is rejected on create.
  • "Renew certificates" → kubeadm certs renew all + restart static Pods + refresh admin kubeconfig.

Hands-on lab (20 min)

$ openssl genrsa -out jane.key 2048 && openssl req -new -key jane.key -subj "/CN=jane/O=developers" -out jane.csr
$ kubectl apply -f - <<EOF
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata: {name: jane}
spec:
  request: $(base64 -w0 jane.csr)
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages: [client auth]
EOF
$ kubectl get csr jane; kubectl certificate approve jane; kubectl get csr jane
$ kubectl get csr jane -o jsonpath='{.status.certificate}' | base64 -d > jane.crt
$ openssl x509 -in jane.crt -noout -subject -issuer -enddate
$ kubectl config set-credentials jane --client-certificate=jane.crt --client-key=jane.key --embed-certs=true
$ kubectl config set-context jane --cluster=$(kubectl config view --minify -o jsonpath='{.contexts[0].context.cluster}') --user=jane
$ kubectl --context=jane auth whoami
$ kubectl --context=jane get pods                        # Forbidden
$ kubectl create rolebinding jane-view --clusterrole=view --user=jane
$ kubectl --context=jane get pods                        # works (default namespace)
$ kubectl --context=jane auth can-i delete pods          # no
$ kubectl config delete-context jane; kubectl config delete-user jane; kubectl delete csr jane rolebinding jane-view; rm jane.*

Key takeaways

  • "Creating a user" = key pair + CSR (CN = user, O = groups) + signature by the cluster CA + kubeconfig + RBAC.
  • The CSR API (certificates.k8s.io/v1) lets admins approve requests without touching ca.key; the controller-manager signs.
  • signerName and usages must match the purpose; the certificate lands in status.certificate.
  • Authentication ≠ authorization: a valid cert still gets 403 until bound.
  • Cluster leaf certs expire after 1 year; kubeadm certs check-expiration / renew all + restart static Pods.
