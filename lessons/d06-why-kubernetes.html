Docker solved "how do I package and run one container on one machine". Production is a different question: hundreds of containers, dozens of machines, machines that die at 3 a.m., traffic that triples on Monday morning, and releases that must not cause downtime. Kubernetes is the answer to that second question, and its core idea — declare the desired state and let controllers converge on it — is worth understanding before you learn a single command.

What you'll learn

  • The operational problems that appear the moment you run containers on more than one machine
  • What an orchestrator does: scheduling, self-healing, scaling, rollouts, service discovery, config
  • The desired-state / reconciliation model that every Kubernetes feature is built on
  • Where Kubernetes came from and what it deliberately does not do

Life with containers but without an orchestrator

Imagine five services, each in a container, across three servers. Now answer these questions by hand:

Placement

Which server has enough free memory for the new API container? You check free -m on each box and pick one. Tomorrow the answer is different.

Failure

Server 2 loses its disk at night. Everything on it is gone. Someone has to notice, then re-create those containers elsewhere, then update whatever pointed at them.

Scaling

Traffic spikes. You SSH in and start three more copies of the frontend… and register them in the load balancer… and remember to remove them later.

Releases

Version 2 of the API must replace version 1 without dropping requests. That means starting new, waiting until healthy, shifting traffic, stopping old — per replica, in order, with a rollback plan.

Discovery

The frontend needs the API's address. Containers get new IPs every restart. You maintain a config file, or a DNS zone, by hand.

Configuration & secrets

Database passwords, feature flags, TLS certificates — distributed to the right containers on the right servers, rotated occasionally, never baked into images.

Each of these is solvable with scripts. Together, at scale, they are a full-time job for a team, and the scripts become the most fragile software you own. An orchestrator is a system that does all six continuously, automatically, from a description of what you want.

The idea: desired state and reconciliation

Kubernetes does not take commands like "start a container on server 2". It takes declarations: "there should be three replicas of this container, each with 512 MiB of memory, reachable under the name api". You store that declaration in the cluster. Then a set of controllers run a loop forever:

Observe actual state→Compare with desired state→Act to close the gap→repeat

The consequence is that failure handling is not a special case. A node dying, a Pod crashing, you editing the replica count from 3 to 5, a rolling update — they all look the same to the controller: the actual state no longer matches the desired state, so act.

Mental model

Think of a thermostat. You do not tell it "turn the heater on for 12 minutes"; you set 21 °C. It measures, compares, acts, and keeps doing so when someone opens a window. Kubernetes is a building full of thermostats, one per kind of object, all reading and writing the same shared record of desired state — the API server backed by etcd.

What Kubernetes is not

  • Not a PaaS. It does not build your code, has no opinion about languages or frameworks, and does not ship with CI/CD, logging or monitoring — it provides the hooks for those (Argo CD, Jenkins, Prometheus and friends plug in).
  • Not a container runtime. It drives containerd/CRI-O through the CRI; it does not run containers itself.
  • Not magic. Every feature is a controller writing to the API, a kubelet calling a runtime, or a Linux primitive on a node. This site's "under the hood" boxes exist to keep that visible.

Where it came from

Google ran containers at planetary scale for a decade with an internal system called Borg. In 2014 engineers from that team open-sourced a redesign in Go, named Kubernetes (Greek for "helmsman"; "k8s" counts the eight letters between k and s). In 2015 Google donated it to the newly formed Cloud Native Computing Foundation (CNCF), which also certifies conformant distributions (EKS, GKE, AKS, OpenShift, Rancher, k3s…) and runs the CKA/CKAD/CKS exams. Releases ship roughly three times a year; each minor version is supported for about 14 months, which is why cluster upgrades (Day 55) are a routine skill, not a project.

Under the hood · Linux

The reconciliation loop is also how Linux itself keeps services alive: systemd compares the units you enabled with the processes that exist and restarts what died (Restart=always). On every Kubernetes node the kubelet is itself a systemd unit — so the base of the whole self-healing stack is a plain systemd service on each machine, and systemctl status kubelet is the first troubleshooting command you will learn.

CKA exam tip

Nothing on this page is asked directly, but the reflex it teaches is: when something is wrong, ask "what is the desired state (the spec), what is the actual state (the status/events), and which controller is supposed to close the gap?" kubectl describe shows all three. That is the troubleshooting method for 30% of the exam.

Key takeaways

  • One machine → Docker. Many machines, failures, scaling, releases → an orchestrator.
  • You declare desired state; controllers loop observe → diff → act. Failures, scaling and upgrades are all just "diffs".
  • Kubernetes provides scheduling, self-healing, scaling, rollouts, discovery, config and storage — and leaves building, CI/CD and observability to the ecosystem.
  • Born from Google's Borg, governed by the CNCF, released three times a year.
