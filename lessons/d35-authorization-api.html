Every request to the API server passes through the same three gates in order: authentication (who are you?), authorization (may you do this?), and admission (should this object be allowed/changed?). Day 32 covered the first gate. This lesson opens the second — the pluggable authorization modes and the order they run in — and, because authorization decisions are made in terms of the API's own vocabulary (groups, resources, verbs), it also teaches you to read the API like the API server does, with nothing but curl.

What you'll learn

  • The request pipeline: authn → authz → admission → validation → etcd
  • Authorization modes: Node, RBAC, ABAC, Webhook, AlwaysAllow, AlwaysDeny — and how a chain of them decides
  • API structure: core group vs named groups, versions, resources, subresources, verbs
  • Exploring the API directly: kubectl proxy, kubectl get --raw, curl with a token, -v=8
  • Reading a request the way an authorizer sees it

The pipeline

  1. TLS + Authentication. Client cert, bearer token (ServiceAccount, OIDC, static file, bootstrap), or authenticating proxy. Each authenticator is tried in turn; the first to recognise the credential wins. Result: a user name, a set of groups, and extra attributes. Unrecognised → 401 Unauthorized, or treated as system:anonymous in group system:unauthenticated if anonymous auth is on (default).
  2. Authorization. The request is reduced to attributes — user, groups, verb, API group, resource, subresource, namespace, name — and each configured authorizer is asked. Denied → 403 Forbidden.
  3. Admission. Only for writes. Mutating plugins/webhooks may change the object; validating ones may reject it. Day 38.
  4. Schema validation and persistence. The object is checked against its type's OpenAPI schema and written to etcd; watchers are notified.

Authorization modes

$ grep authorization-mode /etc/kubernetes/manifests/kube-apiserver.yaml
    - --authorization-mode=Node,RBAC          # kubeadm default; order matters
ModeHow it decidesUse
NodeSpecial-purpose: lets a kubelet (user system:node:<name>, group system:nodes) read only the Secrets, ConfigMaps, PVCs… referenced by Pods on its own node, and write only its own Node/Pod status. Paired with the NodeRestriction admission plugin.Always on; keeps a compromised node from reading the whole cluster.
RBACRoles (rules) bound to subjects via RoleBindings — objects in the API, changed with kubectl, no restart.The standard. Day 36.
ABACA JSON-lines policy file on the API server (--authorization-policy-file): one line per rule matching user/group/resource/namespace. Needs an API server restart to change.Legacy; you will only meet it in old clusters and exam trivia.
WebhookPOSTs a SubjectAccessReview to an external HTTPS service that answers allowed/denied.Integrating an enterprise policy engine (OPA, cloud IAM).
AlwaysAllow / AlwaysDenyWhat they say.Testing only. AlwaysAllow is what "no authorization" means — never in production.

The chain: authorizers run in the order listed. Each returns allow, deny, or no opinion. The first allow or deny wins; no-opinion passes to the next; if every authorizer has no opinion, the request is denied. With Node,RBAC: a kubelet request is decided by Node; anything else falls through to RBAC. (Since 1.30 the same chain can be expressed in a structured AuthorizationConfiguration file that also allows multiple webhooks and CEL pre-filters.)

The API, the way an authorizer sees it

An RBAC rule says "verb X on resource Y in API group Z". Those words are the URL structure:

/api/v1/namespaces/{ns}/pods/{name}            ← core group ("" in RBAC), version v1, resource pods
/api/v1/namespaces/{ns}/pods/{name}/log        ← subresource: pods/log
/api/v1/namespaces/{ns}/pods/{name}/exec       ← subresource: pods/exec  (a websocket)
/api/v1/nodes                                  ← cluster-scoped: no "namespaces" segment
/apis/apps/v1/namespaces/{ns}/deployments      ← named group apps, resource deployments
/apis/apps/v1/namespaces/{ns}/deployments/web/scale   ← subresource deployments/scale (what HPA uses)
/apis/batch/v1/…/jobs   /apis/networking.k8s.io/v1/…/ingresses   /apis/rbac.authorization.k8s.io/v1/…/roles
/apis/metrics.k8s.io/v1beta1/…                 ← an aggregated API (served by metrics-server)
/apis/example.com/v1/…/widgets                 ← a CRD's group
HTTPURL shapeRBAC verb
GET…/pods/{name}get
GET…/podslist (and watch with ?watch=true)
POST…/podscreate
PUT…/pods/{name}update (whole object; kubectl replace, edit)
PATCH…/pods/{name}patch (kubectl apply, patch, set, scale, label)
DELETE…/pods/{name} · …/podsdelete · deletecollection
—non-resource: /healthz, /metrics, /apinonResourceURLs in ClusterRoles

Two consequences that trip people up: kubectl get pods needs list, not get; and reading logs needs get on pods/log — a separate subresource — even if you can get pods.

$ kubectl api-resources -o wide                 # NAME SHORTNAMES APIVERSION NAMESPACED KIND VERBS
$ kubectl api-resources --api-group=apps
$ kubectl api-versions                          # every group/version served
$ kubectl explain deployment --api-version=apps/v1 | head

Talking to the API without kubectl

# 1. see what kubectl actually sends
$ kubectl get pods -n kube-system -v=8 2>&1 | grep -E 'GET|Response Status'
# 2. kubectl proxy: local plain-HTTP port that adds your kubeconfig credentials for you
$ kubectl proxy --port=8001 &
$ curl -s localhost:8001/api/v1/namespaces/default/pods | jq '.items[].metadata.name'
$ curl -s localhost:8001/apis/apps/v1/namespaces/default/deployments/web/scale
$ curl -s -X PATCH -H 'Content-Type: application/merge-patch+json' -d '{"spec":{"replicas":3}}' localhost:8001/apis/apps/v1/namespaces/default/deployments/web/scale
# 3. --raw: same thing without the proxy
$ kubectl get --raw /healthz?verbose
$ kubectl get --raw /apis/metrics.k8s.io/v1beta1/nodes | jq .
# 4. from inside a Pod, with the ServiceAccount token (Day 37)
$ TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
$ curl -s --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt -H "Authorization: Bearer $TOKEN" https://kubernetes.default.svc/api/v1/namespaces/default/pods

Asking the authorizer directly

$ kubectl auth can-i create deployments -n dev                  # yes / no, for you
$ kubectl auth can-i list secrets --as=jane --as-group=developers -n dev     # impersonate (needs impersonate permission)
$ kubectl auth can-i --list -n dev                              # everything you can do there
$ kubectl auth can-i get pods --subresource=log
$ kubectl create -f - <<EOF                                   # what can-i sends under the hood
apiVersion: authorization.k8s.io/v1
kind: SubjectAccessReview
spec:
  user: jane
  groups: [developers]
  resourceAttributes: {namespace: dev, verb: delete, resource: pods}
EOF
Under the hood · Linux

The API server is an ordinary HTTPS server; everything above is visible with the usual tools. curl -v shows the TLS handshake and the exact verb/path; jq slices the JSON (the shell toolkit page). Audit logging (--audit-policy-file, --audit-log-path) writes one JSON line per request with the user, verb, URI, and the authorization decision and reason — jq 'select(.verb=="delete")' /var/log/kubernetes/audit.log answers "who deleted that?". On a busy control plane, ss -tnp | grep 6443 shows every component holding a connection to the API server — kubelets, controllers, kube-proxy — each of which authenticated with the certificates from Day 33.

CKA exam tip
  • kubectl auth can-i (with --as) is the fastest way to verify any RBAC task. Use it before you say you are done.
  • "Which authorization modes are enabled?" → read the API server manifest. Changing them = edit the static Pod manifest; the API server restarts itself.
  • Know the group of the common kinds: core ("") for pods/services/configmaps/secrets/nodes/pv/pvc/namespaces; apps; batch; networking.k8s.io; rbac.authorization.k8s.io; storage.k8s.io. You will write them in Role rules on Day 36.

Key takeaways

  • Pipeline: authenticate (who) → authorize (may) → admit (should/mutate) → validate → etcd.
  • Modes run as a chain: first allow/deny wins, no opinion falls through, all-no-opinion = deny. kubeadm uses Node,RBAC.
  • Authorization vocabulary = the API's URL structure: group (core is ""), resource, subresource (pods/log, deployments/scale), verb (get list watch create update patch delete).
  • kubectl proxy, --raw, -v=8, curl + token: see the API without kubectl. auth can-i --as: ask the authorizer.
