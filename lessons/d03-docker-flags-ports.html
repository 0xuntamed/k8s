"I started the container, why can't I reach it?" is the most common Docker question, and the answer is always the same: the container has its own network namespace, and nothing gets in unless you publish a port. This lesson covers the docker run flags you will use daily, the Dockerfile instructions Day 2 skipped, and — because it is the same mechanism Kubernetes Services use — exactly how a published port works.

What you'll learn

  • The essential docker run flags: detach, interactive, name, ports, env, volumes, restart, limits
  • EXPOSE vs -p, and how port publishing is implemented with a bridge, a veth pair and iptables
  • Docker network modes and container-to-container DNS
  • ARG, USER, HEALTHCHECK, LABEL, COPY --chown

EXPOSE is documentation, -p is the wire

EXPOSE 80 in a Dockerfile records "this image listens on 80" in the image metadata. It does not open anything. Traffic only reaches the container when you publish a port with -p, and you can publish ports that were never EXPOSEd.

Under the hood · Linux

When dockerd starts, it creates a Linux bridge called docker0 (172.17.0.1/16). Each container gets a veth pair — a virtual cable: one end becomes eth0 inside the container's network namespace, the other end is plugged into docker0. -p 8080:80 adds an iptables rule in the nat table's DOCKER chain: DNAT any packet arriving on host port 8080 to 172.17.0.2:80. Replies are un-NATed by conntrack. Kubernetes' kube-proxy does the same thing for Services, just with more rules.

$ ip link show docker0                 # the bridge
$ ip link | grep veth                  # one veth per running container
$ sudo iptables -t nat -L DOCKER -n    # DNAT tcp dpt:8080 to:172.17.0.2:80
$ docker inspect -f '{{.NetworkSettings.IPAddress}}' web

Network modes

bridge (default)

Private namespace, IP on docker0, outbound via NAT, inbound via -p. Containers on the default bridge can reach each other only by IP.

user-defined bridge

docker network create mynet. Same as bridge, but Docker runs an embedded DNS server so containers resolve each other by name. Always use this for multi-container setups.

host

No network namespace: the process binds directly on the host's interfaces. Fastest, no isolation, port conflicts are yours to manage.

none

A namespace with only loopback. For batch jobs that must not talk to anything.

container:<name>

Share another container's network namespace — two processes on the same localhost. This is exactly how the containers of a Kubernetes Pod are wired together.

$ docker network create appnet
$ docker run -d --name db  --network appnet -e POSTGRES_PASSWORD=pw postgres:16
$ docker run -d --name api --network appnet -e DB_HOST=db my-api:1.0   # "db" resolves via Docker DNS
$ docker exec api getent hosts db          # 172.18.0.2  db

Dockerfile deep dive

# build-time variable; override with --build-arg NODE_VERSION=22
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-alpine

LABEL org.opencontainers.image.source="https://github.com/you/api"

# create an unprivileged user; never run production apps as root
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app

# --chown avoids a second layer just to fix ownership
COPY --chown=app:app package*.json ./
RUN npm ci --omit=dev

COPY --chown=app:app . .
USER app

ENV NODE_ENV=production PORT=3000
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "server.js"]
ARG vs ENV
ARG exists only during the build (and only after the line that declares it — put one before FROM to use it in FROM). ENV persists into the running container. Never put secrets in either; they are visible with docker history / inspect.
USER
Everything after it (remaining RUNs and the runtime process) runs as that user. Kubernetes can enforce this with runAsNonRoot: true (Day 41).
COPY vs ADD
ADD auto-extracts local tar archives and can download URLs. Those surprises are why the convention is COPY unless you specifically want extraction.
HEALTHCHECK
Docker marks the container healthy/unhealthy. Kubernetes ignores this instruction entirely and uses its own probes.
LABEL
Arbitrary metadata. The org.opencontainers.image.* keys are a widely adopted convention.

Volumes preview

-v $(pwd)/data:/data bind-mounts a host directory; -v mydata:/data uses a Docker-managed named volume. Both bypass the writable layer, so data survives docker rm. Day 24 covers this properly as the on-ramp to Kubernetes storage.

CKA exam tip

Two direct mappings show up constantly: -p ⇢ Service NodePort (Day 12) and --network container:x ⇢ the shared network namespace of a Pod (Day 21). If you understand the iptables DNAT above, you already understand kube-proxy.

Hands-on lab (10 min)

See the port-publishing machinery for yourself (Linux host or a Linux VM; Docker Desktop hides it inside its VM).

$ docker run -d --name web -p 8080:80 nginx
$ curl -s localhost:8080 | head -3
$ docker inspect -f '{{.NetworkSettings.IPAddress}}' web
$ sudo iptables -t nat -S DOCKER | grep 8080
$ ip -br link | grep -E 'docker0|veth'
$ docker run --rm --network container:web alpine wget -qO- http://localhost   # shares web's netns
$ docker rm -f web

Key takeaways

  • A container has a private network namespace; -p host:ctr punches a hole with an iptables DNAT rule on the host.
  • EXPOSE is metadata only. -P publishes all exposed ports on random host ports.
  • Use user-defined networks for name resolution between containers; --network container:x is the Pod model.
  • Run as a non-root USER, keep ARG for build-only values, and never bake secrets into images.
