Pod IPs are ephemeral and Pods are many. A Service is a stable virtual IP and DNS name that load-balances to whichever Pods currently match a label selector. Four types build on each other — ClusterIP inside the cluster, NodePort on every node, LoadBalancer in front of the nodes, ExternalName for things outside — and all of them are, underneath, a set of iptables rules that kube-proxy keeps in sync.

What you'll learn

  • ClusterIP, NodePort, LoadBalancer and ExternalName — what each adds and when to use it

  • Endpoints/EndpointSlices: how a Service knows where its Pods are
  • Headless Services and what they return from DNS
  • How kube-proxy implements a Service with iptables DNAT and conntrack

The problem a Service solves

A Deployment of three api Pods has three IPs from the Pod network, say 10.244.1.5, 10.244.2.9, 10.244.2.10. Tomorrow after a rollout they are different. A client cannot hard-code them, and even if it could, it would have to do its own load balancing and health checking. A Service gives the client one address — 10.96.0.42, and the name api — that stays fixed for the Service's lifetime, and the cluster does the rest.

Four types, one layered picture

ClusterIP (default) — reachable inside the cluster

apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  type: ClusterIP
  selector:
    app: api
  ports:
  - name: http
    protocol: TCP
    port: 8080        # the Service's port (what clients use)
    targetPort: 8080  # the container's port (what Pods listen on)
  • selector — Pods with these labels (in the same namespace) become endpoints. A Service without a selector has no automatic endpoints — you can create them by hand to point at external IPs.
  • port — exposed on the ClusterIP. Clients connect to api:8080.
  • targetPort — the port in the Pod. Defaults to port. May be a name (targetPort: http) that matches a containerPort name — then Pods can listen on different numbers.
  • The ClusterIP is allocated from the service CIDR (e.g. 10.96.0.0/12) and is virtual: no interface has it. It only exists in iptables rules.
$ kubectl expose deployment api --port=8080 --target-port=8080 --name=api     # imperative equivalent
$ kubectl get svc api
NAME   TYPE        CLUSTER-IP    EXTERNAL-IP   PORT(S)    AGE
api    ClusterIP   10.96.0.42    <none>        8080/TCP   5s
$ kubectl get endpointslices -l kubernetes.io/service-name=api   # the Pod IPs behind it
$ kubectl run tmp --rm -it --image=busybox -- wget -qO- http://api:8080/health   # test from inside

NodePort — reachable on every node's IP

spec:
  type: NodePort
  selector: {app: web}
  ports:
  - port: 80          # ClusterIP port (still created)
    targetPort: 8080  # container port
    nodePort: 30080   # 30000–32767; omit to auto-allocate

A NodePort Service is a ClusterIP Service plus a rule on every node: traffic to <any-node-IP>:30080 is forwarded to the Service, and from there to a Pod — which may be on a different node. Useful for dev clusters (KIND's extraPortMappings from Day 8) and as the building block for LoadBalancer. Rarely exposed directly in production: awkward port numbers, no TLS, and clients must know node IPs.

LoadBalancer — a cloud load balancer in front

spec:
  type: LoadBalancer
  selector: {app: web}
  ports:
  - port: 443
    targetPort: 8443

On a cloud, the cloud-controller-manager sees this and provisions an external load balancer (AWS NLB/ELB, GCP forwarding rule, Azure LB) whose targets are the nodes on an automatically allocated NodePort. The LB's public IP appears in EXTERNAL-IP. On bare metal there is no cloud — EXTERNAL-IP stays <pending> forever unless you install MetalLB or similar. One LB per Service is expensive, which is why HTTP traffic usually goes through a single Ingress instead.

ExternalName — a DNS alias, no proxying

apiVersion: v1
kind: Service
metadata:
  name: orders-db
spec:
  type: ExternalName
  externalName: prod-db.abc123.eu-west-1.rds.amazonaws.com

No selector, no ClusterIP, no iptables. CoreDNS simply returns a CNAME: orders-db.default.svc.cluster.local → prod-db.…rds.amazonaws.com. Lets you refer to an external system by a cluster-local name and swap it later without touching applications. (Only works for hostnames; for a bare IP, create a selector-less Service and a manual EndpointSlice.)

Headless Services

spec:
  clusterIP: None      # headless
  selector: {app: postgres}
  ports: [{port: 5432}]

Set clusterIP: None and there is no virtual IP and no load balancing. A DNS lookup of the Service name returns all the Pod IPs as A records, and each Pod of a StatefulSet additionally gets its own stable name, postgres-0.postgres.default.svc.cluster.local. Use it when clients need to talk to specific replicas (database primaries, peer discovery in clustered systems) — Day 44.

Endpoints and EndpointSlices

A Service does not track Pods itself. The EndpointSlice controller watches Pods matching the selector and writes their IPs and readiness into EndpointSlice objects (max 100 endpoints each; the older Endpoints object still exists for compatibility). kube-proxy watches EndpointSlices, not Pods. A Pod that fails its readiness probe is marked not-ready in the slice and stops receiving traffic — without being restarted.

$ kubectl get endpointslices
$ kubectl describe svc api | grep -E 'Endpoints|TargetPort'
# "Endpoints: <none>" means: selector matches no Pods, or none are Ready, or the port name is wrong

How kube-proxy makes a virtual IP work

Under the hood · Linux

In iptables mode, kube-proxy writes a chain per Service (KUBE-SVC-…) in the nat table, hooked from KUBE-SERVICES in PREROUTING and OUTPUT. The Service chain has one rule per endpoint using the statistic module: with 3 endpoints, rule 1 matches with probability 1/3, rule 2 with 1/2 of the rest, rule 3 always — a random pick. Each endpoint chain (KUBE-SEP-…) does the actual DNAT --to-destination 10.244.2.9:8080. conntrack records the choice so every packet of that TCP connection goes to the same Pod, and replies are un-NATed on the way back. NodePorts are just an extra KUBE-NODEPORTS chain matching dport 30080 that jumps to the same Service chain. IPVS mode replaces the rule list with a kernel hash table (better at thousands of Services); Cilium replaces it all with eBPF.

$ sudo iptables -t nat -L KUBE-SERVICES -n | grep api
$ sudo iptables -t nat -L KUBE-SVC-XXXX -n           # the statistic rules
$ sudo conntrack -L | grep 10.96.0.42                # live NAT mappings
$ kubectl -n kube-system logs ds/kube-proxy | head   # "Using iptables Proxier"

Useful fields

FieldPurpose
sessionAffinity: ClientIPPin a client IP to one Pod (uses conntrack + timeout, default 3 h). Only tool for stickiness at L4.
externalTrafficPolicy: LocalNodePort/LB: only route to Pods on the node that received the packet — preserves the client source IP and avoids an extra hop, but nodes without a Pod drop traffic (the LB health check handles that).
internalTrafficPolicy: LocalSame idea for ClusterIP traffic (keep it on-node, e.g. for node-local caches).
publishNotReadyAddresses: trueInclude not-ready Pods in DNS — used by StatefulSets during bootstrap.
ipFamilyPolicy / ipFamiliesDual-stack IPv4/IPv6.
loadBalancerClass, annotationsSelect which LB implementation; cloud-specific options (internal LB, NLB vs ALB, etc.).
CKA exam tip
  • kubectl expose deploy web --port=80 --target-port=8080 --type=NodePort then edit the nodePort if a specific one is required (expose cannot set it).
  • "Service has no endpoints": compare kubectl get svc -o yaml | grep -A3 selector with kubectl get pods --show-labels; then check targetPort against containerPort; then Pod readiness.
  • Test from inside with a throwaway Pod: kubectl run t --rm -it --image=busybox:1.36 -- sh, then wget -qO- http://svc:port or nc -zv svc port.

Hands-on lab (20 min)

$ kubectl create deploy web --image=nginx --replicas=3 --port=80
$ kubectl expose deploy web --port=80 --name=web
$ kubectl get svc web -o wide && kubectl get endpointslices -l kubernetes.io/service-name=web
$ kubectl run t --rm -it --image=busybox:1.36 -- sh -c 'for i in 1 2 3 4 5; do wget -qO- http://web | grep -o "nginx/[0-9.]*"; done; nslookup web'
# NodePort
$ kubectl patch svc web -p '{"spec":{"type":"NodePort","ports":[{"port":80,"nodePort":30080}]}}'
$ curl localhost:30080                    # via KIND extraPortMappings from Day 8
# readiness removes an endpoint without killing the pod
$ kubectl exec deploy/web -- rm /usr/share/nginx/html/index.html   # (only one pod affected)
# headless
$ kubectl create svc clusterip web-headless --clusterip=None --tcp=80:80 --dry-run=client -o yaml | sed 's/app: web-headless/app: web/' | kubectl apply -f -
$ kubectl run t --rm -it --image=busybox:1.36 -- nslookup web-headless   # three A records
# under the hood (KIND node)
$ docker exec cka-control-plane iptables -t nat -L KUBE-SERVICES -n | grep -E 'web'

Key takeaways

  • A Service = stable virtual IP + DNS name + label selector → EndpointSlices of ready Pod IPs.
  • ClusterIP (inside) ⊂ NodePort (every node, 30000–32767) ⊂ LoadBalancer (cloud LB → NodePorts). ExternalName is just a CNAME.
  • port is the Service's, targetPort is the Pod's, nodePort is the node's.
  • Headless (clusterIP: None) skips the VIP and returns Pod IPs from DNS — for StatefulSets and peer discovery.
  • kube-proxy implements all of it with iptables DNAT + random endpoint selection + conntrack. No proxy process in the data path.
