When a cluster is full, which Pod waits and which one runs? By default: whoever asked first. Priority lets you say that the payment API matters more than the nightly report — so the scheduler orders the queue by priority, and if a high-priority Pod cannot fit, it preempts (evicts) lower-priority Pods to make room. The same number also decides who is evicted first when a node runs out of memory. It is a small feature with sharp edges; the animation shows both.

PriorityClass

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high                      # cluster-scoped
value: 100000                     # higher = more important; user classes ≤ 1 000 000 000
globalDefault: false              # true = applied to Pods with no priorityClassName (only one class may be default)
preemptionPolicy: PreemptLowerPriority   # or Never (queue-jump only, no eviction)
description: "Customer-facing services"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: batch
value: -1000                      # negative is allowed
preemptionPolicy: Never
globalDefault: true
# in a Pod / template
spec:
  priorityClassName: high         # admission resolves it to spec.priority: 100000
  containers: [...]
$ kubectl get priorityclasses
NAME                      VALUE        GLOBAL-DEFAULT   AGE
system-cluster-critical   2000000000   false            30d
system-node-critical      2000001000   false            30d
$ kubectl get pod api-xyz -o jsonpath='{.spec.priority}{" "}{.spec.priorityClassName}{"\n"}'
$ kubectl create priorityclass high --value=100000 --description="customer facing"

The two system-* classes are reserved for cluster components (CoreDNS, kube-proxy, CNI, metrics-server use system-cluster-critical; static control-plane Pods and the CNI DaemonSet use system-node-critical). Pods with no class and no global default get priority 0. The Priority admission plugin resolves the name to a number at creation; changing the class later does not change existing Pods.

What priority changes

1 · Queue order

The scheduling queue is sorted by priority, then arrival time. A high-priority Pod that arrives while 50 batch Pods are Pending is scheduled next.

2 · Preemption

If no node fits, the scheduler looks for a node where evicting some lower-priority Pods would make it fit, evicts them, and reserves the node.

3 · Kubelet eviction

Under node pressure, the kubelet ranks Pods by (usage above request, then priority): among Pods exceeding their requests, lower priority goes first.

Preemption, precisely

  1. Trigger. Pod P (priority 100000) fails filtering on every node (Insufficient cpu). Preemption is only attempted for unschedulable Pods.
  2. Candidate search. For each node, the scheduler simulates removing Pods with priority lower than P and checks whether P would fit. Pods with equal or higher priority are never victims. Nodes with a matching taint that P does not tolerate are skipped — preemption does not bypass taints or affinity.
  3. Victim selection. Among feasible nodes it prefers: fewest PodDisruptionBudget violations, lowest highest-victim-priority, smallest sum of victim priorities, fewest victims, earliest start times. Then it removes as few Pods as possible from the chosen node.
  4. Eviction. Victims are deleted through the API with their normal terminationGracePeriodSeconds. They are not killed instantly. Their ReplicaSets will re-create them elsewhere (or queue them).
  5. Nomination. P gets status.nominatedNodeName so other Pods do not grab the freed space during the grace period. P is still Pending until the victims are gone and it is actually scheduled — and if a better node appears meanwhile, it may go there instead.
$ kubectl get pod api-xyz -o jsonpath='{.status.nominatedNodeName}{"\n"}'
$ kubectl get events --field-selector reason=Preempted
$ kubectl describe pod batch-abc | grep -i preempt        # "Preempted by default/api-xyz on node worker-2"
Sharp edges
  • PDBs are best-effort here. Preemption prefers nodes where it does not violate a PodDisruptionBudget, but it will violate one if that is the only way to schedule a higher-priority Pod. Priority outranks PDBs.
  • Priority inflation. If every team sets high, nothing is high. Restrict who may use a class with a ResourceQuota scopeSelector on PriorityClass per namespace.
  • Cascades. A preempted Pod of priority 50 may in turn preempt priority 10 Pods on another node. Fine by design, surprising in practice.
  • Non-preempting (preemptionPolicy: Never) classes jump the queue but never evict — the right choice for batch work that should merely go first when space is free.

So a Guaranteed, high-priority Pod is nearly untouchable; a BestEffort, priority-0 Pod is the first to go in every scenario. Set both deliberately for anything that matters (Day 19).

CKA exam tip
  • "Create a PriorityClass with value N and use it in a Pod" — kubectl create priorityclass, then priorityClassName in the spec. Verify spec.priority on the Pod.
  • Pods being "randomly" evicted with reason Preempted → a higher-priority Pod could not fit. Check get events and the PriorityClasses.
  • The system-* classes exist on every cluster; do not create classes above 1e9 — the API refuses.

Hands-on lab (20 min)

$ kubectl create priorityclass low --value=1000 && kubectl create priorityclass high --value=100000
# fill a node: find allocatable CPU and request nearly all of it with low-priority pods
$ kubectl describe node cka-worker | grep -A2 'Allocatable' | grep cpu
$ kubectl create deploy filler --image=busybox --replicas=6 $do -- sleep 3600 | sed '/spec:/{n;s/containers:/priorityClassName: low\n      containers:/}' | sed '/image: busybox/a\        resources: {requests: {cpu: 500m}}' | kubectl apply -f -
$ kubectl get pods -o wide -l app=filler                             # some Running, maybe some Pending — that is fine
# now a high-priority pod that needs 1 CPU
$ kubectl run vip --image=busybox --command --overrides='{"spec":{"priorityClassName":"high","containers":[{"name":"vip","image":"busybox","command":["sleep","3600"],"resources":{"requests":{"cpu":"1"}}}]}}' -- sleep 3600
$ kubectl get pods -o wide -w                                        # filler pods get Terminating; vip gets nominatedNodeName then Running
$ kubectl get events --field-selector reason=Preempted
$ kubectl get pod vip -o jsonpath='{.spec.priority}{"\n"}'
$ kubectl delete deploy filler; kubectl delete pod vip $now; kubectl delete priorityclass low high

Key takeaways

  • PriorityClass = a number attached to Pods via priorityClassName; default 0; system-* reserved for components.
  • Priority orders the scheduling queue, drives preemption when nothing fits, and breaks ties in kubelet eviction.
  • Preemption evicts only lower-priority Pods, respects taints/affinity, uses grace periods, and nominates the node; PDBs are preferred but not guaranteed.
  • Use preemptionPolicy: Never for "go first but never evict"; quota classes per namespace to prevent inflation.
