A Dockerfile is a recipe: a short list of instructions that turns a base image plus your source code into a new image. Each instruction produces one filesystem layer, and understanding that one fact explains build caching, image size, and half of the "why is my build slow?" questions you will ever get.

What you'll learn

  • The instructions every Dockerfile uses: FROM, WORKDIR, COPY, RUN, ENV, EXPOSE, CMD
  • How docker build turns instructions into cached layers
  • Tagging and pushing to Docker Hub so a cluster can pull your image

A minimal application

We will containerise a tiny Python web app. The language does not matter — the pattern is identical for Node, Go or Java.

from flask import Flask
import os, socket

app = Flask(__name__)

@app.route("/")
def hello():
    return f"Hello from {socket.gethostname()} (v{os.getenv('APP_VERSION','1')})\n"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
flask==3.0.3

Binding to 0.0.0.0 matters: a container has its own network namespace, so a server listening on 127.0.0.1 is unreachable from outside it.

The Dockerfile

# 1. Start from an image that already has Python
FROM python:3.12-slim

# 2. Every following relative path is inside /app (created if missing)
WORKDIR /app

# 3. Copy dependency list first — this layer changes rarely
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 4. Now copy the source code — this layer changes often
COPY app.py .

# 5. Metadata: environment variable and the port the app listens on
ENV APP_VERSION=1
EXPOSE 5000

# 6. What to run when a container starts from this image
CMD ["python", "app.py"]
InstructionMeaningCreates a layer?
FROMBase image. Must be first (apart from ARG). FROM scratch is an empty image.Reuses the base's layers
WORKDIRSet the working directory for subsequent instructions and for the running container.Metadata (tiny)
COPYCopy files from the build context into the image. Prefer over ADD (which also unpacks tarballs and fetches URLs).Yes
RUNExecute a command at build time and snapshot the resulting filesystem.Yes
ENVEnvironment variable available at build time and in every container.Metadata
EXPOSEDocuments which port the app listens on. It does not publish anything (see Day 3).Metadata
CMDDefault command at run time. Only the last CMD counts.Metadata

Building: instructions become layers

$ docker build -t hello-web:1.0 .
[+] Building 12.4s (10/10) FINISHED
 => [1/5] FROM docker.io/library/python:3.12-slim
 => [2/5] WORKDIR /app
 => [3/5] COPY requirements.txt .
 => [4/5] RUN pip install --no-cache-dir -r requirements.txt
 => [5/5] COPY app.py .
 => exporting to image
 => => naming to docker.io/library/hello-web:1.0

The trailing . is the build context: the directory sent to the Docker daemon. COPY can only reference files inside it. Anything large you do not need (.git, node_modules, local data) should be excluded with a .dockerignore file, exactly like .gitignore.

The layer-ordering rule

Docker rebuilds from the first instruction whose inputs changed and every instruction after it. So put the things that change least (base image, OS packages, dependency install) at the top, and the things that change most (your source code) at the bottom. That is why requirements.txt is copied and installed before app.py: editing your code no longer re-runs pip install.

Under the hood · Linux

Each layer is a directory on disk (/var/lib/docker/overlay2/<id>/diff). A RUN step mounts all previous layers as an OverlayFS "lower" stack with a fresh "upper" directory, executes the command in a temporary container, then keeps the upper directory as the new layer. Files deleted in a later layer are not removed from the earlier one — they are hidden by a whiteout file. That is why RUN rm -rf big-file in a separate step does not make an image smaller.

Run it

$ docker run -d --name hello -p 8080:5000 hello-web:1.0
$ curl localhost:8080
Hello from 3f9c1a2b7d1e (v1)
$ docker run --rm -e APP_VERSION=2 -p 8081:5000 hello-web:1.0   # override ENV at run time

Push to Docker Hub

A registry is how your image gets to a cluster. Kubernetes nodes never see your laptop; they pull from a registry by name.

  1. Log in
    $ docker login          # username + password or access token
  2. Tag with your namespace — Docker Hub repositories are <username>/<repo>.
    $ docker tag hello-web:1.0 yourname/hello-web:1.0
$ docker tag hello-web:1.0 yourname/hello-web:latest   # a second tag on the same image ID
  3. Push — only layers the registry does not already have are uploaded.
    $ docker push yourname/hello-web:1.0
$ docker push yourname/hello-web:latest
  4. Pull from anywhere
    $ docker pull yourname/hello-web:1.0
$ kubectl run hello --image=yourname/hello-web:1.0 --port=5000   # preview of Day 13
Tags are not versions

latest is overwritten every time you push it, and a Kubernetes node that already has yourname/hello-web:latest cached may never pull the new one (the default imagePullPolicy for tagged images is IfNotPresent). Always ship immutable tags like 1.0.3 or a git SHA. Details on Day 22.

Inspecting what you built

$ docker images hello-web
$ docker history hello-web:1.0        # one line per layer with its size
$ docker inspect hello-web:1.0 | jq '.[0].Config'   # Env, Cmd, ExposedPorts, WorkingDir

Hands-on lab (15 min)

Build, break the cache on purpose, push.

$ mkdir hello-web && cd hello-web
# create app.py, requirements.txt and Dockerfile from above
$ docker build -t hello-web:1.0 .
$ docker build -t hello-web:1.0 .            # second build: every step says CACHED
$ sed -i 's/Hello/Hi/' app.py
$ docker build -t hello-web:1.1 .            # only steps 5+ rebuild
$ echo "requests" >> requirements.txt
$ docker build -t hello-web:1.2 .            # steps 3+ rebuild, pip runs again
$ docker history hello-web:1.2
$ docker tag hello-web:1.2 <you>/hello-web:1.2 && docker push <you>/hello-web:1.2

Key takeaways

  • A Dockerfile is executed top to bottom; RUN, COPY and ADD create filesystem layers, everything else is metadata.
  • The cache is invalidated from the first changed instruction downward — order rarely-changing steps first.
  • EXPOSE documents; -p publishes. ENV sets defaults that -e can override.
  • Push with an immutable tag to a registry; clusters pull by name, never from your machine.
