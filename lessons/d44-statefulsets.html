A Deployment's Pods are interchangeable: random names, any order, shared nothing. A database replica is not: it has a role (primary or follower), a disk that must follow it, and peers that address it by name. A StatefulSet gives each Pod a stable identity — an ordinal name, a DNS entry, and its own PersistentVolumeClaim — and creates, updates and deletes them in order. This lesson builds one, shows what "stable" means in practice, and runs through the course's multi-AZ pattern on EKS.

What you'll learn

  • What stable identity means: name, network, storage — and why a headless Service is required
  • volumeClaimTemplates: one PVC per Pod, kept across restarts and scale-downs
  • Ordered creation, deletion and rolling updates; podManagementPolicy, partition, OnDelete
  • The multi-AZ pattern: WaitForFirstConsumer classes and topology spread
  • Operational realities: scaling down does not delete PVCs, updates are not automatic on failure, and when to use an operator instead

Three kinds of stability

DeploymentStatefulSet
Pod namesweb-7d9f8-x4k2p (random)db-0, db-1, db-2 (ordinal, reused after restart)

The manifest

apiVersion: v1
kind: Service
metadata:
  name: db                       # the "serviceName" below
spec:
  clusterIP: None                # HEADLESS: DNS returns pod IPs, per-pod records
  selector: {app: db}
  ports: [{name: pg, port: 5432}]
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db                # governs the per-pod DNS names
  replicas: 3
  selector:
    matchLabels: {app: db}
  podManagementPolicy: OrderedReady   # or Parallel
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0               # only ordinals ≥ partition are updated
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain          # or Delete
    whenScaled: Retain
  template:
    metadata:
      labels: {app: db}
    spec:
      terminationGracePeriodSeconds: 30
      containers:
      - name: postgres
        image: postgres:16
        ports: [{containerPort: 5432, name: pg}]
        env:
        - {name: POD_NAME, valueFrom: {fieldRef: {fieldPath: metadata.name}}}
        - {name: PGDATA, value: /var/lib/postgresql/data/pgdata}
        volumeMounts:
        - {name: data, mountPath: /var/lib/postgresql/data}
  volumeClaimTemplates:          # a PVC "stamp": data-db-0, data-db-1, data-db-2
  - metadata:
      name: data
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: gp3-wffc
      resources: {requests: {storage: 20Gi}}
  • Headless Service — clusterIP: None. Required. It creates the DNS records db-0.db, db-1.db… A second, normal Service can exist for load-balanced reads.
  • serviceName — ties Pods to that headless Service for DNS.
  • podManagementPolicy — OrderedReady (default): strictly sequential; Parallel: create/delete all at once (identity and PVCs still stable — good for systems that do their own coordination, like Cassandra/Elasticsearch).
  • partition — canary control: with 3 replicas and partition: 2, only db-2 gets the new template. Lower it to roll further.
  • persistentVolumeClaimRetentionPolicy — since 1.27 (GA 1.32): whether PVCs are deleted when the StatefulSet is deleted or scaled down. Default keeps them (data safety).
  • volumeClaimTemplates — a PVC spec; the controller creates <template>-<sts>-<ordinal> for each Pod on first creation and re-attaches the same one forever after.
  • Pods also carry the label statefulset.kubernetes.io/pod-name: db-1 — handy for a Service that targets one specific Pod.

Ordered lifecycle

$ kubectl apply -f db.yaml && kubectl get pods -l app=db -w
db-0  0/1  Pending → ContainerCreating → Running (1/1)
db-1  0/1  …                         # created only after db-0 is Ready
db-2  0/1  …
$ kubectl get pvc                    # data-db-0, data-db-1, data-db-2 — Bound
$ kubectl run t --rm -it --image=busybox:1.36 -- nslookup db-1.db.default.svc.cluster.local   # a single pod IP
$ kubectl run t --rm -it --image=busybox:1.36 -- nslookup db                                  # all three
$ kubectl delete pod db-1            # comes back as db-1, same PVC, same DNS name, possibly on another node
$ kubectl scale sts db --replicas=2  # db-2 removed (highest ordinal first); data-db-2 PVC REMAINS
$ kubectl scale sts db --replicas=3  # db-2 returns and re-attaches data-db-2 — its old data is there
$ kubectl set image sts/db postgres=postgres:16.4        # rolling update: db-2, then db-1, then db-0, each waiting for Ready
$ kubectl rollout status sts/db
$ kubectl patch sts db -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'   # canary: only db-2 updates
$ kubectl rollout history sts/db; kubectl rollout undo sts/db
Things that surprise people
  • A stuck Pod (e.g. db-1 CrashLoopBackOff) blocks the ordered rollout and any scale-up beyond it. Fix it, or delete it so the controller re-creates it with the current template.
  • Scaling down never deletes PVCs (unless the retention policy says so). Leftover claims cost money and hold data — decide deliberately.
  • Deleting the StatefulSet with --cascade=orphan leaves Pods running — the way to migrate or re-create the controller object without downtime.
  • A StatefulSet gives you identity, not replication. Postgres does not know db-1 should follow db-0; that is application configuration, or an operator's job (CloudNativePG, Zalando, Percona).

The multi-AZ pattern (EKS demo)

Three replicas should sit in three availability zones with their disks. Two things make that work: a StorageClass with WaitForFirstConsumer so each EBS volume is created in the zone of the Pod that will use it (Day 27), and a topology spread constraint so the Pods themselves are spread (Day 18). Once data-db-1 exists in eu-west-1b, db-1 is pinned to that zone forever — the PV's node affinity does that automatically.

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: {name: gp3-wffc}
provisioner: ebs.csi.aws.com
parameters: {type: gp3, encrypted: "true"}
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
---
# in the StatefulSet's pod template:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector: {matchLabels: {app: db}}
$ kubectl get pods -l app=db -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName
$ kubectl get pv -o custom-columns=NAME:.metadata.name,CLAIM:.spec.claimRef.name,ZONE:.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]
$ kubectl get nodes -L topology.kubernetes.io/zone

Lose a zone and db-1 stays Pending until that zone returns — its disk is there. That is correct behaviour for a database: the alternative (a fresh empty disk elsewhere) would be data loss. Cross-zone failover is the application's or operator's job (promote db-2), not the scheduler's.

CKA exam tip
  • There is no kubectl create statefulset. Generate a Deployment, change kind, add serviceName, replace strategy with updateStrategy, add volumeClaimTemplates. And create the headless Service.
  • Pods stuck at db-0 Pending: usually the PVC — no StorageClass, or WaitForFirstConsumer with an unschedulable Pod. describe pvc.
  • Know the DNS shape: <pod>.<svc>.<ns>.svc.cluster.local.
  • Deleting a StatefulSet does not delete its PVCs by default.

Hands-on lab (20 min)

$ kubectl apply -f - <<EOF
apiVersion: v1
kind: Service
metadata: {name: web}
spec: {clusterIP: None, selector: {app: web}, ports: [{port: 80}]}
---
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: web}
spec:
  serviceName: web
  replicas: 3
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - name: nginx
        image: nginx:1.26
        command: ['sh','-c','echo "$(hostname) $(date)" >> /usr/share/nginx/html/index.html; exec nginx -g "daemon off;"']
        volumeMounts: [{name: www, mountPath: /usr/share/nginx/html}]
  volumeClaimTemplates:
  - metadata: {name: www}
    spec: {accessModes: [ReadWriteOnce], resources: {requests: {storage: 100Mi}}}
EOF
$ kubectl get pods -l app=web -w                                  # ordered creation
$ kubectl get pvc
$ kubectl run t --rm -it --image=busybox:1.36 -- sh -c 'nslookup web-1.web; wget -qO- web-1.web'
$ kubectl delete pod web-1 && sleep 15 && kubectl exec web-1 -- cat /usr/share/nginx/html/index.html   # two lines: same PVC
$ kubectl scale sts web --replicas=1; kubectl get pods,pvc         # web-2, web-1 gone; PVCs stay
$ kubectl scale sts web --replicas=3; kubectl exec web-2 -- cat /usr/share/nginx/html/index.html      # old data back
$ kubectl set image sts/web nginx=nginx:1.27 && kubectl get pods -l app=web -w                        # 2 → 1 → 0
$ kubectl delete sts web; kubectl delete svc web; kubectl delete pvc -l app=web

Key takeaways

  • StatefulSet = stable ordinal names, per-Pod DNS via a headless Service, per-Pod PVCs via volumeClaimTemplates.
  • Ordered create (0→N, wait Ready), delete (N→0), rolling update (N→0, one at a time, partition for canaries).
  • Restart or reschedule keeps name and PVC; scale-down keeps PVCs unless the retention policy says otherwise.
  • Multi-AZ: WaitForFirstConsumer storage + topology spread; a Pod follows its disk's zone.
  • Identity is not replication — use an operator for real database HA.
