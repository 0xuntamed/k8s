Humans authenticate with certificates or an identity provider. Programs running inside the cluster — a controller, a CI runner, an app that lists its own Pods — authenticate with a ServiceAccount: a namespaced identity object whose credential is a signed JWT the kubelet projects into the Pod. This lesson covers how those tokens are minted and verified today (short-lived, bound to the Pod), how a Pod uses one, and rounds out the picture with every authentication method the API server supports.

What you'll learn

  • Users vs ServiceAccounts, and the default SA in every namespace
  • Bound projected tokens: TokenRequest API, expiry, audience, and how the kubelet mounts them
  • Legacy Secret-based tokens and why they are discouraged
  • Using an SA from a Pod and from outside (kubectl create token); binding RBAC to it
  • All authentication strategies: x509, static tokens, bootstrap tokens, OIDC, webhook, proxy — and the built-in groups

Tokens today: bound, projected, short-lived

Since 1.24 an SA has no long-lived Secret. When a Pod starts, the kubelet calls the TokenRequest API (serviceaccounts/token subresource) and the API server mints a JWT signed with sa.key, valid ~1 hour, bound to that specific Pod and audience. The kubelet writes it into a projected volume and refreshes it before expiry (the file changes; clients must re-read it — every official client library does). Delete the Pod and the token is useless even if it leaked.

$ kubectl exec web -- ls /var/run/secrets/kubernetes.io/serviceaccount/    # ca.crt  namespace  token
$ kubectl exec web -- cat /var/run/secrets/kubernetes.io/serviceaccount/token | cut -d. -f2 | base64 -d 2>/dev/null | jq .

Using it from a Pod

apiVersion: v1
kind: Pod
metadata:
  name: lister
spec:
  serviceAccountName: app-reader        # which identity this Pod runs as
  automountServiceAccountToken: true    # default; set false for Pods that never call the API
  containers:
  - name: c
    image: bitnami/kubectl
    command: ["sh", "-c", "kubectl get pods; sleep 3600"]   # kubectl auto-detects in-cluster config
$ kubectl apply -f lister.yaml && kubectl logs lister
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:default:app-reader" cannot list resource "pods"…
$ kubectl create rolebinding app-reader-pods --clusterrole=view --serviceaccount=default:app-reader
$ kubectl delete pod lister $now; kubectl apply -f lister.yaml; kubectl logs lister      # works
# by hand, from inside any Pod:
$ SA=/var/run/secrets/kubernetes.io/serviceaccount
$ curl -s --cacert $SA/ca.crt -H "Authorization: Bearer $(cat $SA/token)" https://kubernetes.default.svc/api/v1/namespaces/$(cat $SA/namespace)/pods

In-cluster config is the convention every client library follows: read the token and CA from that directory and connect to https://kubernetes.default.svc (the API server's ClusterIP Service, injected as KUBERNETES_SERVICE_HOST/PORT env vars). Authentication then works like any bearer token; authorization is RBAC on system:serviceaccount:ns:name or its groups.

Tokens from outside the Pod

$ kubectl create token app-reader                          # a bound token for the SA, 1 h, for use from your terminal or CI
$ kubectl create token app-reader --duration=10m --audience=vault
$ kubectl config set-credentials ci --token=$(kubectl create token app-reader --duration=8h)
# Legacy: a long-lived token in a Secret (avoid; audit with: kubectl get secrets -A --field-selector type=kubernetes.io/service-account-token)
$ kubectl apply -f - <<EOF
apiVersion: v1
kind: Secret
metadata:
  name: app-reader-token
  annotations: {kubernetes.io/service-account.name: app-reader}
type: kubernetes.io/service-account-token
EOF
$ kubectl get secret app-reader-token -o jsonpath='{.data.token}' | base64 -d   # never expires, not bound — treat like a password

Under the hood · Linux

The token file is on a tmpfs projected volume with mode 0644 by default — readable by any UID in the container, which is what you want for a non-root app but also means a compromised process gets it. Mitigations: automountServiceAccountToken: false for Pods that never talk to the API (most of them), a dedicated SA per workload with minimal RBAC, and short expirationSeconds. The JWT is verified by the API server with sa.pub — no lookup, purely cryptographic — but for bound tokens it additionally checks that the referenced Pod and SA still exist (via the kubernetes.io claims), which is how deleting a Pod invalidates its token instantly. Compare to a Linux process credential: the kernel checks a uid it can verify itself, and a process that exits takes its credentials with it.

CKA exam tip
  • "Create an SA and let a Pod use it to list pods": create sa → create rolebinding --clusterrole=view --serviceaccount=ns:name → serviceAccountName in the Pod spec (or kubectl set serviceaccount deploy/x name). Verify: auth can-i list pods --as=system:serviceaccount:ns:name.
  • Need a token to paste somewhere? kubectl create token <sa>. Do not go looking for a Secret; modern clusters do not create one.
  • Pod fails to start with "serviceaccount not found" → the SA must exist in the Pod's namespace before the Pod is created.

Hands-on lab (20 min)

$ kubectl create sa reader
$ kubectl run sa-test --image=bitnami/kubectl --overrides='{"spec":{"serviceAccountName":"reader"}}' --command -- sleep 3600
$ kubectl exec sa-test -- kubectl get pods                 # Forbidden as system:serviceaccount:default:reader
$ kubectl exec sa-test -- sh -c 'cat /var/run/secrets/kubernetes.io/serviceaccount/token | cut -d. -f2 | base64 -d 2>/dev/null; echo' | jq '.["kubernetes.io"].pod.name, .exp'
$ kubectl create rolebinding reader-view --clusterrole=view --serviceaccount=default:reader
$ kubectl exec sa-test -- kubectl get pods                 # works
$ kubectl exec sa-test -- kubectl auth whoami
$ TOKEN=$(kubectl create token reader --duration=5m)
$ kubectl --token=$TOKEN --server=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}') --certificate-authority=<(kubectl config view --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d) get pods
$ kubectl run noapi --image=nginx --overrides='{"spec":{"automountServiceAccountToken":false}}'
$ kubectl exec noapi -- ls /var/run/secrets/kubernetes.io/ 2>&1   # No such file — nothing mounted
$ kubectl delete pod sa-test noapi $now; kubectl delete sa reader; kubectl delete rolebinding reader-view

Key takeaways

  • ServiceAccount = namespaced identity for Pods; identity string system:serviceaccount:ns:name; every namespace has default.
  • Tokens are JWTs signed with sa.key, requested by the kubelet via TokenRequest, bound to the Pod, ~1 h, refreshed in a projected volume. No Secrets by default.
  • In-cluster clients read token + ca.crt from /var/run/secrets/kubernetes.io/serviceaccount and call kubernetes.default.svc.
  • kubectl create token for external use; disable automount for Pods that do not need the API.
  • Humans should use OIDC; certs for components; static tokens never in production. Know the system:* groups.
