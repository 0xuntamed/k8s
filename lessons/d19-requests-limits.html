Two numbers per container decide almost everything about how your workload behaves under load: the request, which the scheduler uses to find room, and the limit, which the kernel uses to enforce a ceiling. CPU and memory react to the ceiling in completely different ways — CPU gets throttled, memory gets the process killed — and the combination of requests and limits determines which Pods die first when a node runs out. All of it is implemented by one Linux feature: cgroups.

What you'll learn

  • Units: millicores and Mi/Gi, and what "1 CPU" means
  • Requests (scheduling, guaranteed share) vs limits (enforcement)
  • CPU throttling vs memory OOMKill, and how to recognise each
  • QoS classes — Guaranteed, Burstable, BestEffort — and eviction order
  • LimitRange (per-container defaults/bounds) and ResourceQuota (per-namespace totals)

The spec

spec:
  containers:
  - name: api
    image: myapi:2.1
    resources:
      requests:
        cpu: 250m        # 0.25 CPU — used for scheduling and as a fair-share weight
        memory: 128Mi    # used for scheduling and eviction ranking
      limits:
        cpu: "1"         # hard ceiling: throttled above 1 CPU
        memory: 512Mi    # hard ceiling: OOMKilled above 512 MiB
cpu
1 = one core / vCPU / hyperthread. 500m = 0.5. Fractions are fine because CPU is time-sliced. Always an absolute quantity, never a percentage.
memory
Bytes. Mi/Gi are powers of two (128Mi = 134 217 728 B); M/G are powers of ten. Use the binary ones.
ephemeral-storage
Node disk used by the writable layer, logs and emptyDir. Exceeding the limit evicts the Pod.
extended resources
nvidia.com/gpu: 1 — advertised by device plugins, always integer, request must equal limit.
$ kubectl set resources deploy/api --requests=cpu=250m,memory=128Mi --limits=cpu=1,memory=512Mi
$ kubectl describe node worker-1 | grep -A8 'Allocated resources'    # requests/limits sum vs allocatable
$ kubectl top pod api-xyz --containers                                # actual usage (metrics-server)

Requests: how the scheduler packs nodes

The scheduler never looks at real usage. It sums the requests of Pods already on a node and compares with the node's allocatable (capacity minus reservations for the kubelet and OS). If your Pod's requests do not fit, the node is filtered out. Over-request and you waste money on idle capacity; under-request and the node is oversubscribed and things get throttled or killed.

Limits: what the kernel does at the ceiling

CPU limit → throttling

CPU is compressible. The cgroup gets a quota per 100 ms period (limit 500m = 50 ms per 100 ms). When the container uses its 50 ms, the kernel pauses its threads until the next period. The process does not crash; latency goes up. Visible as container_cpu_cfs_throttled_seconds_total in metrics, or nr_throttled in cpu.stat.

Memory limit → OOMKilled

Memory is not compressible. When the cgroup's usage hits memory.max and nothing can be reclaimed, the kernel's OOM killer terminates the largest process in the cgroup. The container exits with code 137 (128 + SIGKILL 9), the Pod shows OOMKilled in Last State, and the kubelet restarts it per restartPolicy — hence CrashLoopBackOff for chronic leaks.

$ kubectl describe pod api-xyz | grep -A4 'Last State'
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
$ kubectl get pod api-xyz -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'
Under the hood · Linux

Every container is a cgroup v2 directory under /sys/fs/cgroup/kubepods.slice/. The kubelet (via the runtime) writes:

  • cpu.weight — derived from the CPU request (request 250m → weight ≈ 10, 1000m → 39). Only matters under contention: two containers competing for a saturated core get CPU in proportion to their weights. This is why a request is a guaranteed share, not just a scheduling hint.
  • cpu.max — from the CPU limit: 50000 100000 means 50 ms per 100 ms period (CFS bandwidth control).
  • memory.max — from the memory limit; memory.min/memory.low may reflect the request depending on kubelet configuration.
# on the node, find the container's cgroup
$ CID=$(crictl ps --name api -q); crictl inspect $CID | jq -r '.info.runtimeSpec.linux.cgroupsPath'
$ cat /sys/fs/cgroup/kubepods.slice/.../cpu.max cpu.weight memory.max
$ cat /sys/fs/cgroup/kubepods.slice/.../cpu.stat | grep throttled     # nr_throttled, throttled_usec
$ cat /sys/fs/cgroup/kubepods.slice/.../memory.events                 # oom_kill counter
$ dmesg | grep -i 'killed process'                                     # the OOM killer's log line

The kubelet reserves capacity for itself and the OS (--kube-reserved, --system-reserved) in sibling cgroups, which is why allocatable is smaller than capacity.

QoS classes and eviction

Kubernetes derives a Quality-of-Service class from your requests and limits. It is not something you set; it is how the kubelet ranks Pods when the node (not a single container) runs short of memory or disk.

ClassConditionUnder node pressureOOM score adj
GuaranteedEvery container has limits = requests for both CPU and memoryEvicted last; only if using more than requested (impossible) or system needs it-997
BurstableAt least one request or limit set, but not GuaranteedEvicted after BestEffort, ordered by usage above request2 – 999 (scaled by request)
BestEffortNo requests or limits anywhereEvicted first1000
$ kubectl get pod api-xyz -o jsonpath='{.status.qosClass}'

Two different mechanisms use this ranking: the kubelet's eviction manager (soft/hard thresholds like memory.available < 100Mi → evicts Pods, phase Failed, reason Evicted) and the kernel OOM killer when the node runs out before the kubelet reacts (uses oom_score_adj — BestEffort processes die first).

Practical guidance
  • Always set memory requests and limits, and set them equal — memory cannot be reclaimed, so a burst that works today is an OOM tomorrow.
  • Set CPU requests; consider not setting CPU limits for latency-sensitive services (throttling hurts tail latency, and the request already guarantees a share). Set them for batch jobs and noisy neighbours.
  • Requests too high → Pending Pods and idle nodes. Use kubectl top / VPA recommendations (Day 20) to right-size.

LimitRange: defaults and bounds per namespace

apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: dev
spec:
  limits:
  - type: Container
    defaultRequest: {cpu: 100m, memory: 64Mi}   # injected if the container sets no request
    default:        {cpu: 500m, memory: 256Mi}  # injected if the container sets no limit
    min:            {cpu: 50m,  memory: 32Mi}   # reject smaller
    max:            {cpu: "2",  memory: 2Gi}    # reject larger
    maxLimitRequestRatio: {cpu: "4"}            # limit ≤ 4 × request
  - type: Pod
    max: {cpu: "4", memory: 4Gi}                # sum over containers
  - type: PersistentVolumeClaim
    min: {storage: 1Gi}
    max: {storage: 50Gi}

Applied by the LimitRanger admission plugin at Pod creation: defaults are injected (you will see them in get -o yaml though you never wrote them), violations are rejected with a clear message. It does not affect Pods that already exist.

ResourceQuota: totals per namespace

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a
  namespace: dev
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
    pods: "50"
    requests.nvidia.com/gpu: "2"
  scopeSelector:                       # optional: quota only for a priority class
    matchExpressions:
    - operator: In
      scopeName: PriorityClass
      values: [high]

When a quota constrains a resource, every Pod must specify it, or it is rejected with must specify requests.cpu — pair quotas with a LimitRange that supplies defaults. kubectl describe quota shows Used vs Hard. Quotas count requests/limits, not usage.

CKA exam tip
  • Pod Pending with Insufficient cpu/memory → requests exceed what any node has free. Lower the request or find the node hog with kubectl describe nodes | grep -A5 Allocated.
  • Exit code 137 / OOMKilled → raise the memory limit (or fix the leak). Exit code 137 without OOMKilled = something sent SIGKILL (e.g. grace period expired).
  • "Pod rejected: must specify…" or "exceeded quota" → look at the namespace's LimitRange and ResourceQuota.
  • kubectl set resources is the fastest way to add requests/limits to a Deployment.

Hands-on lab (20 min)

# OOMKill on purpose
$ kubectl run hog --image=polinux/stress --restart=Never --limits=memory=100Mi --requests=memory=50Mi -- stress --vm 1 --vm-bytes 200M --vm-hang 1
$ sleep 15; kubectl describe pod hog | grep -A3 'Last State'; kubectl get pod hog   # OOMKilled, exit 137
# CPU throttling: limit 200m, try to burn a full core
$ kubectl run burn --image=busybox --restart=Never --limits=cpu=200m --requests=cpu=100m -- sh -c 'while true; do :; done'
$ kubectl top pod burn        # stays at ~200m — throttled, not killed
$ docker exec cka-worker sh -c 'cat /sys/fs/cgroup/kubepods.slice/*/*/cpu.stat 2>/dev/null | grep nr_throttled | head' 2>/dev/null
# QoS
$ kubectl run be --image=nginx; kubectl get pod be -o jsonpath='{.status.qosClass}{"\n"}'        # BestEffort
$ kubectl run g --image=nginx --requests=cpu=100m,memory=64Mi --limits=cpu=100m,memory=64Mi; kubectl get pod g -o jsonpath='{.status.qosClass}{"\n"}'   # Guaranteed
# LimitRange defaults
$ kubectl create ns lr && kubectl apply -n lr -f - <<EOF
apiVersion: v1
kind: LimitRange
metadata: {name: d}
spec: {limits: [{type: Container, default: {cpu: 300m, memory: 128Mi}, defaultRequest: {cpu: 100m, memory: 64Mi}}]}
EOF
$ kubectl run x --image=nginx -n lr && kubectl get pod x -n lr -o jsonpath='{.spec.containers[0].resources}{"\n"}'
$ kubectl delete pod hog burn be g $now; kubectl delete ns lr

Key takeaways

  • Requests: scheduling + guaranteed share (cpu.weight). Limits: enforcement (cpu.max, memory.max).
  • CPU over limit → throttled (slow). Memory over limit → OOMKilled, exit 137, restart.
  • QoS: Guaranteed (req = lim) > Burstable > BestEffort in eviction and OOM order. Set memory req = lim.
  • LimitRange injects defaults and bounds per container; ResourceQuota caps namespace totals and forces requests to be specified.
