Troubleshooting is 30% of the CKA and most of real operations. The control plane is four static Pods and a kubelet on one or three machines, so every failure is one of a short list: a manifest with a typo, a wrong path or flag, an expired certificate, a full disk, a broken kubeconfig, or etcd unhappy. This lesson is a decision tree: from the symptom kubectl shows you, to the node, to the file, to the fix — with each component's characteristic failure and where its evidence lives.

What you'll learn

  • The first five commands, in order, and what each rules in or out
  • Working without kubectl: crictl, journalctl, the manifests directory, static Pod logs
  • API server failures: flags, certificates, etcd connectivity, ports
  • etcd failures: data dir, certs, disk, quorum
  • Scheduler and controller-manager failures: Pods Pending / nothing reconciling; kubeconfig and leader election
  • kubelet on the control-plane node, and kubeconfig/cert problems on the client side

The decision tree

  1. Does kubectl work at all? kubectl get nodes. Errors: connection refused → API server down (or wrong port/address in kubeconfig); timeout → network/firewall or wrong server IP; x509 → certificate problem (client cert, CA, expiry, or server SAN); Unauthorized/Forbidden → authn/authz, not the control plane. Cross-check with kubectl --kubeconfig /etc/kubernetes/admin.conf get nodes on the control-plane node — if that works, your kubeconfig is the problem.
  2. On the control-plane node: is the kubelet running? systemctl status kubelet. If not, nothing else can be — see the kubelet section below.
  3. Are the static Pods running? crictl ps -a | grep -E 'apiserver|etcd|scheduler|controller'. Missing entirely → the manifest is not being read (wrong directory, invalid YAML, kubelet staticPodPath). Exited/restarting → read its log: crictl logs <id> (use -a to find exited containers; the last few lines say why).
  4. Read the manifest. cat /etc/kubernetes/manifests/kube-apiserver.yaml: compare flag values to the files they name (ls -l each path), the ports, and the etcd address. Typos in flags produce unknown flag in the log; wrong paths produce no such file; wrong certs produce x509.
  5. Check certificates and disk. kubeadm certs check-expiration; df -h /var/lib/etcd /var/log; free -m.
  6. Once the API server answers: kubectl get pods -n kube-system, kubectl get events -A --sort-by=.lastTimestamp, kubectl get componentstatuses (deprecated but still prints), kubectl get --raw /readyz?verbose.

kube-apiserver

$ crictl ps -a --name kube-apiserver          # state and restart count
$ crictl logs --tail 30 $(crictl ps -a --name kube-apiserver -q | head -1)
# typical last lines and what they mean:
#   "unknown flag: --etcd-server"            → typo in a flag name (it is --etcd-servers)
#   "open /etc/kubernetes/pki/apiserver.crt: no such file or directory"   → wrong path in --tls-cert-file or hostPath volume
#   "x509: certificate has expired"          → kubeadm certs renew all
#   "context deadline exceeded" / "connection refused" to 127.0.0.1:2379   → etcd is down, or --etcd-servers is wrong
#   "bind: address already in use"           → --secure-port conflicts (another process, or a duplicate apiserver)
$ grep -E '^\s+- --' /etc/kubernetes/manifests/kube-apiserver.yaml | head -40
$ ss -tlnp | grep -E '6443|2379'
$ curl -sk https://127.0.0.1:6443/livez?verbose | tail -5      # once it is listening
$ kubeadm certs check-expiration

Editing the manifest is the fix in most cases; the kubelet restarts the Pod within seconds of the file changing (watch crictl ps). If nothing happens after an edit, the YAML is now invalid — journalctl -u kubelet | grep -i manifest will say so.

etcd

$ crictl logs --tail 30 $(crictl ps -a --name etcd -q | head -1)
#   "open /var/lib/etcd/member/…: no such file"   → --data-dir or the hostPath volume points somewhere wrong (common after a restore)
#   "no space left on device"                     → disk full; etcd stops writing (alarm NOSPACE)
#   "x509" / "tls: bad certificate"               → etcd/server.crt, peer.crt or the CA in --trusted-ca-file
#   "lost leader" / "request timed out"           → quorum lost in HA (check the other members) or disk latency
$ ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key endpoint health
$ ETCDCTL_API=3 etcdctl … endpoint status -w table          # leader, db size, raft index
$ ETCDCTL_API=3 etcdctl … alarm list; etcdctl … defrag; etcdctl … alarm disarm     # after freeing space
$ df -h /var/lib/etcd; ls -la /var/lib/etcd/member

kube-scheduler and kube-controller-manager

Symptoms are indirect: with the scheduler down, new Pods stay Pending with no events; with the controller-manager down, Deployments do not create ReplicaSets, ReplicaSets do not create Pods, nodes never go NotReady, Jobs never complete, CSRs are never signed, Endpoints do not update. Existing workloads keep running in both cases.

$ kubectl get pods -n kube-system | grep -E 'scheduler|controller'      # CrashLoopBackOff? missing?
$ kubectl -n kube-system logs kube-scheduler-cp-1 --tail=20
#   "unable to load client CA / kubeconfig"  → --kubeconfig=/etc/kubernetes/scheduler.conf path or the file's cert
#   "unknown flag"                          → typo
#   "error retrieving resource lock … leases": leader election failing → RBAC or API connectivity
$ kubectl -n kube-system get lease kube-scheduler kube-controller-manager   # holderIdentity shows the active instance (HA)
$ crictl ps -a | grep -E 'scheduler|controller'; crictl logs …            # if they never register as pods

A trick question loves the image name: image: registry.k8s.io/kube-scheduler:v1.32.1 misspelled → ErrImagePull on the mirror Pod. Or the hostPath for /etc/kubernetes/scheduler.conf pointing at a non-existent file → the container starts and exits immediately.

kubelet on the control-plane node

$ systemctl status kubelet; journalctl -u kubelet -n 50 --no-pager
#   "failed to load Kubelet config file /var/lib/kubelet/config.yaml"   → path in the systemd drop-in / file missing or invalid YAML
#   "running with swap on is not supported"                             → swapoff -a
#   "unable to load client CA file … kubelet.conf"                      → kubelet.conf cert expired/wrong (check /var/lib/kubelet/pki/)
#   "misconfiguration: kubelet cgroup driver: systemd is different from docker cgroup driver: cgroupfs"   → containerd config
#   "connection refused" to containerd.sock                             → systemctl restart containerd
$ cat /var/lib/kubelet/kubeadm-flags.env; cat /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf
$ grep staticPodPath /var/lib/kubelet/config.yaml                     # must be /etc/kubernetes/manifests
$ systemctl daemon-reload && systemctl restart kubelet

Client side: kubeconfig and certificates

$ kubectl config view --minify                                  # which server? which user?
$ kubectl config view --raw -o jsonpath='{.clusters[0].cluster.server}'   # port 6443? right IP?
$ kubectl config view --raw -o jsonpath='{.users[0].user.client-certificate-data}' | base64 -d | openssl x509 -noout -dates -subject
$ openssl s_client -connect <server>:6443 < /dev/null 2>/dev/null | openssl x509 -noout -ext subjectAltName   # is the IP you use in the SANs?
# "certificate signed by unknown authority" → wrong CA in kubeconfig; compare with /etc/kubernetes/pki/ca.crt
# "certificate is valid for 10.96.0.1, 192.168.56.10, not 1.2.3.4" → use an address in the SANs, or add one (kubeadm init phase certs apiserver --apiserver-cert-extra-sans)
$ sudo cp /etc/kubernetes/admin.conf ~/.kube/config            # the known-good admin kubeconfig
Under the hood · Linux

When kubectl is useless, the node still has everything: systemctl/journalctl for the kubelet and containerd, crictl for containers, ls -l/cat/diff for manifests and certs, openssl x509 for expiry and SANs, ss -tlnp for who listens on 6443/2379/10250, df -h/free -m for resources, dmesg for OOM kills of etcd or the API server. The kubelet re-reads a manifest when its mtime changes — touch forces a restart; mv to /tmp and back is a clean "restart this component". The shell toolkit page lists these with examples.

CKA exam tip
  • The exam breaks one thing at a time: a flag typo, a wrong file path, a wrong image tag, a swapped port, an expired cert, a bad kubeconfig path in a manifest. Read the failing component's crictl logs and the manifest side by side; the log names the exact problem.
  • After editing a manifest, wait (20–60 s) and verify with crictl ps before concluding it did not work. Do not restart the kubelet unless you changed kubelet config.
  • Keep a mental map: kubectl error → API server or kubeconfig; Pending without events → scheduler; objects not reconciling → controller-manager; everything read-only + apiserver log mentions etcd → etcd.
  • Fix from the node with sudo -i; the exam gives you SSH to the control plane.

Hands-on lab (40 min) — break it, then fix it (Day 54 cluster or KIND control-plane container)

# 1. flag typo
$ sudo sed -i 's/--etcd-servers=/--etcd-server=/' /etc/kubernetes/manifests/kube-apiserver.yaml
$ sleep 30; kubectl get nodes; sudo crictl ps -a | grep apiserver; sudo crictl logs $(sudo crictl ps -a --name kube-apiserver -q | head -1) 2>&1 | tail -2
$ sudo sed -i 's/--etcd-server=/--etcd-servers=/' /etc/kubernetes/manifests/kube-apiserver.yaml; sleep 30; kubectl get nodes
# 2. wrong kubeconfig path for the scheduler
$ sudo sed -i 's#scheduler.conf#scheduler.yaml#g' /etc/kubernetes/manifests/kube-scheduler.yaml
$ kubectl run pending --image=nginx; sleep 10; kubectl get pod pending; kubectl describe pod pending | tail -2    # Pending, no events
$ kubectl -n kube-system get pods | grep scheduler; sudo crictl logs $(sudo crictl ps -a --name kube-scheduler -q | head -1) 2>&1 | tail -2
$ sudo sed -i 's#scheduler.yaml#scheduler.conf#g' /etc/kubernetes/manifests/kube-scheduler.yaml; sleep 20; kubectl get pod pending -o wide
# 3. kubelet config path
$ sudo sed -i 's#/var/lib/kubelet/config.yaml#/var/lib/kubelet/config.yml#' /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf
$ sudo systemctl daemon-reload && sudo systemctl restart kubelet; sleep 5; systemctl status kubelet | head -5; journalctl -u kubelet -n 3 --no-pager
$ sudo sed -i 's#config.yml#config.yaml#' /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf && sudo systemctl daemon-reload && sudo systemctl restart kubelet
# 4. broken client kubeconfig
$ sed -i 's/6443/6444/' ~/.kube/config; kubectl get nodes; sed -i 's/6444/6443/' ~/.kube/config
$ kubectl delete pod pending $now

Key takeaways

  • Order: does kubectl work (and with admin.conf on the node)? → kubelet running? → static Pods running (crictl ps -a)? → read their logs → read their manifests → certs and disk.
  • API server: flags, file paths, certs, etcd address — the log line names it. Edit the manifest; the kubelet restarts it.
  • etcd: data dir, disk space, certs, quorum; etcdctl endpoint health/status with the three cert flags.
  • Scheduler down = Pending with no events; controller-manager down = nothing reconciles. Check their kubeconfig paths and images.
  • Client errors (x509, refused, wrong port) are kubeconfig problems until proven otherwise.
