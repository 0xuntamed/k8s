A worker node is simpler than the control plane — a kubelet, a container runtime, a CNI, and kube-proxy — but it fails in more ways, because it also has the disk, the memory, the network and the workloads. This lesson is the runbook for the two questions that cover it: "the node is NotReady" and "the node is Ready but Pods on it are broken", plus the Service/DNS layer that lives on every node.

What you'll learn

  • Reading kubectl describe node: conditions, taints, allocatable, events
  • NotReady: kubelet down, runtime down, CNI missing, certificates, node pressure, network partition
  • Pods failing on one node: image pulls, volumes, sandbox creation, cgroups, disk
  • Service traffic and DNS failing on a node: kube-proxy, iptables, conntrack, CNI routes
  • The node-side commands: systemctl, journalctl, crictl, ip/ss/iptables, df/free

After a node is Unknown/NotReady, the node controller taints it not-ready/unreachable:NoExecute; Pods are evicted 5 minutes later (Day 16) and show Terminating until the node returns or you --force delete them.

NotReady: the checklist on the node

$ ssh worker-1
# 1. kubelet
$ systemctl status kubelet                       # active (running)? if not: systemctl start kubelet, then:
$ journalctl -u kubelet -n 50 --no-pager         # the reason it will not start / keeps restarting
#   "failed to load Kubelet config file"          → /var/lib/kubelet/config.yaml missing/invalid or wrong path in the drop-in
#   "running with swap on"                        → swapoff -a; comment out in /etc/fstab
#   "x509: certificate has expired"               → /var/lib/kubelet/pki/kubelet-client-current.pem; rejoin or renew
#   "Unable to register node … Unauthorized"      → kubelet.conf/bootstrap credentials wrong
#   "dial tcp 192.168.56.10:6443: connect: no route to host" → network to the API server; wrong server in kubelet.conf
#   "cgroup driver mismatch"                      → containerd SystemdCgroup
# 2. runtime
$ systemctl status containerd; crictl info | head -30; crictl ps        # socket reachable? containers running?
$ grep -E 'containerRuntimeEndpoint|cgroupDriver' /var/lib/kubelet/config.yaml
# 3. CNI
$ ls /etc/cni/net.d/ /opt/cni/bin/                # empty → "cni plugin not initialized"; CNI DaemonSet pod on this node?
$ kubectl get pods -n calico-system -o wide --field-selector spec.nodeName=worker-1     # from anywhere
# 4. resources
$ df -h / /var/lib/containerd /var/lib/kubelet    # DiskPressure at 85–90%: crictl rmi --prune; journalctl --vacuum-size=200M; find big logs
$ free -m; dmesg | grep -i -E 'oom|killed process' | tail
$ ps -eo pid,ppid,stat,cmd | grep -c Z            # zombie storm → PIDPressure
# 5. network to the control plane
$ curl -sk https://192.168.56.10:6443/healthz     # ok? if not: routing, firewall, or the API server (Day 57)
$ ip route; ip addr; ss -tlnp | grep -E '10250|10256'
# 6. time
$ timedatectl | grep -E 'synchronized|NTP'         # clock skew breaks TLS ("certificate is not yet valid")
# common one-line fixes
$ sudo systemctl daemon-reload && sudo systemctl restart kubelet
$ sudo systemctl restart containerd
$ sudo swapoff -a
$ sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml && sudo systemctl restart containerd
$ sudo crictl rmi --prune                          # reclaim disk from unused images
$ kubeadm token create --print-join-command        # on cp: then on the node: kubeadm reset -f && kubeadm join …   (last resort: re-register)

Networking on the node: Services and DNS

# is kube-proxy running here and healthy?
$ kubectl get pods -n kube-system -l k8s-app=kube-proxy -o wide --field-selector spec.nodeName=worker-1
$ kubectl -n kube-system logs -l k8s-app=kube-proxy --field-selector spec.nodeName=worker-1 --tail=20   # "Using iptables Proxier", errors syncing rules?
$ curl -s localhost:10256/healthz                   # kube-proxy health on the node
# are the Service rules present?
$ sudo iptables -t nat -L KUBE-SERVICES -n | head; sudo iptables -t nat -L KUBE-NODEPORTS -n
$ sudo ipvsadm -Ln                                  # if in IPVS mode
$ sudo conntrack -L 2>/dev/null | wc -l; sysctl net.netfilter.nf_conntrack_max     # table full → dropped connections
$ sysctl net.ipv4.ip_forward net.bridge.bridge-nf-call-iptables                    # both must be 1
# pod network
$ ip route | grep -E '192.168|10.244'               # routes to other nodes' pod CIDRs (Calico/kindnet) or the VXLAN/tunnel device
$ ip link | grep -E 'cali|veth|vxlan|tunl'
$ crictl inspectp <sandbox> | jq '.info.runtimeSpec.linux.namespaces' ; nsenter -t <pid> -n ip addr   # inside a pod's netns
$ kubectl run t --rm -it --image=nicolaka/netshoot --overrides='{"spec":{"nodeName":"worker-1"}}' -- sh   # test FROM this node: curl svc, nslookup, ping a pod on another node
# DNS specifically: CoreDNS pods healthy? ClusterIP 10.96.0.10 reachable from this node?
$ kubectl run t --rm -it --image=busybox:1.36 --overrides='{"spec":{"nodeName":"worker-1"}}' -- nslookup kubernetes.default
Under the hood · Linux

Every row above maps to a Linux subsystem: systemd units for kubelet/containerd; cgroups for pressure and evictions (/sys/fs/cgroup/kubepods.slice, memory.events); the VFS for volumes (findmnt, mount); netfilter for Services (iptables -t nat, conntrack); netlink for the Pod network (ip route, ip link, ip netns/nsenter); the journal for everything the daemons say. The node-level tools — ss, tcpdump -i any port 53, strace -p, dmesg, df, free, top — answer questions kubectl cannot ask. The shell toolkit page is the reference.

CKA exam tip
  • "Node NotReady, fix it" is nearly always: kubelet stopped (start it), kubelet misconfigured (config path / cert / swap), or containerd stopped. Start with systemctl status kubelet and journalctl -u kubelet. Two minutes.
  • After a fix, kubectl get nodes takes up to ~40 s to flip to Ready. Verify before moving on.
  • Pods stuck Terminating on a dead node: kubectl delete pod X --force --grace-period=0.
  • For "Service unreachable" questions, check kube-proxy on the node and the Service's endpoints before touching iptables.

Hands-on lab (30 min) — Day 54 cluster or KIND (docker exec into a worker)

# 1. kubelet down
$ ssh worker-1 sudo systemctl stop kubelet; sleep 60; kubectl get nodes           # NotReady after ~40 s
$ kubectl get pods -o wide | grep worker-1                                         # still Running (from the API's view) — 5 min to eviction
$ ssh worker-1 sudo systemctl start kubelet; sleep 15; kubectl get nodes
# 2. broken kubelet config
$ ssh worker-1 "sudo sed -i 's/cgroupDriver: systemd/cgroupDriver: cgroupfs/' /var/lib/kubelet/config.yaml && sudo systemctl restart kubelet"
$ sleep 30; kubectl get nodes; ssh worker-1 "sudo journalctl -u kubelet -n 5 --no-pager | grep -i cgroup"
$ ssh worker-1 "sudo sed -i 's/cgroupDriver: cgroupfs/cgroupDriver: systemd/' /var/lib/kubelet/config.yaml && sudo systemctl restart kubelet"
# 3. runtime down
$ ssh worker-1 sudo systemctl stop containerd; sleep 60; kubectl describe node worker-1 | grep -A2 'Ready '   # "container runtime is down"
$ ssh worker-1 sudo systemctl start containerd
# 4. kube-proxy gone on one node
$ kubectl -n kube-system patch ds kube-proxy -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/hostname":"worker-2"}}}}}'
$ sleep 20; kubectl run t --rm -it --image=busybox:1.36 --overrides='{"spec":{"nodeName":"worker-1"}}' -- wget -qO- --timeout=2 http://kubernetes.default   # existing rules linger; new services would not sync
$ kubectl -n kube-system patch ds kube-proxy --type=json -p '[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'
# 5. disk pressure (careful)
$ ssh worker-1 "sudo fallocate -l 90%FREE /var/lib/containerd/big 2>/dev/null || sudo dd if=/dev/zero of=/var/lib/containerd/big bs=1M count=3000"
$ sleep 60; kubectl describe node worker-1 | grep -E 'DiskPressure|Taints'; ssh worker-1 sudo rm /var/lib/containerd/big

Key takeaways

  • describe node: the Ready condition's message and the pressure conditions tell you which layer failed.
  • NotReady checklist on the node: kubelet → containerd → CNI files/DaemonSet → disk/memory/PIDs → network to :6443 → clock.
  • Ready-but-broken Pods: sandbox/CNI (ContainerCreating), pulls (registry from this node), volumes (CSI node plugin, attachments), evictions (pressure).
  • Service/DNS problems on a node are kube-proxy, sysctls, conntrack or CNI routes; test from a Pod pinned to that node.
  • Evictions from a dead node take 5 minutes; force-delete stuck Terminating Pods.
