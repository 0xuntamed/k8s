Kubernetes orchestrates containers, so the first question is the one most tutorials skip: what is a container? Not "a lightweight VM" — a container is an ordinary Linux process that has been given a restricted view of the machine. Once you see that, images, volumes, networking and Pods all become concrete.

The problem: "it works on my machine"

An application is never just its code. It is code plus a runtime (Python 3.12, Node 22, the JVM), plus system libraries (glibc, OpenSSL), plus config files, plus environment variables, plus assumptions about paths and users. Move the code to another machine where any one of those differs and it breaks.

Before containers there were two answers, both bad:

Install everything on the server

Fast and cheap, but two apps that need different versions of the same library cannot coexist, servers drift over time, and "the server" becomes a snowflake nobody dares rebuild.

One virtual machine per app

Perfect isolation, but every VM boots a full operating system: gigabytes of disk, minutes to start, and a whole kernel's worth of RAM overhead per app.

Containers are the third answer: package the app with everything it depends on (the whole userland, down to the C library), but share the host's kernel instead of booting a new one.

Mental model

A VM virtualises hardware — it pretends to be a computer, so you install an OS on it. A container virtualises the operating system — it pretends to be a fresh Linux install, so you just start a process in it. The kernel is shared; everything above the kernel is private.

A container is a process

Run docker run -d nginx and then look at the host with ps. You will find an nginx process, owned by the host kernel, scheduled by the host scheduler, using host memory. It is not "inside" anything in the way a VM is. What makes it a container is that the kernel has been told to lie to it about three things:

  1. What it can see — its own process tree, network stack, hostname, mount table, users. These lies are namespaces.
  2. How much it can use — CPU time, memory, I/O. These caps are cgroups (control groups).
  3. What its filesystem looks like — a root filesystem assembled from read-only image layers plus a thin writable layer, using a union filesystem (OverlayFS).
Under the hood · Linux

You can build a container by hand without Docker. unshare --pid --net --mount --uts --fork bash gives you a shell in new PID, network, mount and hostname namespaces; cgcreate/systemd-run puts it in a cgroup with a memory cap; mount -t overlay assembles a root filesystem from layers; chroot or pivot_root switches into it. Docker, containerd and Kubernetes automate exactly these system calls — nothing more exotic. The three Linux-track pages linked below walk through each one with commands you can run.

Images vs containers

An image is a read-only, layered filesystem snapshot plus some metadata (which command to run, which ports it listens on, environment variables). A container is a running (or stopped) instance of an image: the image's layers, plus one writable layer on top, plus a process.

This is why containers start in milliseconds (nothing is copied) and why anything written inside a container disappears when the container is removed (the writable layer is deleted). Persisting data is what volumes are for.

What happens on docker run

Docker is not one program. The docker CLI talks to the dockerd daemon over a Unix socket; dockerd delegates container lifecycle to containerd; containerd uses runc (the reference OCI runtime) to actually create the namespaces and cgroups and exec the process. Kubernetes talks to containerd directly, which is why "Kubernetes dropped Docker" (in v1.24) changed nothing for your images.

OCI: the standards that make this interchangeable

The Open Container Initiative defines two specs: the image spec (how layers and metadata are packaged — what Docker Hub stores) and the runtime spec (how a bundle is turned into a running container — what runc implements). Any OCI image runs on any OCI runtime: Docker, containerd, CRI-O, Podman, and every Kubernetes cluster.

Registries and image names

A registry stores images; Docker Hub is the default public one. A full image reference has four parts:

docker.io/library/nginx:1.27
└──┬───┘ └──┬──┘ └─┬─┘ └─┬─┘
registry  namespace  repo   tag (default: latest)
  • nginx alone expands to docker.io/library/nginx:latest. Official images live in the library namespace.
  • Tags are mutable pointers. latest is just a tag someone chose to push — it is not automatically the newest. For anything reproducible, pin a version tag or better, a digest (nginx@sha256:…).
  • Private registries (ECR, GCR, ACR, Harbor, GitLab) use the same protocol; you just log in first. Kubernetes handles credentials with imagePullSecrets.

Essential commands

CommandWhat it does
docker pull nginx:1.27Download image layers you do not already have.
docker imagesList local images (with size and ID).
docker run -d --name web -p 8080:80 nginxCreate + start a container in the background, publish host port 8080 → container 80.
docker ps / docker ps -aRunning containers / all containers including stopped.
docker logs -f webStream the container's stdout/stderr.
docker exec -it web shStart an extra process (a shell) inside the container's namespaces.
docker stop webSend SIGTERM, wait 10 s, then SIGKILL.
docker rm web / docker rmi nginxDelete a container / an image.
docker inspect webFull JSON: IPs, mounts, env, cgroup path, PID.

Hands-on lab (10 min)

Prove to yourself that a container is a process.

$ docker run -d --name web nginx
$ docker exec web ps -ef          # inside: nginx is PID 1
$ ps -ef | grep "nginx: master"   # on the host: same process, a big PID
$ PID=$(docker inspect -f '{{.State.Pid}}' web)
$ sudo ls -l /proc/$PID/ns        # its namespaces (pid, net, mnt, uts, ipc…)
$ sudo cat /proc/$PID/cgroup      # the cgroup it lives in
$ docker exec web hostname        # = the container ID (UTS namespace)
$ docker exec web ip addr         # its own eth0 (network namespace)
$ docker rm -f web

Compare the two ps outputs: identical process, different PID. That difference is the PID namespace, and it is the whole trick.

Key takeaways

  • A container is a normal process with a restricted view (namespaces), a resource budget (cgroups) and a layered root filesystem (OverlayFS). The kernel is shared with the host.
  • Images are immutable stacks of read-only layers; a container adds one writable layer that dies with it.
  • docker → dockerd → containerd → runc. Kubernetes skips the first two and talks to containerd via CRI.
  • Image references are registry/namespace/repo:tag; latest is just a tag.
