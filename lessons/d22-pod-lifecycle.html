Every STATUS you see in kubectl get pods is a summary of three things: the Pod's phase, each container's state, and the kubelet's reason for that state. Once you can read them, "CrashLoopBackOff" stops being a mystery and becomes "the app exited, exit code N, here is its last log". This lesson also covers what really happens when a Pod is deleted — a 30-second dance between endpoints, hooks and signals that decides whether your users see errors during every deploy.

What you'll learn

  • Pod phases, container states, and Pod conditions — and how kubectl summarises them
  • restartPolicy and the exponential back-off behind CrashLoopBackOff
  • imagePullPolicy defaults and the :latest trap
  • The termination sequence: deletion → endpoints → preStop → SIGTERM → grace period → SIGKILL
  • Lifecycle hooks and a decoder for every common error status

Phases, states and conditions

Pod phase (status.phase)Meaning
PendingAccepted, but not all containers are running: waiting for scheduling, image pulls, volume mounts, init containers.
RunningBound to a node, at least one container running or (re)starting.
SucceededAll containers exited 0 and will not restart (Jobs, restartPolicy: Never/OnFailure).
FailedAll containers terminated, at least one with non-zero exit, no restarts coming. Also Evicted Pods.
UnknownThe node stopped reporting (kubelet down or unreachable).

Each container has a state: Waiting (with a reason: ContainerCreating, ImagePullBackOff, CrashLoopBackOff…), Running (since when), or Terminated (exit code, reason, finished at). kubectl get pods STATUS shows the phase unless a container has a more specific Waiting reason, in which case it shows that. describe also shows conditions: PodScheduled, Initialized, ContainersReady, Ready (all containers ready and readiness gates satisfied — this is what puts the Pod into Service endpoints).

$ kubectl get pod api -o jsonpath='{.status.phase}{"\n"}{.status.containerStatuses[*].state}{"\n"}'
$ kubectl get pod api -o jsonpath='{range .status.conditions[*]}{.type}={.status} {end}{"\n"}'

restartPolicy and back-off

spec:
  restartPolicy: Always      # Always (default; required by Deployments) · OnFailure · Never

The policy is Pod-wide and applies to app containers (init containers use it too; native sidecars override with their own). It is enforced by the kubelet on the node — the control plane is not involved, which is why containers restart even while the API server is down.

Back-off starts at 10 s and doubles — 10, 20, 40, 80, 160 — capped at 300 s, and resets after a container has run for 10 minutes without exiting. RESTARTS in get pods counts them; describe shows Last State: Terminated, Reason, Exit Code; logs --previous shows the crashed container's output.

Exit codeTypical meaning
0Clean exit. With restartPolicy: Always it is restarted anyway (a container that "finishes" under a Deployment is a bug — use a Job).
1, 2, 3…Application error. Read the logs.
126 / 127Command not executable / not found — wrong command, missing binary in a slim image.
137SIGKILL (128+9): OOMKilled, or grace period expired during termination.
139SIGSEGV (128+11): the process crashed.
143SIGTERM (128+15): asked to stop and did so — normal during a rollout.

imagePullPolicy

containers:
- name: api
  image: myapi:2.1
  imagePullPolicy: IfNotPresent    # Always · IfNotPresent · Never
  • Default is IfNotPresent — except when the tag is :latest or omitted, where the default is Always.
  • Always still uses the local cache when the registry's digest matches; it only guarantees a check, not a download.
  • Never fails if the image is not already on the node — useful with kind load docker-image.
  • The trap: you push a new build to myapi:2.1 (mutable tag) and Pods on nodes that already cached 2.1 keep running the old bits. Use immutable tags or digests; kubectl rollout restart does not help if the policy is IfNotPresent and the node has the old layer.

Termination, step by step

  1. Deletion requested. kubectl delete, a rollout, an eviction, a scale-down. The API server sets metadata.deletionTimestamp and the Pod shows Terminating. It is not removed yet.
  2. Two things happen in parallel. The EndpointSlice controller removes the Pod from Service endpoints (kube-proxy and ingress controllers update within a second or so), and the kubelet begins shutting containers down. The race between these is why in-flight requests can fail on a naive app.
  3. preStop hook runs, if defined — inside the container, synchronously. Its duration counts against the grace period.
  4. SIGTERM to PID 1 of each container (Day 4: exec form matters). The app should stop accepting new connections, finish in-flight work, and exit.
  5. Grace period — terminationGracePeriodSeconds, default 30 s, counted from step 2. If the container exits earlier, done.
  6. SIGKILL when the period expires. Exit code 137.
  7. Pod object removed from the API once all containers are gone (and finalizers, if any, are cleared).
spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: api
    image: myapi:2.1
    lifecycle:
      postStart:                          # runs right after the container starts (no ordering guarantee vs ENTRYPOINT)
        exec: {command: ["sh", "-c", "echo started >> /tmp/log"]}
      preStop:                            # runs before SIGTERM; typical: sleep to let endpoints propagate
        exec: {command: ["sh", "-c", "sleep 5"]}
      # httpGet and sleep (1.30+) are also valid hook handlers
The 5-second sleep trick

A preStop: sleep 5 gives kube-proxy and load balancers time to remove the Pod from rotation before the app receives SIGTERM. Combined with an app that handles SIGTERM gracefully, this is what makes rolling updates truly zero-downtime. kubectl delete pod x --grace-period=0 --force skips all of this and removes the object immediately (the container may briefly keep running).

Under the hood · Linux

The kubelet asks containerd to stop the container; containerd's shim sends SIGTERM to the container's PID 1 (its init process in the PID namespace), waits timeout seconds, then sends SIGKILL. The kernel then tears down the namespaces as the last process exits. A PID 1 that ignores SIGTERM — a shell in shell-form CMD, or a Java app without a shutdown hook — cannot be stopped by anything but SIGKILL, which is exactly why "every deploy takes 30 seconds longer than it should" is so common. kill -TERM 1 from kubectl exec is a quick way to test whether your app handles it.

CKA exam tip
  • "Pod keeps restarting" → logs --previous + exit code. Fix the cause (missing env, wrong command, wrong port), not the symptom.
  • "Reduce time to terminate" → terminationGracePeriodSeconds; "run a command before shutdown" → lifecycle.preStop.
  • Pod stuck Terminating in the exam is usually a dead node → kubectl delete pod x --force --grace-period=0.

Hands-on lab (15 min)

$ kubectl run boom --image=busybox --command -- sh -c 'echo booting; sleep 3; echo failing; exit 2'
$ kubectl get pod boom -w                 # Running → Error → CrashLoopBackOff, RESTARTS climbing, growing gaps
$ kubectl logs boom --previous; kubectl describe pod boom | grep -A4 'Last State'
$ kubectl run once --image=busybox --restart=Never --command -- sh -c 'echo hi; exit 0'; sleep 5; kubectl get pod once   # Completed
$ kubectl run cfg --image=nginx --env=X=1 $do | sed 's/value: "1"/valueFrom: {configMapKeyRef: {name: nope, key: k}}/' | kubectl apply -f -
$ kubectl get pod cfg                     # CreateContainerConfigError
# termination timing
$ kubectl run slow --image=nginx $do | sed '/spec:/a\  terminationGracePeriodSeconds: 5' | kubectl apply -f -
$ kubectl run shell --image=busybox --command -- sleep 3600      # sleep ignores SIGTERM
$ time kubectl delete pod slow            # ~1 s: nginx handles SIGTERM
$ time kubectl delete pod shell           # ~30 s: waits the full grace period, then SIGKILL
$ kubectl delete pod boom once cfg $now

Key takeaways

  • STATUS = phase, unless a container's Waiting reason is more specific. Conditions (Ready) decide endpoint membership.
  • Restarts are the kubelet's doing: back-off 10 s → 300 s, reset after 10 min stable. logs --previous + exit code diagnose them.
  • imagePullPolicy defaults to IfNotPresent, or Always for :latest. Mutable tags cause stale Pods.
  • Termination: deletionTimestamp → endpoints removed ∥ preStop → SIGTERM → grace (30 s) → SIGKILL. Handle SIGTERM and add a short preStop sleep.
