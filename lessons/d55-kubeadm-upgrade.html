Kubernetes ships three minor versions a year and supports each for about fourteen months, so upgrading is routine — and it is a guaranteed CKA task. The procedure is the same every time: upgrade kubeadm, upgrade the control plane, upgrade the kubelet, node by node, one minor version at a time, draining workloads off each node first. This lesson is that runbook, with the version-skew rules that make the order non-negotiable and an etcd backup before you touch anything.

What you'll learn

  • Version skew: why control plane first, one minor at a time, kubelet never ahead
  • etcd snapshot and restore — the safety net (and its own exam task)
  • Control plane: kubeadm upgrade plan / apply, then kubelet + kubectl
  • Workers: drain → upgrade kubeadm → kubeadm upgrade node → kubelet → uncordon
  • What drain really does, PodDisruptionBudgets, and verifying the result

Version skew rules

ComponentRelative to kube-apiserver (vX.Y)
Other API servers (HA)Same minor, or one behind during the upgrade
kube-controller-manager, kube-scheduler, cloud-controller-managerSame or one minor behind — never ahead
kubeletUp to three minors behind — never ahead
kube-proxySame as kubelet on that node (three behind), never ahead
kubectlWithin one minor either way
kubeadmMust be the target version when you run it; can upgrade a cluster only one minor at a time (1.30 → 1.31 → 1.32, never 1.30 → 1.32)

Hence the order: kubeadm binary → control plane → kubelets, per minor version, repeated for each hop.

Step 0 — Back up etcd

# on cp-1 (etcdctl from the etcd image, or apt install etcd-client)
$ sudo ETCDCTL_API=3 etcdctl snapshot save /var/backups/etcd-$(date +%F).db \
    --endpoints=https://127.0.0.1:2379 \
    --cacert=/etc/kubernetes/pki/etcd/ca.crt \
    --cert=/etc/kubernetes/pki/etcd/server.crt \
    --key=/etc/kubernetes/pki/etcd/server.key
$ sudo ETCDCTL_API=3 etcdctl snapshot status /var/backups/etcd-*.db -w table    # (older etcdctl) or: etcdutl snapshot status
$ sudo cp -r /etc/kubernetes/pki /var/backups/pki-$(date +%F)                   # certs too
How do you restore it? (exam task)
$ sudo ETCDCTL_API=3 etcdctl snapshot restore /var/backups/etcd-2025-01-01.db --data-dir /var/lib/etcd-restored   # or etcdutl snapshot restore
$ sudo sed -i 's#/var/lib/etcd#/var/lib/etcd-restored#' /etc/kubernetes/manifests/etcd.yaml   # hostPath volume + --data-dir
# the kubelet notices the manifest change and restarts etcd from the restored directory
$ watch crictl ps | grep etcd; kubectl get nodes

Restore into a new directory and repoint the static Pod; never restore over a running etcd's data dir. In an HA cluster restore on all members with matching --initial-cluster flags.

Step 1 — Control plane

# 1. new package repo for the target minor
$ sudo sed -i 's#/v1.31/#/v1.32/#' /etc/apt/sources.list.d/kubernetes.list && sudo apt-get update
$ apt-cache madison kubeadm | head -3                       # pick the exact version, e.g. 1.32.1-1.1
# 2. upgrade kubeadm only
$ sudo apt-mark unhold kubeadm && sudo apt-get install -y kubeadm=1.32.1-1.1 && sudo apt-mark hold kubeadm
$ kubeadm version -o short
# 3. see what would happen
$ sudo kubeadm upgrade plan                                 # component versions, target, "You can now apply the upgrade by executing…"
# 4. do it — this rewrites static pod manifests one at a time and renews certificates
$ sudo kubeadm upgrade apply v1.32.1
[upgrade/successful] SUCCESS! Your cluster was upgraded to "v1.32.1". Enjoy!
# 5. the node's own kubelet and kubectl
$ kubectl drain cp-1 --ignore-daemonsets                    # only needed if workloads run on the control plane
$ sudo apt-mark unhold kubelet kubectl && sudo apt-get install -y kubelet=1.32.1-1.1 kubectl=1.32.1-1.1 && sudo apt-mark hold kubelet kubectl
$ sudo systemctl daemon-reload && sudo systemctl restart kubelet
$ kubectl uncordon cp-1
$ kubectl get nodes                                         # cp-1 VERSION v1.32.1; workers still v1.31.x — allowed (skew)

kubeadm upgrade apply: pulls the new images, upgrades etcd (if bundled), then for each of API server / controller-manager / scheduler writes a new manifest to /etc/kubernetes/manifests and waits for the kubelet to restart it healthy before moving on; renews all certificates; updates the kubelet ConfigMap, kube-proxy and CoreDNS add-ons. Workloads keep running throughout — the data plane does not depend on the control plane being up. For additional control-plane nodes run kubeadm upgrade node (not apply) after the first.

Step 2 — Each worker

# from cp-1 (or anywhere with kubectl): move workloads away
$ kubectl drain worker-1 --ignore-daemonsets --delete-emptydir-data     # cordon + evict; blocks until pods are gone
# on worker-1:
$ sudo sed -i 's#/v1.31/#/v1.32/#' /etc/apt/sources.list.d/kubernetes.list && sudo apt-get update
$ sudo apt-mark unhold kubeadm && sudo apt-get install -y kubeadm=1.32.1-1.1 && sudo apt-mark hold kubeadm
$ sudo kubeadm upgrade node                              # updates the kubelet config from the cluster's ConfigMap
$ sudo apt-mark unhold kubelet kubectl && sudo apt-get install -y kubelet=1.32.1-1.1 kubectl=1.32.1-1.1 && sudo apt-mark hold kubelet kubectl
$ sudo systemctl daemon-reload && sudo systemctl restart kubelet
# from cp-1:
$ kubectl uncordon worker-1
$ kubectl get nodes                                      # worker-1 v1.32.1 Ready
# repeat for worker-2. Never drain more nodes at once than your capacity and PDBs allow.

What drain does

  1. Cordon — spec.unschedulable: true (+ the unschedulable taint). No new Pods land here. Running ones are untouched.
  2. Evict — for every Pod on the node, POST an Eviction (the Eviction API, which respects PodDisruptionBudgets: if evicting would drop a Deployment below its PDB's minAvailable, the request is refused with 429 and drain retries until it can). Controllers re-create the Pods elsewhere.
  3. Flags you need: --ignore-daemonsets (DaemonSet Pods cannot be moved; drain refuses without it), --delete-emptydir-data (Pods with emptyDir lose that data — confirm you accept), --force (bare Pods with no controller would be lost forever — required to proceed). --timeout, --grace-period as needed.
  4. Uncordon — spec.unschedulable: false. Pods do not move back automatically; the next scheduling decisions may use the node.
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: api-pdb}
spec:
  minAvailable: 2               # or maxUnavailable: 1 / 25%
  selector: {matchLabels: {app: api}}
$ kubectl create pdb api-pdb --selector=app=api --min-available=2
$ kubectl get pdb                      # ALLOWED DISRUPTIONS: 1 — drain proceeds one pod at a time
Drain hangs

Usually a PDB that can never be satisfied (minAvailable: 3 with 3 replicas → 0 allowed disruptions) or a Pod whose remaining replicas cannot schedule anywhere else. kubectl get pdb -A and describe the stuck Pod. Fix the PDB/capacity rather than --disable-eviction, which bypasses PDBs and defeats their purpose.

Verify

$ kubectl get nodes                                          # every VERSION the target
$ kubectl version                                            # client and server
$ kubectl get pods -n kube-system -o custom-columns=NAME:.metadata.name,IMAGE:.spec.containers[0].image | grep -E 'apiserver|scheduler|controller|proxy|coredns'
$ sudo kubeadm certs check-expiration                        # renewed: one year from today
$ kubectl get --raw /readyz?verbose | tail -3
$ kubectl rollout status deploy -A 2>/dev/null | head       # workloads healthy
Under the hood · Linux

An upgrade is mostly package management and systemd: apt-mark hold/unhold keeps unattended upgrades from bumping the kubelet unexpectedly (which would break skew rules); systemctl daemon-reload is required because the package installs a new unit file and drop-in; systemctl restart kubelet hands the node to the new binary while containers keep running (the runtime is separate — containerd is upgraded independently and can be restarted without killing containers thanks to the shim design from Day 1). The control-plane upgrade is a file swap in /etc/kubernetes/manifests: kubeadm upgrade apply -v=5 shows it moving manifests into /etc/kubernetes/tmp/ and back, with backups you can restore by hand if it fails halfway.

CKA exam tip
  • The exam question says which node and which version. Sequence: drain → (on node) repo → kubeadm → upgrade plan/apply or upgrade node → kubelet + kubectl → daemon-reload + restart → uncordon. Do not skip daemon-reload; do not forget to uncordon.
  • Match the exact package version string (apt-cache madison kubeadm). The version in kubeadm upgrade apply vX.Y.Z needs the v.
  • etcd backup/restore is a separate, frequent task: memorise the three cert flags (pki/etcd/ca.crt, server.crt, server.key) and the data-dir swap in the static Pod manifest.
  • Drain needs --ignore-daemonsets; add --delete-emptydir-data if it complains.

Hands-on lab (45 min) — on the Day 54 cluster

$ kubectl create deploy web --image=nginx --replicas=4 && kubectl create pdb web --selector=app=web --min-available=3
$ sudo ETCDCTL_API=3 etcdctl snapshot save /tmp/pre-upgrade.db --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key
# control plane: follow Step 1 to the next minor
# worker-1: watch the PDB in action
$ kubectl get pdb web -w &
$ kubectl drain worker-1 --ignore-daemonsets --delete-emptydir-data       # evicts web pods one at a time, keeping 3 available
# … Step 2 on worker-1 … uncordon … repeat worker-2
$ kubectl get nodes; kubectl get pods -o wide                             # all upgraded, web still 4/4
# restore drill (destructive — do it last, then rebuild if it goes wrong):
$ kubectl create cm marker --from-literal=before=restore
$ sudo ETCDCTL_API=3 etcdctl snapshot restore /tmp/pre-upgrade.db --data-dir /var/lib/etcd-restored
$ sudo sed -i 's#/var/lib/etcd$#/var/lib/etcd-restored#; s#path: /var/lib/etcd$#path: /var/lib/etcd-restored#' /etc/kubernetes/manifests/etcd.yaml
$ sleep 30; kubectl get cm marker      # NotFound — the cluster state is from before the snapshot

Key takeaways

  • Order: kubeadm → control plane (upgrade apply) → kubelets (upgrade node), one minor at a time; kubelet never ahead of the API server.
  • Snapshot etcd (and copy pki) first; restore into a new data dir and repoint the etcd static Pod.
  • Per node: drain (cordon + PDB-aware evict) → packages with hold/unhold → daemon-reload + restart kubelet → uncordon.
  • kubeadm upgrade apply swaps static Pod manifests and renews all certificates; workloads keep running.
  • PDBs make drains safe and can make them hang; fix the budget, do not bypass it.
