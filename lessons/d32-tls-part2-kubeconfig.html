When you run kubectl get pods, two certificate checks happen in a fraction of a second: kubectl verifies the API server's certificate against a CA in your kubeconfig, and the API server verifies your client certificate against its CA — then reads your username and groups out of it. That is mutual TLS, and a kubeconfig file is nothing more than the three ingredients it needs: a CA to trust, a certificate and key to present, and the address to connect to.

Mutual TLS

Server-only TLS answers "is this really the API server?". Mutual TLS additionally answers "who is this client?" — cryptographically, before a single API request is read. The API server sends a CertificateRequest during the handshake; the client responds with its certificate and a CertificateVerify signature made with its private key. The API server checks the chain against its client CA (--client-ca-file=/etc/kubernetes/pki/ca.crt) and, if valid, treats the certificate's Subject as the authenticated identity:

CN (Common Name) → username  ·  every O (Organization) → a group
$ kubectl config view --raw -o jsonpath='{.users[0].user.client-certificate-data}' | base64 -d | openssl x509 -noout -subject
subject=O = kubeadm:cluster-admins, CN = kubernetes-admin
# → user "kubernetes-admin", group "kubeadm:cluster-admins" (older kubeadm: O=system:masters)

No password, no user database: if you hold a key whose certificate the cluster CA signed, you are whoever the Subject says. This is why the CA private key is the most sensitive file in the cluster, and why revocation is hard (Kubernetes does not check CRLs — a leaked cert is valid until it expires).

kubeconfig, field by field

apiVersion: v1
kind: Config
clusters:
- name: prod
  cluster:
    server: https://10.0.0.10:6443
    certificate-authority-data: LS0tLS1CRUdJTi…
    # or certificate-authority: /path/ca.crt
    # insecure-skip-tls-verify: true   ← never in prod
users:
- name: jane
  user:
    client-certificate-data: LS0tLS1CRUdJTi…
    client-key-data: LS0tLS1CRUdJTi…
    # or client-certificate: /path/jane.crt
    #    client-key: /path/jane.key
- name: ci-bot
  user:
    token: eyJhbGciOiJSUzI1NiIs…        # bearer token instead
- name: eks-user
  user:
    exec:                                # plugin that mints a token
      apiVersion: client.authentication.k8s.io/v1
      command: aws
      args: [eks, get-token, --cluster-name, prod]
contexts:
- name: jane@prod
  context:
    cluster: prod
    user: jane
    namespace: shop
current-context: jane@prod
  • clusters[].server — where to connect. Must match a SAN in the API server's cert (IP or DNS).
  • certificate-authority(-data) — the CA kubectl uses to verify the server. This is the cluster CA's public cert, base64 of the PEM. Wrong CA → "certificate signed by unknown authority".
  • users[].client-certificate(-data) / client-key(-data) — what kubectl presents in mTLS. The cert must be signed by the API server's client CA; the key is the private half. This is the credential — protect the file (chmod 600).
  • users[].token — a bearer token sent as Authorization: Bearer … inside the TLS session, for ServiceAccounts or OIDC. Server is still verified via the CA.
  • users[].exec — run a command that returns a short-lived token (cloud IAM, OIDC helpers). How EKS/GKE/AKS kubeconfigs work.
  • contexts[] — a named (cluster, user, namespace) triple. current-context — which one applies by default.
  • "user" here is just a credential set name in the file; the actual identity is whatever the certificate/token says.
Mental model

A kubeconfig answers three questions, each mapping to one half of mTLS: Where? (server), Why should I believe it's really them? (certificate-authority → verifies the server), and How do I prove who I am? (client-certificate + client-key, or a token → presented to the server). A context is a bookmark that picks one answer to each.

The files behind the -data

$ kubectl config view --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > ca.crt
$ openssl x509 -in ca.crt -noout -subject -dates        # subject=CN = kubernetes — the cluster CA
$ kubectl config view --raw -o jsonpath='{.users[0].user.client-certificate-data}' | base64 -d | openssl x509 -noout -subject -issuer -dates
$ openssl s_client -connect 127.0.0.1:6443 -CAfile ca.crt < /dev/null 2>&1 | grep -E 'Verify return|subject='   # verify the server yourself
# the same call kubectl makes, by hand:
$ curl --cacert ca.crt --cert client.crt --key client.key https://127.0.0.1:6443/api/v1/namespaces/default/pods

On a kubeadm control plane, /etc/kubernetes/admin.conf is exactly this file for the admin identity, and scheduler.conf, controller-manager.conf, kubelet.conf are kubeconfigs for those components — each with its own client certificate whose CN names the component (Day 33).

Contexts, revisited

$ kubectl config get-contexts
$ kubectl config use-context jane@prod
$ kubectl config set-context --current --namespace=shop
$ kubectl config set-context ci --cluster=prod --user=ci-bot --namespace=build     # compose a new one
$ kubectl config set-cluster prod --server=https://10.0.0.10:6443 --certificate-authority=ca.crt --embed-certs=true
$ kubectl config set-credentials jane --client-certificate=jane.crt --client-key=jane.key --embed-certs=true
$ kubectl config delete-context old; kubectl config delete-user old; kubectl config delete-cluster old
$ KUBECONFIG=~/.kube/config:/tmp/other.yaml kubectl config view --flatten > merged.yaml
$ kubectl --kubeconfig=/etc/kubernetes/admin.conf get nodes                        # one-off file

--embed-certs inlines the files as -data so the kubeconfig is self-contained (portable, but the private key is now inside it). Precedence: --kubeconfig flag → KUBECONFIG env (colon-separated list, merged) → ~/.kube/config.

Under the hood · Linux

Those LS0tLS1CRUdJTi… blobs are base64 of PEM files — LS0tLS1 is -----, the start of -----BEGIN CERTIFICATE-----. Decode with base64 -d and inspect with openssl x509 -text. The private key is -----BEGIN RSA PRIVATE KEY----- (or EC PRIVATE KEY); check it matches the cert with openssl x509 -noout -modulus -in c.crt | md5sum vs openssl rsa -noout -modulus -in c.key | md5sum. kubectl performs the TLS handshake with Go's crypto/tls, which enforces SAN matching strictly — a server cert with only a CN and no SANs is rejected outright.

CKA exam tip
  • Given a cert/key pair for a user, build access with set-credentials + set-context; verify with kubectl --context=… auth whoami (1.28+) or auth can-i.
  • "Unable to connect to the server: x509: certificate signed by unknown authority" → wrong certificate-authority-data for that server (often a copied kubeconfig pointing at a rebuilt cluster). "certificate is valid for 10.96.0.1, 192.168.1.10, not 1.2.3.4" → the server address is not in the API server's SANs.
  • kubectl config view --minify shows only the current context — quickest way to see which cluster/user/namespace you are actually using.

Hands-on lab (15 min)

$ kubectl config view --raw > /tmp/kc.yaml
$ yq '.clusters[0].cluster.certificate-authority-data' /tmp/kc.yaml | base64 -d > /tmp/ca.crt
$ yq '.users[0].user.client-certificate-data' /tmp/kc.yaml | base64 -d > /tmp/me.crt
$ yq '.users[0].user.client-key-data' /tmp/kc.yaml | base64 -d > /tmp/me.key
$ openssl x509 -in /tmp/me.crt -noout -subject -issuer            # CN and O → your identity and groups
$ openssl verify -CAfile /tmp/ca.crt /tmp/me.crt                   # OK: signed by the cluster CA
$ SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
$ curl -s --cacert /tmp/ca.crt --cert /tmp/me.crt --key /tmp/me.key $SERVER/api/v1/nodes | jq '.items[].metadata.name'
$ curl -s --cacert /tmp/ca.crt $SERVER/api/v1/nodes | head -5       # no client cert → 403 as system:anonymous
$ curl -sk $SERVER/version                                          # -k skips server verification: works, but you have no idea who answered
$ kubectl auth whoami; rm /tmp/me.key /tmp/kc.yaml

Key takeaways

  • mTLS = server TLS + client certificate. The API server maps the client cert's CN to the username and each O to a group. No passwords involved.
  • kubeconfig: server (where), certificate-authority (verify them), client-certificate/client-key or token/exec (prove you). Contexts bookmark a triple.
  • -data fields are base64 PEM; decode and openssl x509 them when debugging.
  • The CA private key is the crown jewel; certificates cannot be revoked, only expired.
