Real applications live in private registries. The kubelet pulls images, so the kubelet needs credentials — and the way to give them is a Secret of type kubernetes.io/dockerconfigjson referenced from the Pod (imagePullSecrets) or, better, from the ServiceAccount so every Pod using it inherits the reference. Short lesson, but ImagePullBackOff against a private registry is one of the most frequent tickets you will ever get.

What you'll learn

  • How the kubelet authenticates to a registry and what a .dockerconfigjson contains
  • Creating the Secret with kubectl create secret docker-registry or from an existing ~/.docker/config.json
  • Referencing it per Pod vs attaching it to a ServiceAccount
  • Cloud registries (ECR, GAR, ACR): short-lived tokens and node-level credential providers
  • Diagnosing pull failures

How a private pull works

The kubelet asks containerd to pull ghcr.io/acme/api:2.1. containerd hits the registry, gets 401 Unauthorized with a WWW-Authenticate challenge, and needs a username/password (or token) for ghcr.io. The kubelet supplies it from the Pod's imagePullSecrets — Secrets it reads on the Pod's behalf — merged with any node-level config (/var/lib/kubelet/config.json) and credential-provider plugins.

The Secret

$ kubectl create secret docker-registry ghcr-creds \
    --docker-server=ghcr.io \
    --docker-username=acme-bot \
    --docker-password=ghp_xxxxxxxxxxxx \        # a token with read:packages, not your password
    --docker-email=bot@acme.example \
    -n shop
$ kubectl get secret ghcr-creds -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
{
  "auths": {
    "ghcr.io": {
      "username": "acme-bot",
      "password": "ghp_xxxxxxxxxxxx",
      "auth": "YWNtZS1ib3Q6Z2hwX3h4eHg…"       # base64(username:password) — what is actually sent
    }
  }
}
# from an existing docker login:
$ kubectl create secret generic ghcr-creds --from-file=.dockerconfigjson=$HOME/.docker/config.json --type=kubernetes.io/dockerconfigjson
apiVersion: v1
kind: Secret
metadata:
  name: ghcr-creds
  namespace: shop
type: kubernetes.io/dockerconfigjson
data:
  .dockerconfigjson: eyJhdXRocyI6…            # base64 of the JSON above

The Secret is namespaced: a Pod in shop can only use a Secret in shop. Multiple registries go in one Secret's auths map, or in multiple Secrets listed together.

Referencing it

Per Pod (explicit)

spec:
  imagePullSecrets:
  - name: ghcr-creds
  containers:
  - name: api
    image: ghcr.io/acme/api:2.1

Works, but every Deployment, Job and CronJob template must repeat it. Easy to forget.

Via ServiceAccount (recommended)

$ kubectl patch serviceaccount default -n shop \
    -p '{"imagePullSecrets":[{"name":"ghcr-creds"}]}'
# or in YAML:
apiVersion: v1
kind: ServiceAccount
metadata: {name: default, namespace: shop}
imagePullSecrets:
- name: ghcr-creds

The ServiceAccount admission plugin copies the reference into every new Pod using that SA. Existing Pods are not changed — restart them.

$ kubectl get pod api-xyz -o jsonpath='{.spec.imagePullSecrets}'     # [{"name":"ghcr-creds"}] — injected
$ kubectl set image deploy/api api=ghcr.io/acme/api:2.1              # after fixing, roll to pick it up

Cloud registries

Amazon ECR
Passwords are 12-hour tokens from aws ecr get-login-password. Managed node groups on EKS pull via the node's IAM role automatically — no Secret needed. Elsewhere, a CronJob refreshing the Secret, or the kubelet credential provider plugin (ecr-credential-provider).
Google Artifact Registry
GKE nodes use their service account; otherwise a JSON key as password with username _json_key.
Azure Container Registry
AKS attaches ACR to the cluster identity; otherwise a service principal or a token.
Docker Hub
Anonymous pulls are rate-limited (100 per 6 h per IP — a whole cluster behind NAT shares it). A free account's token in a Secret raises the limit; a mirror/pull-through cache removes it.
Kubelet credential providers
--image-credential-provider-config + --image-credential-provider-bin-dir: node-level plugins that fetch short-lived credentials per registry. No Secrets in the API at all.

Diagnosing pull failures

$ kubectl get pod api-xyz                           # ErrImagePull → ImagePullBackOff
$ kubectl describe pod api-xyz | grep -A3 -iE 'failed to pull|unauthorized|not found|denied'
  Failed to pull image "ghcr.io/acme/api:2.1": … 401 Unauthorized        → wrong/missing credentials
  … 403 Forbidden / denied: requested access to the resource is denied   → credentials valid, no permission on that repo
  … manifest unknown / not found                                         → wrong tag or repo name
  … x509: certificate signed by unknown authority                        → private registry with an internal CA: add it to the node's trust store / containerd config
  … dial tcp: i/o timeout                                                → node cannot reach the registry (proxy, firewall, DNS)
$ kubectl get secret ghcr-creds -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq '.auths | keys'   # does the server key match the image's registry host exactly?
$ kubectl get pod api-xyz -o jsonpath='{.spec.imagePullSecrets}{"\n"}{.spec.serviceAccountName}{"\n"}'
# on the node, bypass Kubernetes to isolate the problem:
$ crictl pull --creds acme-bot:ghp_xxx ghcr.io/acme/api:2.1
$ ctr -n k8s.io images pull --user acme-bot:ghp_xxx ghcr.io/acme/api:2.1
The exact-host rule

The auths key must match the registry host in the image reference: ghcr.io for ghcr.io/acme/api; https://index.docker.io/v1/ for Docker Hub images (which is what --docker-server=docker.io is translated to); 123456789.dkr.ecr.eu-west-1.amazonaws.com for ECR. A Secret for docker.io does nothing for registry-1.docker.io.

CKA exam tip
  • Task: "the Deployment cannot pull from private registry X with these credentials" → kubectl create secret docker-registry in the right namespace, add imagePullSecrets to the Pod template (or patch the SA), then rollout restart or wait for the back-off retry.
  • The Secret type is kubernetes.io/dockerconfigjson and the key is .dockerconfigjson — a generic Secret with the wrong key silently does not work.
  • describe pod tells you 401 vs 404 vs timeout; fix the right thing.

Hands-on lab (15 min)

Uses a throwaway registry inside the cluster so no external account is needed.

$ kubectl create deploy registry --image=registry:2 --port=5000 && kubectl expose deploy registry --port=5000
# (a real private registry would need auth; here we demonstrate the Secret plumbing and the failure modes)
$ kubectl create secret docker-registry regcred --docker-server=registry.default.svc:5000 --docker-username=u --docker-password=p
$ kubectl get secret regcred -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
$ kubectl patch sa default -p '{"imagePullSecrets":[{"name":"regcred"}]}'
$ kubectl run pulltest --image=registry.default.svc:5000/nope:1 ; sleep 10
$ kubectl describe pod pulltest | grep -A2 'Failed to pull'         # http vs https / not found — read the exact error
$ kubectl get pod pulltest -o jsonpath='{.spec.imagePullSecrets}{"\n"}'   # injected from the SA
$ kubectl run wrongtag --image=nginx:9.9.9; sleep 10; kubectl describe pod wrongtag | grep -i 'manifest'   # "not found" ≠ auth problem
$ kubectl delete pod pulltest wrongtag $now; kubectl delete deploy registry; kubectl delete svc registry; kubectl delete secret regcred; kubectl patch sa default -p '{"imagePullSecrets":null}'

The other half of this Secret lives in CI: a pipeline needs write credentials to push the image (C3), and a kaniko build inside the cluster mounts the very same dockerconfigjson Secret as /kaniko/.docker/config.json to push (C5). Use separate read-only and write robot accounts for the two directions.

Key takeaways

  • The kubelet needs registry credentials: a kubernetes.io/dockerconfigjson Secret whose auths key exactly matches the registry host.
  • Reference it with imagePullSecrets on the Pod, or attach it to the ServiceAccount so it is injected automatically (new Pods only).
  • Cloud clusters usually pull with the node's identity; otherwise rotate short-lived tokens or use kubelet credential providers.
  • 401 = credentials, 403 = permissions, not found = name/tag, x509 = CA trust on the node, timeout = network. describe pod says which.
