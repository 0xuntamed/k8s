Kubernetes assumes your software is split into independently deployable pieces that talk over the network. If you have only ever run a monolith, the objects in the next lessons — Services, ConfigMaps, StatefulSets — will feel arbitrary. Spend twenty minutes on why applications are decomposed and how a classic three-tier app maps onto Kubernetes objects, and the rest of the course reads as the obvious consequence.

What you'll learn

  • Monolith vs microservices: what you gain, what you pay
  • The three-tier pattern (presentation, application, data) and how each tier becomes Kubernetes objects
  • Stateless vs stateful components and why they get different controllers
  • The twelve-factor habits that make an app "cloud-native" enough to run well on Kubernetes

Monolith vs microservices

Monolith

One codebase, one deployable, one process (or a few identical copies). Simple to develop and debug locally; every function call is in-process.

Pain at scale: the whole thing scales together (the image-resizer and the login page get the same replica count), one team's bug takes everything down, releases are big-bang events, and the tech stack is frozen.

Microservices

Many small services, each owning one capability and its data, communicating over HTTP/gRPC/queues. Each is built, deployed, scaled and fixed independently, by a team that can move at its own pace.

New pain: network calls fail and are slow, you need service discovery, distributed tracing, per-service config and secrets, and consistent deployment tooling — precisely the problems Kubernetes exists to solve.

Mental model

Microservices move complexity from inside the code to between the services. Kubernetes is the platform that makes the "between" manageable: Services for discovery and load balancing, Deployments for independent rollouts, Namespaces for team boundaries, NetworkPolicies for who-may-talk-to-whom. You do not need dozens of services to benefit — three is enough to need all of it.

The three-tier pattern

TierRoleState?Kubernetes objects
Presentation (frontend)Serves the UI: static files, SSR, or a reverse proxy. Talks to the API tier.StatelessDeployment + Service (ClusterIP) + Ingress for external access
Application (backend / API)Business logic. Talks to the database and to other services.StatelessDeployment + Service (ClusterIP) + ConfigMap + Secret + HPA
Data (database, cache, queue)Stores state. Needs stable identity and durable disks.StatefulStatefulSet + headless Service + PersistentVolumeClaims (or a managed cloud DB outside the cluster, via ExternalName)

Two rules fall out of this table and they drive most design decisions in Kubernetes:

  1. Tiers talk through Services, never Pod IPs. Pods come and go; the Service name (api, resolvable via cluster DNS as api.shop.svc.cluster.local) is the stable contract. Day 12.
  2. Stateless tiers use Deployments; stateful ones use StatefulSets. A Deployment's Pods are interchangeable — any of them can die and be replaced anywhere. A database replica is not interchangeable: it has a name (db-0), a disk, and often a role (primary/replica). Day 44.

A concrete example: an online shop

# frontend tier
Deployment  frontend   image: shop/web:2.3      replicas: 3
Service     frontend   ClusterIP → port 80
Ingress     shop       host shop.example.com → frontend:80

# application tier
Deployment  api        image: shop/api:5.1      replicas: 4   env from ConfigMap api-config + Secret api-secrets
Service     api        ClusterIP → port 8080
HorizontalPodAutoscaler api   2..10 replicas at 70% CPU

# data tier
StatefulSet postgres   image: postgres:16       replicas: 1   volumeClaimTemplate 20Gi
Service     postgres   headless (clusterIP: None) → port 5432
Deployment  redis      image: redis:7 (cache, safe to lose)
Service     redis      ClusterIP → port 6379

Notice what is not here: no IP addresses, no hostnames of machines, no "which server does postgres run on". The frontend's config says API_URL=http://api:8080; the API's config says DB_HOST=postgres. Everything else is discovered.

Twelve-factor habits that matter on Kubernetes

Config from the environment

Read settings and secrets from env vars or mounted files, not from files baked into the image. ⇒ ConfigMaps & Secrets (Day 28).

Logs to stdout/stderr

Never write log files inside the container. The kubelet captures stdout; kubectl logs and the logging stack read it (Day 56).

Stateless processes

No local session state, no "upload directory" on the container's disk. Put state in the data tier so any replica can serve any request and Pods can be replaced freely.

Disposability

Start fast, stop gracefully on SIGTERM (Day 4, Day 22). Rolling updates and autoscaling depend on it.

Health endpoints

Expose /healthz and /ready so probes can tell "alive" from "ready for traffic" (Day 23).

Port binding

The app listens on a port it is told (PORT env), on 0.0.0.0. Routing is the platform's job.

CKA exam tip

Exam scenarios are usually a mini three-tier app: "create a Deployment, expose it with a Service, make the frontend reach it by name". Recognising the pattern lets you predict the next step. Also remember which tier owns which failure: a frontend that cannot reach the API is a Service/DNS/NetworkPolicy problem, not a Deployment problem.

Key takeaways

  • Microservices trade in-process simplicity for independent scaling and deployment; Kubernetes manages the resulting network-level complexity.
  • Three tiers: stateless frontend and API as Deployments behind ClusterIP Services; the stateful data tier as a StatefulSet with persistent volumes.
  • Components find each other by Service name via DNS — never by Pod IP.
  • Config from env, logs to stdout, stateless processes, fast start / graceful stop, health endpoints.
