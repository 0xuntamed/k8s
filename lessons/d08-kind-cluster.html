Reading about clusters only gets you so far. KIND (Kubernetes IN Docker) runs a real, multi-node, conformant Kubernetes cluster on your laptop in about a minute, using Docker containers as "nodes". This lesson installs the tools, creates a cluster with one control plane and two workers, and explains the kubeconfig file and contexts that kubectl uses to find it.

What you'll learn

  • Installing kubectl and kind
  • Creating single- and multi-node clusters from a KIND config file, with port mappings for later lessons
  • What a KIND "node" actually is (a container running systemd, kubelet and containerd)
  • kubeconfig: clusters, users, contexts — and switching between them

Install the tools

# kubectl — the CLI (pick your platform from kubernetes.io/docs/tasks/tools)
$ curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
$ sudo install -m 0755 kubectl /usr/local/bin/kubectl
$ kubectl version --client

# kind — needs Docker (or Podman) running
$ go install sigs.k8s.io/kind@latest              # or: brew install kind / choco install kind
$ kind version

On macOS/Windows use Docker Desktop; on Linux, Docker Engine. Everything KIND creates lives inside Docker, so docker ps shows your cluster.

Create a cluster

$ kind create cluster                     # one node, named "kind", ~60 s
$ kubectl cluster-info --context kind-kind
$ kubectl get nodes
NAME                 STATUS   ROLES           AGE   VERSION
kind-control-plane   Ready    control-plane   50s   v1.31.0
$ kind delete cluster

For the rest of the course you want multiple nodes (scheduling, taints, DaemonSets and node troubleshooting all need them) and a couple of host port mappings so NodePort Services and an Ingress controller are reachable from your browser.

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: cka
nodes:
- role: control-plane
  kubeadmConfigPatches:
  - |
    kind: InitConfiguration
    nodeRegistration:
      kubeletExtraArgs:
        node-labels: "ingress-ready=true"   # for the ingress lessons
  extraPortMappings:
  - containerPort: 80        # host:80  → control-plane:80  (ingress)
    hostPort: 80
  - containerPort: 443
    hostPort: 443
  - containerPort: 30080     # host:30080 → NodePort 30080 (Day 12)
    hostPort: 30080
- role: worker
- role: worker
$ kind create cluster --config kind-config.yaml
$ kubectl get nodes -o wide
NAME                STATUS   ROLES           AGE   VERSION   INTERNAL-IP
cka-control-plane   Ready    control-plane   2m    v1.31.0   172.18.0.2
cka-worker          Ready    <none>          90s   v1.31.0   172.18.0.3
cka-worker2         Ready    <none>          90s   v1.31.0   172.18.0.4
$ docker ps --format '{{.Names}}\t{{.Image}}'   # three containers = three nodes
Pin the Kubernetes version

kind create cluster --image kindest/node:v1.31.0 selects the version. KIND publishes a node image per Kubernetes release, so you can practise upgrades too — but kubeadm on VMs (Day 54) is the realistic way to do that.

What a KIND node really is

Under the hood · Linux

Each node is a privileged Docker container whose PID 1 is systemd. Inside it, systemd starts kubelet.service and containerd.service, exactly as on a real VM — so the Pods you create become containers inside the node container (nested container runtimes, made possible by nested namespaces and cgroups). On the control-plane node, /etc/kubernetes/manifests holds the static-Pod manifests for etcd, the API server, scheduler and controller-manager, just like a kubeadm cluster — because KIND uses kubeadm to bootstrap. That makes it a faithful model of Module 12.

$ docker exec -it cka-control-plane bash
root@cka-control-plane:/# systemctl status kubelet
root@cka-control-plane:/# crictl ps                          # containers of every Pod on this node
root@cka-control-plane:/# ls /etc/kubernetes/manifests/
root@cka-control-plane:/# journalctl -u kubelet --no-pager | tail

kubeconfig and contexts

kubectl needs three things to talk to a cluster: where it is (server URL + CA), who you are (a client certificate or token), and which namespace to default to. A kubeconfig file stores these as reusable pieces and a context ties one cluster, one user and a namespace together.

apiVersion: v1
kind: Config
clusters:
- name: kind-cka
  cluster:
    server: https://127.0.0.1:43521
    certificate-authority-data: LS0tLS1CRUdJTi…   # CA that signed the API server's cert
users:
- name: kind-cka
  user:
    client-certificate-data: LS0tLS1CRUdJTi…   # who you are (CN=kubernetes-admin, O=system:masters)
    client-key-data: LS0tLS1CRUdJTi…
contexts:
- name: kind-cka
  context:
    cluster: kind-cka
    user: kind-cka
    namespace: default
current-context: kind-cka
CommandPurpose
kubectl config viewShow the merged config (secrets redacted; add --raw to see them).
kubectl config get-contextsList contexts; * marks the current one.
kubectl config current-contextPrint the active context name.
kubectl config use-context kind-ckaSwitch clusters.
kubectl config set-context --current --namespace=devChange the default namespace for the current context (huge time-saver in the exam).
kubectl --context=prod get podsOne-off override without switching.
KUBECONFIG=a.yaml:b.yaml kubectl config view --flattenMerge several files into one.

KIND writes its context into ~/.kube/config automatically (kind get kubeconfig --name cka prints it). The why of every field — the CA, the client cert, what "system:masters" means — is Day 32.

CKA exam tip

Every exam question starts with a line like kubectl config use-context k8s-c2. Run it every time, even if you think you are already there. Then, if the task lives in one namespace, kubectl config set-context --current --namespace=<ns> so you cannot forget -n. Also set alias k=kubectl and export do="--dry-run=client -o yaml" at the start.

Useful KIND commands

$ kind get clusters
$ kind get nodes --name cka
$ kind load docker-image myapp:1.0 --name cka     # push a local image into the nodes (no registry needed)
$ kind export logs ./kind-logs --name cka          # kubelet/containerd/journal logs from every node
$ docker stop cka-worker2 && docker start cka-worker2   # simulate a node outage (Day 58)
$ kind delete cluster --name cka

Hands-on lab (15 min)

$ kind create cluster --config kind-config.yaml
$ kubectl get nodes,pods -A
$ kubectl config get-contexts
$ kubectl create namespace dev
$ kubectl config set-context --current --namespace=dev
$ kubectl run nginx --image=nginx && kubectl get pods       # lands in dev without -n
$ kubectl config set-context --current --namespace=default
$ docker exec cka-worker crictl ps                          # is the nginx container on this node?
$ docker exec cka-worker2 crictl ps                         # or this one?

Key takeaways

  • KIND = real Kubernetes, bootstrapped by kubeadm, with Docker containers as nodes. Perfect for every lesson except real upgrades and cloud integrations.
  • Use a config file for multi-node clusters and extraPortMappings to reach NodePorts/Ingress from the host.
  • kubeconfig = clusters + users + contexts; a context is (cluster, user, namespace). use-context and set-context --current --namespace are daily commands.
  • Each node container runs systemd → kubelet + containerd; Pods are nested containers.
