Once Pods declare resource requests, Kubernetes can scale them automatically. The HorizontalPodAutoscaler changes the replica count of a Deployment based on measured load; the VerticalPodAutoscaler changes the requests themselves; the Cluster Autoscaler (or Karpenter) adds and removes nodes when Pods cannot be scheduled. All three depend on a metrics pipeline, and all three are just controllers running the observe → compare → act loop from Day 6 with a formula in the middle.

What you'll learn

  • metrics-server and the resource metrics API that kubectl top and the HPA read
  • HPA v2: targets on CPU/memory utilisation, the scaling formula, min/max, and stabilisation behaviour
  • VPA: recommendation modes and why HPA and VPA must not both manage CPU
  • Cluster-level scaling: Cluster Autoscaler vs Karpenter

The metrics pipeline

The kubelet on every node already collects container CPU and memory usage (from cgroups, via cAdvisor). metrics-server scrapes every kubelet every 15 s, keeps only the latest values in memory, and serves them through the aggregated API at metrics.k8s.io. That is the only source the HPA uses for CPU and memory. It is an add-on — KIND and kubeadm clusters do not ship it.

$ kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
# KIND / self-signed kubelets: add --kubelet-insecure-tls to the metrics-server container args
$ kubectl -n kube-system patch deploy metrics-server --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
$ kubectl top nodes
$ kubectl top pods -A --sort-by=memory
$ kubectl get --raw /apis/metrics.k8s.io/v1beta1/pods | jq '.items[0]'
Three metric APIs
  • metrics.k8s.io — resource metrics (CPU, memory) from metrics-server. HPA type: Resource.
  • custom.metrics.k8s.io — per-object metrics like requests-per-second, served by an adapter (usually prometheus-adapter). HPA type: Pods / Object.
  • external.metrics.k8s.io — metrics from outside the cluster (queue length in SQS, Kafka lag). HPA type: External. KEDA is the popular implementation.

HorizontalPodAutoscaler

$ kubectl autoscale deployment api --cpu-percent=70 --min=2 --max=10        # imperative (v1: CPU only)
$ kubectl get hpa api -w
NAME   REFERENCE        TARGETS   MINPODS   MAXPODS   REPLICAS
api    Deployment/api   45%/70%   2         10        2
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment          # anything with a /scale subresource: Deployment, StatefulSet, RS…
    name: api
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization     # % of the container's REQUEST, averaged across pods
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue    # absolute, e.g. 400Mi per pod
        averageValue: 400Mi
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Percent
        value: 100            # at most double every 15 s
        periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300   # wait 5 min of consistently low load before shrinking
      policies:
      - type: Pods
        value: 1              # remove at most one pod per minute
        periodSeconds: 60

The formula

desiredReplicas = ceil( currentReplicas × ( currentMetricValue / desiredMetricValue ) )

With 4 replicas averaging 140% of their CPU request and a target of 70%: ceil(4 × 140/70) = 8. With several metrics, the HPA computes a desired count for each and takes the largest. Changes within a 10% tolerance are ignored to avoid flapping. Pods without a CPU request cannot be scaled on CPU utilisation — the HPA shows <unknown> and does nothing.

sync period
The controller-manager evaluates every HPA every 15 s (--horizontal-pod-autoscaler-sync-period).
stabilizationWindowSeconds
For scale-down (default 300 s), the HPA uses the highest desired count seen in the window — so a brief dip does not shrink the fleet. Scale-up default is 0.
behavior.policies
Rate limits: at most N pods or N% per period. Multiple policies → the most permissive wins unless selectPolicy: Min.
Not-yet-ready Pods
Newly started Pods are excluded from the average for a while (--horizontal-pod-autoscaler-initial-readiness-delay) and CPU spikes during start-up are ignored, so a scale-up does not immediately trigger another.
HPA + Deployment replicas
Once an HPA manages a Deployment, remove replicas from your manifest (or every kubectl apply will fight the HPA — Day 9's three-way merge in action).

VerticalPodAutoscaler

VPA is not built in; install it from the autoscaler repo. It watches usage history and recommends (or applies) new requests per container. Because a Pod's requests are immutable, applying a change means re-creating the Pod (in-place resize is beta since 1.33 and used by VPA's InPlaceOrRecreate mode where available).

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: api
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  updatePolicy:
    updateMode: "Off"        # Off = only recommend · Initial = set on creation · Auto/Recreate = evict & re-create
  resourcePolicy:
    containerPolicies:
    - containerName: '*'
      minAllowed: {cpu: 50m, memory: 64Mi}
      maxAllowed: {cpu: "2", memory: 2Gi}
      controlledResources: [cpu, memory]
$ kubectl describe vpa api | grep -A12 'Container Recommendations'
    Lower Bound: cpu 63m  memory 110Mi
    Target:      cpu 120m memory 180Mi      # what it would set
    Upper Bound: cpu 900m memory 512Mi
HPA and VPA on the same metric = oscillation

If HPA scales replicas on CPU utilisation (a % of the request) while VPA changes the request, each one's action changes the other's input. Use VPA in Off mode to inform your requests, or let HPA drive CPU and VPA drive memory only (controlledResources: [memory]), or scale HPA on custom metrics like RPS instead.

Scaling nodes

Cluster Autoscaler

Watches for Pods that are Pending with FailedScheduling: Insufficient …. Asks the cloud's node-group API (ASG, MIG, VMSS) to add a node of that group's fixed type; removes nodes that have been under-utilised for 10 min after draining them. Node groups are pre-defined; it picks among them.

Karpenter

Same trigger, but it reads the Pending Pods' requests, affinities and topology constraints and provisions the cheapest instance type that fits directly through the cloud API, in seconds, with no node groups. Consolidates by replacing several small nodes with one larger one. AWS-first, now multi-cloud.

Node scaling only works if Pods have accurate requests — the autoscaler reasons about requests, not usage, exactly like the scheduler. And it needs Pods to be evictable: PodDisruptionBudgets (kubectl create pdb api --selector=app=api --min-available=2) tell drains how many replicas must stay up.

Under the hood · Linux

"CPU utilisation" in the HPA is cpu.stat usage_usec from the container's cgroup, sampled by the kubelet, divided by the request converted to the same units. Memory is memory.current (working set: total minus inactive file cache). Neither number exists at the Pod level in the kernel — the kubelet sums the container cgroups under the Pod's cgroup. This is why a Pod with no CPU request shows <unknown>: the denominator is missing, not the measurement.

CKA exam tip
  • kubectl autoscale deploy X --min=A --max=B --cpu-percent=N is all you need for the classic task; verify with kubectl get hpa.
  • TARGETS <unknown> → metrics-server missing/unhealthy (kubectl top fails too) or Pods have no CPU request.
  • HPA never scales to zero (minReplicas ≥ 1); scale-to-zero needs KEDA or Knative.

Hands-on lab (20 min)

$ kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
$ kubectl -n kube-system patch deploy metrics-server --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
$ kubectl create deploy php --image=registry.k8s.io/hpa-example --port=80 && kubectl set resources deploy/php --requests=cpu=200m
$ kubectl expose deploy php --port=80
$ kubectl autoscale deploy php --cpu-percent=50 --min=1 --max=6
$ kubectl run load --rm -it --image=busybox:1.36 -- sh -c 'while true; do wget -qO- http://php > /dev/null; done'   # in a second terminal
$ kubectl get hpa php -w            # TARGETS climb past 50%, REPLICAS follow: 1 → 2 → 4 …
# stop the load, watch it hold for ~5 min (stabilization) then scale down
$ kubectl describe hpa php | tail -15     # Events: "New size: 4; reason: cpu resource utilization above target"
$ kubectl delete hpa php; kubectl delete deploy php; kubectl delete svc php

Key takeaways

  • metrics-server → metrics.k8s.io → kubectl top and HPA. Install it; it is not built in.
  • HPA: desired = ceil(current × metric/target), evaluated every 15 s, bounded by min/max and behavior rate limits, with a 5-minute scale-down stabilisation.
  • Utilisation is relative to requests — no request, no scaling. Remove replicas from manifests the HPA owns.
  • VPA right-sizes requests (by re-creating Pods); do not let it fight the HPA on the same resource.
  • Cluster Autoscaler / Karpenter add nodes when Pods are unschedulable — again based on requests.
