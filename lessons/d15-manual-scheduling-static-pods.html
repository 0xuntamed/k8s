The scheduler is just another client of the API server: it finds Pods with an empty nodeName and fills it in. That means you can do its job yourself by setting nodeName — and it means that if the scheduler is down, Pods simply wait. Separately, the kubelet can run Pods with no API server at all, from files on disk: static Pods, the mechanism that bootstraps every kubeadm control plane. Both are exam favourites.

What you'll learn

  • What the scheduler actually writes, and what happens when it is not running
  • Manual scheduling with spec.nodeName and the Binding API
  • Static Pods: the manifests directory, mirror Pods, and how to find the path on any node
  • When to use each (and why you rarely should)

What "scheduling" means

A Pod object is created with spec.nodeName empty. The scheduler watches for exactly those Pods, picks a node, and creates a Binding — which the API server applies by setting nodeName. From that moment the Pod belongs to that node's kubelet. The scheduler never contacts the node and never touches the Pod again. If nodeName is already set when the Pod is created, the scheduler ignores it entirely.

$ kubectl get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,PHASE:.status.phase
$ kubectl get pods --field-selector spec.nodeName=""          # everything still waiting for the scheduler
$ kubectl get events --field-selector reason=Scheduled          # "Successfully assigned default/web to worker-2"

Manual scheduling

apiVersion: v1
kind: Pod
metadata:
  name: pinned
spec:
  nodeName: worker-2          # skip the scheduler entirely
  containers:
  - name: nginx
    image: nginx

With nodeName set, the kubelet on worker-2 starts the Pod immediately — even if the node is full, tainted, or does not match any affinity rule. Nothing is checked. If the node does not exist, the Pod sits in Pending forever; if it runs out of resources, the kubelet fails the Pod with OutOfcpu/OutOfmemory. nodeName is immutable: to move a running Pod you delete and re-create it.

The Binding API (for completeness)

For an existing Pending Pod you cannot edit nodeName, but you can do what the scheduler does: POST a Binding.

$ cat <<EOF | kubectl create -f -
apiVersion: v1
kind: Binding
metadata:
  name: pinned
target:
  apiVersion: v1
  kind: Node
  name: worker-2
EOF

You will never do this in practice, but it demonstrates that scheduling is "just an API write", and custom schedulers (spec.schedulerName) work exactly this way.

When the scheduler is down

Pods stay Pending with no events — not even FailedScheduling, because nothing is looking at them. Existing Pods keep running. On a kubeadm cluster: kubectl get pods -n kube-system | grep scheduler, then check /etc/kubernetes/manifests/kube-scheduler.yaml on the control-plane node (Day 57). Setting nodeName by hand is the workaround that keeps things moving while you fix it.

Static Pods

A static Pod is managed directly by the kubelet, not by the API server. The kubelet watches a directory (by default /etc/kubernetes/manifests) and runs every Pod manifest it finds there — creating, updating and deleting as the files change. No scheduler, no controller-manager, no API server required. This is how kubeadm solves the bootstrap problem: the API server itself is a static Pod.

Mirror Pod
Once the API server is reachable, the kubelet creates a read-only mirror of each static Pod in the API so it shows up in kubectl get pods. Its name is <name>-<nodename>, e.g. kube-apiserver-cka-control-plane. Deleting the mirror through the API does nothing lasting: the kubelet re-creates it.
Removing one
Delete (or move) the file from the manifests directory. The kubelet stops the Pod within seconds.
Where is the directory?
In the kubelet's config file, key staticPodPath. Find the config file from the kubelet's command line.
Limitations
Only Pods — no Deployments, no Services. They cannot reference ConfigMaps or Secrets (there may be no API server). Use hostPath volumes.
# on the node
$ ps -ef | grep kubelet | grep -o -- '--config=[^ ]*'        # --config=/var/lib/kubelet/config.yaml
$ grep staticPodPath /var/lib/kubelet/config.yaml            # staticPodPath: /etc/kubernetes/manifests
$ ls /etc/kubernetes/manifests
$ cat <<EOF | sudo tee /etc/kubernetes/manifests/static-web.yaml
apiVersion: v1
kind: Pod
metadata:
  name: static-web
spec:
  containers:
  - name: web
    image: nginx
EOF
$ crictl ps | grep static-web                                # running within seconds, no API involved
# from anywhere
$ kubectl get pod static-web-<nodename>                      # the mirror pod
$ kubectl delete pod static-web-<nodename>                   # comes straight back
$ sudo rm /etc/kubernetes/manifests/static-web.yaml          # the real way to delete it
Under the hood · Linux

The kubelet polls the manifests directory (file source, default every 20 s, and reacts faster to inotify events) the same way it consumes Pods from the API (apiserver source). Both feed one internal "pod manager"; static Pods are simply Pods whose source is a file. Because the kubelet is a systemd service that starts at boot, static Pods come up with the machine, before the network, before etcd — which is exactly the property a control plane needs. Change a manifest and the kubelet does a stop/start of that Pod; a syntax error in the YAML is logged in journalctl -u kubelet and the Pod silently does not run — the classic Day 57 failure.

CKA exam tip
  • "Create a static Pod on node X" → SSH to the node, find staticPodPath, drop a manifest generated with kubectl run … $do. Verify with kubectl get pods from the control plane (look for the node-name suffix).
  • A Pod you cannot delete (it keeps coming back) with a node-name suffix is a static Pod. Remove the file.
  • Pods Pending with no events at all → is the scheduler running? kubectl get pods -n kube-system.
  • Static-Pod manifests must be valid YAML and cannot use ConfigMap/Secret references.

Hands-on lab (15 min)

$ kubectl run pinned --image=nginx $do | sed '/spec:/a\  nodeName: cka-worker2' | kubectl apply -f -
$ kubectl get pod pinned -o wide                   # on cka-worker2, no Scheduled event
$ kubectl get events --field-selector involvedObject.name=pinned
# static pod on a KIND worker
$ docker exec cka-worker sh -c 'grep staticPodPath /var/lib/kubelet/config.yaml'
$ kubectl run static-web --image=nginx $do | docker exec -i cka-worker tee /etc/kubernetes/manifests/static-web.yaml
$ sleep 10; kubectl get pods                       # static-web-cka-worker
$ kubectl delete pod static-web-cka-worker; sleep 5; kubectl get pods    # it is back
$ docker exec cka-worker rm /etc/kubernetes/manifests/static-web.yaml; sleep 10; kubectl get pods
# break the scheduler and watch pods wait
$ docker exec cka-control-plane mv /etc/kubernetes/manifests/kube-scheduler.yaml /tmp/
$ kubectl run waiting --image=nginx; sleep 5; kubectl get pod waiting; kubectl describe pod waiting | tail -3   # Pending, no events
$ docker exec cka-control-plane mv /tmp/kube-scheduler.yaml /etc/kubernetes/manifests/; sleep 15; kubectl get pod waiting -o wide

Key takeaways

  • Scheduling = writing spec.nodeName. Set it yourself and the scheduler (and all its checks) are bypassed.
  • Scheduler down → Pods Pending with no events; running Pods are unaffected.
  • Static Pods are run by the kubelet from staticPodPath (usually /etc/kubernetes/manifests); the API only holds a read-only mirror named <pod>-<node>.
  • Delete a static Pod by deleting its file. The control plane on kubeadm clusters is four static Pods.
