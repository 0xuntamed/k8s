CMD and ENTRYPOINT both say "what should run when this container starts", which is why people confuse them. The difference is simple once you see it as executable versus default arguments. Along the way we meet the single most important process in any container — PID 1 — and why the "shell form" of these instructions silently breaks graceful shutdown.

What you'll learn

  • ENTRYPOINT = the program, CMD = its default arguments, and how they combine

The rule

When a container starts, Docker builds one command line: ENTRYPOINT followed by CMD. Whatever you type after the image name in docker run replaces CMD. --entrypoint replaces ENTRYPOINT.

ENTRYPOINTCMDdocker run img runsdocker run img -v runs
—["python","app.py"]python app.py-v ✗ (CMD replaced; nothing to run)
["python"]["app.py"]python app.pypython -v
["python","app.py"]—python app.pypython app.py -v
["curl"]["--help"]curl --helpcurl -v
Mental model

Make the image behave like a command-line tool. ENTRYPOINT is the binary; CMD is what you would type if you gave no arguments. docker run myimage --help then reads naturally. Images that are "a service", like nginx or postgres, use the same pattern with a small docker-entrypoint.sh that does setup and then exec "$@".

Exec form vs shell form

Shell form

CMD python app.py

Docker runs /bin/sh -c "python app.py". PID 1 is sh; python is its child. Variable expansion works ($PORT), but signals sent to the container go to sh, which does not forward them.

Exec form

CMD ["python", "app.py"]

Docker execs python directly. PID 1 is python. No shell, no variable expansion (use ["sh","-c","python $APP"] if you need it), and signals reach your app.

Under the hood · Linux

PID 1 is special in a PID namespace. The kernel gives it default signal handlers of "ignore" for any signal it has not explicitly handled — so a PID 1 that does not install a SIGTERM handler cannot be terminated by SIGTERM at all, only by SIGKILL. PID 1 is also responsible for reaping orphaned children; a naive PID 1 leaks zombies. docker run --init (or tini) inserts a minimal init that handles both. In Kubernetes the same rules apply to the first process of every container, and the grace period defaults to 30 s before SIGKILL (Day 22).

The Kubernetes mapping

A Pod spec has command and args. They override the image's ENTRYPOINT and CMD respectively, with the same combination rules:

ENTRYPOINT ["sleep"]
CMD ["5"]
apiVersion: v1
kind: Pod
metadata:
  name: sleeper
spec:
  containers:
  - name: sleeper
    image: ubuntu-sleeper
    command: ["sleep"]   # overrides ENTRYPOINT
    args: ["10"]         # overrides CMD
Pod fieldDocker equivalentNote
commandENTRYPOINTAlways exec form (a list). Replaces the image's entrypoint entirely.
argsCMDIf only args is set, the image's ENTRYPOINT is kept and args replaces CMD.
CKA exam tip

Classic task: "Create a pod that runs sleep 3600 in busybox". Fast answer: kubectl run sleeper --image=busybox --command -- sleep 3600. Without --command, everything after -- becomes args, which only works if the image's entrypoint accepts them. Check with kubectl get pod sleeper -o yaml | grep -A3 command.

A custom Dockerfile with a real entrypoint script

#!/bin/sh
set -e
# one-time setup: render config from env, wait for a dependency, etc.
envsubst < /etc/app/config.tmpl > /etc/app/config.yaml
# hand PID 1 to the real process so it receives signals
exec "$@"
FROM alpine:3.20
RUN apk add --no-cache gettext          # provides envsubst
COPY docker-entrypoint.sh /usr/local/bin/
RUN chmod +x /usr/local/bin/docker-entrypoint.sh
ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["myserver", "--config", "/etc/app/config.yaml"]

The exec "$@" line is the whole point: the shell replaces itself with the server, so the server becomes PID 1 and docker stop works. Every official database and web-server image uses exactly this pattern.

Hands-on lab (10 min)

Watch shell form ignore SIGTERM.

$ printf 'FROM alpine\nCMD sleep 300\n' > Dockerfile.shell
$ printf 'FROM alpine\nCMD ["sleep","300"]\n' > Dockerfile.exec
$ docker build -q -t s-shell -f Dockerfile.shell . && docker build -q -t s-exec -f Dockerfile.exec .
$ docker run -d --name a s-shell && docker run -d --name b s-exec
$ docker exec a ps            # PID 1 = /bin/sh -c sleep 300, PID 7 = sleep
$ docker exec b ps            # PID 1 = sleep 300
$ time docker stop a          # ~10 s: sh ignores SIGTERM, Docker escalates to SIGKILL
$ time docker stop b          # instant? no — sleep also has no handler. Try with nginx:
$ docker run -d --name n nginx && time docker stop n   # < 1 s, nginx handles SIGTERM
$ docker rm -f a b n

Key takeaways

  • Final command = ENTRYPOINT + CMD; run-time arguments replace CMD; --entrypoint replaces ENTRYPOINT.
  • Always use exec (JSON array) form so your process is PID 1 and receives SIGTERM. In entrypoint scripts, finish with exec "$@".
  • Kubernetes command ⇢ ENTRYPOINT, args ⇢ CMD.
  • Log to stdout; use docker logs, exec, inspect and stats for day-to-day debugging.
