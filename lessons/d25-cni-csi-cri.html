Kubernetes itself does not run containers, does not assign IP addresses, and does not attach disks. It defines three interfaces — CRI for runtimes, CNI for networking, CSI for storage — and lets you plug in an implementation for each. Everything else that a cluster "obviously has" (DNS, metrics, a dashboard) is an add-on: a normal workload you install. Knowing which layer owns which job is the difference between a 5-minute fix and an afternoon of guessing.

What you'll learn

  • Core vs extensions: what Kubernetes ships and what it expects you to bring
  • CRI: how the kubelet talks to containerd/CRI-O, and crictl

  • CSI: the controller/node split, the sidecar pattern, and dynamic provisioning

CRI — the runtime

The kubelet's only way to run a container is the CRI: RunPodSandbox (the pause container + namespaces), PullImage, CreateContainer, StartContainer, ContainerStatus, Exec… containerd implements it directly through its cri plugin. The socket is configured in the kubelet (--container-runtime-endpoint=unix:///run/containerd/containerd.sock).

$ crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps      # or set /etc/crictl.yaml once
$ crictl pods                            # sandboxes (one per Pod)
$ crictl ps -a                           # containers incl. exited
$ crictl logs <container-id>
$ crictl inspect <container-id> | jq '.info.runtimeSpec.linux.namespaces'
$ crictl images; crictl rmi --prune
$ systemctl status containerd; journalctl -u containerd -n 50
$ cat /etc/containerd/config.toml | grep -A3 'runc.options'    # SystemdCgroup = true is required with the systemd cgroup driver
cgroup driver mismatch

The kubelet and the runtime must agree on who manages cgroups: cgroupfs or systemd. Modern kubeadm defaults the kubelet to systemd; containerd must then have SystemdCgroup = true. A mismatch produces a node that flaps NotReady with cryptic kubelet errors. Day 54 sets this up.

CNI — the network

When the kubelet creates a Pod sandbox, the runtime looks in /etc/cni/net.d/ for the first config file, finds the plugin binary named there in /opt/cni/bin/, and executes it with CNI_COMMAND=ADD, the sandbox's network-namespace path, and the config on stdin. The plugin creates a veth pair, moves one end into the namespace, assigns an IP from the node's Pod CIDR, sets routes, and returns the IP as JSON. On Pod deletion it is called with DEL. That is the whole interface; everything a CNI does across nodes (routing, overlays, policies) is the implementation's business.

$ ls /etc/cni/net.d/                       # 10-calico.conflist, 10-kindnet.conflist …
$ cat /etc/cni/net.d/10-calico.conflist | jq '.plugins[].type'
$ ls /opt/cni/bin/                         # calico, bridge, host-local, loopback, portmap, bandwidth …
$ kubectl get pods -n kube-system -l k8s-app=calico-node -o wide   # the DaemonSet that installs and runs it
$ kubectl get node worker-1 -o jsonpath='{.spec.podCIDR}'          # this node's Pod IP range

Calico

BGP or VXLAN routing, mature NetworkPolicy, optional eBPF data plane. The course uses it with kubeadm (Day 54).

Cilium

eBPF-based: replaces kube-proxy, L7 policies, Hubble observability. Fast and increasingly the default.

Flannel

Simplest overlay (VXLAN). No NetworkPolicy support on its own.

Cloud VPC CNIs

AWS VPC CNI, Azure CNI, GKE: Pods get real VPC IPs; policies via an add-on.

No CNI installed is the most recognisable failure: every node stays NotReady with container runtime network not ready: cni plugin not initialized, and CoreDNS Pods sit in Pending/ContainerCreating. kubeadm deliberately leaves this step to you.

Under the hood · Linux

You can run a CNI plugin by hand. Create a netns (ip netns add test), then CNI_COMMAND=ADD CNI_CONTAINERID=x CNI_NETNS=/var/run/netns/test CNI_IFNAME=eth0 CNI_PATH=/opt/cni/bin /opt/cni/bin/bridge < /etc/cni/net.d/10-bridge.conf. The plugin prints the JSON result with the assigned IP, and ip netns exec test ip addr shows a new eth0. The "reference" plugins (bridge, host-local IPAM, loopback, portmap) are exactly what kindnet chains together; Calico and Cilium replace bridge with their own routing but still chain portmap for hostPort and bandwidth for traffic shaping.

CSI — the storage

A CSI driver has two halves. The controller half (a Deployment, usually 1–2 replicas) creates and deletes volumes in the backend and attaches/detaches them to nodes. The node half (a DaemonSet) formats and mounts an attached volume into the Pod's directory. Kubernetes talks to both through standard sidecar containers that translate API objects into gRPC calls: external-provisioner (watches PVCs), external-attacher (VolumeAttachment objects), external-resizer, external-snapshotter, node-driver-registrar (tells the kubelet the driver exists), livenessprobe.

$ kubectl get csidrivers                          # ebs.csi.aws.com, csi.tigera.io …
$ kubectl get csinodes -o yaml | grep -A4 drivers   # which drivers each node has registered
$ kubectl get pods -n kube-system -l app=ebs-csi-controller   # controller Deployment
$ kubectl get pods -n kube-system -l app=ebs-csi-node -o wide  # node DaemonSet
$ ls /var/lib/kubelet/plugins/                     # driver sockets on a node
$ kubectl get volumeattachments                    # what is attached where

The flow for a dynamically provisioned disk: PVC created → external-provisioner calls CreateVolume → PV object created and bound → Pod scheduled → external-attacher calls ControllerPublishVolume (attach disk to that VM) → kubelet calls NodeStageVolume (format + mount to a staging dir) and NodePublishVolume (bind-mount into the Pod). Day 27 covers the objects; this is the machinery behind them. The old "in-tree" plugins (awsElasticBlockStore: etc.) are gone — migrated to CSI and removed from core.

CKA exam tip
  • Node NotReady + "cni plugin not initialized" → install/repair the CNI (check the DaemonSet, /etc/cni/net.d, /opt/cni/bin).
  • Node NotReady + kubelet logs mention the runtime socket → systemctl status containerd, socket path in kubelet config.
  • PVC Pending with "waiting for a volume to be created" → provisioner (CSI controller or StorageClass) problem, not a Pod problem.
  • crictl is your docker ps on exam nodes.

Key takeaways

  • Kubernetes core delegates running containers (CRI), Pod networking (CNI) and storage (CSI) to pluggable implementations.
  • CRI = kubelet → containerd over gRPC; crictl is the CLI. cgroup drivers must match.
  • CNI = a binary in /opt/cni/bin configured by /etc/cni/net.d, run per Pod with ADD/DEL. No CNI → nodes NotReady.
  • CSI = controller (provision/attach) + node (mount) halves, driven by standard sidecars; PVC → CreateVolume → attach → stage → publish.
  • DNS, metrics, ingress, GPUs, policy engines are add-ons and plugins, installed and troubleshot like any workload.
