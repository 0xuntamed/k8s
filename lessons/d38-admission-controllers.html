Authentication says who you are; authorization says what you may do. Neither looks at the content of what you are creating. That is the job of admission controllers: code that runs inside the API server after authorization and before persistence, which can mutate the object (fill in defaults, inject sidecars) or validate it (reject a privileged container, enforce a quota). Half of "why did Kubernetes change my YAML?" and all of "why was my Pod rejected even though I'm cluster-admin?" is answered here.

What you'll learn

  • Where admission sits in the pipeline and the mutating → validating order
  • The built-in plugins you rely on without knowing: NamespaceLifecycle, LimitRanger, ServiceAccount, DefaultStorageClass, ResourceQuota, PodSecurity, NodeRestriction…
  • Enabling/disabling plugins on the API server and reading the current set
  • Dynamic admission: MutatingWebhookConfiguration and ValidatingWebhookConfiguration
  • ValidatingAdmissionPolicy (CEL) and where Kyverno/Gatekeeper fit

The admission phase

Admission only runs for requests that change state (create, update, patch, delete, connect) — never for reads. Two sub-phases, in a fixed order:

  1. Mutating — built-in mutating plugins, then mutating webhooks (in name order, and re-run if one changes the object after another). They may alter the object.
  2. Schema validation of the (now mutated) object against its OpenAPI type.
  3. Validating — built-in validating plugins, then validating webhooks, then ValidatingAdmissionPolicies, all in parallel. Any single rejection fails the request with the plugin's message.

Mutation first, validation last, so validators always see the final object — a webhook that injects a sidecar cannot sneak a privileged container past PodSecurity.

Enabling a non-default plugin means editing the static Pod manifest (--enable-admission-plugins=NodeRestriction,AlwaysPullImages); the kubelet restarts the API server. Some plugins need a config file via --admission-control-config-file.

Dynamic admission: webhooks

Built-in plugins are compiled into the API server. Webhooks let you add policy at runtime: the API server POSTs an AdmissionReview (the object, the user, the operation) to an HTTPS endpoint — usually a Service in the cluster — and acts on the JSON response.

apiVersion: admissionregistration.k8s.io/v1
kind: MutatingWebhookConfiguration
metadata:
  name: sidecar-injector
webhooks:
- name: inject.example.com
  clientConfig:
    service: {name: injector, namespace: infra, path: /mutate, port: 443}
    caBundle: LS0tLS1CRUdJTi…              # CA that signed the webhook server's cert
  rules:
  - apiGroups: [""]
    apiVersions: [v1]
    operations: [CREATE]
    resources: [pods]
  namespaceSelector:                        # only namespaces labelled injection=enabled
    matchLabels: {injection: enabled}
  objectSelector: {}                        # optionally, only objects with certain labels
  failurePolicy: Fail                       # Fail (reject if webhook unreachable) or Ignore
  sideEffects: None
  timeoutSeconds: 5
  admissionReviewVersions: [v1]
  reinvocationPolicy: IfNeeded

A mutating webhook responds with a JSON patch ({"op":"add","path":"/spec/containers/-","value":{…}}); a validating one with allowed: true/false and a message. Istio's sidecar injection, cert-manager's CA injector, and Kyverno's mutations are all mutating webhooks; OPA Gatekeeper and Kyverno's validations are validating webhooks.

A webhook can take the cluster down

failurePolicy: Fail plus a webhook that matches everything (resources: ["*"], no namespaceSelector) and whose Pods are down = no object can be created or updated anywhere, including the webhook's own Pods and kube-system. Always exclude kube-system via namespaceSelector, set a short timeoutSeconds, and understand that Ignore trades safety for availability. When the API server logs failed calling webhook, this is what happened; the fix is kubectl delete mutatingwebhookconfiguration <name> (RBAC permitting) — the API server does not call webhooks for the webhook configuration objects themselves.

ValidatingAdmissionPolicy: in-process rules with CEL

GA since 1.30, this lets you write validation rules in CEL that the API server evaluates itself — no webhook server, no TLS, no availability risk:

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-team-label
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: ["apps"]
      apiVersions: ["v1"]
      operations: [CREATE, UPDATE]
      resources: ["deployments"]
  validations:
  - expression: "has(object.metadata.labels) && 'team' in object.metadata.labels"
    message: "every Deployment must carry a team label"
  - expression: "object.spec.replicas <= 20"
    messageExpression: "'replicas must be ≤ 20, got ' + string(object.spec.replicas)"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-team-label-prod
spec:
  policyName: require-team-label
  validationActions: [Deny]          # or Warn, Audit
  matchResources:
    namespaceSelector:
      matchLabels: {env: prod}

Use it for anything expressible as "look at the object and decide". Webhooks remain for mutation, for decisions that need external data, and for policy engines' richer UX (Kyverno, Gatekeeper, which increasingly compile to CEL themselves).

CKA exam tip
  • "Enable the X admission plugin" → edit /etc/kubernetes/manifests/kube-apiserver.yaml, add to --enable-admission-plugins (comma-separated), wait for the API server to come back (watch crictl ps). A typo keeps the API server down — check crictl logs of the failed container.
  • "Pod created but has fields I never set" → an admission plugin (ServiceAccount, LimitRanger, DefaultTolerationSeconds) or a mutating webhook.
  • "Everything fails with 'failed calling webhook'" → find and fix/delete the webhook configuration.
  • Rejections from admission are HTTP 4xx with the plugin's message in the kubectl error — read it; it usually says exactly what to change.

Hands-on lab (15 min)

$ docker exec cka-control-plane grep -E 'admission' /etc/kubernetes/manifests/kube-apiserver.yaml
$ kubectl run plain --image=nginx && kubectl get pod plain -o yaml | grep -A6 -E '^  tolerations:|serviceAccountName'
$ kubectl create ns lr && kubectl create -n lr -f - <<EOF
apiVersion: v1
kind: LimitRange
metadata: {name: lr}
spec: {limits: [{type: Container, max: {cpu: "1"}, default: {cpu: 200m}, defaultRequest: {cpu: 100m}}]}
EOF
$ kubectl run big --image=nginx -n lr --limits=cpu=2          # rejected by LimitRanger: maximum cpu usage per Container is 1
$ kubectl run ok --image=nginx -n lr && kubectl get pod ok -n lr -o jsonpath='{.spec.containers[0].resources}{"\n"}'   # defaults injected
# a CEL policy
$ kubectl apply -f - <<EOF
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: {name: no-latest}
spec:
  failurePolicy: Fail
  matchConstraints: {resourceRules: [{apiGroups: [""], apiVersions: [v1], operations: [CREATE], resources: [pods]}]}
  validations:
  - expression: "object.spec.containers.all(c, !c.image.endsWith(':latest') && c.image.contains(':'))"
    message: "images must be tagged and must not use :latest"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata: {name: no-latest}
spec: {policyName: no-latest, validationActions: [Deny]}
EOF
$ kubectl run l --image=nginx:latest                         # denied with your message
$ kubectl run l --image=nginx:1.27 && kubectl delete pod l plain $now
$ kubectl delete validatingadmissionpolicybinding no-latest; kubectl delete validatingadmissionpolicy no-latest; kubectl delete ns lr

Key takeaways

  • Admission runs after authz on writes: mutating (built-ins, then webhooks) → schema validation → validating (built-ins, webhooks, CEL policies). Any validator can reject.
  • Built-ins explain the "magic": ServiceAccount, LimitRanger, DefaultStorageClass, DefaultTolerationSeconds mutate; NamespaceLifecycle, ResourceQuota, PodSecurity, NodeRestriction validate.
  • Enable/disable via the API server manifest flags. NodeRestriction should always be on.
  • Webhooks add runtime policy but can block the whole cluster — scope them, exclude kube-system, set timeouts.
  • ValidatingAdmissionPolicy (CEL) validates in-process with no webhook risk; use it first.
