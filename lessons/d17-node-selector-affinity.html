Taints keep Pods away from nodes. To pull Pods toward nodes — "run on SSD nodes", "prefer zone eu-west-1a", "never on ARM" — you label the nodes and tell the Pod what labels it wants. nodeSelector is the simple form (exact match, all required); node affinity is the expressive one, with operators, OR-groups, and soft preferences that influence scoring instead of filtering.

What you'll learn

  • Labelling nodes and the labels every node already has
  • nodeSelector: exact-match, AND semantics
  • Node affinity: required… (hard filter) vs preferred… (weighted score)
  • Operators: In, NotIn, Exists, DoesNotExist, Gt, Lt — and how terms combine (OR of ANDs)
  • Why "IgnoredDuringExecution" is in the name

Node labels

$ kubectl get nodes --show-labels
$ kubectl label nodes worker-1 disktype=ssd
$ kubectl label nodes worker-1 disktype=nvme --overwrite
$ kubectl label nodes worker-1 disktype-                    # remove
$ kubectl get nodes -l disktype=ssd
$ kubectl get nodes -L disktype,topology.kubernetes.io/zone  # show as columns

Nodes come with useful labels already: kubernetes.io/hostname, kubernetes.io/os, kubernetes.io/arch, node.kubernetes.io/instance-type, topology.kubernetes.io/zone and …/region (set by the cloud provider), and node-role.kubernetes.io/control-plane. Your own labels are just conventions — pool=batch, gpu=a100, env=prod.

nodeSelector — the simple form

apiVersion: v1
kind: Pod
metadata:
  name: db
spec:
  nodeSelector:
    disktype: ssd
    topology.kubernetes.io/zone: eu-west-1a   # ALL listed labels must match exactly
  containers:
  - name: postgres
    image: postgres:16

If no node has all those labels, the Pod stays Pending with FailedScheduling: … didn't match Pod's node affinity/selector. There is no "prefer", no "not", no "one of". For that you need affinity.

Node affinity — the expressive form

spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:     # HARD: filter
        nodeSelectorTerms:                                  # terms are OR-ed
        - matchExpressions:                                 # expressions inside a term are AND-ed
          - key: disktype
            operator: In
            values: [ssd, nvme]
          - key: kubernetes.io/arch
            operator: NotIn
            values: [arm64]
        - matchExpressions:                                 # OR this whole term
          - key: pool
            operator: Exists
      preferredDuringSchedulingIgnoredDuringExecution:    # SOFT: score
      - weight: 80                                          # 1–100
        preference:
          matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values: [eu-west-1a]
      - weight: 20
        preference:
          matchExpressions:
          - key: cpu-generation
            operator: Gt
            values: ["5"]
OperatorMatches when the node label…
Inexists and its value is one of values
NotIndoes not exist, or its value is not in values
Existsexists (any value; values must be empty)
DoesNotExistdoes not exist
Gt / Ltexists and parses as an integer greater/less than the single value

Reading the long names

requiredDuringScheduling
Used as a filter: nodes that fail are removed. No node passes → Pending.
preferredDuringScheduling
Used in scoring: each satisfied preference adds its weight to the node's score; the highest total wins among the nodes that passed filtering. Never causes Pending.
IgnoredDuringExecution
Once the Pod is running, label changes on the node do not evict it. (A RequiredDuringExecution variant has been proposed for years; it does not exist. Taints with NoExecute are the way to evict.)
Mental model

The scheduler runs two phases for every Pod: filter (yes/no per node: resources, taints, required affinity, nodeSelector, ports, volumes) and score (0–100 per surviving node: preferred affinity, spreading, least-allocated, image locality). nodeSelector and required are filters; preferred is a score. CKA exam tip
  • Tasks usually say "schedule on nodes labelled X". nodeSelector is the fastest correct answer unless they say "prefer" or use NotIn/Exists.
  • Copy the affinity block from kubectl explain pod.spec.affinity.nodeAffinity --recursive or the docs page "Assign Pods to Nodes" — indentation errors here are the classic time sink.
  • For a Deployment, the affinity goes under spec.template.spec, not spec.
  • Pending + "didn't match Pod's node affinity/selector" → compare kubectl get nodes --show-labels with the Pod's rule; a typo in the label key is the usual culprit.

Hands-on lab (15 min)

$ kubectl label nodes cka-worker disktype=ssd && kubectl label nodes cka-worker2 disktype=hdd zone=b
$ kubectl run ssd --image=nginx $do | sed '/spec:/a\  nodeSelector:\n    disktype: ssd' | kubectl apply -f -
$ kubectl get pod ssd -o wide                                   # cka-worker
$ kubectl run nowhere --image=nginx $do | sed '/spec:/a\  nodeSelector:\n    disktype: nvme' | kubectl apply -f -
$ kubectl describe pod nowhere | tail -3                        # FailedScheduling: didn't match
$ cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: {name: prefer-b}
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions: [{key: zone, operator: In, values: [b]}]
  containers: [{name: n, image: nginx}]
EOF
$ kubectl get pod prefer-b -o wide                              # cka-worker2 (preferred, but would run anywhere)
$ kubectl label nodes cka-worker2 zone-                         # IgnoredDuringExecution: pod stays
$ kubectl delete pod ssd nowhere prefer-b $now

Key takeaways

  • Label nodes; select with nodeSelector (exact, AND) or nodeAffinity (operators, OR-ed terms, soft weights).
  • required… filters (can cause Pending); preferred… scores (never blocks).
  • Both are IgnoredDuringExecution: label changes never evict running Pods.
  • nodeName skips the scheduler entirely; the other two go through filter + score.
