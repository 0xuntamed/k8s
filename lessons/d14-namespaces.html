A Namespace is a named partition of the cluster's API objects: a place to put a team's or an environment's Deployments, Services and Secrets so names do not collide, quotas can be applied and permissions can be scoped. It is not a security boundary by itself and it does not isolate networks — those come from RBAC and NetworkPolicies layered on top. Understanding exactly what a Namespace does and does not partition saves a lot of confusion.

What a Namespace partitions

$ kubectl api-resources --namespaced=true  | head     # pods, services, deployments, configmaps, secrets, pvc, roles…
$ kubectl api-resources --namespaced=false | head     # nodes, namespaces, persistentvolumes, storageclasses, clusterroles, crds…
Namespaced (per-namespace names)Cluster-scoped (one flat set)
Pod, Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, CronJobNode, Namespace

Rule of thumb: things that represent your workload are namespaced; things that represent the cluster's infrastructure are not. A PVC (a request by an app) is namespaced; the PV it binds to (a disk) is not.

Built-in namespaces

default
Where things go when you do not say -n. Fine for learning; in real clusters, create your own and leave this empty.
kube-system
Cluster components: CoreDNS, kube-proxy, the CNI, metrics-server, and on kubeadm clusters the static-Pod mirrors for etcd/API server/scheduler/controller-manager. Look here first when the cluster itself misbehaves.
kube-public
Readable by everyone including unauthenticated users. Holds the cluster-info ConfigMap used by kubeadm join. Almost never used otherwise.
kube-node-lease
One Lease object per node, renewed by its kubelet every 10 s — the cheap heartbeat the node controller uses to decide a node is unreachable.

Working with namespaces

$ kubectl create namespace dev                         # or: kubectl create ns dev
$ kubectl get ns
$ kubectl run web --image=nginx -n dev                 # -n on any command
$ kubectl get pods -A                                  # --all-namespaces
$ kubectl config set-context --current --namespace=dev # make dev the default for this context
$ kubectl config view --minify | grep namespace
$ kubectl get pods -n kube-system -o wide
$ kubectl delete ns dev                                # deletes EVERYTHING inside — no confirmation
apiVersion: v1
kind: Namespace
metadata:
  name: dev
  labels:
    team: payments            # labels on namespaces are what NetworkPolicy namespaceSelector matches
    pod-security.kubernetes.io/enforce: baseline   # Pod Security Admission (Day 41)

A manifest can pin its namespace with metadata.namespace; if it does, -n on the command line must agree or the apply is rejected. If it does not, the object goes to the current context's namespace. Most teams leave it out of files and set it at apply time (or with Kustomize) so the same manifests work in dev and prod.

DNS across namespaces

Every Service gets the DNS name <service>.<namespace>.svc.cluster.local. A Pod's /etc/resolv.conf carries a search list for its own namespace, so from a Pod in dev:

api                          # → api.dev.svc.cluster.local      (same namespace: short name works)
api.prod                     # → api.prod.svc.cluster.local     (another namespace: add it)
api.prod.svc.cluster.local   # fully qualified — always works, fastest (no search-list retries)
Under the hood · Linux

Inside any Pod, cat /etc/resolv.conf shows something like nameserver 10.96.0.10 (the CoreDNS Service), search dev.svc.cluster.local svc.cluster.local cluster.local, options ndots:5. The resolver appends each search domain in turn for any name with fewer than 5 dots — which is why api works and why looking up api.prod costs one failed query (api.prod.dev.svc.cluster.local) before it succeeds. That search list is the only thing that makes a namespace feel "local" to DNS; CoreDNS itself serves every namespace. Details on Day 48. Note the naming overlap: a Kubernetes Namespace is an API-object partition and has nothing to do with the Linux kernel namespaces that isolate containers.

What a Namespace does NOT do

No network isolation

By default any Pod can reach any Service in any namespace. Isolation requires NetworkPolicies, enforced by the CNI.

No access control by itself

A user with a ClusterRoleBinding sees every namespace. Scoping needs Roles and RoleBindings in that namespace.

No node isolation

Pods from different namespaces share nodes and kernels. Dedicated nodes need taints/affinity (Days 16–18).

No resource isolation by default

One namespace can consume the whole cluster — until you add a ResourceQuota.

ResourceQuota and LimitRange

apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    pods: "20"
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    persistentvolumeclaims: "5"
    services.loadbalancers: "1"
    count/deployments.apps: "10"
apiVersion: v1
kind: LimitRange
metadata:
  name: dev-limits
  namespace: dev
spec:
  limits:
  - type: Container
    default:            # limit applied if the container sets none
      cpu: 500m
      memory: 256Mi
    defaultRequest:     # request applied if none
      cpu: 100m
      memory: 128Mi
    max:
      cpu: "2"
      memory: 2Gi

ResourceQuota caps the sum across the namespace; when a request would exceed it, the API server rejects the create with 403 Forbidden: exceeded quota. Important gotcha: once a quota on requests.cpu exists, every Pod must declare a CPU request or it is rejected — which is why a LimitRange with defaults usually accompanies it. LimitRange applies per object (Container, Pod, PVC): defaults, minimums, maximums. Both are covered in depth with requests/limits on Day 19.

$ kubectl describe quota -n dev            # Used vs Hard, live
$ kubectl describe limitrange -n dev
$ kubectl create quota dev-q --hard=pods=5 -n dev   # imperative

Deleting a namespace (and when it hangs)

kubectl delete ns dev puts the namespace in Terminating and the namespace controller deletes every object inside it. It can hang forever if some object has a finalizer whose controller is gone (a CRD's operator was uninstalled first, a webhook is down). Find it with kubectl api-resources --verbs=list --namespaced -o name | xargs -n1 kubectl get -n dev --ignore-not-found, then remove the finalizer from that object (kubectl patch … -p '{"metadata":{"finalizers":[]}}' --type=merge). Removing the finalizer from the Namespace object itself is a last resort that can leak resources.

CKA exam tip
  • Every task names a namespace. Set it as the context default, then verify with kubectl config view --minify.
  • "Pod cannot be created: exceeded quota" or "must specify cpu request" → look at describe quota / describe limitrange in that namespace.
  • Cross-namespace Service access questions are DNS questions: svc.ns or the FQDN.

Hands-on lab (15 min)

$ kubectl create ns dev && kubectl create ns prod
$ kubectl create deploy api --image=nginx -n prod && kubectl expose deploy api --port=80 -n prod
$ kubectl run t --rm -it --image=busybox:1.36 -n dev -- sh -c 'cat /etc/resolv.conf; wget -qO- --timeout=2 http://api || echo FAIL; wget -qO- --timeout=2 http://api.prod | head -1'
$ kubectl create quota q --hard=pods=2 -n dev
$ kubectl create deploy many --image=nginx --replicas=5 -n dev
$ kubectl get deploy,rs -n dev; kubectl describe rs -n dev | grep -A3 Events     # "exceeded quota"
$ kubectl describe quota q -n dev
$ kubectl delete ns dev prod

Key takeaways

  • Namespaces partition names of namespaced objects; nodes, PVs, StorageClasses, ClusterRoles and CRDs are cluster-wide.
  • default, kube-system, kube-public, kube-node-lease exist from the start; make your own for real work.
  • DNS: svc in-namespace, svc.ns across, svc.ns.svc.cluster.local always.
  • Isolation of network, access and resources needs NetworkPolicy, RBAC and ResourceQuota/LimitRange respectively.
  • Deleting a namespace deletes everything in it; a stuck Terminating namespace means a finalizer nobody is processing.
