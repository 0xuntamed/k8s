Everything a container writes goes into its thin writable layer, and that layer is deleted with the container. For a stateless web server that is a feature. For a database it is a disaster. Docker's answer — mount a directory from outside the layer stack into the container — is the exact idea Kubernetes generalises into volumes, PersistentVolumes and CSI. Learn it here where there is only one machine and no controllers in the way.

What you'll learn

  • Why the writable layer is ephemeral and slow
  • Bind mounts vs named volumes vs tmpfs, and the -v / --mount syntax
  • Sharing data between containers; volume lifecycle and backup
  • The mount-namespace mechanics underneath, which are identical in Kubernetes

The writable layer problem

Two problems with writing into the container layer: it is lost on docker rm, and it is slow — every write to a file that exists in a lower layer first triggers a copy-up of the whole file through OverlayFS. Databases, uploads, caches and logs all belong outside the layer stack.

Three kinds of mounts

Bind mount

A host directory (or file) mounted at a container path. You choose the host path; Docker does not manage it.

docker run -v /srv/data:/var/lib/postgresql/data postgres
docker run --mount type=bind,src=$(pwd),dst=/app,readonly node

Dev loops (live code), host config files, host sockets (/var/run/docker.sock).

Named volume

A directory Docker creates and manages under /var/lib/docker/volumes/<name>/_data. Portable across hosts (with drivers), listed and deleted by name.

docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres
docker run --mount type=volume,src=pgdata,dst=/var/lib/postgresql/data postgres

Databases, anything that must outlive the container.

tmpfs

RAM-backed, never written to disk, gone when the container stops.

docker run --tmpfs /run:rw,size=64m nginx
docker run --mount type=tmpfs,dst=/scratch,tmpfs-size=100m app

Secrets in flight, scratch space, anything sensitive.

Working with volumes

$ docker volume ls
$ docker volume inspect pgdata                 # Mountpoint: /var/lib/docker/volumes/pgdata/_data
$ docker run -d --name db -v pgdata:/var/lib/postgresql/data -e POSTGRES_PASSWORD=pw postgres:16
$ docker rm -f db                              # container gone…
$ docker run -d --name db2 -v pgdata:/var/lib/postgresql/data -e POSTGRES_PASSWORD=pw postgres:16   # …data still there
$ docker run --rm --volumes-from db2 alpine ls /var/lib/postgresql/data     # share another container's mounts
$ docker run --rm -v pgdata:/from -v $(pwd):/to alpine tar czf /to/pgdata.tgz -C /from .   # backup
$ docker volume prune                          # delete volumes not used by any container
$ docker volume rm pgdata

Anonymous volumes appear when an image declares VOLUME /data and you run it without -v: Docker creates a random-named volume so writes there do not hit the layer. They are removed with docker rm -v; otherwise they accumulate — docker volume prune cleans up.

Under the hood · Linux

Every one of these is a plain mount executed inside the container's mount namespace before the process starts. A bind mount is mount --bind /srv/data /merged/var/lib/postgresql/data; a named volume is the same thing with a Docker-chosen source; tmpfs is mount -t tmpfs. The container's root filesystem is itself an OverlayFS mount; the volume mounts sit on top of specific paths within it, which is why the image's contents at that path become invisible (shadowed) for bind mounts. From inside the container: cat /proc/self/mountinfo lists every mount with its source; from the host: findmnt -N <pid> shows the same for any process. Kubernetes' kubelet performs exactly these mounts under /var/lib/kubelet/pods/<uid>/volumes/ and the runtime bind-mounts them into containers.

$ docker run -d --name v -v pgdata:/data -v $(pwd):/host:ro --tmpfs /tmp alpine sleep 3600
$ docker exec v cat /proc/self/mountinfo | grep -E ' /data | /host | /tmp | / '
$ docker exec v df -h /data /host /tmp /
$ sudo findmnt -N $(docker inspect -f '{{.State.Pid}}' v) | head

Compose preview: volumes as first-class objects

services:
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data        # named volume
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro   # bind mount
volumes:
  pgdata: {}

Notice the shape: volumes are declared once at the top level and referenced by services with a mount path. A Kubernetes Pod does the same — volumes: at Pod level, volumeMounts: per container — and a PersistentVolumeClaim is the cluster-wide version of that top-level declaration.

CKA exam tip

Nothing Docker-specific is examined, but the mapping is: bind mount ⇢ hostPath (Day 27), named volume ⇢ PV + PVC, tmpfs ⇢ emptyDir with medium: Memory (Day 26), --volumes-from ⇢ two containers in one Pod mounting the same volume (Day 21).

Hands-on lab (10 min)

$ docker run --name a alpine sh -c 'echo hello > /data.txt'; docker rm a
$ docker run --rm alpine cat /data.txt          # No such file — writable layer was deleted
$ docker volume create keep
$ docker run --rm -v keep:/data alpine sh -c 'echo hello > /data/data.txt'
$ docker run --rm -v keep:/data alpine cat /data/data.txt      # hello — survives across containers
$ docker run --rm -v $(pwd):/host:ro alpine ls /host             # bind mount of your cwd, read-only
$ docker run --rm -v $(pwd):/host:ro alpine touch /host/x        # Read-only file system
$ docker volume inspect keep; docker volume rm keep

Key takeaways

  • The writable layer dies with the container and is slow for heavy writes; put data in a volume.
  • Bind mounts use a host path you choose; named volumes are Docker-managed; tmpfs is RAM.
  • Volumes are mounts inside the container's mount namespace — the same mechanism Kubernetes uses for every volume type.
  • Declare once, mount per container — the shape of Pod volumes/volumeMounts and PVCs.
