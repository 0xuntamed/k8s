Config from the environment, not from the image — that is the rule from Day 11, and ConfigMaps and Secrets are how Kubernetes delivers it. Both are key-value objects you inject as environment variables or files. The difference is intent and handling: a Secret is meant to hold credentials, so the API, the kubelet and RBAC treat it a little more carefully — but base64 is not encryption, and a Secret is only as secret as your cluster's etcd and RBAC make it.

What you'll learn

  • Creating ConfigMaps and Secrets from literals, files and env-files; the data/stringData/binaryData fields
  • Consuming them: env, envFrom, volumes, and when each updates
  • Secret types (Opaque, docker-registry, tls, service-account-token, basic-auth, ssh-auth)
  • What actually protects a Secret: RBAC, tmpfs, encryption at rest, external secret stores
  • immutable: true and rollout strategies for config changes

ConfigMap

$ kubectl create configmap app-config \
    --from-literal=LOG_LEVEL=info \
    --from-literal=FEATURE_X=true \
    --from-file=app.yaml \                         # key = filename, value = contents
    --from-file=nginx=./conf/nginx.conf \          # key=path to choose the key name
    --from-env-file=.env                           # KEY=VALUE lines → keys
$ kubectl get cm app-config -o yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:                          # UTF-8 strings
  LOG_LEVEL: info
  FEATURE_X: "true"            # quote booleans/numbers — values must be strings
  app.yaml: |
    server:
      port: 8080
      timeout: 30s
binaryData:                    # base64 for non-UTF-8 content
  logo.png: iVBORw0KGgo…
immutable: false

Limit: 1 MiB per object (an etcd limit). Keys must be valid filenames. A ConfigMap is not a place for secrets, large files, or anything the application should not be able to read in plain text.

Secret

$ kubectl create secret generic db-creds --from-literal=username=app --from-literal=password='s3cr3t!'
$ kubectl create secret generic tls-files --from-file=tls.crt --from-file=tls.key
$ kubectl create secret tls web-tls --cert=tls.crt --key=tls.key          # type kubernetes.io/tls
$ kubectl create secret docker-registry regcred --docker-server=ghcr.io --docker-username=me --docker-password=$TOKEN   # for imagePullSecrets
$ kubectl get secret db-creds -o jsonpath='{.data.password}' | base64 -d   # read it back

base64 ≠ encryption

echo czNjcjN0IQ== | base64 -d and anyone who can get secrets has your password. Encoding exists only so binary data survives JSON. What protects a Secret is (1) RBAC — grant get/list on secrets sparingly, and never let a Role wildcard resources in a namespace with credentials; (2) encryption at rest in etcd (EncryptionConfiguration with aescbc/aesgcm/KMS — off by default on kubeadm, on by default on most managed clusters); (3) not committing Secret manifests to git — use Sealed Secrets, SOPS, or External Secrets Operator pulling from Vault/AWS Secrets Manager.

Consuming: env vars vs files

containers:
- name: api
  envFrom:                          # every key becomes a variable
  - configMapRef: {name: app-config}
  - secretRef: {name: db-creds}
  - prefix: DB_                     # optional prefix
    secretRef: {name: db-creds}     # → DB_username, DB_password
  env:                              # or pick single keys, with your own names
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef: {name: app-config, key: LOG_LEVEL}
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef: {name: db-creds, key: password, optional: false}
volumes:
- name: cfg
  configMap:
    name: app-config
    items:                          # optional subset + rename
    - key: app.yaml
      path: config/app.yaml
- name: creds
  secret:
    secretName: db-creds
    defaultMode: 0400               # file permissions (octal)
containers:
- name: api
  volumeMounts:
  - {name: cfg,   mountPath: /etc/app,   readOnly: true}
  - {name: creds, mountPath: /etc/creds, readOnly: true}
# /etc/app/config/app.yaml, /etc/creds/username, /etc/creds/password

Env var names must be valid identifiers; keys with dots or dashes are skipped by envFrom (with an event) — rename via env[].valueFrom. Env vars can also be referenced in command/args as $(VAR).

Rolling out config changes

Because env vars freeze at start and Deployments only roll on template changes, editing a ConfigMap does nothing visible to a Deployment using it as env. Options:

  • kubectl rollout restart deploy/api — re-creates all Pods, which read the new values.
  • Versioned/immutable objects: create app-config-v2 with immutable: true, change the reference in the Deployment → a real rollout with rollback. Kustomize's configMapGenerator does this automatically by appending a content hash to the name (Day 42). Immutable objects also let the kubelet stop watching them — a measurable win on large clusters.
  • Hash annotation: put checksum/config: <sha256 of the ConfigMap> in the Pod template (Helm charts do this) so any config change alters the template.
Under the hood · Linux

Secret volumes are always tmpfs — the kubelet mounts a RAM filesystem per Secret volume so credentials are never written to the node's disk (ConfigMaps too, for simplicity). Files are created with the mode from defaultMode and owned by root, which matters when your container runs as a non-root USER: use fsGroup in the Pod's securityContext so the kubelet chowns the mount to that group, or set defaultMode: 0444. The kubelet fetches Secrets on the Pod's behalf using its own credentials (the Node authorizer only lets it read Secrets referenced by Pods on its node) and caches them; that cache TTL is the delay you see before volume updates land. Environment variables, by contrast, are passed through the CRI to runc and end up in the process's environ — readable by any process with the same UID via /proc.

CKA exam tip
  • kubectl create cm/secret … --from-literal --from-file then reference — do not hand-type base64. If you must, stringData avoids it.
  • "Expose all keys as env" → envFrom; "mount as files at path" → volume + volumeMount; "only key X" → items or secretKeyRef.
  • CreateContainerConfigError = missing ConfigMap/Secret or key. kubectl describe pod names it.
  • Decode fast: kubectl get secret x -o jsonpath='{.data.k}' | base64 -d.

Hands-on lab (20 min)

$ kubectl create cm app --from-literal=LOG_LEVEL=info --from-literal=GREETING=hello
$ kubectl create secret generic creds --from-literal=password='p@ss'
$ cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: {name: cfg}
spec:
  volumes: [{name: c, configMap: {name: app}}, {name: s, secret: {secretName: creds, defaultMode: 0400}}]
  containers:
  - name: app
    image: busybox:1.36
    command: ['sh','-c','while true; do echo "env=$GREETING file=$(cat /cfg/GREETING)"; sleep 5; done']
    envFrom: [{configMapRef: {name: app}}]
    env: [{name: PW, valueFrom: {secretKeyRef: {name: creds, key: password}}}]
    volumeMounts: [{name: c, mountPath: /cfg}, {name: s, mountPath: /creds}]
EOF
$ kubectl logs cfg --tail=1
$ kubectl exec cfg -- sh -c 'ls -la /creds/; df -h /creds; cat /creds/password; echo; env | grep PW'
$ kubectl patch cm app -p '{"data":{"GREETING":"bonjour"}}'
$ sleep 75; kubectl logs cfg --tail=1               # env=hello file=bonjour — file updated, env did not
$ kubectl get secret creds -o jsonpath='{.data.password}' | base64 -d; echo
$ kubectl run bad --image=nginx --env=X=1 $do | sed 's/value: "1"/valueFrom: {secretKeyRef: {name: creds, key: nope}}/' | kubectl apply -f -
$ kubectl get pod bad; kubectl describe pod bad | grep -i 'not found'      # CreateContainerConfigError
$ kubectl delete pod cfg bad $now; kubectl delete cm app; kubectl delete secret creds

Key takeaways

  • ConfigMap for settings, Secret for credentials; both are key-value objects ≤ 1 MiB, injected as env or files.
  • Env vars freeze at start; volume files update (except subPath). Missing references fail the Pod.
  • Secrets are base64, not encrypted: protect with RBAC, etcd encryption at rest, and an external secret store; mounted as tmpfs.
  • Roll config changes with rollout restart, immutable versioned objects, or a checksum annotation.
