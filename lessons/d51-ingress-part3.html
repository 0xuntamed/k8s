Production ingress means HTTPS and real hostnames: shop.example.com to the storefront, api.example.com to the API, both on one load balancer, each with a valid certificate. Two mechanisms make it work: host-based routing (the proxy reads the Host header / SNI) and TLS termination (the proxy holds the certificate and decrypts). This lesson does it on AWS with ACM and Route 53, then shows the portable equivalent with cert-manager and Let's Encrypt on any controller.

What you'll learn

  • Host-based (subdomain) routing rules and how SNI selects the certificate
  • TLS termination: spec.tls with a kubernetes.io/tls Secret vs an ACM certificate on the ALB
  • HTTP → HTTPS redirect, and what the backend sees after termination
  • DNS: Route 53 records by hand or with external-dns
  • Automatic certificates with cert-manager + Let's Encrypt (HTTP-01 / DNS-01)

Host-based routing

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
spec:
  ingressClassName: alb            # or nginx
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend: {service: {name: web, port: {number: 80}}}
  - host: api.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend: {service: {name: api, port: {number: 5678}}}
  - host: "*.preview.example.com"   # wildcard: one label
    http:
      paths:
      - path: /
        pathType: Prefix
        backend: {service: {name: preview, port: {number: 80}}}

Both hostnames resolve to the same address; the proxy distinguishes them by the Host header (HTTP) and by SNI (the hostname the client sends in the TLS ClientHello — before any HTTP is readable). A rule without host is the catch-all.

TLS termination

In-cluster controllers (nginx, Traefik…)

spec:
  tls:
  - hosts: [shop.example.com, api.example.com]
    secretName: example-tls        # type kubernetes.io/tls, same namespace
  rules: …
$ kubectl create secret tls example-tls --cert=fullchain.pem --key=privkey.pem -n shop

The controller loads the cert/key from the Secret and presents it for those hosts. One Secret per host, or a multi-SAN/wildcard cert. Without a matching entry, clients get the controller's self-signed "Kubernetes Ingress Controller Fake Certificate".

AWS ALB

metadata:
  annotations:
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:eu-west-1:123:certificate/abc…   # or omit: auto-discovered by host
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    alb.ingress.kubernetes.io/ssl-policy: ELBSecurityPolicy-TLS13-1-2-2021-06
spec:
  # no tls: section needed — ACM holds the cert; the ALB terminates

The certificate lives in ACM (free, auto-renewed, validated by a DNS CNAME in Route 53). The controller attaches it to the HTTPS listener; with no ARN given, it discovers ACM certs matching the Ingress hosts. Multiple certs → SNI picks the right one.

After termination the backend receives plain HTTP with headers X-Forwarded-Proto: https, X-Forwarded-For: <client IP>, X-Forwarded-Host. Apps that generate absolute URLs or enforce HTTPS must trust these headers (from the proxy only). If the backend itself must speak TLS (end-to-end encryption), use alb.ingress.kubernetes.io/backend-protocol: HTTPS or nginx's backend-protocol: "HTTPS" annotation — the proxy re-encrypts to the Pod.

DNS

# by hand: an alias/CNAME per host → the ALB (or the nginx LoadBalancer hostname)
$ ALB=$(kubectl get ingress shop -n shop -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
$ aws route53 change-resource-record-sets --hosted-zone-id Z123 --change-batch "{\"Changes\":[{\"Action\":\"UPSERT\",\"ResourceRecordSet\":{\"Name\":\"shop.example.com\",\"Type\":\"CNAME\",\"TTL\":60,\"ResourceRecords\":[{\"Value\":\"$ALB\"}]}}]}"
# automatically: external-dns watches Ingress hosts and manages records
$ helm install external-dns external-dns/external-dns -n kube-system --set provider=aws --set policy=sync --set txtOwnerId=cka
$ dig +short shop.example.com                                 # the ALB's IPs
$ curl -sv https://shop.example.com 2>&1 | grep -E 'subject:|issuer:|HTTP/'
$ curl -sI http://shop.example.com | head -1                  # 301 → https (ssl-redirect)

Automatic certificates: cert-manager + Let's Encrypt

For in-cluster controllers, cert-manager can obtain and renew public certificates from Let's Encrypt via ACME. You declare an Issuer; an annotation on the Ingress asks for a cert; the operator solves the challenge, stores the cert in the Secret the Ingress references, and renews it 30 days before expiry — forever.

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ops@example.com
    privateKeySecretRef: {name: letsencrypt-account-key}
    solvers:
    - http01:                       # LE fetches http://host/.well-known/acme-challenge/… through your Ingress
        ingress: {ingressClassName: nginx}
    # - dns01:                      # or prove ownership via a TXT record (needed for wildcards, private clusters)
    #     route53: {region: eu-west-1}
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt     # ← this line requests the certificate
spec:
  ingressClassName: nginx
  tls:
  - hosts: [shop.example.com, api.example.com]
    secretName: shop-tls                            # cert-manager creates and renews this Secret
  rules: …
$ kubectl get certificate,order,challenge -n shop      # progress of the ACME flow
$ kubectl describe certificate shop-tls -n shop | tail -6
$ kubectl get secret shop-tls -n shop -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -issuer -dates -ext subjectAltName
Under the hood · Linux

Watch SNI-based selection happen: openssl s_client -connect <lb>:443 -servername api.example.com < /dev/null | openssl x509 -noout -subject vs -servername shop.example.com — same IP, different certificate. Omit -servername and you get the default (or fake) cert, which is exactly what a client without SNI support (or a monitoring probe by IP) sees. A kubernetes.io/tls Secret's tls.crt must contain the full chain (leaf then intermediates) or clients that lack the intermediate will fail verification; openssl s_client -showcerts shows what the proxy actually sends, and openssl verify -untrusted chain.pem leaf.pem checks it.

CKA exam tip
  • "Secure the Ingress with the given cert and key" → kubectl create secret tls NAME --cert --key -n ns, then spec.tls[].secretName with the hosts. kubectl create ingress … --rule="host/*=svc:port,tls=NAME" does it in one line.
  • Host rules: the Host header must match exactly (or a wildcard). Test with curl -k --resolve host:443:IP https://host/.
  • cert-manager and ACM are outside the CKA; the TLS Secret + spec.tls mechanics are inside it.

Hands-on lab (20 min, KIND + ingress-nginx)

# self-signed cert with two SANs (Day 31 skills)
$ openssl req -x509 -newkey rsa:2048 -nodes -keyout tls.key -out tls.crt -days 30 -subj "/CN=shop.local" -addext "subjectAltName=DNS:shop.local,DNS:api.local"
$ kubectl create secret tls local-tls --cert=tls.crt --key=tls.key
$ kubectl create deploy web --image=nginx && kubectl expose deploy web --port=80
$ kubectl create deploy api --image=hashicorp/http-echo --port=5678 -- -text=api && kubectl expose deploy api --port=5678
$ kubectl create ingress hosts --class=nginx --rule="shop.local/*=web:80,tls=local-tls" --rule="api.local/*=api:5678,tls=local-tls"
$ curl -sk --resolve shop.local:443:127.0.0.1 https://shop.local/ | grep -o '<title>.*</title>'
$ curl -sk --resolve api.local:443:127.0.0.1 https://api.local/          # api
$ openssl s_client -connect 127.0.0.1:443 -servername api.local < /dev/null 2>/dev/null | openssl x509 -noout -subject -ext subjectAltName   # your cert
$ openssl s_client -connect 127.0.0.1:443 < /dev/null 2>/dev/null | openssl x509 -noout -subject                                       # no SNI → Fake Certificate
$ curl -sI --resolve shop.local:80:127.0.0.1 http://shop.local/ | head -1   # 308 redirect to https (nginx default when tls is set)
$ kubectl delete ingress hosts; kubectl delete deploy web api; kubectl delete svc web api; kubectl delete secret local-tls

Key takeaways

  • Host-based routing: one address, many hostnames; the proxy matches Host/SNI. Wildcards match one label.
  • TLS terminates at the proxy: in-cluster controllers read a kubernetes.io/tls Secret via spec.tls; the ALB uses ACM certificates via annotations. Backends then see HTTP + X-Forwarded-* headers.
  • DNS records point every host at the controller's address — by hand or with external-dns.
  • cert-manager + Let's Encrypt automates issuance and renewal for in-cluster controllers; ACM does it for ALB.
