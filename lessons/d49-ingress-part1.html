A type: LoadBalancer Service gives every application its own cloud load balancer, its own IP, and no idea what HTTP is. Ingress puts one L7 proxy in front of many Services and routes by hostname and path, terminates TLS, and costs one load balancer instead of twenty. The Ingress object is just the routing table; an Ingress controller you install is what actually proxies. This lesson is the model and the request flow; the next two are hands-on on AWS.

What you'll learn

  • Why Services alone are not enough for HTTP: cost, L7 routing, TLS
  • Ingress resource vs Ingress controller vs IngressClass
  • Rules: host, paths, pathType, backends, defaultBackend; TLS section
  • The full request path from DNS to Pod, and what each hop needs to be correct
  • Controller landscape: nginx, Traefik, HAProxy, cloud controllers (AWS ALB, GKE)

The problem

One LoadBalancer Service per app

  • An external IP and a cloud LB per Service — $15–25/month each, and IPs to manage in DNS
  • L4 only: no routing by URL, no TLS termination, no redirects, no rewrites
  • Certificates live in each app

One Ingress controller

  • One LB, one IP; shop.example.com and api.example.com both point at it
  • Routes /api to one Service and / to another; virtual hosts; TLS terminated once with centrally managed certs
  • Rate limiting, auth, canary weights, rewrites — via controller features

Three pieces

Ingress (resource)
A namespaced API object: "for host H and path P, send to Service S port N". Pure data; does nothing by itself.
Ingress controller
A Deployment/DaemonSet running a reverse proxy (nginx, Envoy, HAProxy, Traefik) plus a controller that watches Ingress objects and rewrites the proxy's config. Exposed by its own Service of type LoadBalancer (or NodePort). Not installed by default — a cluster without one accepts Ingress objects and ignores them.
IngressClass
Cluster-scoped: names a controller (spec.controller: k8s.io/ingress-nginx). An Ingress picks one with spec.ingressClassName; one class may be annotated default. Multiple controllers (internal/external) coexist by class.

The resource

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /   # controller-specific knobs
spec:
  ingressClassName: nginx
  defaultBackend:                       # anything not matched by a rule
    service:
      name: web
      port: {number: 80}
  tls:
  - hosts: [shop.example.com]
    secretName: shop-tls                # kubernetes.io/tls Secret in this namespace
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix                # /api, /api/, /api/orders …
        backend:
          service:
            name: api
            port: {number: 8080}
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web
            port: {name: http}
  - host: admin.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service: {name: admin, port: {number: 80}}
  • ingressClassName — which controller should act. Omit only if a default class exists.
  • rules[].host — matched against the HTTP Host header (and SNI for TLS). Omit host → applies to any host. Wildcards: *.example.com matches one label.
  • pathType — Prefix (path-segment prefix: /api matches /api/x but not /apix), Exact, or ImplementationSpecific (controller decides; nginx treats it as a regex-capable prefix). Longest match wins; Exact beats Prefix.
  • backend.service — a Service in the same namespace, by name and port (number or name). The controller resolves it to endpoints; most controllers proxy straight to Pod IPs, bypassing kube-proxy.
  • tls[] — terminate TLS for these hosts using the certificate in secretName. Without it, the controller serves HTTP (or its default fake cert on 443).
  • defaultBackend — catch-all; otherwise the controller's own 404 page.
  • annotations — the escape hatch for features the spec lacks (rewrites, timeouts, CORS, auth, canary). Different per controller — the main reason Gateway API exists (Day 52).
$ kubectl create ingress shop --class=nginx --rule="shop.example.com/api*=api:8080" --rule="shop.example.com/*=web:80,tls=shop-tls"
$ kubectl get ingress -n shop
NAME   CLASS   HOSTS                                ADDRESS        PORTS     AGE
shop   nginx   shop.example.com,admin.example.com   203.0.113.7    80, 443   1m
$ kubectl describe ingress shop -n shop               # rules, backends → endpoints; events from the controller

The request path, hop by hop

  1. DNS. shop.example.com → the controller's external address (the LB IP/hostname in the ADDRESS column). You manage this record (or external-dns does).
  2. Cloud LB → controller Service. The LB forwards TCP 80/443 to the ingress controller's Service (NodePort on every node, or directly to Pod IPs with cloud target-type ip).
  3. Controller Pod. nginx/Envoy receives the connection, terminates TLS using the cert from shop-tls, reads Host and path, matches an Ingress rule.
  4. Upstream. The proxy forwards to a Pod IP from the backend Service's EndpointSlice (it watches them itself), adding X-Forwarded-For/X-Real-IP headers.
  5. Pod. Your app answers on targetPort; the response goes back the same way.

Each hop has a failure mode: wrong DNS → nothing arrives; controller Service pending → no external address; no IngressClass match → controller ignores the object; backend Service name/port typo → 503 from the controller; Pod not Ready → 502/503; missing TLS Secret → the controller's fake certificate.

CKA exam tip
  • Exam clusters have a controller installed; check kubectl get ingressclass and use that name.
  • kubectl create ingress NAME --class=X --rule="host/path*=svc:port" is fast; the trailing * makes pathType Prefix. Add ,tls=secret for TLS.
  • Ingress and its backend Services must share a namespace.
  • Test without DNS: curl -H "Host: h" http://<address>/path or curl --resolve h:80:<ip>.

Key takeaways

  • Ingress = one L7 entry point for many Services: host/path routing, TLS termination, one LB.
  • Resource (routing rules) + controller (the proxy, installed separately) + IngressClass (which controller).
  • Rules match Host then path (Prefix/Exact, longest wins) → Service in the same namespace → Pod IPs from endpoints.
  • Request path: DNS → LB → controller Service → proxy Pod → backend Pod; each hop has a recognisable failure.
