A Pod is not "a container"; it is a group of containers that share a network namespace, can share volumes, and are always scheduled together on one node. Most Pods have one container. The rest use a handful of named patterns — init, sidecar, ambassador, adapter — to bolt cross-cutting behaviour onto an application without changing its image. Knowing what a Pod actually shares tells you exactly when a second container belongs in it.

What you'll learn

  • What containers in a Pod share (network, volumes, IPC, lifecycle) and what they do not (filesystem, processes by default)
  • Init containers: sequential, run-to-completion setup
  • Native sidecars (restartPolicy: Always in initContainers) vs the old sidecar pattern
  • Ambassador and adapter patterns and when to use each
  • Debugging: -c, ephemeral debug containers, shared process namespace

What a Pod shares

Shared by all containers in a PodPrivate to each container
Network namespace — one IP, one port space; containers talk over localhost. Two containers cannot both listen on :8080.Mount namespace / root filesystem — each container sees its own image. To share files, mount the same volume in both.
Volumes declared at Pod level, mounted per container at any path.PID namespace — by default each container sees only its own processes (shareProcessNamespace: true changes this).
IPC namespace — SysV shared memory, semaphores.cgroup limits — requests/limits are per container (the Pod cgroup is the sum).
Node, scheduling, lifecycle — created, scheduled and deleted as a unit.Environment variables, securityContext, probes — per container.
Under the hood · Linux

The kubelet first creates a pause container (image registry.k8s.io/pause) — a tiny process that does nothing but sleep. Its only job is to own the Pod's network and IPC namespaces so they outlive any application container restarts. Every application container is then started with --net=container:pause semantics (Day 3's --network container:x), joining those namespaces. That is why a Pod keeps its IP when a container crashes, and why crictl ps on a node shows a pause container per Pod. Each application container still gets its own mount namespace built from its own image layers.

Init containers

Init containers run before the app containers, one at a time, in order, each to completion. If one fails, the kubelet restarts it (per restartPolicy) and the app containers never start. They use their own images — perfect for tools you do not want in the app image.

apiVersion: v1
kind: Pod
metadata:
  name: api
spec:
  initContainers:
  - name: wait-for-db
    image: busybox:1.36
    command: ['sh', '-c', 'until nc -z db 5432; do echo waiting; sleep 2; done']
  - name: migrate
    image: myapi:2.1
    command: ['./migrate', '--up']
    envFrom: [{secretRef: {name: db-creds}}]
  - name: fetch-config
    image: curlimages/curl
    command: ['sh', '-c', 'curl -s http://config-svc/api.json -o /config/api.json']
    volumeMounts: [{name: cfg, mountPath: /config}]
  containers:
  - name: api
    image: myapi:2.1
    volumeMounts: [{name: cfg, mountPath: /etc/api, readOnly: true}]
  volumes:
  - name: cfg
    emptyDir: {}
  • Status while inits run: Init:0/3, Init:1/3… then PodInitializing, then Running. Init:Error / Init:CrashLoopBackOff point at the failing init.
  • Init containers cannot have probes or lifecycle hooks; their resources count toward scheduling as the max of any single init (they run serially) vs the sum of app containers.
  • kubectl logs api -c wait-for-db to read an init container's output.

Sidecars — and the native sidecar feature

A sidecar is a long-running helper that lives alongside the app: a log shipper that tails a shared volume, a proxy that terminates TLS, an agent that refreshes credentials. Historically you put it in containers next to the app, which had two problems: no start ordering (the app could start before its proxy was ready) and no stop ordering (the sidecar could die first, leaving the app unable to reach the network during shutdown; in Jobs the sidecar never exited, so the Job never completed).

Since Kubernetes 1.29 (GA in 1.33), an init container with restartPolicy: Always is a native sidecar: it starts in init order, is considered "started" once its startup probe passes, keeps running for the whole Pod lifetime, is restarted if it dies, and is stopped after the app containers during termination. Jobs complete when the main containers finish.

spec:
  initContainers:
  - name: log-shipper              # native sidecar
    image: fluent/fluent-bit
    restartPolicy: Always          # ← the whole feature
    volumeMounts: [{name: logs, mountPath: /var/log/app}]
    startupProbe:
      httpGet: {path: /api/v1/health, port: 2020}
  containers:
  - name: app
    image: myapp:3.0
    volumeMounts: [{name: logs, mountPath: /var/log/app}]
  volumes:
  - name: logs
    emptyDir: {}

Ambassador and adapter

Ambassador — outbound proxy

The app talks to localhost:5432; an ambassador container in the same Pod forwards to the real database, handling discovery, TLS, retries, sharding or connection pooling. The app image stays environment-agnostic. Service meshes (Istio's Envoy sidecar) are ambassadors for all traffic.

containers:
- name: app
  env: [{name: DB_HOST, value: "127.0.0.1"}]
- name: pgbouncer            # ambassador
  image: edoburu/pgbouncer
  env: [{name: DB_HOST, value: "prod-db.internal"}]

Adapter — normalise output

The app exposes metrics or logs in its own format; an adapter container reads them (via a shared volume or localhost) and re-exposes them in the format the platform expects — Prometheus exposition, JSON logs. Nothing in the app changes.

containers:
- name: redis
  image: redis:7
- name: redis-exporter     # adapter: redis INFO → /metrics
  image: oliver006/redis_exporter
  args: ["--redis.addr=localhost:6379"]
  ports: [{containerPort: 9121}]

Working with multi-container Pods

$ kubectl get pod api                          # READY 2/2 — one number per container
$ kubectl logs api -c log-shipper -f           # -c is mandatory with 2+ containers
$ kubectl logs api --all-containers --prefix
$ kubectl exec -it api -c app -- sh
$ kubectl describe pod api                     # per-container state, restarts, init container section
$ kubectl debug -it api --image=busybox --target=app   # ephemeral container sharing app's PID namespace
spec:
  shareProcessNamespace: true    # all containers see each other's processes; kill -HUP 1 works across them
CKA exam tip
  • "Add a sidecar that tails the app's log file" → shared emptyDir, mounted in both, sidecar runs tail -F /var/log/app.log. Generate the Pod YAML, add the second container and the volume.
  • Pod stuck Init:0/1 → kubectl logs pod -c <init-name>; the init is waiting for something.
  • Always pass -c when the task mentions a specific container; the default is the first one and the grader checks the right one.

Hands-on lab (15 min)

$ cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: {name: multi}
spec:
  initContainers:
  - name: init
    image: busybox:1.36
    command: ['sh','-c','echo "$(date) init done" > /work/init.txt; sleep 5']
    volumeMounts: [{name: work, mountPath: /work}]
  containers:
  - name: writer
    image: busybox:1.36
    command: ['sh','-c','while true; do date >> /work/app.log; sleep 2; done']
    volumeMounts: [{name: work, mountPath: /work}]
  - name: reader
    image: busybox:1.36
    command: ['sh','-c','tail -F /work/app.log']
    volumeMounts: [{name: work, mountPath: /work}]
  - name: web
    image: nginx
  volumes: [{name: work, emptyDir: {}}]
EOF
$ kubectl get pod multi -w                         # Init:0/1 → PodInitializing → Running 3/3
$ kubectl logs multi -c reader --tail=3            # sees writer's lines via the shared volume
$ kubectl exec multi -c reader -- cat /work/init.txt
$ kubectl exec multi -c writer -- wget -qO- http://localhost | head -2     # nginx via localhost: shared netns
$ kubectl exec multi -c writer -- ps                # only its own processes: separate PID ns
$ kubectl delete pod multi $now

Key takeaways

  • Containers in a Pod share network (localhost, one IP), volumes and IPC; they keep separate filesystems and (by default) PID namespaces. The pause container holds the shared namespaces.
  • Init containers run sequentially to completion before app containers; use them for waiting, migrations, fetching config.
  • Native sidecar = init container with restartPolicy: Always: ordered start, restarts, stops after the app, lets Jobs finish.
  • Ambassador proxies outbound; adapter normalises outbound formats. Both keep the app image unchanged.
  • Use -c everywhere; kubectl debug --target for images without a shell.
