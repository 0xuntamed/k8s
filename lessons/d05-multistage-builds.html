A 1.2 GB image and a 12 MB image can run the exact same application. The difference is everything that was needed to build the app but is useless at run time: compilers, SDKs, package caches, test tooling. Multi-stage builds let one Dockerfile use a fat image to build and a tiny image to ship — and small images are faster to pull, cheaper to store and far harder to attack.

What you'll learn

  • Why image size matters on a Kubernetes cluster (scheduling latency, node disk, attack surface)
  • Multi-stage Dockerfiles: build in one stage, copy only artifacts into the final stage
  • Choosing a base: full → slim → alpine → distroless → scratch, and the glibc/musl trap
  • Layer hygiene: cache order, combining RUNs, cleaning package caches, .dockerignore

Why size matters more in Kubernetes

  • Pod start-up latency. A Pod scheduled to a node that lacks the image cannot start until the pull finishes. Autoscaling, node failures and rolling updates all trigger pulls; 1 GB × 50 nodes is real time and real egress cost.
  • Node disk pressure. The kubelet garbage-collects images when disk fills, and DiskPressure evicts Pods. Big images make that happen sooner.
  • Attack surface. Every binary in the image is something a scanner will flag and an attacker can use. An image with no shell cannot be exec'd into by an intruder either.

The multi-stage pattern

Every FROM starts a new stage. Later stages can COPY --from= earlier ones. Only the last stage becomes the image; everything else is discarded.

Go: static binary → scratch

# ---- stage 1: build (≈ 800 MB, thrown away) ----
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                      # cached unless go.mod changes
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /out/api ./cmd/api

# ---- stage 2: ship (≈ 8 MB) ----
FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/api /api
USER 65534:65534                          # "nobody" — scratch has no /etc/passwd, so use numbers
EXPOSE 8080
ENTRYPOINT ["/api"]

CGO_ENABLED=0 produces a fully static binary with no dependency on a C library, which is what makes scratch (a completely empty image) viable. The CA bundle is copied so the app can make HTTPS calls.

Node: build with dev deps, run with production deps

FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci                                # includes devDependencies for the build

FROM deps AS build
COPY . .
RUN npm run build                         # e.g. TypeScript → dist/

FROM node:22-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]

Name stages with AS, and build a specific one with docker build --target build . — useful in CI to run tests in the build stage without producing a runtime image.

The Alpine / musl trap

Alpine uses musl instead of glibc. Pre-built binaries and Python wheels compiled against glibc may crash with "not found" errors (the dynamic loader is missing) or subtle DNS-resolution differences. Either build on Alpine in the build stage too, or prefer -slim / distroless, which are glibc-based. Check with ldd ./binary.

Under the hood · Linux

Why can a Go binary run on an empty filesystem? Because a statically linked ELF executable contains everything it needs; the kernel maps it into memory and jumps to _start. A dynamically linked binary instead asks the kernel to load /lib64/ld-linux-x86-64.so.2 (the dynamic loader), which then opens libc.so.6 and friends from the image's filesystem — none of which exist in scratch. That is also why distroless images still carry libc: Java, Python and Node are dynamically linked. Running as a numeric non-root USER works in scratch because the kernel only needs a UID, not a /etc/passwd entry.

Layer hygiene checklist

  1. Order by change frequency — base, OS packages, dependencies, then source (from Day 2).
  2. Clean up in the same RUN — deletions in a later layer do not shrink the image, they only hide files. 
    RUN apt-get update && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*
  3. Use .dockerignore — keep .git, node_modules, test data and secrets out of the build context. 
    .git
node_modules
*.log
.env
Dockerfile*
  4. Copy specific paths — COPY . . after dependency install is fine; COPY . . before it defeats the cache.
  5. Pin versions — FROM python:3.12.6-slim, not python:latest. Reproducible builds and no surprise upgrades.
  6. Measure — docker history img shows each layer's size; dive shows what changed per layer.
CKA exam tip

Image building is not on the CKA (it is on the CKAD), but image size shows up indirectly: a Pod stuck in ContainerCreating with a slow pull, or a node under DiskPressure. Know that kubectl describe pod shows pull progress events and that the kubelet's image GC thresholds are --image-gc-high-threshold/low-threshold (defaults 85%/80%).

Hands-on lab (15 min)

Shrink a Go hello-world from 800 MB to under 10 MB.

$ mkdir gosmall && cd gosmall && go mod init example.com/hello
$ cat > main.go <<'EOF'
package main
import ("fmt";"net/http")
func main(){ http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request){ fmt.Fprintln(w,"hello") }); http.ListenAndServe(":8080", nil) }
EOF
# single stage
$ printf 'FROM golang:1.23\nWORKDIR /src\nCOPY . .\nRUN go build -o /hello .\nCMD ["/hello"]\n' > Dockerfile.big
$ docker build -q -t hello:big -f Dockerfile.big .
# multi-stage
$ printf 'FROM golang:1.23 AS b\nWORKDIR /src\nCOPY . .\nRUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /hello .\nFROM scratch\nCOPY --from=b /hello /hello\nENTRYPOINT ["/hello"]\n' > Dockerfile.small
$ docker build -q -t hello:small -f Dockerfile.small .
$ docker images hello          # compare SIZE
$ docker run --rm -d -p 8080:8080 hello:small && curl localhost:8080
$ docker run --rm -it hello:small sh    # fails: there is no shell to exec — that is the point

Key takeaways

  • Multi-stage builds: build with the SDK, COPY --from only the artifacts into a minimal final stage.
  • Prefer -slim or distroless for dynamically linked runtimes; scratch for static Go/Rust binaries.
  • Alpine = musl; check ldd before assuming a glibc binary will run there.
  • Clean up in the same layer, ignore junk with .dockerignore, pin base image versions, and measure with docker history.
