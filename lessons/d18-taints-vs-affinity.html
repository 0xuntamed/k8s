Taints and affinity answer different questions. A taint answers "who is allowed here?" from the node's side; affinity answers "where do I want to go?" from the Pod's side. Used alone, each has a hole: a taint cannot stop your special Pods from landing on ordinary nodes, and affinity cannot stop ordinary Pods from landing on your special nodes. Used together they give you a truly dedicated node pool. This lesson also completes the picture with Pod affinity/anti-affinity, topology spread, and the full scheduling cycle.

What you'll learn

  • The two-sided problem and the taint + affinity recipe for dedicated nodes
  • Pod affinity and anti-affinity: placing Pods relative to other Pods with topologyKey
  • Topology spread constraints for even distribution across zones/nodes
  • The scheduling cycle end to end: queue → filter → score → reserve → bind

The two-sided problem

Taint alone

Taint the GPU nodes. Ordinary Pods stay off them ✔. But the GPU Pods, which tolerate the taint, are allowed anywhere — and may be scheduled onto a cheap node with no GPU ✘.

Affinity alone

Give GPU Pods a required affinity for gpu=true. They always land on GPU nodes ✔. But nothing stops ordinary Pods from filling those nodes first ✘.

$ kubectl label nodes gpu-1 gpu-2 pool=gpu                      # the attractor
$ kubectl taint nodes gpu-1 gpu-2 pool=gpu:NoSchedule            # the repellent
spec:
  tolerations:                                    # allowed onto the pool
  - key: pool
    operator: Equal
    value: gpu
    effect: NoSchedule
  affinity:                                       # and only onto the pool
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: pool
            operator: In
            values: [gpu]

Pod affinity and anti-affinity

Node affinity looks at node labels. Pod affinity looks at the labels of Pods already running and at a topologyKey — a node label that defines "the same place": kubernetes.io/hostname for "same node", topology.kubernetes.io/zone for "same zone".

spec:
  affinity:
    podAffinity:                       # run NEAR pods matching the selector
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: {app: cache}
        topologyKey: kubernetes.io/hostname      # same node as a cache pod
    podAntiAffinity:                   # run AWAY from pods matching the selector
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: {app: web}                # my own label → one web pod per node
        topologyKey: kubernetes.io/hostname
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels: {app: web}
          topologyKey: topology.kubernetes.io/zone   # and prefer spreading across zones
  • Anti-affinity to yourself with hostname is the classic HA rule: three replicas on three different nodes. With required and only two nodes, the third replica is Pending — use preferred or topology spread if that is not acceptable.
  • namespaces / namespaceSelector in the term let you match Pods in other namespaces; default is the Pod's own.
  • Pod affinity is expensive for the scheduler on very large clusters (it must inspect all Pods); prefer topology spread when you just want distribution.

Topology spread constraints

spec:
  topologySpreadConstraints:
  - maxSkew: 1                                  # max difference in pod count between any two domains
    topologyKey: topology.kubernetes.io/zone    # domains = zones
    whenUnsatisfiable: DoNotSchedule            # or ScheduleAnyway (soft)
    labelSelector:
      matchLabels: {app: web}
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway

"Keep the count of app=web Pods per zone within 1 of each other." Simpler and cheaper than anti-affinity for the common "spread evenly" case, and it scales to any replica count. Clusters have default constraints (maxSkew: 3 on hostname, 5 on zone, both soft) so Deployments spread reasonably even with nothing specified.

The scheduling cycle, end to end

  1. Queue. Unscheduled Pods are queued, ordered by priority then time. Pods that fail scheduling go to a back-off queue and are retried when the cluster changes (node added, Pod deleted).
  2. Filter (predicates). Plugins reject nodes: NodeResourcesFit (requests ≤ allocatable), TaintToleration, NodeAffinity (nodeSelector + required affinity), NodeUnschedulable (cordon), NodePorts (hostPort conflicts), VolumeBinding / VolumeZone (can the PV be attached here?), InterPodAffinity, PodTopologySpread. Zero survivors → FailedScheduling event listing why each node failed, and possibly preemption of lower-priority Pods.
  3. Score (priorities). Each survivor gets 0–100 from each scoring plugin, multiplied by plugin weight: NodeAffinity preferences, InterPodAffinity preferences, NodeResourcesBalancedAllocation, LeastAllocated (default) or MostAllocated (bin-packing), ImageLocality, TaintToleration (PreferNoSchedule), PodTopologySpread.
  4. Reserve & permit. The winning node's resources are reserved in the scheduler's cache so the next Pod in the queue sees them as used (this avoids two Pods "winning" the same last slot).
  5. Bind. The scheduler POSTs a Binding; the API server sets nodeName. The kubelet takes over.
Reading FailedScheduling messages
0/5 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: },
2 Insufficient cpu, 1 node(s) didn't match Pod's node affinity/selector,
1 node(s) had volume node affinity conflict. preemption: 0/5 nodes are available: 5 No preemption victims found…

Every node is accounted for, by plugin. Fix the reason that applies to the nodes you intended — the control-plane taint line is usually noise.

CKA exam tip
  • "Ensure the Pod runs only on nodes labelled X and no other Pod runs there" → taint + toleration + node affinity (or nodeSelector).
  • "Each replica on a different node" → podAntiAffinity on its own label with topologyKey: kubernetes.io/hostname.
  • Look at the FailedScheduling message before changing anything; it tells you exactly which plugin rejected which node.

Hands-on lab (15 min)

$ kubectl label node cka-worker pool=gpu && kubectl taint node cka-worker pool=gpu:NoSchedule
$ kubectl create deploy plain --image=nginx --replicas=3 && kubectl get pods -o wide   # none on cka-worker
$ cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: {name: gpu}
spec:
  replicas: 2
  selector: {matchLabels: {app: gpu}}
  template:
    metadata: {labels: {app: gpu}}
    spec:
      tolerations: [{key: pool, operator: Equal, value: gpu, effect: NoSchedule}]
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms: [{matchExpressions: [{key: pool, operator: In, values: [gpu]}]}]
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector: {matchLabels: {app: gpu}}
            topologyKey: kubernetes.io/hostname
      containers: [{name: n, image: nginx}]
EOF
$ kubectl get pods -o wide            # one gpu pod on cka-worker, the other Pending (anti-affinity + only one gpu node)
$ kubectl describe pod -l app=gpu | grep -A2 FailedScheduling
$ kubectl taint node cka-worker pool-; kubectl label node cka-worker pool-; kubectl delete deploy plain gpu

Key takeaways

  • Dedicated nodes = taint (keep others out) + toleration (let mine in) + node affinity (keep mine in).
  • Pod affinity/anti-affinity place Pods relative to other Pods within a topologyKey domain; anti-affinity to self on hostname = one per node.
  • Topology spread constraints are the cheap, scalable way to distribute evenly.
  • Scheduler: queue → filter (hard rules) → score (soft rules) → reserve → bind. The FailedScheduling message names the failing plugin per node.
