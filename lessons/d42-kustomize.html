The same application runs in dev, staging and prod with a different namespace, replica count, image tag and ConfigMap — and you do not want three copies of every manifest. Kustomize solves this without templates: keep one base of plain YAML, and write small overlays that patch it. It is built into kubectl (kubectl apply -k), it never invents syntax inside your manifests, and the output is always plain YAML you can inspect before applying.

What you'll learn

  • The kustomization.yaml file: resources, namespace, namePrefix, commonLabels, images, replicas
  • Bases and overlays; how the directory layout expresses environments
  • Patches: strategic merge and JSON 6902, and targeting by kind/name
  • configMapGenerator / secretGenerator and the hash suffix that forces rollouts
  • kubectl kustomize to render, apply -k to deploy, and how it relates to Helm

The idea: base + overlays

app/
├── base/
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   ├── service.yaml
│   └── configmap.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml
    │   └── replicas.yaml
    └── prod/
        ├── kustomization.yaml
        ├── replicas.yaml
        └── resources-patch.yaml

The base

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:                # plain manifests (or other kustomizations / URLs)
- deployment.yaml
- service.yaml
commonLabels:             # added to every object AND every selector — set once, never change
  app.kubernetes.io/name: web
configMapGenerator:
- name: web-config
  literals:
  - LOG_LEVEL=info
  files:
  - app.properties       # key = filename
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 1
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
      - name: web
        image: ghcr.io/acme/web:1.0.0
        envFrom:
        - configMapRef: {name: web-config}     # kustomize will rewrite this to the hashed name
        ports: [{containerPort: 8080}]

An overlay

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base                     # inherit everything
namespace: prod                  # set metadata.namespace on all objects
namePrefix: prod-                # web → prod-web (and fixes references: Service selectors, configMapRef…)
commonAnnotations:
  owner: platform-team
images:                          # change image name/tag without touching the Deployment
- name: ghcr.io/acme/web
  newTag: 1.4.2
replicas:                        # shortcut for the most common patch
- name: web
  count: 5
configMapGenerator:
- name: web-config
  behavior: merge                # merge / replace / create
  literals:
  - LOG_LEVEL=warn
patches:
- path: resources-patch.yaml     # strategic merge patch (a partial object)
- target:                        # JSON 6902 patch, targeted by kind/name/labels
    kind: Deployment
    name: web
  patch: |-
    - op: add
      path: /spec/template/spec/containers/0/env/-
      value: {name: ENV, value: prod}
    - op: replace
      path: /spec/strategy/rollingUpdate/maxUnavailable
      value: 0
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web                      # matched by kind + name; only the fields below are merged in
spec:
  template:
    spec:
      containers:
      - name: web                # lists of containers merge by "name" — that is the "strategic" part
        resources:
          requests: {cpu: 500m, memory: 512Mi}
          limits: {cpu: "2", memory: 1Gi}

Render, diff, apply

$ kubectl kustomize overlays/prod                # print the final YAML — always look first
$ kubectl kustomize overlays/prod | grep -E 'name:|namespace:|image:|replicas:' | head
$ kubectl diff -k overlays/prod                  # what would change in the cluster
$ kubectl apply -k overlays/prod
$ kubectl delete -k overlays/prod
$ kustomize build overlays/prod                  # standalone binary: newer features, same output

The rendered output for prod: a Deployment named prod-web in namespace prod, 5 replicas, image :1.4.2, resources set, an extra env var, and envFrom pointing at prod-web-config-7f8g9h2k4m — the generated ConfigMap with a hash of its contents in the name.

Generators and the hash suffix

configMapGenerator and secretGenerator create the object and append a content hash to its name, then rewrite every reference. Change a value → new name → the Deployment's template changes → a rollout happens. That is the clean fix for Day 28's "editing a ConfigMap does nothing to running Pods". Old generations are left behind (harmless; prune with kubectl apply -k … --prune -l app=web or a GitOps tool). Disable with generatorOptions: {disableNameSuffixHash: true} when an external tool needs a stable name.

secretGenerator:
- name: db-creds
  envs: [.env.prod]              # KEY=VALUE file, kept out of git
  type: Opaque
generatorOptions:
  labels: {generated: "true"}

Strategic merge vs JSON patch

Strategic merge patch

A partial YAML object. Maps merge; lists of objects merge by a key field (name for containers, env, volumes). Readable, good for "set these fields". Delete a field with $patch: delete or set it to null.

JSON 6902 patch

Explicit operations (add, remove, replace, move, test) on JSON-pointer paths. Precise, works on CRDs whose list-merge keys kustomize does not know, can append to arrays (/-). Less readable.

Other useful features

components
Reusable feature bundles (e.g. "add a sidecar", "enable TLS") that any overlay can include: components: [../../components/tls].
replacements
Copy a value from one object's field into another's (successor to vars): e.g. Service name into an Ingress backend.
Remote bases
resources: [github.com/org/repo/base?ref=v1.2] — reuse a vendor's manifests and overlay your changes.
helmCharts
Render a Helm chart inside a kustomization (--enable-helm) and patch its output — a common hybrid.
labels vs commonLabels
labels: [{pairs: {...}, includeSelectors: false}] adds labels without touching selectors, which commonLabels does (and selectors are immutable — changing commonLabels on a live Deployment fails).
Kustomize vs Helm

Kustomize patches real YAML; Helm templates YAML with a values file. Kustomize is better for your own apps across environments (no templating language, output is greppable, no release state); Helm is better for distributing software to strangers (parameters, hooks, versioned packages, rollback). Many teams use both: Helm to install third-party charts, Kustomize overlays (sometimes patching Helm output) for their own services. Day 43.

Under the hood · Linux

Kustomize is a pure text transformation — there is no cluster interaction until apply. That makes it script-friendly: kubectl kustomize overlay | yq '.spec.replicas' -, kubectl kustomize a > a.yaml; kubectl kustomize b > b.yaml; diff a.yaml b.yaml to compare environments, and kubectl kustomize . | kubectl apply --dry-run=server -f - to validate against the live API including admission. The shell toolkit page covers yq and diff.

CKA exam tip
  • Kustomize is in the CKA curriculum ("understand Helm and Kustomize"). Expect: render a given overlay (kubectl kustomize dir), apply it (-k), or fix a broken kustomization (wrong resources path, patch name not matching).
  • kubectl apply -k takes a directory, not a file. -f on a kustomization.yaml does not work.
  • If a patch "does nothing", the target kind/name does not match — remember namePrefix applies after patches target the base name.

Hands-on lab (20 min)

$ mkdir -p app/base app/overlays/dev app/overlays/prod && cd app
$ kubectl create deploy web --image=nginx:1.26 --port=80 $do > base/deployment.yaml
$ kubectl create svc clusterip web --tcp=80:80 $do > base/service.yaml
$ cat > base/kustomization.yaml <<EOF
resources: [deployment.yaml, service.yaml]
configMapGenerator:
- name: web-config
  literals: [GREETING=hello]
EOF
$ cat > overlays/dev/kustomization.yaml <<EOF
resources: [../../base]
namespace: dev
namePrefix: dev-
replicas: [{name: web, count: 1}]
EOF
$ cat > overlays/prod/kustomization.yaml <<EOF
resources: [../../base]
namespace: prod
namePrefix: prod-
images: [{name: nginx, newTag: "1.27"}]
replicas: [{name: web, count: 3}]
configMapGenerator:
- name: web-config
  behavior: merge
  literals: [GREETING=bonjour]
patches:
- target: {kind: Deployment, name: web}
  patch: |-
    - op: add
      path: /spec/template/spec/containers/0/envFrom
      value: [{configMapRef: {name: web-config}}]
EOF
$ kubectl kustomize overlays/prod                       # note the hashed ConfigMap name and rewritten envFrom
$ kubectl create ns dev prod
$ kubectl apply -k overlays/dev && kubectl apply -k overlays/prod
$ kubectl get deploy,svc,cm -n prod
$ sed -i 's/bonjour/hola/' overlays/prod/kustomization.yaml && kubectl apply -k overlays/prod && kubectl rollout status deploy/prod-web -n prod   # new hash → rollout
$ kubectl delete ns dev prod; cd ..

Key takeaways

  • Base = plain manifests + a kustomization.yaml; overlays inherit the base and change namespace, names, images, replicas, labels, and apply patches.
  • Strategic merge for "set these fields", JSON 6902 for precise or list-append operations; target by kind/name.
  • Generators add a content hash to ConfigMap/Secret names and rewrite references → config changes trigger rollouts.
  • kubectl kustomize to see, diff -k to compare, apply -k dir to deploy. No templating, no state, plain YAML out.
