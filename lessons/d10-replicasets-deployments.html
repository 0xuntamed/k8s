You almost never create a Pod directly. Pods are mortal: they are not rescheduled when their node dies, and nothing restarts a deleted one. Instead you create a Deployment, which manages ReplicaSets, which manage Pods. This layering is what gives you self-healing, scaling, rolling updates and one-command rollbacks — and it is the first place the "controller watches labels" pattern really matters.

What you'll learn

  • Why bare Pods are not enough, and why ReplicationController was replaced by ReplicaSet
  • ReplicaSet: replicas, selector, template — and how label matching decides ownership
  • Deployment: a controller for ReplicaSets that implements RollingUpdate and Recreate strategies
  • maxSurge / maxUnavailable, rollout status, history, undo, pause/resume
  • The imperative commands that generate and modify all of this

Three layers, one purpose

Deploymentmanages →ReplicaSet (one per revision)manages →Pods (identical, label-selected)
Pod
One or more containers sharing a network namespace and volumes. Disposable. Has no controller of its own.
ReplicaSet
"Keep N Pods matching this selector alive, using this template to make new ones." Handles crashes and node loss. Knows nothing about versions.
Deployment
"Run this Pod template with N replicas, and when the template changes, move from the old ReplicaSet to a new one gradually." Keeps old ReplicaSets around (scaled to 0) so you can roll back.
ReplicationController
The original ReplicaSet (2014). Same idea, but its selector only supported equality. Legacy; you will only see it in old manifests and exam trivia.

ReplicaSet

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
    matchExpressions:
    - key: tier
      operator: In
      values: [frontend]
  template:
    metadata:
      labels:
        app: web
        tier: frontend
    spec:
      containers:
      - name: nginx
        image: nginx:1.26
  • replicas — desired count. Default 1.
  • selector — which Pods this ReplicaSet owns. matchLabels is AND-ed equality; matchExpressions adds In, NotIn, Exists, DoesNotExist. Immutable after creation.
  • template — a full Pod spec (minus apiVersion/kind) used to create new Pods. Its labels must satisfy the selector, or the API server rejects the object.
  • Pods created by the ReplicaSet get an ownerReferences entry pointing at it; deleting the ReplicaSet garbage-collects them (unless --cascade=orphan).
Selectors are about labels, not lineage

A ReplicaSet counts every Pod in the namespace that matches its selector and has no other owner — including ones you created by hand. Create a bare Pod with app: web and a ReplicaSet with replicas: 3 already satisfied will delete one to get back to three. Conversely, remove the label from a managed Pod and the ReplicaSet "loses" it and makes a replacement, leaving your orphan running. This is a useful trick for pulling a misbehaving Pod out of service to debug it.

Deployment

$ kubectl create deployment web --image=nginx:1.26 --replicas=3 --dry-run=client -o yaml > web.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 3
  revisionHistoryLimit: 10
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
  minReadySeconds: 5
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.26
        ports:
        - containerPort: 80
  • strategy.type — RollingUpdate (default) replaces Pods gradually; Recreate kills all old Pods, then creates new ones (downtime, but no two versions overlap — needed for some databases).
  • maxSurge — how many Pods above replicas may exist during the rollout (number or %). Default 25%.
  • maxUnavailable — how many Pods below replicas may be unavailable. Default 25%. Setting it to 0 guarantees capacity; setting maxSurge: 0 guarantees no extra resource usage. They cannot both be 0.
  • minReadySeconds — a new Pod must be Ready this long before it counts as available and the rollout proceeds. Cheap insurance against fast crash loops.
  • revisionHistoryLimit — how many old ReplicaSets to keep for rollback.
  • Everything under template is what a change to triggers a new revision; changing replicas alone does not.

A rolling update, frame by frame

With replicas: 4, maxSurge: 1, maxUnavailable: 1 the controller may run up to 5 Pods and must keep at least 3 available. It scales the new ReplicaSet up and the old one down in steps that never break those bounds, waiting for each new Pod to become Ready (readiness probes, Day 23) before continuing. Traffic shifts automatically because the Service selects app: web, which both revisions carry.

Working with rollouts

CommandWhat it does
kubectl set image deploy/web nginx=nginx:1.27Change the container image → new ReplicaSet → rolling update. (nginx= is the container name.)
kubectl edit deploy webOpen the live object in $EDITOR; any template change triggers a rollout.
kubectl rollout status deploy/webBlock until the rollout finishes (or fails). Use in scripts and in the exam to confirm.
kubectl rollout history deploy/webList revisions. --revision=2 shows that revision's template.
kubectl rollout undo deploy/webRoll back to the previous revision (--to-revision=N for a specific one). Rollback is itself a new revision.
kubectl rollout pause / resume deploy/webPause: make several changes without triggering several rollouts; resume to roll them out together.
kubectl rollout restart deploy/webRe-create all Pods with the same template (adds a timestamp annotation). For picking up new ConfigMap/Secret contents.
kubectl scale deploy web --replicas=5Change replicas without a new revision.
kubectl get rs -l app=webSee the ReplicaSets: the active one has DESIRED=replicas, old ones 0.

The CHANGE-CAUSE column in rollout history comes from the annotation kubernetes.io/change-cause. Set it with kubectl annotate deploy/web kubernetes.io/change-cause="bump to 1.27" (the old --record flag is deprecated).

When a rollout goes wrong

$ kubectl set image deploy/web nginx=nginx:1.27-typo
$ kubectl rollout status deploy/web            # "Waiting for deployment "web" rollout to finish: 1 out of 3 new replicas have been updated..."
$ kubectl get pods                             # one Pod in ImagePullBackOff; the old ones still serve traffic
$ kubectl describe deploy web | grep -A5 Conditions   # Progressing=False, reason ProgressDeadlineExceeded (after progressDeadlineSeconds, default 600)
$ kubectl rollout undo deploy/web              # back to 1.26 in seconds

Because the old ReplicaSet is still there and maxUnavailable bounds the damage, a bad image never takes down more than one slice of your capacity. That is the whole reason to prefer Deployments over anything hand-rolled.

CKA exam tip
  • Fastest way to fix a "Pod template has wrong image" question: kubectl set image, then kubectl rollout status to prove it.
  • If a ReplicaSet won't create Pods, check kubectl describe rs events — a template label that does not match the selector, or a resource quota, are the usual causes.
  • Remember that selector is immutable: to change it you must delete and re-create the Deployment (--cascade=orphan keeps the Pods running while you do).

Hands-on lab (15 min)

$ kubectl create deploy web --image=nginx:1.26 --replicas=4
$ kubectl get deploy,rs,pods -l app=web
$ kubectl delete pod -l app=web --wait=false && kubectl get pods -l app=web -w   # watch replacements appear
# orphan a pod
$ P=$(kubectl get pod -l app=web -o name | head -1); kubectl label $P app-
$ kubectl get pods --show-labels                # 5 pods: 4 owned + 1 orphan
$ kubectl delete pod -l 'app notin (web)'       # clean up
# rolling update
$ kubectl set image deploy/web nginx=nginx:1.27 && kubectl rollout status deploy/web
$ kubectl get rs -l app=web                     # two ReplicaSets, old one at 0
$ kubectl rollout history deploy/web
$ kubectl rollout undo deploy/web && kubectl get rs -l app=web

Key takeaways

  • Pod → ReplicaSet (keep N alive by label) → Deployment (manage ReplicaSets across revisions). Create Deployments, not Pods.
  • Ownership is by selector, not by who created the Pod; template labels must match the selector.
  • Any change to spec.template creates a new ReplicaSet and a rolling update bounded by maxSurge/maxUnavailable.
  • rollout status / history / undo / pause / restart are the operational verbs; set image is the fastest change.
