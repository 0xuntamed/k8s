Every field in a Pod's securityContext sets a Linux process attribute: its UID and GIDs, its capability sets, its no_new_privs flag, its seccomp filter, its LSM profile. The kernel checks those attributes on every file open, every socket bind, every mount. Know the attributes and the checks, and "why can't my non-root container write to the volume" or "why does privileged equal root on the node" have exact answers.

What you'll learn

  • UIDs, GIDs, /etc/passwd, the effective/real/saved ids, and what root means
  • File permissions and ownership: mode bits, setuid/setgid/sticky, umask, fsGroup mechanics
  • Capabilities: the sets, the list that matters, capsh/getpcaps, file capabilities
  • no_new_privs, seccomp, AppArmor/SELinux — the extra fences
  • What privileged actually enables

Users and groups

$ id                                  # uid=1000(alice) gid=1000(alice) groups=1000(alice),27(sudo),999(docker)
$ cat /etc/passwd | head -3           # name:x:uid:gid:comment:home:shell — a mapping for humans; the KERNEL only knows numbers
$ getent passwd 65534                 # nobody
$ cat /proc/$$/status | grep -E '^(Uid|Gid|Groups)'   # real, effective, saved, filesystem uid; supplementary groups
$ sudo -u nobody id; su -s /bin/sh nobody -c id

The kernel identifies a process by numeric uid/gid plus a list of supplementary groups. /etc/passwd and /etc/group only translate names — which is why a container image can run as UID 1000 with no passwd entry at all (USER 1000 works; USER app needs the entry), and why runAsNonRoot: true with USER app fails unless the kubelet can resolve the name to a non-zero number. UID 0 is root: the kernel skips most permission checks for it — modulo capabilities, below.

File permissions

$ ls -l /etc/shadow /usr/bin/passwd /tmp
-rw-r-----  1 root shadow   1234  /etc/shadow      # owner rw, group r, other none
-rwsr-xr-x  1 root root    68208  /usr/bin/passwd  # s = SETUID: runs as the file's owner (root) regardless of who executes it
drwxrwxrwt 15 root root     4096  /tmp             # t = STICKY: only the owner may delete their files
$ stat -c '%a %U:%G %n' /etc/shadow               # 640 root:shadow
$ chmod 0640 f; chmod u+x,g-w f; chown app:app f; chgrp 2000 -R /data
$ umask                                            # 0022 → new files 644, dirs 755
$ chmod g+s /data                                  # SETGID on a dir: new files inherit the dir's group (what fsGroup relies on)

The check on open(): if the process's effective uid owns the file, use the owner bits; else if any of its gids matches the file's group, use the group bits; else other bits. Root (with CAP_DAC_OVERRIDE) bypasses it. This is the whole story behind fsGroup: the kubelet chowns the volume to the gid, sets setgid on directories, and adds the gid to the container's supplementary groups — so a non-root process passes the group check.

Capabilities

Since Linux 2.2 the privileges of root are split into ~41 capabilities, checked individually by the kernel. A process carries several sets; the ones that matter for containers:

Effective
What the kernel checks right now. CapEff in /proc/PID/status.
Permitted
What the process may raise into effective.
Bounding
The ceiling: nothing outside it can ever be gained, even via setuid binaries. Containers set this to the allowed list.
Inheritable / Ambient
What survives execve; ambient lets non-root processes keep caps across exec (how a non-root nginx keeps NET_BIND_SERVICE).

$ grep Cap /proc/$$/status                       # CapInh/CapPrm/CapEff/CapBnd/CapAmb as hex masks
$ capsh --decode=00000000a80425fb                 # → cap_chown,cap_dac_override,…,cap_net_bind_service,…  (containerd's default set)
$ getpcaps $$; getpcaps $(pgrep -o nginx)         # by PID
$ getcap /usr/bin/ping                            # file capabilities: cap_net_raw=ep — lets ping work without setuid
$ sudo setcap cap_net_bind_service=+ep /usr/local/bin/myserver     # non-root process may bind :80
$ capsh --drop=cap_net_raw -- -c 'ping -c1 1.1.1.1'                # simulate a drop
$ docker run --rm --cap-drop=ALL --cap-add=NET_BIND_SERVICE alpine sh -c 'grep CapEff /proc/self/status'   # 0000000000000400

Inside a container the runtime sets the bounding set to the allowed list (default ~14, or exactly what capabilities.add says after drop: [ALL]). A root process gets those as effective; a non-root process gets none unless ambient/file caps grant them. That is why "run as non-root + drop ALL + add NET_BIND_SERVICE" is the restricted profile: the process has one narrowly scoped power and no way to get more.

no_new_privs, seccomp, LSMs

no_new_privs
prctl(PR_SET_NO_NEW_PRIVS): once set, execve can never grant more privilege — setuid bits and file capabilities are ignored. allowPrivilegeEscalation: false. Cheap, always set it.
seccomp
A BPF filter on system calls. containerd's default profile blocks ~40 dangerous ones (mount, reboot, kexec_load, ptrace on older kernels…). seccompProfile: {type: RuntimeDefault}. Unconfined = no filter (what privileged implies). Custom: a JSON profile on the node, type: Localhost.
AppArmor
Path-based mandatory access control on Debian/Ubuntu: a profile lists which files/capabilities/network a program may use. appArmorProfile: {type: RuntimeDefault} (1.30+; previously an annotation). aa-status on the node.
SELinux
Label-based MAC on RHEL/Fedora: every process and file has a context; policy decides. Containers get a unique MCS label so one cannot read another's files even as root. seLinuxOptions; getenforce, ls -Z.
$ grep -E 'NoNewPrivs|Seccomp' /proc/$(pgrep -o nginx)/status     # NoNewPrivs: 1, Seccomp: 2 (filter mode)
$ docker run --rm alpine grep Seccomp /proc/self/status             # 2 = default profile applied
$ docker run --rm --security-opt seccomp=unconfined alpine grep Seccomp /proc/self/status   # 0
$ cat /sys/kernel/security/apparmor/profiles | head; aa-status | head -5

What privileged: true does

All capabilities in the bounding set; all host devices in /dev; /sys and /proc/sys writable; no seccomp filter; no AppArmor/SELinux confinement; masked paths unmasked. The process is root on the host kernel with every tool needed to escape: mount /dev/sda1 /mnt, nsenter -t 1 -a, load a kernel module. It exists for infrastructure Pods (CNI, CSI, some monitoring) and nothing else — which is what the baseline Pod Security Standard forbids.

Hands-on lab (15 min)

$ docker run --rm alpine sh -c 'id; grep CapEff /proc/self/status'                       # root, default caps
$ docker run --rm -u 1000 alpine sh -c 'id; grep CapEff /proc/self/status; touch /etc/x || echo denied'   # non-root: caps 0, EACCES
$ docker run --rm --cap-drop=ALL alpine sh -c 'id; chown 1 /tmp || echo "root without CAP_CHOWN cannot chown"'
$ docker run --rm -u 1000 --cap-add=NET_BIND_SERVICE alpine sh -c 'grep CapEff /proc/self/status'   # still 0! non-root needs ambient caps…
$ docker run --rm -u 1000 alpine sh -c 'nc -l -p 80 & sleep 1; echo $?'                 # …bind :80 fails as uid 1000
$ docker run --rm --security-opt no-new-privileges alpine sh -c 'grep NoNewPrivs /proc/self/status'
$ docker run --rm --privileged alpine sh -c 'grep CapEff /proc/self/status; ls /dev | wc -l; grep Seccomp /proc/self/status'   # all caps, all devices, no seccomp
# fsGroup mechanics by hand
$ mkdir /tmp/vol; sudo chown root:2000 /tmp/vol; sudo chmod 2770 /tmp/vol
$ docker run --rm -u 1000:1000 --group-add 2000 -v /tmp/vol:/data alpine sh -c 'id; touch /data/f && ls -l /data'   # writable via group 2000; file inherits gid (setgid dir)

Key takeaways

  • The kernel knows numbers: uid/gid/supplementary groups. Names come from /etc/passwd and are optional.
  • File access = owner/group/other bits checked against the process's ids; fsGroup works by chown + setgid + supplementary group.
  • Root's power is ~41 capabilities checked per operation; containers bound them; drop ALL and add back only what is needed. Non-root processes get none unless ambient/file caps grant them.
  • no_new_privs, seccomp and AppArmor/SELinux are independent fences; privileged removes all of them and equals root on the node.
