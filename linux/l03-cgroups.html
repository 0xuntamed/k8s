Namespaces decide what a process can see; control groups decide how much it can use. Every CPU request, memory limit, OOMKilled event, throttled latency spike, kubectl top number and node-pressure eviction is a cgroup file being written or read. cgroups are a filesystem, so you can watch all of it happen with cat.

What you'll learn

  • The cgroup v2 unified hierarchy under /sys/fs/cgroup and how processes are placed in it
  • The controllers that matter: cpu (weight, max), memory (max, min, events), pids, io
  • How systemd, containerd and the kubelet lay out the tree (kubepods.slice) and the cgroup driver
  • Reading a container's usage and limits directly; reproducing throttling and OOM
  • v1 vs v2 and why the driver mismatch breaks nodes

A filesystem of limits

$ mount | grep cgroup                          # cgroup2 on /sys/fs/cgroup type cgroup2   (v2, "unified")
$ ls /sys/fs/cgroup/                            # controllers + top-level groups: system.slice, user.slice, kubepods.slice …
$ cat /sys/fs/cgroup/cgroup.controllers         # cpuset cpu io memory hugetlb pids rdma misc
$ cat /proc/$$/cgroup                           # 0::/user.slice/user-1000.slice/session-3.scope  ← where THIS process lives
$ sudo mkdir /sys/fs/cgroup/demo                # creating a directory creates a group…
$ ls /sys/fs/cgroup/demo                        # …and the kernel populates it with control files
$ echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs    # move this shell into it (children inherit)
$ echo "50000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max    # 50 ms per 100 ms = 0.5 CPU
$ echo 200M | sudo tee /sys/fs/cgroup/demo/memory.max

Groups form a tree; a child cannot exceed its parent; limits are enforced on the sum of all processes in the group and its descendants. Every process is in exactly one cgroup (v2). Controllers must be enabled for children via cgroup.subtree_control in the parent.

The tree on a Kubernetes node

$ systemd-cgls --no-pager | head -40             # the whole hierarchy with process names
/sys/fs/cgroup
├── system.slice               ← systemd services: containerd.service, kubelet.service, sshd…
├── user.slice
└── kubepods.slice             ← the kubelet's root for pods (allocatable = capacity − reserved)
    ├── kubepods-burstable.slice
    │   └── kubepods-burstable-pod6b1e…slice        ← one pod (QoS class in the parent name)
    │       ├── cri-containerd-3f9c….scope           ← pause container
    │       └── cri-containerd-a12b….scope           ← app container ← limits live HERE
    ├── kubepods-besteffort.slice
    └── kubepods-pod9d2f….slice                      ← Guaranteed pods sit directly under kubepods
$ CID=$(crictl ps -q --name api); CG=$(crictl inspect $CID | jq -r '.info.runtimeSpec.linux.cgroupsPath'); echo $CG
# kubepods-burstable-pod6b1e….slice:cri-containerd:a12b…   → systemd driver naming; the path is:
$ CGP=/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-pod6b1e….slice/cri-containerd-a12b….scope
$ cat $CGP/cpu.max $CGP/cpu.weight $CGP/memory.max $CGP/memory.current $CGP/pids.current
$ cat $CGP/cpu.stat | grep throttled; cat $CGP/memory.events
$ cat $CGP/cgroup.procs                          # host PIDs of the container's processes

The QoS layout is visible in the names: Guaranteed Pods get their own slice directly under kubepods; Burstable and BestEffort Pods sit under sub-slices whose cpu.weight and memory protection the kubelet tunes so that BestEffort loses first. Node-level reservations (--kube-reserved, --system-reserved) are limits on system.slice siblings, which is why allocatable is less than capacity.

The cgroup driver

Someone has to create these directories. Two conventions exist: cgroupfs (the runtime writes directly under /sys/fs/cgroup) and systemd (the runtime asks systemd to create transient scopes/slices, which is why the names above end in .slice/.scope). On a systemd host there must be exactly one manager of the tree, so the kubelet (cgroupDriver in its config) and the runtime (SystemdCgroup = true in containerd's config.toml) must agree. Mismatch → containers created in one part of the tree while the kubelet accounts in another → phantom resource usage, nodes flapping NotReady, "failed to create cgroup" errors (Day 54).

$ grep cgroupDriver /var/lib/kubelet/config.yaml             # cgroupDriver: systemd
$ grep SystemdCgroup /etc/containerd/config.toml              # SystemdCgroup = true
$ stat -fc %T /sys/fs/cgroup                                   # cgroup2fs (v2) or tmpfs (v1)

Seeing throttling and OOM happen

# with systemd-run: a transient scope with limits (no Docker needed)
$ systemd-run --scope -p CPUQuota=50% -p MemoryMax=100M --user bash
# inside: cat /proc/self/cgroup; CG=/sys/fs/cgroup$(cut -d: -f3 /proc/self/cgroup)
# yes > /dev/null &                                  # burn CPU
# sleep 5; cat $CG/cpu.stat | grep -E 'throttled'     # nr_throttled climbing; usage ~50% in top
# kill %1
# python3 -c 'x=bytearray(200*1024*1024)'            # try to allocate 200 MiB with a 100 MiB max
# Killed                                              ← the OOM killer; exit 137
# cat $CG/memory.events                               # oom_kill 1
# dmesg | tail -3                                     # "Memory cgroup out of memory: Killed process … (python3)"
# with Docker (same files underneath):
$ docker run --rm --cpus 0.5 --memory 100m alpine sh -c 'cat /sys/fs/cgroup/cpu.max /sys/fs/cgroup/memory.max'

Two behaviours to internalise: CPU over the quota is paused until the next period (latency, not death); memory over the max is reclaimed (page cache dropped) and then a process is killed — memory cannot be paused.

v1 vs v2

cgroup v1 had a separate hierarchy per controller (/sys/fs/cgroup/cpu/…, /sys/fs/cgroup/memory/…) with files like cpu.cfs_quota_us, cpu.shares, memory.limit_in_bytes. v2 (default on Ubuntu 22.04+, RHEL 9+, Debian 11+, Fedora 31+; Kubernetes GA since 1.25) unifies them into one tree with the files above, adds memory.min/low protection and pressure-stall information (cpu.pressure, memory.pressure, io.pressure — PSI), and has no "shares" — hence the weight conversion. If you see memory.limit_in_bytes on a node, it is v1; the concepts map one-to-one.

Hands-on lab (15 min)

$ stat -fc %T /sys/fs/cgroup; cat /proc/self/cgroup
$ systemd-run --scope -p CPUQuota=30% -p MemoryMax=64M --user sh -c '
  CG=/sys/fs/cgroup$(cut -d: -f3 /proc/self/cgroup); echo "cgroup: $CG"; cat $CG/cpu.max $CG/memory.max;
  yes > /dev/null & sleep 3; grep throttled $CG/cpu.stat; kill %1;
  head -c 100M /dev/zero | tail 2>/dev/null; echo "exit=$?"; cat $CG/memory.events'
# on a Kubernetes node with a pod that has limits:
$ CID=$(crictl ps -q | head -1); P=$(crictl inspect $CID | jq -r '.info.runtimeSpec.linux.cgroupsPath' | sed 's/:/\//g; s#^#/sys/fs/cgroup/#'); # path shape varies by driver — or:
$ PID=$(crictl inspect $CID | jq .info.pid); CG=/sys/fs/cgroup$(cut -d: -f3 /proc/$PID/cgroup); cat $CG/cpu.max $CG/memory.max $CG/memory.current

Key takeaways

  • cgroups = a tree of directories under /sys/fs/cgroup; processes are placed with cgroup.procs; limits are files.
  • cpu.weight ← request (share under contention), cpu.max ← limit (throttle), memory.max ← limit (OOM kill), pids.max.
  • The kubelet lays out kubepods.slice by QoS; each container is a scope; read its files for ground truth.
  • kubelet and runtime must use the same cgroup driver (systemd on modern nodes).
  • CPU throttles, memory kills — cpu.stat and memory.events record both.
