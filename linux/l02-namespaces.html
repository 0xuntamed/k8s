A namespace wraps a global kernel resource — the process table, the network stack, the mount table, hostnames — so that a group of processes sees its own private copy. Eight of them together are what a "container" is: not a thing the kernel knows about, but a process started inside a fresh set of namespaces. Build one by hand and Docker, containerd and Pods stop being abstractions.

What you'll learn

  • The eight namespace types and what each one isolates
  • Seeing namespaces: lsns, /proc/<pid>/ns, nsenter
  • Creating them: unshare, and the syscalls (clone, unshare, setns) runc uses
  • How a Pod shares some namespaces and not others
  • User namespaces and why they matter for rootless containers

The eight namespaces

hostNetwork: true, hostPID: true, hostIPC: true in a Pod spec mean "do not create that namespace — use the host's". That is why a node-exporter Pod can see all host processes and interfaces.

Seeing them

$ ls -l /proc/$$/ns/                        # each entry is a symlink to an inode: the namespace's identity
lrwxrwxrwx cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx ipc -> 'ipc:[4026531839]'
lrwxrwxrwx mnt -> 'mnt:[4026531841]'
lrwxrwxrwx net -> 'net:[4026531840]'
lrwxrwxrwx pid -> 'pid:[4026531836]'
lrwxrwxrwx user -> 'user:[4026531837]'
lrwxrwxrwx uts -> 'uts:[4026531838]'
$ sudo lsns                                  # every namespace on the host, with the PID that created it and how many processes are in it
$ sudo lsns -t net                           # one per pod (plus the host)
$ PID=$(crictl inspect $(crictl ps -q --name nginx) | jq .info.pid); sudo ls -l /proc/$PID/ns/    # a container's set
$ sudo readlink /proc/$PID/ns/net /proc/1/ns/net     # different inode numbers = different network stacks

Two processes are in the same namespace if their /proc/<pid>/ns/<type> links point to the same inode. All containers in a Pod share the net inode of the pause container.

Building a container by hand

# 1. new pid + mount + uts + ipc namespaces, with a forked child as PID 1
$ sudo unshare --pid --fork --mount --uts --ipc --mount-proc bash
# inside:
# echo $$                    → 1            (PID namespace: I am init)
# ps -ef                     → just bash    (--mount-proc mounted a fresh /proc for this pid ns)
# hostname box; hostname     → box          (UTS namespace: the host is unaffected)
# ip addr                    → host's NICs  (we did NOT unshare net)
# exit
$ hostname                   # unchanged on the host
# 2. add a network namespace and wire it (see the Networking page for the veth part)
$ sudo unshare --net bash -c 'ip addr'      # only lo, and it is DOWN
# 3. a root filesystem: mount a directory as / (chroot is the crude version; runc uses pivot_root)
$ mkdir -p /tmp/rootfs && docker export $(docker create alpine) | tar -C /tmp/rootfs -xf -
$ sudo unshare --pid --fork --mount --uts --mount-proc chroot /tmp/rootfs /bin/sh
# / # ps; cat /etc/os-release      → Alpine, one process
# 4. enter an existing container's namespaces (this is what docker exec / kubectl exec do)
$ sudo nsenter -t $PID -n ip addr             # only the network namespace: see the pod's eth0 from the host
$ sudo nsenter -t $PID -p -m -u -i -n -- /bin/sh     # all of them: effectively "exec into" it
$ sudo nsenter -t $PID -n ss -tlnp              # what is listening inside the pod — with host tools, no shell needed in the image

That last trick is how you debug a distroless container with no shell: enter only its network namespace from the node and use the node's ss, curl, tcpdump. It is also exactly what kubectl debug --target automates.

The syscalls (what runc actually does)

  • clone(CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC …) — create the child in new namespaces. runc's init process is born this way.
  • unshare(flags) — move the calling process into new namespaces (the unshare command).
  • setns(fd, type) — join an existing namespace by opening /proc/<pid>/ns/<type> (the nsenter command; how app containers join the pause container's net namespace).
  • Then: mount the rootfs, pivot_root into it, mount /proc, /sys, /dev, apply cgroups, capabilities, seccomp, and finally execve the entrypoint.
$ sudo strace -f -e trace=clone,clone3,unshare,setns,pivot_root,execve docker run --rm alpine true 2>&1 | grep -E 'CLONE_NEW|pivot_root|execve' | head

Namespaces in a Pod

The kubelet asks the runtime for a sandbox: the pause container is created with new net, uts and ipc namespaces (and pid, if shared). Each app container is then created with setns into the sandbox's net/uts/ipc, but with its own mnt (its image), pid (unless shared) and cgroup namespaces. Consequences you have met: one IP per Pod, localhost between containers, separate filesystems, separate ps views, and a Pod IP that survives container restarts because the pause process never restarts.

User namespaces

Without a user namespace, UID 0 in a container is UID 0 on the host kernel — only capabilities and seccomp stand between a container escape and root. A user namespace maps container UID 0 to an unprivileged host UID (e.g. 100000), so even a full escape lands as nobody. Docker's userns-remap and rootless Podman use it; Kubernetes supports it per Pod with hostUsers: false (beta since 1.30, needs runtime + filesystem support). Until it is universal, runAsNonRoot (Day 41) is the practical defence.

$ unshare --user --map-root-user bash        # no sudo needed: you are "root" in a new user namespace
# id                    → uid=0(root) — but only here
# cat /proc/self/uid_map → 0 1000 1  (container 0 ↔ host 1000)
# touch /etc/x           → Permission denied: the kernel checks with the mapped host UID

Hands-on lab (15 min)

$ sudo lsns -t pid -t net | head
$ sudo unshare --pid --fork --uts --mount --mount-proc bash -c 'hostname inner; echo "pid=$$ host=$(hostname)"; ps -ef'
$ hostname                                                              # unchanged
$ docker run -d --name n nginx; PID=$(docker inspect -f '{{.State.Pid}}' n)
$ sudo readlink /proc/$PID/ns/{pid,net,mnt} ; readlink /proc/$$/ns/{pid,net,mnt}      # all different
$ sudo nsenter -t $PID -n ss -tlnp                                      # :80 inside the container, seen from the host
$ sudo nsenter -t $PID -p -m -- ps -ef                                  # nginx as PID 1
$ docker run -d --name side --network container:n alpine sleep 3600; SP=$(docker inspect -f '{{.State.Pid}}' side)
$ sudo readlink /proc/$PID/ns/net /proc/$SP/ns/net                      # SAME inode: shared network ns (the Pod model)
$ sudo readlink /proc/$PID/ns/mnt /proc/$SP/ns/mnt                      # different: own filesystems
$ docker rm -f n side

Key takeaways

  • Namespaces give a process group a private view of PIDs, network, mounts, hostname, IPC, users, cgroups. A container is a process in a fresh set of them.
  • /proc/<pid>/ns/* identifies namespaces; same inode = same namespace. lsns, unshare, nsenter are the tools.
  • Pods share net/uts/ipc via the pause container and keep mnt/pid per container; hostNetwork/hostPID opt out of isolation.
  • nsenter -t PID -n lets you debug a container's network with host tools — no shell in the image required.
  • User namespaces map container root to an unprivileged host UID; until they are default, run as non-root.
