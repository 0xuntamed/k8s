Every CNI plugin, every Service, every NetworkPolicy and every "Pod cannot reach X" ticket is built from five Linux primitives: network namespaces, veth pairs, bridges, the routing table, and netfilter (iptables/nftables, plus conntrack). This page builds a two-"Pod" network by hand with nothing but ip and iptables, then shows you the exact rules kube-proxy and Calico write.

What you'll learn

  • Network namespaces and the ip netns / nsenter tools
  • veth pairs, Linux bridges, and how a packet crosses from a namespace to the host
  • Routing: ip route, forwarding, the route each CNI installs per node
  • netfilter: tables, chains, DNAT/SNAT/MASQUERADE, conntrack — the mechanism behind -p, Services and NetworkPolicy
  • Diagnostics: ss, tcpdump, nc, ip -s link, conntrack; IPVS and eBPF in one paragraph each

Build a Pod network by hand

# two "pods" (network namespaces), a bridge, veth cables, IPs, routes
$ sudo ip netns add pod1 && sudo ip netns add pod2
$ sudo ip link add br0 type bridge && sudo ip addr add 10.244.1.1/24 dev br0 && sudo ip link set br0 up
$ sudo ip link add veth1 type veth peer name eth0 netns pod1      # a cable: veth1 on host, eth0 inside pod1
$ sudo ip link add veth2 type veth peer name eth0 netns pod2
$ sudo ip link set veth1 master br0 && sudo ip link set veth1 up   # plug host ends into the bridge
$ sudo ip link set veth2 master br0 && sudo ip link set veth2 up
$ sudo ip -n pod1 addr add 10.244.1.10/24 dev eth0 && sudo ip -n pod1 link set eth0 up && sudo ip -n pod1 link set lo up
$ sudo ip -n pod2 addr add 10.244.1.11/24 dev eth0 && sudo ip -n pod2 link set eth0 up && sudo ip -n pod2 link set lo up
$ sudo ip -n pod1 route add default via 10.244.1.1               # the bridge IP is the gateway
$ sudo ip -n pod2 route add default via 10.244.1.1
$ sudo ip netns exec pod1 ping -c1 10.244.1.11                     # pod → pod, through the bridge (L2)
$ sudo ip netns exec pod1 ping -c1 10.244.1.1                      # pod → host
# to the internet: forwarding + masquerade
$ sudo sysctl -w net.ipv4.ip_forward=1
$ sudo iptables -t nat -A POSTROUTING -s 10.244.1.0/24 ! -o br0 -j MASQUERADE
$ sudo ip netns exec pod1 ping -c1 1.1.1.1                          # pod → world, source-NAT'd to the host IP
# see it
$ ip link show type veth; bridge link; ip -n pod1 addr; ip -n pod1 route
$ sudo ip netns exec pod1 ss -tlnp; sudo nsenter --net=/var/run/netns/pod1 ip addr   # two ways in

That is the reference CNI bridge plugin (and Docker's docker0, and kindnet) in ten commands. Calico and Cilium skip the bridge and use direct routes to each veth (10.244.1.10 dev cali1234), but the veth-into-namespace step is universal.

Across nodes: the routing table

$ ip route                                     # on a Calico/kindnet node:
default via 192.168.56.1 dev eth0
10.244.1.0/24 dev br0 proto kernel scope link   # my pods (or per-pod /32 routes on Calico)
10.244.2.0/24 via 192.168.56.12 dev eth0        # worker-2's pod CIDR → send to worker-2's node IP  (BGP / static / kindnet)
10.244.3.0/24 via 192.168.56.13 dev eth0
# or, with an overlay (Flannel VXLAN, Calico VXLAN mode):
10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink    # encapsulated in UDP 8472 to the other node
$ ip route get 10.244.2.9                       # which route/interface a destination would use
$ ip -s link show eth0                          # counters: RX/TX packets, errors, drops

Each node owns a Pod CIDR (kubectl get node -o jsonpath='{.spec.podCIDR}'). Pod-to-pod across nodes is plain IP routing: the CNI installs one route per remote node (learned via BGP for Calico, written by the kindnet/flannel DaemonSet, or via the cloud route table for VPC CNIs). No NAT between Pods — the Kubernetes network model requires that every Pod can reach every Pod by its real IP. net.ipv4.ip_forward=1 is what lets the node pass packets between its interfaces at all.

$ sudo iptables -t nat -L -n --line-numbers | head -40        # or: iptables-save | less
$ sudo iptables -t nat -L KUBE-SERVICES -n | grep 10.96.0.10   # cluster DNS Service → KUBE-SVC-… chain
$ sudo iptables -t nat -L KUBE-SVC-TCOU7JCQXEZGVUNU -n         # statistic --probability rules → KUBE-SEP-… (one per endpoint)
$ sudo iptables -t nat -L KUBE-SEP-XXXX -n                     # DNAT --to-destination 10.244.1.5:53
$ sudo iptables -t nat -L KUBE-NODEPORTS -n                    # NodePort entry points
$ sudo iptables -t filter -L FORWARD -n | head                  # KUBE-FORWARD, cali-FORWARD …
$ sudo iptables -t filter -L cali-tw-cali1a2b3c4d -n            # "to workload": a pod's ingress NetworkPolicy chain (Calico)
$ sudo nft list ruleset | head                                  # modern kernels: iptables is a compatibility layer over nftables; kube-proxy has a native nftables mode
$ sudo conntrack -L | grep 10.96.0.10 | head                    # live NAT state: VIP ↔ chosen endpoint per connection
$ sudo conntrack -S; sysctl net.netfilter.nf_conntrack_max      # table pressure → "nf_conntrack: table full, dropping packet" in dmesg
DNAT
Change the destination before routing. -p 8080:80 and every ClusterIP/NodePort rule.
SNAT / MASQUERADE
Change the source after routing (MASQUERADE = to the outgoing interface's IP). Pod → internet; also NodePort traffic when externalTrafficPolicy: Cluster forwards to another node (hence lost client IPs).
conntrack
The connection-tracking table: remembers each flow and its NAT mapping so replies are un-NAT'ed and later packets skip the rule chains. Entries time out (TCP established: 5 days; UDP: 30 s) — which is why DNS over UDP through a Service can hit stale entries, and why the table has a max size.

IPVS and eBPF in one paragraph each

IPVS (kube-proxy mode: ipvs) replaces the linear iptables chain per Service with a kernel hash table of virtual servers → real servers (ipvsadm -Ln), with scheduling algorithms (rr, lc, sh). O(1) lookup at thousands of Services; still uses iptables for masquerade marks. eBPF (Cilium, Calico eBPF mode) attaches programs to the veth's TC hook and does Service translation, policy and routing without iptables at all; identity-based policy (labels → numeric identity) instead of IP sets; cilium bpf lb list, hubble observe replace the iptables commands above. The model — DNAT to a Pod IP, policy at the Pod's interface — is unchanged.

Hands-on lab (25 min)

# build the two-pod network above, then add a "Service" by hand:
$ sudo iptables -t nat -A OUTPUT -d 10.96.0.42 -p tcp --dport 80 -j DNAT --to-destination 10.244.1.11:8080     # VIP → pod2
$ sudo iptables -t nat -A PREROUTING -d 10.96.0.42 -p tcp --dport 80 -j DNAT --to-destination 10.244.1.11:8080
$ sudo ip netns exec pod2 sh -c 'while true; do echo -e "HTTP/1.1 200 OK\r\n\r\nhello from pod2" | nc -l -p 8080 -q1; done' &
$ curl -s 10.96.0.42                                     # host → "Service" VIP → DNAT → pod2
$ sudo ip netns exec pod1 curl -s 10.96.0.42             # pod1 → VIP: PREROUTING DNAT (its packets enter the host via veth1)
$ sudo conntrack -L | grep 10.96.0.42                    # the mapping conntrack remembers
$ sudo tcpdump -i veth2 -nn -c4 port 8080 &              # watch the DNAT'ed packets arrive on pod2's cable
$ sudo ip netns exec pod1 curl -s 10.96.0.42 >/dev/null
# a "NetworkPolicy": drop pod1 → pod2 on 8080
$ sudo iptables -I FORWARD -s 10.244.1.10 -d 10.244.1.11 -p tcp --dport 8080 -j DROP
$ sudo ip netns exec pod1 timeout 2 curl -s 10.96.0.42 || echo blocked
# cleanup
$ sudo iptables -D FORWARD -s 10.244.1.10 -d 10.244.1.11 -p tcp --dport 8080 -j DROP; sudo iptables -t nat -F; kill %1 %2 2>/dev/null
$ sudo ip netns del pod1; sudo ip netns del pod2; sudo ip link del br0

Key takeaways

  • Pod networking = a network namespace + a veth pair + (a bridge or direct route) + routes; the CNI automates exactly these commands.
  • Cross-node traffic is IP routing over per-node Pod CIDRs (direct or encapsulated); ip_forward must be on; no NAT between Pods.
  • Services are DNAT rules in the nat table (kube-proxy); NetworkPolicies are filter rules on Pod interfaces (CNI); conntrack makes both stateful.
  • IPVS and eBPF change the data structure, not the model.
  • ip, ss, tcpdump, conntrack, iptables -t nat -S and nsenter -n are the debugging kit.
