A container is a process. A Pod is a few processes. "Restart", "terminate", "graceful shutdown", "exit code 137", "CrashLoopBackOff" — every one of these is a statement about Linux processes and the signals sent between them. This page covers the process model well enough that Day 4 and Day 22 read as obvious consequences.

Processes and the tree

Every running program is a process with a numeric PID, a parent (PPID), a user, an environment, open file descriptors, a working directory, and a state. New processes are made by fork() — the parent duplicates itself — and usually then exec() — the copy replaces its program image with a new one, keeping the same PID. The first process, PID 1 (systemd on a normal machine), is started by the kernel and is the ancestor of everything.

$ ps -ef                                  # all processes: UID PID PPID … CMD
$ ps -o pid,ppid,stat,etime,cmd -p $$     # your shell; STAT: R running, S sleeping, D uninterruptible IO, Z zombie, T stopped
$ pstree -p | head -20                    # the tree
$ pstree -p $(pgrep -o containerd-shim)   # a container's process subtree under its shim
$ top / htop                              # live view
$ ls /proc/1/                             # everything the kernel knows about PID 1
$ cat /proc/$$/status | head -12          # Name, State, Pid, PPid, Uid, … and (below) capabilities
$ ls -l /proc/$$/fd                       # open files/sockets
$ cat /proc/$$/cmdline | tr '\0' ' '; echo
$ readlink /proc/$$/exe; readlink /proc/$$/cwd; cat /proc/$$/environ | tr '\0' '\n' | head

/proc is a virtual filesystem where the kernel exposes process state as files. Containers get their own /proc mounted inside their PID namespace, so ls /proc inside a container lists only its own processes — that is the entire "isolation" of ps (see Namespaces).

Signals

A signal is a one-byte asynchronous notification the kernel delivers to a process. The process either has a handler for it (runs a function), ignores it, or takes the default action — for most signals, terminate.

Why PID 1 is special

Inside a PID namespace the first process is PID 1, and the kernel treats it like init:

  1. Default signal actions do not apply. If PID 1 has not installed a handler for a signal, the signal is ignored — even SIGTERM. Only SIGKILL (and SIGSTOP) work unconditionally. This protects init from accidental termination on a real system; in a container it means a naive PID 1 cannot be stopped gracefully.
  2. It must reap orphans. When a process exits, it becomes a zombie (state Z) until its parent calls wait() to collect its exit status. If the parent has already died, the orphan is re-parented to PID 1, which must reap it. A PID 1 that never calls wait() accumulates zombies until the PID table fills.
  3. When PID 1 exits, the namespace dies: every other process in it gets SIGKILL. This is why a container "is" its PID 1: when the main process ends, the container ends.
$ docker run -d --name z nginx; docker exec z ps -o pid,stat,cmd     # PID 1 = nginx master; workers as children
$ docker exec z sh -c 'sleep 30 & sleep 1; kill -9 $!; sleep 1; ps -o pid,stat,cmd'   # a killed child is reaped by nginx (it handles SIGCHLD)
$ docker run -d --name badinit busybox sh -c 'while true; do sleep 1; done'
$ time docker stop badinit                 # ~10 s: sh (PID 1) ignores SIGTERM, Docker escalates to SIGKILL
$ docker run -d --init --name goodinit busybox sh -c 'while true; do sleep 1; done'   # tini as PID 1 forwards signals and reaps
$ time docker stop goodinit                # < 1 s

Exit codes

CodeMeaning
0Success.
1–125Application-defined error. Conventions: 1 general, 2 misuse.
126Command found but not executable (permissions, wrong arch, missing interpreter).
127Command not found — wrong command/ENTRYPOINT, missing binary in a slim image.
128 + NKilled by signal N: 137 = 9 (SIGKILL: OOM or grace period), 143 = 15 (SIGTERM handled by exiting), 139 = 11 (SIGSEGV), 130 = 2 (SIGINT).
255Out of range / exit -1.
$ ./prog; echo $?                           # last exit code
$ sh -c 'kill -9 $$'; echo $?               # 137
$ kubectl describe pod x | grep -A3 'Last State'     # Exit Code: 137, Reason: OOMKilled (or Error)

exec: replacing the shell

exec cmd in a shell script replaces the shell process with cmd — same PID, no child. That is why entrypoint scripts end with exec "$@": the real server becomes PID 1 and receives signals directly. Without exec, the shell stays PID 1, the server is PID 7, and SIGTERM stops at the shell.

$ cat entrypoint.sh
#!/bin/sh
set -e
envsubst < /etc/app.tmpl > /etc/app.conf
exec /usr/bin/myserver --config /etc/app.conf     # ← replaces sh; myserver is now PID 1
$ docker exec c ps -o pid,cmd                       # PID 1 /usr/bin/myserver — no sh in sight

How this appears in Kubernetes

  • Pod termination (Day 22): SIGTERM to each container's PID 1 → grace period → SIGKILL. Exit code 143 (handled) vs 137 (killed).
  • CMD/ENTRYPOINT forms (Day 4): shell form puts sh at PID 1; exec form puts your program there.
  • OOMKilled: the kernel sends SIGKILL to the biggest process in the cgroup — exit 137 with reason OOMKilled.
  • Liveness probe failure: the kubelet stops the container (SIGTERM → SIGKILL) and starts a new one.
  • shareProcessNamespace: true (Day 21): all containers share one PID namespace; the pause container is PID 1 and reaps for everyone; kill -HUP across containers works.
  • Zombies in Pods: an app that spawns children and never waits shows Z processes in kubectl exec … ps; eventually PIDPressure. Fix the app, or use tini / shared process namespace.

Hands-on lab (15 min)

$ sleep 300 & P=$!; ps -o pid,ppid,stat,cmd -p $P; kill -TERM $P; wait $P; echo "exit $?"        # 143
$ sleep 300 & P=$!; kill -KILL $P; wait $P; echo "exit $?"                                        # 137
$ (trap 'echo got TERM; exit 0' TERM; while true; do sleep 1; done) & P=$!; sleep 1; kill -TERM $P; wait $P; echo $?   # 0 — handled
# PID 1 in a namespace ignoring SIGTERM (needs util-linux unshare)
$ sudo unshare --pid --fork sh -c 'echo "I am PID $$"; sleep 300' &
$ sleep 1; sudo kill -TERM $(pgrep -f 'sleep 300' | head -1); sleep 1; pgrep -f 'sleep 300' && echo "still alive: PID 1 ignored SIGTERM"
$ sudo pkill -KILL -f 'sleep 300'
# zombie
$ sh -c 'sleep 1 & exec sleep 30' & sleep 2; ps -o pid,ppid,stat,cmd | grep -E 'Z|sleep'      # the "sleep 1" is a zombie: its parent (now sleep 30) never waits
$ pkill -f 'sleep 30'

Key takeaways

  • Processes form a tree from PID 1; fork copies, exec replaces; /proc exposes it all.
  • SIGTERM asks, SIGKILL forces; only SIGTERM can be handled. Exit 128+N means killed by signal N.
  • PID 1 ignores unhandled signals, must reap orphans, and ends the namespace when it exits — so containers need a proper PID 1 (exec form, exec "$@", or tini).
  • Kubernetes termination, restarts, OOMKilled and probes are all signals to PID 1.
