Every certificate in /etc/kubernetes/pki, every kubeconfig blob, every Ingress TLS Secret is a PEM file that openssl can read, verify, create and sign. This page is the reference: the dozen commands that inspect any cert, check expiry and chains, generate keys and CSRs, run a private CA, and debug a live TLS endpoint — plus the format conversions that trip people up.

What you'll learn

  • Formats: PEM vs DER, what the BEGIN lines mean, base64 in kubeconfigs and Secrets
  • Inspecting: subject, issuer, SANs, dates, key usage, fingerprint
  • Verifying: chains, key/cert matching, live endpoints with s_client
  • Creating: keys, CSRs with SANs, self-signed certs, a private CA that signs CSRs
  • Expiry checks in scripts and the Kubernetes files to run them on

Formats

$ head -1 /etc/kubernetes/pki/ca.crt          # -----BEGIN CERTIFICATE-----          PEM = base64 of DER between BEGIN/END lines
$ head -1 /etc/kubernetes/pki/ca.key          # -----BEGIN RSA PRIVATE KEY-----      (PKCS#1) or -----BEGIN PRIVATE KEY----- (PKCS#8) or EC PRIVATE KEY
$ head -1 jane.csr                            # -----BEGIN CERTIFICATE REQUEST-----
$ openssl x509 -in cert.pem -outform DER -out cert.der          # PEM → DER (binary; Java/Windows)
$ openssl x509 -inform DER -in cert.der -out cert.pem            # DER → PEM
$ openssl pkcs12 -export -in cert.pem -inkey key.pem -certfile chain.pem -out bundle.p12   # PKCS#12 for Java keystores/browsers
$ base64 -w0 ca.crt                            # what goes into kubeconfig certificate-authority-data / Secret .data
$ kubectl get secret web-tls -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -subject   # and back

Kubernetes only ever wants PEM. A file with several BEGIN CERTIFICATE blocks is a chain: leaf first, then intermediates. ca.crt in a kubeconfig or a Secret may contain several roots.

Inspect

$ openssl x509 -in cert.pem -noout -text                         # everything
$ openssl x509 -in cert.pem -noout -subject -issuer -dates -serial
$ openssl x509 -in cert.pem -noout -ext subjectAltName            # the names it is valid for (clients match these, not CN)
$ openssl x509 -in cert.pem -noout -ext keyUsage,extendedKeyUsage # serverAuth? clientAuth? CA:TRUE?
$ openssl x509 -in cert.pem -noout -ext basicConstraints          # CA:TRUE = can sign others
$ openssl x509 -in cert.pem -noout -fingerprint -sha256           # pin / compare
$ openssl x509 -in cert.pem -noout -checkend 604800 || echo "expires within 7 days"   # exit 1 if expiring — for scripts/alerts
$ openssl req -in jane.csr -noout -text                           # a CSR: subject, public key, requested extensions
$ openssl rsa -in key.pem -noout -check; openssl rsa -in key.pem -noout -text | head -3    # key sanity, size
$ openssl ec -in key.pem -noout -text 2>/dev/null | head -3        # EC keys
$ for f in /etc/kubernetes/pki/*.crt /etc/kubernetes/pki/etcd/*.crt; do printf '%-50s %s\n' "$f" "$(sudo openssl x509 -in $f -noout -enddate | cut -d= -f2)"; done

Verify

# chain: does cert.pem chain to ca.pem?
$ openssl verify -CAfile ca.pem cert.pem                                    # cert.pem: OK
$ openssl verify -CAfile root.pem -untrusted intermediate.pem cert.pem      # with an intermediate
$ openssl verify -CAfile ca.pem -purpose sslclient cert.pem                 # also check usage (clientAuth)
# does this key belong to this cert? compare public keys (works for RSA and EC)
$ diff <(openssl x509 -in cert.pem -noout -pubkey) <(openssl pkey -in key.pem -pubout) && echo "key matches cert"
# older RSA-only trick:
$ openssl x509 -noout -modulus -in cert.pem | md5sum; openssl rsa -noout -modulus -in key.pem | md5sum
# a live endpoint
$ openssl s_client -connect 10.0.0.10:6443 -servername kubernetes -CAfile /etc/kubernetes/pki/ca.crt < /dev/null 2>/dev/null | grep -E 'Verify return|subject=|issuer='
$ openssl s_client -connect example.com:443 -showcerts < /dev/null 2>/dev/null | openssl x509 -noout -dates   # first cert in the chain
$ openssl s_client -connect example.com:443 -showcerts < /dev/null 2>/dev/null | grep -E '^ [0-9] s:| i:'         # the chain as sent
$ openssl s_client -connect 10.0.0.10:6443 -cert admin.crt -key admin.key -CAfile ca.crt < /dev/null   # mTLS: present a client cert
$ echo | openssl s_client -connect host:443 -servername api.example.com 2>/dev/null | openssl x509 -noout -ext subjectAltName   # SNI-selected cert
$ curl -v --cacert ca.pem https://host:6443/version 2>&1 | grep -E 'SSL connection|subject|issuer|expire'

Create

# keys
$ openssl genrsa -out key.pem 2048                              # RSA 2048 (Kubernetes default)
$ openssl ecparam -name prime256v1 -genkey -noout -out key.pem  # EC P-256 (smaller, faster)
$ chmod 600 key.pem
# CSR with subject and SANs (modern openssl: -addext)
$ openssl req -new -key key.pem -subj "/CN=api.internal/O=platform" -addext "subjectAltName=DNS:api.internal,DNS:api,IP:10.0.0.5" -out api.csr
# self-signed cert in one go (labs, tests)
$ openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 365 -subj "/CN=test.local" -addext "subjectAltName=DNS:test.local"
# a private CA
$ openssl genrsa -out ca.key 4096
$ openssl req -x509 -new -key ca.key -sha256 -days 3650 -subj "/CN=my-ca" -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign" -out ca.crt
# sign a CSR with the CA, carrying over the requested SANs and setting usage
$ cat > ext.cnf <<EOF
subjectAltName=DNS:api.internal,DNS:api,IP:10.0.0.5
extendedKeyUsage=serverAuth
keyUsage=digitalSignature,keyEncipherment
basicConstraints=CA:FALSE
EOF
$ openssl x509 -req -in api.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 365 -sha256 -extfile ext.cnf -out api.crt
$ openssl x509 -in api.crt -noout -subject -issuer -ext subjectAltName,extendedKeyUsage
$ openssl verify -CAfile ca.crt api.crt       # OK
# client cert (for mTLS / a Kubernetes user): extendedKeyUsage=clientAuth, CN=user, O=group
$ openssl req -new -key jane.key -subj "/CN=jane/O=developers" -out jane.csr
$ printf 'extendedKeyUsage=clientAuth\nbasicConstraints=CA:FALSE\n' > client.cnf
$ openssl x509 -req -in jane.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 90 -extfile client.cnf -out jane.crt
Two things people forget
  • SANs are not copied from a CSR by default. openssl x509 -req ignores requested extensions unless you pass -extfile (or -copy_extensions copy on OpenSSL 3.x). A server cert without SANs is rejected by Go clients (kubectl) and modern browsers.
  • Usage must match the role. A cert without clientAuth cannot authenticate to the API server; without serverAuth it cannot serve. Kubernetes' CSR signers enforce this via usages:.

Hands-on lab (15 min)

$ mkdir -p /tmp/pki && cd /tmp/pki
# CA + server cert with SANs + client cert, then prove each property
$ openssl genrsa -out ca.key 2048 && openssl req -x509 -new -key ca.key -days 365 -subj "/CN=lab-ca" -addext "basicConstraints=critical,CA:TRUE" -out ca.crt
$ openssl genrsa -out srv.key 2048 && openssl req -new -key srv.key -subj "/CN=srv" -addext "subjectAltName=DNS:srv.local,IP:127.0.0.1" -out srv.csr
$ printf 'subjectAltName=DNS:srv.local,IP:127.0.0.1\nextendedKeyUsage=serverAuth\n' > srv.cnf
$ openssl x509 -req -in srv.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 30 -extfile srv.cnf -out srv.crt
$ openssl x509 -in srv.crt -noout -subject -issuer -dates -ext subjectAltName,extendedKeyUsage
$ openssl verify -CAfile ca.crt srv.crt; openssl verify srv.crt 2>&1 | tail -1     # OK vs unknown authority
$ diff <(openssl x509 -in srv.crt -noout -pubkey) <(openssl pkey -in srv.key -pubout) && echo "key matches"
$ openssl s_server -accept 8443 -cert srv.crt -key srv.key -www & sleep 1
$ openssl s_client -connect 127.0.0.1:8443 -CAfile ca.crt < /dev/null 2>/dev/null | grep 'Verify return'   # 0 (ok)
$ curl -s --cacert ca.crt https://127.0.0.1:8443 | head -2; curl -s --cacert ca.crt https://localhost:8443 2>&1 | head -1   # "localhost" is not in the SANs
$ openssl x509 -in srv.crt -noout -checkend $((40*86400)) || echo "expires within 40 days"
$ kill %1; cd -

Key takeaways

  • PEM everywhere; base64 of PEM in kubeconfigs and Secrets; chains are concatenated PEM blocks, leaf first.
  • x509 -noout -subject -issuer -dates -ext subjectAltName answers 90% of questions; -checkend for expiry scripts.
  • verify -CAfile for chains, the pubkey diff for key/cert matching, s_client for live endpoints (with -servername for SNI, -cert/-key for mTLS).
  • Create with genrsa → req -new -addext subjectAltName → x509 -req -CA … -extfile; SANs and usages must be set explicitly.
  • Error text maps directly to a check: unknown authority (CA), expired (dates/clock), valid for X not Y (SANs), bad certificate (client cert), local issuer (chain).
