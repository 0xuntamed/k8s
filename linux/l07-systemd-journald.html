On every node there are exactly two Kubernetes processes that are not containers: the kubelet and the container runtime. Both are systemd services. Starting, stopping, configuring and reading the logs of those two is half of node troubleshooting, and the other half (static Pods, upgrades, cgroup drivers) touches systemd too. This page is the working subset of systemd and journald an operator needs.

What you'll learn

Units

systemd is PID 1. It manages units: services (.service), mount points, timers, sockets, and grouping constructs — slices (cgroup subtrees) and scopes (externally started processes it should track). Unit files live in /usr/lib/systemd/system (packages) and /etc/systemd/system (yours; wins). Small overrides go in drop-in directories: <unit>.d/*.conf, merged over the base file.

$ systemctl status kubelet                     # loaded? enabled? active (running) since…? recent log lines, main PID, cgroup, memory
$ systemctl cat kubelet                        # the unit file AND every drop-in, in order
$ systemctl show kubelet -p ExecStart -p Environment -p Restart   # resolved properties
$ systemctl list-units --type=service --state=running | head
$ systemctl list-unit-files | grep -E 'kubelet|containerd'        # enabled/disabled
$ systemctl is-active kubelet; systemctl is-enabled containerd     # scriptable yes/no
$ systemctl start|stop|restart|reload kubelet   # reload = SIGHUP if the unit supports it
$ systemctl enable --now containerd            # start now and at boot
$ systemctl disable kubelet                     # stay off at boot (does not stop it now)
$ systemctl edit kubelet                        # create a drop-in interactively
$ systemctl daemon-reload                       # REQUIRED after editing any unit file or drop-in, before restart
The daemon-reload rule

systemd caches unit definitions. Editing a unit file or drop-in changes nothing until systemctl daemon-reload; a following restart then uses the new definition. Forgetting it is the most common "I changed the config and nothing happened" in kubelet troubleshooting — and systemctl status warns: "Warning: The unit file … changed on disk. Run 'systemctl daemon-reload'". (Changing /var/lib/kubelet/config.yaml only needs a restart; it is the kubelet's own file, not systemd's.)

The kubelet unit, dissected

[Unit]
Description=kubelet: The Kubernetes Node Agent
Documentation=https://kubernetes.io/docs/
Wants=network-online.target
After=network-online.target

[Service]
ExecStart=/usr/bin/kubelet
Restart=always                 # restart on any exit
StartLimitInterval=0           # never give up
RestartSec=10                  # 10 s between attempts (why a broken kubelet "flaps")

[Install]
WantedBy=multi-user.target
# Note: This dropin only works with kubeadm and kubelet v1.11+
[Service]
Environment="KUBELET_KUBECONFIG_ARGS=--bootstrap-kubeconfig=/etc/kubernetes/bootstrap-kubelet.conf --kubeconfig=/etc/kubernetes/kubelet.conf"
Environment="KUBELET_CONFIG_ARGS=--config=/var/lib/kubelet/config.yaml"
EnvironmentFile=-/var/lib/kubelet/kubeadm-flags.env      # per-node flags kubeadm generated (container runtime endpoint, node IP…)
EnvironmentFile=-/etc/default/kubelet                    # your extra flags (Debian) / /etc/sysconfig/kubelet (RHEL)
ExecStart=                                               # empty line CLEARS the package ExecStart…
ExecStart=/usr/bin/kubelet $KUBELET_KUBECONFIG_ARGS $KUBELET_CONFIG_ARGS $KUBELET_KUBEADM_ARGS $KUBELET_EXTRA_ARGS   # …then redefines it
$ cat /var/lib/kubelet/kubeadm-flags.env     # KUBELET_KUBEADM_ARGS="--container-runtime-endpoint=unix:///run/containerd/containerd.sock --pod-infra-container-image=…"
$ cat /etc/default/kubelet                    # KUBELET_EXTRA_ARGS=--node-ip=192.168.56.11   (typical VirtualBox fix)
$ ps -o args= -p $(pidof kubelet)             # the fully expanded command line actually running

So the kubelet's configuration comes from four places, in this precedence: command-line flags (from the env files above) > /var/lib/kubelet/config.yaml (the KubeletConfiguration: cgroupDriver, staticPodPath, clusterDNS, eviction thresholds, rotateCertificates…) > defaults. Most tuning belongs in config.yaml; --node-ip and the runtime endpoint are the flags you will actually see.

journald

systemd captures stdout/stderr of every service into the journal, a binary indexed log in /var/log/journal (persistent) or /run/log/journal (volatile). The kubelet and containerd log there; container logs do not (they go to files under /var/log/pods, see Day 56).

$ journalctl -u kubelet                        # everything from the unit (pager)
$ journalctl -u kubelet -f                     # follow
$ journalctl -u kubelet -n 100 --no-pager      # last 100 lines, no pager (scripts, exam)
$ journalctl -u kubelet --since "10 min ago"; journalctl -u kubelet --since "2025-01-01 09:00" --until "2025-01-01 09:30"
$ journalctl -u kubelet -p err                 # priority err and worse (emerg alert crit err warning notice info debug)
$ journalctl -u kubelet -b                     # this boot only; -b -1 = previous boot (why did it crash before reboot?)
$ journalctl -u kubelet -o json-pretty | head -30   # structured fields
$ journalctl -u kubelet | grep -iE 'error|fail' | tail -20
$ journalctl -u containerd -u kubelet --since "5 min ago"   # several units interleaved
$ journalctl -k | grep -iE 'oom|killed process'             # kernel messages (dmesg) — OOM kills
$ journalctl --disk-usage; sudo journalctl --vacuum-size=200M; sudo journalctl --vacuum-time=7d   # DiskPressure relief
$ grep -E '^(SystemMaxUse|Storage)' /etc/systemd/journald.conf

Reading kubelet logs: lines are Ixxxx/Wxxxx/Exxxx (info/warning/error) with the source file. Search for E lines first; the phrases you want are in Day 58.

systemd and cgroups

systemd owns the cgroup tree on a modern node. Every service runs in its own cgroup under system.slice; resource directives in unit files map to cgroup files (CPUQuota= → cpu.max, MemoryMax= → memory.max). With the systemd cgroup driver, containerd asks systemd to create a transient scope per container (the cri-containerd-….scope names in L3) under the kubelet's slices, so there is one manager of the tree. With cgroupfs, the runtime writes directories itself and systemd does not know about them — which works until systemd reorganises the tree and orphans them.

$ systemd-cgls --no-pager | head -30                       # the tree with unit names
$ systemctl status kubelet | grep -A3 CGroup               # /system.slice/kubelet.service and its processes
$ systemd-run --unit=burn --scope -p CPUQuota=20% sh -c 'yes > /dev/null'   # an ad-hoc limited process; Ctrl-C to stop
$ systemctl set-property containerd.service MemoryMax=2G   # live + persisted drop-in
$ systemd-cgtop                                            # top, by cgroup

$ journalctl -u kubelet -n 3 --no-pager
$ sed -i 's#config.yml#config.yaml#' /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf && systemctl daemon-reload && systemctl restart kubelet; sleep 5; systemctl is-active kubelet

Key takeaways

  • kubelet and containerd are systemd services; everything else is a container. systemctl status/restart and journalctl -u are the node's first commands.
  • Unit file + drop-ins define ExecStart and environment; kubeadm's drop-in assembles the kubelet command line from env files. daemon-reload after any edit.
  • Restart=always + RestartSec=10 is why a misconfigured kubelet flaps instead of dying.
  • journalctl -u X -n N --no-pager, -f, --since, -p err, -b -1, -k; vacuum when the journal fills the disk.
  • systemd owns the cgroup tree; the systemd cgroup driver keeps the runtime and kubelet inside it.
