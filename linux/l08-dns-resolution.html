CoreDNS answers queries; it does not decide which queries get asked. That is decided inside each container by the C library, following /etc/nsswitch.conf, /etc/hosts and /etc/resolv.conf — three files the kubelet writes for every Pod. Understanding the resolver explains short names, the ndots tax, why Alpine behaves differently, and how to debug "cannot resolve" with the right tool.

What you'll learn

  • The resolution pipeline: getaddrinfo → nsswitch → hosts file → resolv.conf → nameserver
  • resolv.conf fields: nameserver, search, options (ndots, timeout, attempts, rotate)
  • systemd-resolved and the stub resolver; what the node's resolv.conf really is
  • Tools and their differences: getent, dig, nslookup, host, resolvectl
  • Record types you will query and how caching/TTL behave

The pipeline

$ cat /etc/nsswitch.conf | grep hosts
hosts: files dns                                # order of sources: /etc/hosts first, then DNS (systemd: "files resolve dns", "mymachines", "myhostname")
$ cat /etc/hosts
127.0.0.1 localhost
10.244.1.9 api-7f9c                              # the kubelet writes the Pod's own name here (+ hostAliases)
$ cat /etc/resolv.conf
nameserver 10.96.0.10
search shop.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

Every program that calls getaddrinfo("api") (curl, python, Go's resolver in cgo mode, java) goes through this. Go's pure-Go resolver and musl (Alpine) reimplement it with small differences; dig bypasses it entirely and talks DNS directly — which is why dig api fails while curl api works: dig does not use the search list unless you pass +search.

resolv.conf

nameserver
Up to 3 servers, tried in order (unless options rotate); each gets timeout seconds × attempts tries. In a Pod: the CoreDNS Service IP.
search
Domains appended to names that are not fully qualified. Up to 6 domains / 256 chars (glibc). The kubelet writes the Pod's namespace domain first.
options ndots:N
A name with fewer than N dots is tried with each search domain first, then as-is. Default 1; Kubernetes sets 5 so svc.ns.svc (2 dots) still searches. A trailing dot (example.com.) marks a name absolute and skips the search list.
options timeout:T attempts:A
Per-server timeout (default 5 s) and retries (2). With 3 search domains failing and one slow server, a single lookup can take 30+ seconds — the "DNS is slow" symptom.
options single-request-reopen / use-vc
Workarounds for conntrack races on parallel A/AAAA UDP queries (glibc sends both at once; some setups lose one). use-vc forces TCP.
$ resolvectl status                       # on systemd-resolved hosts: the REAL upstream servers per interface
$ ls -l /etc/resolv.conf                  # → ../run/systemd/resolve/stub-resolv.conf (nameserver 127.0.0.53) on Ubuntu
$ cat /run/systemd/resolve/resolv.conf     # the actual upstream servers — what the kubelet's --resolv-conf should point at (kubeadm handles this)

That last point matters for CoreDNS: its Pod runs with dnsPolicy: Default, so it inherits the node's resolv.conf. If that says 127.0.0.53 (the resolved stub), CoreDNS would forward to itself → the loop plugin detects it and crashes. kubeadm sets the kubelet's resolvConf to the real file; on custom setups this is a classic CoreDNS CrashLoopBackOff.

$ dig +short api.shop.svc.cluster.local              # 10.96.4.7
$ dig api.shop.svc.cluster.local | grep -E 'status|ANSWER|^api'   # NOERROR / NXDOMAIN, TTL 30
$ dig +search +short api                            # honours resolv.conf search — like an app would
$ dig -t SRV _http._tcp.api.shop.svc.cluster.local  # SRV: port + target
$ dig -x 10.96.4.7 +short                           # PTR: api.shop.svc.cluster.local.
$ dig +norecurse @10.96.0.10 api.shop.svc.cluster.local    # authoritative answer flag (aa) from CoreDNS
$ getent hosts api || echo "libc cannot resolve api here"

Records and caching

TypeMapsIn Kubernetes
A / AAAAname → IPv4 / IPv6Services, Pods, headless endpoints
CNAMEalias → canonical nameExternalName Services
SRVservice → priority, weight, port, targetNamed ports: _port._proto.svc.ns.svc.cluster.local
PTRIP → name (reverse)Service and Pod IPs (in-addr.arpa zone handled by CoreDNS)
NS / SOAZone delegation / authoritycluster.local SOA from CoreDNS
TXTTextACME DNS-01 challenges, external-dns ownership records

Every record carries a TTL; resolvers cache for that long. CoreDNS uses 30 s for cluster records and caches upstream answers (cache 30). glibc itself does not cache (nscd/sssd do, if installed); Java's JVM caches forever by default (networkaddress.cache.ttl) — an old gotcha when Service IPs change. Node-local caches (NodeLocal DNSCache, systemd-resolved) add another layer. When a name "still resolves to the old IP", walk the layers.

Debugging "cannot resolve"

  1. Which resolver? cat /etc/resolv.conf in the Pod. Wrong nameserver → dnsPolicy/hostNetwork issue (Day 48).
  2. Is it reachable? nc -zu 10.96.0.10 53, or dig @10.96.0.10 kubernetes.default.svc.cluster.local. Timeout → NetworkPolicy, kube-proxy, CoreDNS Pods down.
  3. Does the record exist? dig the FQDN with a trailing dot. NXDOMAIN → wrong name/namespace or Service missing.
  4. Is it the search list? getent hosts short-name vs the FQDN. Works FQDN-only → search/ndots problem (dnsConfig, or the app uses a resolver that ignores search).
  5. Is it slow rather than broken? time getent hosts x; tcpdump port 53 shows retries and which server is not answering.
  6. External names? CoreDNS forwarding: kubectl -n kube-system logs -l k8s-app=kube-dns; the node's own resolv.conf; egress firewall on 53.

Hands-on lab (15 min)

$ grep hosts /etc/nsswitch.conf; cat /etc/resolv.conf; resolvectl status 2>/dev/null | head
$ getent hosts localhost; getent hosts kubernetes.io; getent hosts nope.invalid || echo "NXDOMAIN via libc"
$ dig +short kubernetes.io; dig kubernetes.io | grep -E 'status|Query time|SERVER'
$ dig +trace kubernetes.io | grep -E '^(kubernetes|io\.|\.)' | head
# see the search list in action (any Linux box): add a search domain and watch the queries
$ sudo tcpdump -i any port 53 -nn -l 2>/dev/null & sleep 1
$ RES_OPTIONS="ndots:3" getent hosts www.example.com >/dev/null      # glibc honours RES_OPTIONS: watch extra queries with your search domain appended
$ kill %1
# in a Pod (KIND):
$ kubectl run t --rm -it --image=nicolaka/netshoot -- sh -c 'cat /etc/resolv.conf; getent hosts kubernetes.default; dig +short kubernetes.default.svc.cluster.local; dig kubernetes.default 2>&1 | grep status; dig +search +short kubernetes.default'

Key takeaways

  • Resolution happens in libc: nsswitch → /etc/hosts → resolv.conf nameservers, with the search list and ndots applied to short names.
  • The kubelet writes hosts/resolv.conf per Pod; CoreDNS is just the nameserver they point at.
  • getent hosts tests what apps see; dig tests DNS itself (no search list unless +search); nslookup is in between.
  • ndots:5 + search list = extra queries for external names; trailing dots and lower ndots fix it.
  • systemd-resolved's stub (127.0.0.53) must not be what CoreDNS forwards to; TTLs and caches explain stale answers.
